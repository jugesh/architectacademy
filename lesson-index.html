01.1 · Start with correctness (3)

System boundaries & invariants

Start architecture with who owns each decision, not with a framework. An invariant is a rule that must remain true even during retries and outages.

Partial failures and ambiguous outcomes

A network timeout does not tell you whether the server committed an operation. Distributed applications must represent UNKNOWN as a real state.

Safety vs liveness

Safety means bad outcomes never occur; liveness means useful work eventually progresses. Different controls protect each.

01.2 · Understand workload (4)

Latency, throughput & concurrency

Throughput is work finished per second; latency is time per request; concurrency is work in progress. They are related but not interchangeable.

Tail-latency amplification

A user request fans out to many services; even a small fraction of slow dependencies can worsen end-to-end p99.

Coordinated omission

A load test that stops generating new requests when the service stalls systematically hides waiting time.

Thundering herd & cache stampedes

Many requests regenerate the same expired cache entry simultaneously and overload origin storage.

01.3 · Consistency and causality (4)

CAP, PACELC & partitions

CAP concerns linearizable consistency and availability during a network partition. PACELC also reminds us of latency/consistency choices during normal operation.

Linearizability vs serializability

Linearizability is a real-time ordering property for operations. Serializability concerns equivalent transaction execution order. They solve related but different problems.

Lamport clocks, vector clocks & HLC

Logical clocks capture causal ordering without trusting wall time. Lamport clocks give an order compatible with happened-before; vectors can identify concurrency; hybrid logical clocks combine wall time with logical progress.

Quorums and replica math

Quorum operations aim to overlap replica sets, but overlapping quorums alone do not guarantee linearizability without the protocol’s rules.

01.4 · Coordination and identity (4)

Leader election, split-brain & leases

Election chooses who should lead; a stale leader may keep acting after its lease expires. Split-brain is competing authority.

Fencing tokens

A fencing token is a monotonically increasing epoch attached to operations. Storage rejects a stale epoch.

Consistent hashing & rendezvous hashing

Hash-based routing distributes keys over nodes and minimizes movement when membership changes. Virtual nodes and rendezvous hashing improve distribution and simplicity.

Idempotency keys & scope

Idempotency maps repeated attempts of one logical operation to one outcome. A key needs a documented scope, request fingerprint and retention window.

01.5 · Resilience and recovery (3)

Rate limiting, shedding & backpressure

These controls manage different points of overload. Rate limits enforce policy; shedding protects current capacity; backpressure propagates consumer limits upstream.

SLOs, error budgets & burn rates

An SLO defines a measurable acceptable level of service. Error budgets translate this into allowed failures over a window; burn rate reports how quickly the budget is consumed.

RPO, RTO & failure domains

RPO is acceptable data loss window and RTO is acceptable restoration time. Availability Zones and regions represent different correlated failure domains.

01.6 · Decisions and trade-offs (1)

Architecture decision records

An ADR records context, selected solution, rejected alternatives, consequences and revisit triggers.

02 · Scalability and data (6)

Capacity planning and burst budgets

Peak shape, duration, cost per request, headroom and dependency limits determine capacity.

Queueing theory and Little’s Law

Average concurrency L = λW, but it applies to stable flows and consistent scopes. High utilization raises waiting times.

Autoscaling: HPA, KEDA and warm capacity

HPA can scale using metrics; KEDA supports event-driven scale signals. Neither removes startup delay or database limits.

Database indexing and query plans

Indexes reduce documents examined when query shape and selectivity match. Every index costs memory, writes and maintenance.

Sharding and hot partitions

Sharding distributes data and throughput by key. A poor key concentrates load and creates hot partitions.

Caching hierarchy and invalidation

Browser, CDN, service and database caches have different freshness and failure patterns. Cache correctness depends on authoritative validation and invalidation rules.

03 · Consistency and transactions (6)

Replication and read consistency

Async replicas can serve stale reads; synchronous acknowledgements trade write latency for durability/visibility guarantees.

Optimistic locking and lost updates

Version-based compare-and-swap prevents blind lost updates.

Transactions, isolation and write skew

Even transactions can violate multi-row invariants under some isolation levels. Write skew is an important anomaly.

Transactional outbox and inbox

Outbox removes the unsafe DB-commit-then-publish gap; consumers still need idempotency.

Sagas and compensation

Saga workflows coordinate local transactions with compensating actions. Compensation is not an atomic rollback.

CRDTs and conflict resolution

Conflict-free replicated data types can converge under supported merge operations, but not every business invariant is mergeable.

04 · Resilience and recovery (5)

Timeouts, deadlines and retry budgets

Per-hop timeouts without an end-to-end deadline allow latency amplification and futile work.

Circuit breakers and bulkheads

Circuit breakers stop repeated calls to unhealthy dependencies; bulkheads stop one workload from consuming all capacity.

Graceful degradation and priority shedding

Under overload preserve the critical user journey and disable optional features.

Retries, exponential backoff and jitter

Synchronized retries can produce a retry storm and prevent recovery.

Disaster recovery and multi-region

Multi-AZ defends against zonal failures; multi-region targets regional disasters but introduces authority, data movement and routing issues.

05 · Messaging and streaming (5)

Kafka partitioning and ordering

Kafka orders records within one partition, not across a topic. Consumer parallelism is bounded by active partitions for a group.

At-least-once, at-most-once, exactly-once

Delivery guarantees describe broker/processing scopes, not magical end-to-end exactly-once business effects.

Consumer lag, staleness and catch-up

Lag in messages is backlog, whereas freshness measures elapsed delay before a business projection catches up.

DLQ, poison pills and replay

A poison event fails deterministically; retrying forever blocks progress. DLQs isolate failures but do not resolve business inconsistency.

CDC and data migrations

Change data capture captures mutations after a snapshot, enabling catch-up and controlled cutover.

06 · Observability and SRE (3)

Logs, metrics and traces

Observability combines structured events, numerical health signals, and request paths across services.

Profiling and diagnostic reasoning

Diagnose arrival rate vs service time vs resource waiting, not CPU charts in isolation.

Alert design and error-budget policies

Alerts need actionability and sensitivity to user harm. Multiwindow burn alerts catch both fast severe failures and slower chronic regression.

07 · Java Architect Master Pack topics (10)

JVM memory, GC and pauses

Heap allocations, garbage collection and stop-the-world pauses affect p99 and lease expiry. Monitor heap and non-heap memory, allocation rate, thread stacks and GC logs.

Java concurrency & virtual threads

Threads model concurrent tasks; virtual threads make blocking I/O cheaper but do not increase backend capacity. Shared locks, pools and pinning still matter.

Spring Boot lifecycle and transactions

Startup, liveness, readiness and transactions have distinct semantics. @Transactional typically applies through proxy interception and does not cover separate remote services.

REST semantics, idempotency and HTTP

GET should be safe, PUT should be idempotent under its contract, and POST often needs explicit dedup for retry safety. Distinguish 429 throttling, 503 overload and 202 accepted processing.

API versioning and backward compatibility

Changing producer and consumer versions independently requires compatibility. Evolve schema by adding, reading both versions, migrating, then removing old fields.

Security and zero trust

Authentication identifies callers; authorization limits actions. Trust boundaries exist between microservices, accounts and tenants.

Testing strategy & chaos engineering

Unit tests verify logic, integration tests verify boundaries, load tests verify capacity, and fault injection verifies graceful behavior.

AWS networking and IAM fundamentals

VPC, subnets, routing, security groups, NAT and IAM determine connectivity and permissions, not just topology boxes.

Kubernetes scheduling, probes and limits

Requests influence scheduling; limits affect runtime throttling or OOM. Readiness governs traffic; liveness governs restarts; startup protects slow initialization.

Designing a technical interview answer

Strong answers start with requirements and invariants, derive constraints, compare alternatives, and discuss failure modes and observability.

08 · Textbook deep dives (8)

Distributed systems fundamentals

A distributed system has independently failing processes communicating over a network. The network offers latency, loss, duplication, partitions and ambiguous outcomes. Never infer global completion from one component’s local success.

Scalability and capacity engineering

Scalability means sustaining an increasing useful workload within explicit latency, error and cost budgets. Average RPS hides burst shape, request cost, tenant skew and dependency limits.

Consistency and data integrity

Consistency is an observable contract; integrity is the preservation of business invariants. Different objects and operations can require different contracts.

Resilience and overload control

Resilience is maintaining critical outcomes despite faults. Techniques differ: bulkheads contain failure, breakers stop futile dependencies, admission control constrains concurrency, and load shedding rejects optional work.

Messaging and event-driven architecture

Messaging decouples production from consumption, not correctness. Producer acknowledgements, broker durability, consumer offsets, application commits and downstream effects have distinct failure boundaries.

Observability and SRE

Observability turns unbounded system uncertainty into actionable evidence: golden signals, distributed context, business correctness indicators, and explicit service objectives.

Failure response and recovery

A failure response is a controlled sequence: detect, classify, contain, preserve evidence, mitigate, verify, reconcile, learn. Recovery is incomplete until data integrity and customer outcomes are accounted for.

Architectural trade-offs and decision records

Good architecture selects the cheapest complexity that meets measurable constraints. Every decision spends capacity, latency, consistency, availability, dollars and human operability.

09 · Production case studies (25)

Case 01: 20× flash-traffic spike

Incident symptoms: 1,000 → 20,000 RPS in 12 seconds; pods take 90 seconds to start; checkout p99 jumps to 9 seconds. Failure domain: Scalability.

Case 02: Six-month organic growth

Incident symptoms: Daily requests climb 12% monthly; nightly ETL shares the production primary. Failure domain: Scalability.

Case 03: Noisy tenant consumes 80%

Incident symptoms: One tenant exhausts a shared search pool during batch imports. Failure domain: Isolation.

Case 04: Flash-sale inventory overselling

Incident symptoms: Two users see one remaining unit and submit checkout simultaneously. Failure domain: Consistency.

Case 05: Kafka lag continually grows

Incident symptoms: Producer 20k/s; consumers 5k/s for 60 seconds. Failure domain: Messaging.

Case 06: Kafka event processed twice

Incident symptoms: DB write succeeds; consumer crashes before committing offset. Failure domain: Messaging.

Case 07: Kafka events out of order

Incident symptoms: AddressChanged v42 arrives after v43 due to divergent producers. Failure domain: Messaging.

Case 08: Kafka broker unavailable

Incident symptoms: Leader lost during broker maintenance; producer times out. Failure domain: Messaging.

Case 09: MongoDB queries slow suddenly

Incident symptoms: p99 jumps from 25ms to 2.5s after data growth. Failure domain: Database.

Case 10: MongoDB primary election

Incident symptoms: Primary steps down during 3-zone incident. Failure domain: Database.

Case 11: MongoDB cluster migration

Incident symptoms: Move between AWS accounts and clusters; rollback window required. Failure domain: Migration.

Case 12: Redis cache failure at peak

Incident symptoms: Cache cluster unavailable during promotions. Failure domain: Caching.

Case 13: Stale pricing cache

Incident symptoms: Price updated but one region serves old price for 15 minutes. Failure domain: Caching.

Case 14: REST dependency hangs

Incident symptoms: Third-party tax endpoint stalls at 60-second default timeout. Failure domain: Resilience.

Case 15: Retry storm after partial outage

Incident symptoms: Ten callers retry three times with aligned backoff. Failure domain: Resilience.

Case 16: Thread-pool starvation

Incident symptoms: One slow report route holds 100 worker threads. Failure domain: Resilience.

Case 17: Kubernetes CrashLoopBackOff

Incident symptoms: New rollout has OOMKilled pods and aggressive probes. Failure domain: Operations.

Case 18: HPA too slow during peak

Incident symptoms: Traffic triples in 5 seconds; HPA rollout ready in 120 seconds. Failure domain: Scalability.

Case 19: AWS Availability Zone failure

Incident symptoms: One AZ loses connectivity while app and DB are partly zonal. Failure domain: Availability.

Case 20: Entire AWS Region failure

Incident symptoms: Regional control plane or networking unreachable; primary write region lost. Failure domain: Disaster recovery.

Case 21: Payment succeeds, order fails

Incident symptoms: Payment provider commits capture; order DB transaction aborts. Failure domain: Transactions.

Case 22: Partial distributed commit

Incident symptoms: Account saved but provisioning event not published. Failure domain: Transactions.

Case 23: Incompatible API deployment

Incident symptoms: V2 producer removes a field older consumers require. Failure domain: Evolution.

Case 24: Schema migration breaks old pods

Incident symptoms: Column renamed while old pods still serving. Failure domain: Evolution.

Case 25: Green dashboards, failing users

Incident symptoms: Health endpoints return 200 while checkout confirms only 60%. Failure domain: Observability.

OAuth2, OIDC, mTLS and service authorization

Multi-tenancy, noisy neighbors and isolation models

A shared platform needs explicit fairness and isolation guarantees.

16 · Networking and coordination (8)

DNS, TTLs and service discovery

DNS maps names to addresses, but caches mean updates do not instantly redirect everyone.

TCP connection pools, keepalive and head-of-line blocking

Transport choices determine where requests wait when dependencies become slow.

TLS, certificates and trust chains

Encryption is not meaningful unless the client verifies whom it is talking to.

HTTP/2, HTTP/3 and connection multiplexing

A faster protocol is only faster when the request pattern and network support it.

Distributed consensus: Raft, terms and commit indices

Replicas need a safe way to agree which operations are committed.

Failure detectors, heartbeats and phi accrual

A silent node may be crashed, slow, or unreachable; a timeout is a suspicion.

Time synchronization, NTP and clock uncertainty

Physical time is useful for logging and expiry but is not a complete ordering guarantee.

Leader election versus distributed locking

Electing a leader and locking a resource solve related but different authority questions.

17 · API and integration design (4)

Pagination, cursors and stable ordering

A paginated API must define what happens when records change between pages.

BFF, aggregation and API composition

A client-facing API boundary should optimize the client journey without owning every backend's data.

Webhooks, callbacks and eventual delivery

An outbound callback is a distributed message with uncertain delivery.

Data contracts, schema registry and consumer evolution

Events are public APIs even when they travel over a broker.
