Library/Foundations/Security & Identity

Security & Identity · fundamentals to production judgment

Verify the caller, then authorize the exact action

Build from one private order lookup to tokens, delegated access, tenant isolation, credential rotation and auditable decisions.

Technical definitionAuthentication establishes a caller’s identity under a trust mechanism. Authorization decides whether that identity may perform a specific action on a specific resource. OAuth delegates access; OpenID Connect adds an identity layer for authentication flows.
Before you begin. Understand TLS and HTTP and an order resource from API Design. We define tokens and scopes before using Spring configuration.

Learning outcome: Design an authorization boundary that survives valid-but-wrong tokens, cross-tenant IDs and credential rotation.

1. A valid login can still access the wrong order

The channel is protected. Now establish who may perform this resource operation.

Networking established that the caller reached an endpoint over a protected connection. Now ask a different question: who is making this particular request, and why may they read order 42? A server certificate authenticates the expected server under the client’s trust model. It does not establish the customer’s identity, and it does not grant the customer permission over an order.

Start with two legitimate customers, Alice and Bob, in the same application. Both can sign in successfully. Alice requests Bob’s order ID. If the service checks only that a token is valid, the request may leak Bob’s data despite successful authentication. This is the simplest way to see why authorization is a decision over identity, action, resource and relevant context, rather than a synonym for login.

Start with a rule: this caller can read orders in their tenant only when the relevant role/relationship permits it. Express that rule before choosing JWT or a gateway. The token supplies verified inputs; the application makes the resource-specific decision.

2. Follow identity into one authorization decision

Read this slowly: it establishes the distinction used in the implementation sections.

Begin with GET /orders/42. A credential answers who the caller is or which client is acting. That still leaves a separate question: may that caller read order 42? Authorization is the decision over subject, action, resource and context. A role such as customer is insufficient if it grants access to every customer order. Tenant membership and resource ownership are part of the decision.

Walk through the checks in order. Validate a token using an explicitly trusted issuer and expected audience; check its time validity and permitted algorithm through the security library. Establish the subject. Query the order within the authorized tenant or verify ownership before returning it. Shape the response so forbidden fields are absent. Repeat equivalent checks for updates, background jobs and exports. An authenticated internal request is not a universal exemption.

Check your understanding
FoundationalA signed JWT makes its claims safe to use for any API.
A valid signature only establishes integrity under a key. The receiving service must also establish trust in issuer, intended audience and claim semantics. A token intended for another service may be correctly signed and still unacceptable here.
IntermediateWhere should tenant isolation be enforced?
At every authoritative data access or mutation boundary. Derive the tenant from trusted security context and authorized delegation, then constrain queries and writes. UI filtering and a tenant header chosen freely by the caller are insufficient.

3. Threats become requirements

Write a concrete policy before translating it into scopes, roles or annotations.

A tenant is a logical isolation boundary, such as a partner organization. Write an allow/deny rule for one operation before selecting roles or claims. For GET order, the customer may need to own that order within the authenticated tenant. For refund, a partner may need an explicit capability, ownership of the order, an amount bound and a refundable state. Some checks are security policy; others protect business-state correctness. They must all hold at the authoritative operation boundary.

Next identify the entry paths that can reach that operation: REST controller, scheduled task, queue consumer, batch export and support tooling. A secure controller is insufficient if another path bypasses the same rule or acts with excessive authority. Background work should carry a deliberate authorization/actor model, not blindly reuse an arbitrary user token indefinitely.

Non-functional security requirements need observable policies too. Define how quickly a revoked permission must stop working, what happens during identity-provider or signing-key discovery failure, which audit facts must survive and how credentials are excluded from logs. These choices affect availability, caching and operational recovery; “use JWT” does not choose them.

Functional requirements

  • Authenticate browser, mobile and partner clients.
  • Authorize order read, refund and administration separately.
  • Rotate credentials and audit sensitive actions.

Targets and invariants

  • No cross-tenant access or secret leakage.
  • Reject invalid issuer/audience/signature/time policy.
  • Bound credential/key discovery load.
  • Define revocation and audit-retention expectations.

Threat modeling asks what an attacker can submit, observe or influence. Include an authenticated malicious user, a compromised partner credential and a forged callback, not only anonymous traffic. Give every trust boundary an owner.

4. Sessions, tokens, scopes and claims

Distinguish credential format, protocol and application permissions.

A credential is evidence presented under a protocol. A session cookie may refer to server-side session state; an access token grants access under its issuer and audience contract. JWT is a representation format that can carry claims. Its use does not by itself choose an OAuth flow, decide token storage or define resource permissions. A bearer credential can be used by whoever possesses it, so exposure in logs is a meaningful security failure.

OAuth addresses delegated access to protected resources. OpenID Connect adds an authentication layer, including an ID token intended for the client’s sign-in context. The API should receive the appropriate access token rather than assuming an ID token is interchangeable. Scopes express granted capabilities, but a broad orders:read scope still needs a resource-level rule to distinguish Alice’s orders from Bob’s.

Choose the flow from the client and trust boundary. An interactive user-facing client commonly uses authorization code with Proof Key for Code Exchange (PKCE), which binds the code exchange to a client-generated verifier, under a complete supported protocol. A machine acting on its own behalf may use client credentials when the provider supports the required model. Do not put a secret in a mobile app and treat it as proof that only your app can call the API: distributed client software cannot keep that shared secret from its users.

ConceptMeaningBoundary
Session cookieBrowser sends a session reference/cookie under browser rulesRequires CSRF/session-lifecycle policy.
Access tokenCredential presented to a resource serverMust be intended for this API and validated.
JWTSigned/encoded claim format, not an authorization policyDecoded text is not verified identity; encryption is separate.

For an appropriate user-facing client, authorization code with PKCE protects the code exchange; validate redirect URIs and the complete flow. Client credentials fits machine identity where supported. Do not invent a token protocol from base64 JSON or store a client secret in a distributed mobile app.

5. Carry tenant identity safely

Tenant isolation is an end-to-end data-flow property. A correctly filtered controller can still leak through a shared cache, an export job, a message consumer or an object-storage link. Trace one order from authenticated request to database, cache, outbox, worker and download. At each boundary identify where the tenant came from and which actor/service is permitted the intended action.

BoundaryIdentity source and checkCommon failure
Database queryAuthorized tenant plus resource predicatesfindById used on an untrusted global ID.
Cache reuseKey/representation scoped to authorized contextTenant A’s value returned under a shared product/order key.
Queued jobAuthenticated producer path and authorized service operationTreating a payload tenant field as proof of permission.
Export objectTenant-owned job/object mapping and download policyGuessable object key or unscoped pre-signed capability.
Logs/support searchControlled access and minimal identifiersPutting complete private payloads into a shared log index.

  eventId: E91
  tenantId: T7
  aggregateId: O7
  operation: refund.requested

operation, then scopes its own resource access to T7/O7. Copying an
actor string into JSON does not grant that actor's live permissions.

A background workflow may intentionally act under a service capability after the original user’s session ends. State that delegation model and its limits. Alternatively, an operation may require current user authority when executed, in which case queued delay and revocation require another check. Do not accidentally choose one model because the worker happens to have a powerful database credential.

Row-level security or separate databases can add isolation boundaries, but inspect their actual enforcement. A privileged database role may bypass some policies; connection-pool context can leak if session state is not reset. A tenant routing directory must also be protected: directing a valid tenant request to the wrong database can defeat correct row predicates if identities overlap. Defense in depth needs distinct failure assumptions, not repeated trust in the same unchecked header.

Signed object URLs are capabilities under their scope and expiry. They may remain usable after the browser session changes unless the delivery system supports a stronger revocation path. Bind issuance to an authorized job/object identity, choose a bounded lifetime and avoid exposing the URL in logs or referrers. A secret-looking filename alone is not access control.

Build a negative test matrix using fixtures from two tenants and at least two roles. Try another tenant’s resource ID in detail, list, mutation, export, search and replay paths, with warm caches and reused pooled connections. Confirm both denied actions and absent cross-tenant disclosure. Positive tests for the intended owner are necessary too; a system that denies everything has not demonstrated a usable policy.

AdvancedWhy can a background job need authorization even when it was created by a checked API?
The stored request can be stale, malformed, replayed or routed through another producer. The worker needs a defined delegation/service authority, tenant-scoped access and current-state checks appropriate to its operation.
IntermediateIs including tenantId in every log message sufficient isolation?
No. Logs need access controls, data minimization, retention and safe query tools. A tenant label helps correlation but does not prevent another tenant or broadly privileged operator reading private content.

6. Walk one request through policy

Follow the evidence from token receipt to the final resource decision.

Follow an incoming bearer token through distinct stages. First extract it from the supported location without logging it. Establish its integrity and issuer/audience/time policy through a configured security library and trusted key source. Then map validated claims to a principal understood by this application. Finally, authorize the requested operation on the specific resource. Successful completion of one stage is not a shortcut past the later ones.

Consider a correctly signed token issued for an analytics API. The order service may trust the same organization as issuer and still need to reject that token because the audience is wrong. Likewise, a token with a valid signature can be expired. The signed data remains readable and integrity-protected while its use is unacceptable. This distinction explains why “I decoded the JWT” and “the signature verified” are incomplete security checks.

After identity is established, load or mutate the order within the permitted tenant scope and apply the action policy. Do not fetch an arbitrary record, serialize it, and only then filter it in the UI. If permission or business state can change concurrently, locate the decisive checks close enough to the mutation to enforce the required rule. Preserve a consistent existence-hiding policy for unauthorized IDs without treating a 404 as the authorization mechanism itself.

Order order = repository.findByTenantAndId(verifiedTenant(), orderId)
    .orElseThrow(NotFoundException::new);
policy.requireCanRefund(principal(), order);
// Check business state and record the authorized transition.
// tenant supplied in the body is not authority.

Verify allowed signing algorithms, trusted issuer, expected audience, expiry and relevant time claims. Plan key rotation and clock tolerance. Fetch keys only from configured trusted discovery endpoints; an untrusted token must not choose an arbitrary key URL. Choose 401/403 and any existence-hiding 404 policy consistently.

7. Authorize the resource transition

A valid token establishes claims under its issuer/validation contract. A refund still needs a resource decision: may this actor refund this order, in this tenant, for this amount, in its current state? A broad refund scope is one input. It does not establish order ownership, remaining refundable value or the actor’s current delegated authority.

Conceptual application boundary, not a complete Spring service:
  actor = authenticatedPrincipal()     // never a caller's actorId field
  tenant = authorizedTenant(actor, requestedTenantContext)
  order = orders.findWithinTenant(tenant, orderId)
  require permission(actor, "refund", order, requestedAmount)
  perform an atomic allowed transition / refund-intent reservation
  persist original command identity + durable provider intent

Every alternate path (batch, support tool, consumer) must enforce its
own authorized transition. Hiding the button in the UI is not a policy.

Apply tenant scoping to the lookup itself, not only to a later response filter. An unscoped lookup can leak existence through errors, timing or logs even if a later check rejects the body. Choose a consistent disclosure policy for absent versus unauthorized resources. HTTP status selection does not replace the underlying permission check.

-- Illustrative PostgreSQL transition predicate, bound parameters.
UPDATE customer_order
SET state = 'REFUND_PENDING', version = version + 1
WHERE tenant_id = :authorized_tenant
  AND id = :order_id
  AND version = :observed_order_version
  AND state = 'PAID';
-- Require the expected result and create the refund intent/command
-- record in this local transaction. Amount/accounting rules also apply.

This simplified full-refund transition is not a partial-refund ledger. For concurrent partial refunds, reserve the refundable amount atomically with the intended identity; two individually allowed amounts must not jointly exceed the charge. If policy depends on mutable membership or delegation, define when it is observed and how tightly revocation must take effect. An earlier Java check followed by a later mutation can race a revocation or resource-state change.

A version predicate protects the observed order state; it does not freeze an independently stored permission record. Strict revocation at the mutation boundary needs an authority/serialization protocol covering the relevant policy facts, or a deliberately documented decision-freshness contract. If authorization is a remote service, its successful response is not automatically enlisted in the local SQL transaction.

CaseRequired decision
Known order ID from another tenantDeny access through every lookup/mutation/export path.
Same tenant, wrong resource ownerApply resource relationship policy, not tenant membership alone.
Correct actor, old order versionRe-evaluate the permitted transition; do not force the write.
Support operatorUse explicit limited privilege, purpose and audit trail.
Duplicate refund commandResolve original authorized intention without a second amount reservation.
AdvancedDoes @PreAuthorize make a refund transaction safe by itself?
No. It can enforce an application policy at an intercepted boundary, but tenant scoping, mutable policy freshness, concurrent amount/state invariants, commit behavior and remote-effect identity remain separate obligations.
IntermediateCan the tenant header select any tenant if the JWT is valid?
Only after authorization establishes that this actor may act in that requested tenant context. A header is a selector/request, not proof of entitlement.
  • OWASP authorization guidance: default denial and resource/action permission checks.

8. Spring and AWS mapping

Separate framework verification from domain policy and storage enforcement.

Use framework support for the token protocol and keep domain policy in an explicit application boundary. Spring Security resource-server machinery handles configured token validation; a route rule can require authentication or a coarse capability. The service and repository must still enforce resource ownership and tenant scope. Choose one authoritative mapping from validated principal/delegation to tenant; an unverified tenantId in the request body is merely caller input.

An API Gateway authorizer can reject unsuitable credentials before application work, which reduces exposure and load. It does not know every order’s current ownership, refund balance or state unless that information is deliberately part of its policy. Keep the responsibility boundary explicit. IAM authenticates and authorizes AWS resource access under its model; it does not automatically encode the shop’s customer-order policy.

For browser sessions, understand why CSRF and CORS solve different problems. Browsers can automatically attach cookies to requests under applicable rules, so a state-changing cookie-authenticated endpoint needs an appropriate CSRF defense. CORS governs browser cross-origin access behavior; a nonbrowser client is not constrained by it. For outbound callbacks, destination URLs are SSRF-sensitive input: signing an outbound request does not make an attacker-chosen internal destination safe.

Cognito or another identity provider issues credentials; API Gateway can validate suitable tokens at the edge. Application authorization remains necessary. mTLS authenticates a peer connection, not the end user’s refund rights. Store signing material/provider secrets in managed secret storage with least-privilege access and tested rotation.

For browser cookie authentication, assess CSRF because browsers attach cookies automatically. CORS controls browser cross-origin access; it does not stop a nonbrowser caller and is not authentication. For callbacks, prevent SSRF with destination validation and restricted egress, including redirect/DNS behavior.

9. Validate tokens through rotation

JWT verification is a policy over issuer, intended audience, allowed algorithms/keys and time constraints, followed by resource authorization. Merely decoding Base64 claims proves nothing about who issued them. The key identifier is untrusted input used to select among trusted issuer keys; it must not turn an arbitrary token-supplied URL into a place from which the service fetches its trust material.

# Illustrative Spring resource-server issuer configuration.
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://identity.example.invalid/issuer

# Configure audience and algorithm restrictions through the supported
# properties/validators for the chosen Spring version and issuer.
# issuer-uri alone is not the application's complete resource policy.

Use the framework’s supported decoder and validators rather than a homegrown signature parser. Verify the intended audience explicitly under the selected configuration. Keep signature, issuer and time checks when adding custom validators; replacing a validator chain with only an audience predicate can accidentally drop other checks. Token scopes/claims then map into a deliberate application permission model.

Planned signing-key phaseIssuer actionResource-server obligation
Publish new public keyMake the next verification key discoverableRefresh through the trusted issuer path under bounded behavior.
Start signing new tokensUse new kid/key while old tokens can still be validAccept the permitted overlap and reject unknown/untrusted keys safely.
Drain old token lifetimeStop issuing with old key; retain required verification historyAccount for last issuance, allowed lifetime and clock tolerance.
Retire old keyRemove after the permitted overlap, unless emergency policy differsConverge key caches and verify old signatures are no longer accepted as intended.

For illustration, a maximum 15-minute access-token lifetime does not mean “remove the old key 15 minutes after publishing the new key.” Start from the last token issued with the old key and include the supported clock-tolerance/refresh policy. Test verifier behavior when the new kid first appears, the issuer is temporarily unavailable and old keys disappear. Unknown-kid traffic must not cause unbounded outbound discovery or disable validation.

Emergency compromise is a different procedure. Continuing to trust a stolen signing key until every token naturally expires may be unacceptable. Define how trust is revoked, how verifier caches converge and whether sessions/tokens are invalidated or reauthenticated. Short token lifetimes reduce an exposure window but do not create instantaneous revocation by themselves. Preserve a bounded, understood failure mode when the identity provider cannot be reached.

Database/API secret rotation has another lifecycle: provision a new credential, distribute it securely, verify new connections/requests, drain or replace old users, then revoke the old credential under the service’s actual session semantics. Updating a secret file does not prove an existing connection pool stopped using the old credential, nor that already-authenticated sessions were terminated. Keep least privilege and a rollback plan that does not re-expose a compromised secret.

AdvancedShould I disable signature validation temporarily if JWKS refresh fails during a release?
No. Keep the defined trust policy and bounded failure behavior. Rehearse key overlap, trusted cache behavior and issuer outage before rotation; validation bypass converts an availability incident into an authorization failure.
IntermediateDoes a JWT exp claim prove the user still owns this order?
No. It bounds token validity under the issuer/time policy. Current resource ownership, delegation and revocation requirements still govern the requested action.
  • Spring JWT resource server: trusted decoding, issuer validation and key discovery.
  • OWASP secrets guidance: credential lifecycle and rotation.

10. Worked design: partner refunds

Apply the policy and recovery rules to one refund, then vary the failure.

Work one refund from request to provider. A partner asks to refund an order. Establish the partner principal and required capability, resolve the order inside that partner’s scope, validate current refundable state/amount, and create a durable refund intent under a stable operation identity. The external provider call happens under its own credential and idempotency/recovery contract. Do not hold a database lock while waiting merely because every step belongs to the same business operation.

Now vary one condition at a time. A token for another audience fails credential validation. A valid partner token requesting another partner’s order fails authorization without disclosure. A valid authorized request exceeding the remaining refundable amount fails the business rule. A provider timeout after accepting a refund creates an unknown remote outcome. These failures need distinct internal evidence and documented external responses; calling all of them authentication errors hides the real recovery action.

Finally rotate a signing key or provider secret. During an intentional overlap, allow only the defined old/new material, observe errors and verify consumers refresh according to their supported configuration. Retire the old key only after the migration policy permits it. Test recovery from unavailable discovery endpoints and avoid an unbounded refresh on every attacker-supplied unknown key ID.

Audit actor, action, resource, decision, time and stable request/business references without storing bearer tokens or card data. A short-lived token can reduce revocation exposure, but the actual revocation contract may require introspection or explicit state. During signing-key rotation, overlap trusted keys and observe unknown-key errors before removing the old key.

Test a valid token for another audience, another tenant’s order ID, expired tokens, unknown key IDs, mass assignment of tenant/role fields, and a rotated key. Verify both allowed and denied decisions; happy-path login tests cannot prove tenant isolation.

Input variationExpected decisionCorrectness assertion
Valid customer, own tenant, own orderAllow the permitted read.Only permitted fields are returned.
Valid customer, another customer’s orderDeny or hide existence under policy.No sensitive fields or side effects.
Valid signature, wrong audienceReject credential for this API.No domain mutation runs.
Authorized refund, amount exceeds remaining balanceReject business transition.Refund ledger remains unchanged.

11. Authenticate and deduplicate callbacks

A payment callback needs two protections: evidence that the message came through the expected authenticated contract, and a repeat-safe business transition. The following self-contained Java helper demonstrates an illustrative HMAC-SHA256 protocol over timestamp + a dot + raw body bytes. It is not a claim about any particular provider’s wire format. Implement the actual provider specification, including canonicalization, key selection and allowed clock window.

static boolean verifyCallback(byte[] secret, String timestamp,
    byte[] rawBody, String signatureBase64, long nowSeconds)
    throws java.security.GeneralSecurityException {
  if (secret == null || secret.length < 32 || rawBody == null
      || rawBody.length > 1_048_576 || timestamp == null
      || !timestamp.matches("[0-9]{1,12}")
      || signatureBase64 == null || signatureBase64.length() > 128) {
    return false;
  }
  long sent = Long.parseLong(timestamp); // regex bounds fit in long
  if (sent < nowSeconds - 300 || sent > nowSeconds + 30) return false;
  byte[] supplied;
  try { supplied = java.util.Base64.getDecoder().decode(signatureBase64); }
  catch (IllegalArgumentException invalid) { return false; }
  if (supplied.length != 32) return false;
  javax.crypto.Mac mac = javax.crypto.Mac.getInstance("HmacSHA256");
  mac.init(new javax.crypto.spec.SecretKeySpec(secret, "HmacSHA256"));
  mac.update((timestamp + ".").getBytes(java.nio.charset.StandardCharsets.UTF_8));
  byte[] expected = mac.doFinal(rawBody);
  return java.security.MessageDigest.isEqual(expected, supplied);
}

The five-minute past window, 30-second future tolerance and one-megabyte body limit are illustrative policy choices. Use a trusted server clock and monitor skew. Bound the incoming body while reading it, before allocating an arbitrary payload; the helper’s length check is not an HTTP streaming limit. Preserve exact raw bytes until signature verification. Parsing and reserializing JSON can change whitespace/order and invalidate the signed representation.

The shared secret is a random key with adequate entropy, stored through the intended secret-management path, not a password or a client-provided header. A valid tag authenticates the bytes under possession of that key; it does not prove the business transition is allowed. After verification, parse the schema, locate the original payment/order, validate amount/currency/provider references and enforce the permitted conditional transition.

Durable callback application outline:
  verify transport/signature contract and bounded timestamp
  parse validated event identity and business references
  begin local transaction
  claim provider + event identity; compare immutable content on repeat
  apply only the permitted original-intention state transition
  insert next-step outbox intent if that transition wins
  commit receipt + effect + next intent together
  return the provider's required acknowledgement

A lost acknowledgement can cause redelivery. Keep original identities.

A signed request can be replayed within the allowed timestamp window. The verifier intentionally does not remember event IDs; durable deduplication belongs with the local effect. Concurrent duplicate callbacks and a polling reconciler can also race. Use conditional transitions and durable original-intention identity, not an in-memory set that disappears on restart. A reused event ID carrying different authenticated content is a conflict to investigate.

If legitimate delivery retries arrive outside the illustrative window, follow the actual provider’s supported retry/signature/inquiry contract. Do not silently widen the window forever to make errors disappear. Retained event receipts, authenticated inquiry and an authorized recovery operation can have different policies from live callback acceptance. A compromised shared secret requires a defined rotation/revocation procedure, not only duplicate filtering.

AdvancedIf signature verification passes, may I immediately mark the order PAID?
No. Bind the callback to the expected provider intention, tenant, amount, currency and allowed state transition. Record it atomically with repeat-safe effects and handle contradictory or late outcomes through reconciliation.
IntermediateWhy compare the raw HMAC bytes with MessageDigest.isEqual?
Use the platform’s comparison designed for digest bytes rather than ordinary string equality for the tag. Bound/decode the supplied tag first, while keeping the entire verification and business protocol correct.
  • JDK Mac API: HMAC computation.
  • JDK digest comparison: digest byte comparison API.

12. Pitfalls and operational decisions

Check what stays valid when permissions, keys or dependencies change.

Security decisions can become stale. If an allow decision is cached for ten minutes, a permission removal may take that long to affect that path unless another mechanism intervenes. Short-lived credentials reduce some exposure but do not create immediate revocation. State the exact promise for each path, including long-running exports and already-issued download capabilities.

Operational shortcuts can change the trust model. Disabling certificate validation, accepting arbitrary issuers or granting every internal caller an administrator role may hide an incident while exposing data. Prefer diagnosis and constrained recovery. Audit the actor, action, resource and outcome without retaining bearer tokens, sensitive request bodies or provider secrets.

IssueReasoning
JWT revocationStateless verification does not automatically learn revocation. Define lifetime and any revocation/introspection state.
Authorization cachingCached allow decisions can outlive permission changes. State the revocation freshness bound.
Secret rotationReplacing a value is not sufficient if clients keep old pooled/configured credentials. Verify rollout and overlap.
Overprivileged serviceInternal network location is not sufficient authority. Validate identity and scope at the resource boundary.

13. Interview ladder

Defend the boundary: authentication success alone is not resource permission.

FoundationalAuthentication versus authorization?
Authentication establishes identity; authorization applies action/resource policy to that identity.
FoundationalIs a decoded JWT trustworthy?
No. Validate signature and trust/claim policy before using its contents as identity.
IntermediateOAuth versus OIDC?
OAuth delegates access to resources; OIDC adds identity/authentication semantics on top of OAuth flows.
IntermediateWhy is a scope check insufficient?
A broad capability does not prove tenant membership, resource ownership, amount limits or current business state.
AdvancedHow do you revoke JWT access quickly?
Choose short lifetimes and, if required, introspection/revocation state or another explicit protocol. State latency/availability trade-offs rather than promising immediate stateless revocation.
AdvancedHow do you prove isolation?
Exercise valid credentials across tenant/resource combinations at every entry path, inspect query scoping, and assert denied requests cause no side effects or sensitive disclosure.
IntermediateWhy must an export be authorized separately from its creation?
Creation, background processing and later download are distinct paths. Current permissions, the chosen delegated authority model and already-issued bearer capabilities need explicit policies. A successful creation check does not define indefinite download access.
AdvancedHow can a valid scope still allow a cross-tenant breach?
The scope may grant a broad capability without proving ownership of the specific object. Constrain authoritative access by a verified tenant/delegation mapping and apply domain policy at every entry path; test valid credentials against another tenant’s resource.

14. References and practice

Return to one API endpoint and prove both allowed and denied behavior.

When reading the primary references, keep four questions separate: What protocol establishes the credential? What does this API validate? Which resource policy decides the operation? How is a change in permission or keys propagated? A library example answering the second question does not settle the other three.

To connect this lesson back to API Design, take an endpoint from that lesson and write a policy matrix: caller type, action, tenant/ownership, business state and expected allow/deny result. Then test the same matrix through every entry path. This is a stronger demonstration of isolation than showing a successful login screen.
