Technical definitionAn architecture interview answer is an argument: define the concept, connect it to a requirement, explain a mechanism, identify a failure boundary and defend the trade-off.
Before you begin. Read the linked V4 lessons first. Attempt an answer before opening the explanation; memorized product names do not satisfy the reasoning rubric.

Learning outcome: Give precise answers, handle follow-ups and assess what is missing from your own reasoning.

1. Use the answer ladder

Begin with a two-sentence definition and one concrete operation. Then extend the answer only as the question demands. A foundational question tests vocabulary; an intermediate question tests implementation under concurrency; a senior question tests crash windows and trade-offs; an architect question tests ownership, constraints and operations together.

ScoreEvidence
0Names a product or pattern with no mechanism.
1Defines the concept and a plausible happy path.
2Explains implementation and the key concurrency/failure case.
3Defends alternatives, scope, recovery, measurable validation and operational ownership.

The rubric assesses the reasoning shown, not years of experience. For each answer below, add a follow-up you would ask as an interviewer. A strong response explicitly distinguishes what is known from what must be clarified.

2. Foundational: define before naming libraries

FoundationalWhat makes an operation idempotent?
Repeated application of the same intended operation has the same intended effect as applying it once. Responses need not be identical. For POST /orders, explain operation identity and atomic duplicate enforcement rather than assuming POST itself provides the guarantee. Follow-up: what happens when the same key carries a different payload?
FoundationalAuthentication versus authorization?
Authentication establishes identity under a trust model; authorization decides whether that identity may perform an action on a resource. A valid token does not grant access to every order. Follow-up: where is tenant ownership checked for an export?
FoundationalCache versus read replica?
Both can serve copies, but an application cache reuses selected answers with explicit key/freshness policy, while a read replica maintains a database copy under its replication protocol. Both can be stale. Follow-up: which path can confirm a newly committed order?
FoundationalLatency versus throughput?
Latency is the time for an operation over a stated boundary; throughput is completed operations per unit time. Higher concurrency can improve throughput until a resource saturates and waiting increases. Follow-up: which measurements distinguish CPU work from pool waiting?

3. Intermediate: make the mechanism concrete

IntermediateHow do you prevent two buyers taking the last item?
Use an authoritative conditional mutation such as UPDATE inventory SET available=available-:qty WHERE sku=:sku AND available>=:qty with positive validated quantity. Check affected rows and commit the reservation in the same transaction. Follow-up: how is a repeated reservation request recognized?
IntermediateHow do you avoid lost updates in a REST API?
Expose a version or strong validator with a defined representation scope; require a conditional update and atomically compare the expected version at the storage boundary. Return the documented precondition failure when stale. Follow-up: what does the client do after reading the new state?
IntermediateWhy can cursor pagination still repeat or omit results?
The cursor must encode stable ordering and a unique tie-breaker, but changing sort fields, deletions and dataset evolution still affect traversal. Define whether the contract is a live traversal or a snapshot. Follow-up: how would an export establish a consistent view?
IntermediateHow would Spring publish an event safely after an order commit?
Store order and outbox in the same local transaction, then relay committed rows. A relay can republish after a crash, so consumers need repeat-safe processing. An in-memory after-commit callback alone is not a durable publication ledger. Follow-up: what protects an external fulfillment effect?

4. Senior: walk the failure window

SeniorThe payment provider succeeded but the client timed out. Now what?
Treat the outcome as unknown until verified. Keep the provider operation identity, query or retry according to its idempotency contract and persist reconciliation progress. A fresh payment key risks another charge. Follow-up: what if the provider retention window has elapsed?
SeniorWhy did adding replicas increase errors?
Test whether a shared bottleneck was amplified: total pool capacity, retries, hot locks or dependency quotas. Compare fleet admissions with useful completions and dependency saturation. Bound global pressure before adding callers. Follow-up: what capacity remains when one zone fails?
SeniorA message repeatedly fails deserialization. Should it be skipped?
Preserve the event and identity, isolate the incompatible population and establish ordering requirements. Skipping can allow later aggregate events to overtake a prerequisite. Repair a compatible reader and replay under a durable deduplication/state protocol. Follow-up: what proves business recovery?
SeniorHow do you roll back a release that wrote new data states?
Check whether old code can read and act on those states. Image rollback does not reverse data. Disable unsafe new writes if supported, deploy compatible readers or forward repair, then reconcile affected records. Follow-up: what would have prevented the rollout hazard?

5. Architect: a complete checkout prompt

Prompt: design checkout for a multi-tenant shop with a flash sale, external payments and asynchronous fulfillment. Browsing can be stale, overselling is forbidden, and an unknown payment must not cause a second charge. Ask for actual workload, latency, completion and recovery targets before choosing components.

Expected reasoning: establish authoritative inventory and payment state; reserve atomically with repeat-safe identity; commit outbox with local facts; invoke the provider with stable identity outside lock-holding transactions; persist unknown outcomes; deduplicate local consumer effects and reconcile remote fulfillment. Isolate tenants, cap admissions, define expiry/late-success policy and measure completion age.

Strong follow-ups: Where is the last-item claim serialized? Who wins payment versus reservation expiry? What if the provider has no idempotency or lookup contract? Which read may be stale? What state survives a region loss? A strong answer may conclude a guarantee cannot be met under a stated provider constraint and propose a business or integration change.

ArchitectHow would you evaluate two technically plausible designs?
Compare invariant coverage, intermediate states, failure recovery, peak/failure capacity, security and team operating cost. Require evidence at the critical boundaries, not only a clean topology diagram.
ArchitectWhat if the business requires instant completion during every dependency outage?
Expose the contradiction: a final authoritative remote result may be unavailable. Offer durable acceptance with pending state, degraded scope or a revised availability guarantee. Do not promise an outcome that the system cannot establish.

6. Evaluate three answers to the same checkout prompt

Prompt: a Spring API creates an order, reserves the last item and calls a remote payment provider. Clients retry after timeouts. Explain how you prevent overselling and duplicate charges, including a crash after the provider accepts payment.

AnswerAssessmentMissing reasoning
“Use Redis, Kafka and retries.”Score 0: product names without a protocol.No authority, commit boundary, stable identity or recovery evidence.
“Use a unique request key and @Transactional.”Score 1–2 depending on the mechanism explained.Can protect a suitable local effect, but does not include an ordinary provider call or explain competing legitimate buyers.
“Protect local stock/identity atomically, persist remote intent, reuse provider identity and reconcile unknown outcomes.”Score 3 only when qualifications and validation are defended.Must still state provider limitations, expiry races, retention, authorization and evidence.

A strong answer begins by asking whether payment acceptance must be synchronous and what the provider supports. It validates positive quantity, scopes command identity and protects the local reservation with a conditional mutation/appropriate transaction protocol. A repeated intention must not reserve again, while two distinct valid intentions still compete on the stock authority.

It keeps remote payment outside lock-holding local work, records the original provider identity and treats a lost response as unknown. A durable worker/status path reconciles that intention. If the provider has no adequate identity or inquiry contract, the answer exposes the weaker guarantee and governed unresolved path rather than claiming exactly once. Reservation expiry and late success require a conditional business recovery policy.

Follow up with four variations: reuse the same key with a different amount; replay after retention; a worker resumes after ownership expires; restore local data to before a provider completion. The candidate should preserve the right identities and authority under each change. Naming another component without repairing the failure argument does not improve the score.

IntermediateWhat distinguishes an adequate local answer from an architect-level answer?
The local mechanism can explain uniqueness and a transaction. The stronger answer defends every independent authority, ambiguous outcome, failure/retention condition, operating owner and measurable validation without promising an impossible guarantee.

7. Review the mechanisms behind the answers

Use the decision record, the duplicate-payment investigation, capacity calculations and Spring transaction boundaries to strengthen weak answers. Return after studying and explain the same solution without relying on a product name.
