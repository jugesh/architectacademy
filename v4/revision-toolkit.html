1. A practical review cycle

Read one lesson, close it and explain the main operation in plain language. Name the invariant, the simplest implementation, its failure window and the chosen mechanism. Then compare your explanation with the answered checkpoints. Record a gap such as “I cannot explain lease expiry” rather than marking a whole subject vaguely incomplete.

A suggested cadence is next-day recall, another review later in the week and a later scenario-based review. Adjust it to your recall rather than treating a schedule as proof of learning. The checklist below is browser-local, is not an assessment and does not sync across devices.

3. A focused glossary of commonly blurred terms

Invariant

A condition that must hold after every allowed state transition. A target permits a measured error budget; an invariant defines a forbidden outcome.

Atomicity

A defined group of changes commits together or does not commit. Specify which resources share that boundary.

Isolation

Rules governing concurrent transaction observations and permitted anomalies. A transaction annotation alone does not specify every business-safe protocol.

Consistency

The observations or histories an operation permits. State the model and scope; do not confuse replica freshness with multi-system atomicity.

Idempotency

Repeating one intended operation preserves its intended effect. Recognizing identity and enforcing it atomically are separate implementation tasks.

Deadline

The latest acceptable completion time across a defined operation. Individual timeout budgets should account for remaining time.

Backpressure

A mechanism for signaling or limiting work according to downstream demand/capacity. It requires participating boundaries and does not create capacity.

Outbox

A durable publication intent committed with local business changes, then relayed. Relaying can repeat and does not include arbitrary remote effects.

Inbox

A durable consumer-side receipt/identity record used with a local mutation to make repeat processing safe within that boundary.

Fencing

Rejecting actions from an obsolete owner using authoritative ownership/version evidence. Lease expiry alone does not stop old execution.

RPO

Recovery point objective: the tolerated data-loss window. Measure it against recoverable business facts, including external effects.

RTO

Recovery time objective: the tolerated duration to restore a defined usable service, including dependencies and reconciliation.

SLI

A precisely defined measurement of service behavior, with eligible events and good/bad criteria.

SLO

A target for an SLI over a stated window. Acceptance and eventual business completion can require separate indicators.

Projection

A derived representation maintained from authoritative facts. Its ordering, freshness, deletion and replay policies must be explicit.

Cardinality

The number of distinct values/combinations in a dataset or telemetry dimension. Unbounded metric labels can create unbounded series.

Optimistic concurrency

A mutation commits only if an expected version or condition still holds. Handle conflicts explicitly rather than overwriting newer state.

Compensation

A business recovery action after a committed step. It may not perfectly undo the original effect and can itself fail.

5. Self-check: the disappearing response

A customer creates an order. The database commits, the connection drops, and the customer retries. Explain the possible states without assuming the first request failed. Identify the durable operation identity, payload mismatch policy, concurrent duplicate guard and response reconstruction mechanism.

IntermediateWhat should the answer contain?
A stable scoped key, a fingerprint or equivalent mismatch rule, atomic enforcement with the local order effect, and a documented response for completed/in-progress/conflicting requests. A lookup can recover an already committed result. If payment is external, analyze that provider boundary separately.
AdvancedChange the scenario: the retry arrives after retention expires.
The deduplication guarantee may no longer apply. Business uniqueness and provider reconciliation can still matter. Define retention relative to real retry/replay windows and document what happens outside it rather than implying infinite protection.

6. Recall the boundary: five short scenario checks

Attempt each answer before expanding it. Explain the authority, the observation, the uncertainty and the recovery identity in plain language. If you cannot, return to the linked core lesson and try again later with a changed scenario. A checklist mark should reflect an explanation you can give, not only a page you opened.

FoundationalA cache hit is fast. What has that proved?
Only that the cache returned a reusable value according to its current path. It has not proved freshness, tenant isolation or a valid stock/permission decision. Check representation identity and the freshness contract.
IntermediateThe consumer committed and then crashed before acknowledgement. What happens?
Redelivery may occur. A durable consumer-scoped receipt committed with the local effect can recognize the repeat. A remote effect still needs its own identity and recovery contract.
IntermediateThe same RPS suddenly requires more memory. What changed?
Service time or retained work may have increased. In stable averages, more time at the same admitted rate means more work present. Inspect waits, payloads and queues before treating it as a CPU-only scaling problem.
AdvancedThe backup restored, but a customer was charged afterward. What is authoritative?
Identify the local restore point and the original provider operation. Reconcile the provider fact and local state before another irreversible action. A restored pending row is not evidence of remote failure.
AdvancedA token is valid but the user no longer owns the order. What decides access?
Current resource authorization under the chosen freshness/delegation policy. Token validity and broad scopes do not by themselves establish ownership; already-issued capabilities can have a separate revocation/lifetime contract.

For a second round, change one assumption: remove the provider lookup, add a cache layer, replay an old event or require a tighter revocation bound. Explain which mechanism must change and which guarantee is now impossible without a different contract. This tests transfer of understanding rather than memorization of the original answer.

7. Explain it without notes

Choose a weak concept and answer: What does it mean? Why is it needed? Which failure exposes it? Where is it enforced? What remains unprotected? What test would disprove the design? Use the interview rubric to assess the answer.

8. Return to the source of confusion

Use the official references attached to each lesson when an implementation guarantee matters. Use failure cases to test understanding and migration scenarios to check whether the design still works while state and versions change.
