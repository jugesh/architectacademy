Agree on acceptance before building the feature

Turn “reserve stock safely” into concrete acceptance examples, implement one slice, and decide what evidence is sufficient to accept it. Connect business agreement to executable Java checks.

Technical definitionAcceptance test-driven development brings business, development and testing perspectives together to define acceptance examples before implementing the corresponding behavior. Those examples guide development and provide evidence for accepting the change.
Before you begin. Start with BDD example mapping. Basic Java helps with the runnable example; no Cucumber experience is needed.

Learning outcome: Write acceptance examples that expose ambiguity, choose their execution boundary and distinguish a passing domain example from evidence that the deployed feature is acceptable.

1. Start with a decision to accept

A shop asks for “stock reservation that never oversells.” The developer subtracts a quantity from available stock. QA checks that ten minus one is nine. The business expects a buyer asking for all ten units to succeed and two buyers racing for the last unit never both to succeed. Everyone can approve a different interpretation unless the examples come first.

An acceptance example is like agreeing on the delivery contents before signing a receipt. It gives the team an observable condition for saying this slice is ready. It should describe a valuable outcome and its exceptions, rather than prescribe private method calls or a particular framework.

For this lesson, reserve reduces available units immediately when enough units exist. Zero and negative quantities are invalid; an unaffordable request is rejected without changing stock. Reservation expiry, payment and duplicate command handling are separate requirements. Naming these exclusions prevents a small example from becoming an accidental promise about the entire checkout.

2. Connect ATDD, BDD and TDD

PracticeFocus in this storyUseful output
ATDDWhat evidence will let us accept this stock-reservation slice?Agreed acceptance examples before implementation.
BDDWhich rules and concrete cases create shared understanding?A common language and discovered questions.
TDDWhat small behavior should the implementation support next?Fast failing checks, implementation and refactoring.

The practices overlap substantially. Teams need not perform three ceremonies or maintain three copies of every example. Use the acceptance conversation to settle the outer behavior, then smaller tests to evolve and diagnose its implementation. A test written afterward can still supply regression evidence, but did not drive that original decision.

The equality row distinguishes greater-than from greater-than-or-equal. The rejected row checks preservation of state as well as a false result. Invalid quantity is a separate category: it is not simply another insufficient-stock case. A response code will be decided at the HTTP boundary later.

Ask about the missing cases while the change is cheap. Does the stock represent physical units or an available projection? Is reservation an immediate deduction, an expiring hold, or a promise from a remote warehouse? Who owns the last-unit decision? An unanswered authority question is a blocker to the overselling guarantee, even when the arithmetic examples are easy to automate.

4. Run the agreed examples

The table becomes a parameterized JUnit test. The remaining tests check invalid input and two sequential buyers. This runs against a small in-memory Inventory object, not a live service. Read both assertions in each row: the decision and resulting stock jointly describe the rule.

package academy.testing;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import org.junit.jupiter.params.provider.ValueSource;
import static org.junit.jupiter.api.Assertions.*;

class InventoryExamplesTest {
    @ParameterizedTest
    @CsvSource({"10,1,true,9", "10,10,true,0", "10,11,false,10", "0,1,false,0"})
    void agreedReservationExamples(long before, long requested,
                                   boolean accepted, long after) {
        var inventory = new Inventory(before);
        assertEquals(accepted, inventory.reserve(requested));
        assertEquals(after, inventory.available());
    }

    @ParameterizedTest
    @ValueSource(longs = {0, -1, Long.MIN_VALUE})
    void invalidQuantitiesCannotChangeStock(long quantity) {
        var inventory = new Inventory(10);
        assertThrows(IllegalArgumentException.class, () -> inventory.reserve(quantity));
        assertEquals(10, inventory.available());
    }

    @Test void negativeInitialStockIsRejected() {
        assertThrows(IllegalArgumentException.class, () -> new Inventory(-1));
    }

    @Test void sequentialBuyersCannotBothTakeTheLastUnit() {
        var inventory = new Inventory(1);
        assertTrue(inventory.reserve(1));
        assertFalse(inventory.reserve(1));
        assertEquals(0, inventory.available());
    }
}

These checks use the Inventory domain example. They are executable acceptance examples for that domain behavior only. The sequential last-unit test does not run two transactions at once. A real overselling promise still needs a database concurrency mechanism and a test of the actual competing writes.

5. Deliver one thin slice

Start with one owner reserving one product. Connect input validation, the application command, an authoritative conditional update and an observable result. Keep the first slice small enough to demonstrate to the person who owns the rule. Then add invalid input, rejection and the competing buyer with explicit expectations.

LayerEvidence neededTypical omission
DomainThe agreed quantity/state examples pass.Testing only accepted requests.
HTTP/securityIdentity, quantity parsing and error mapping follow the contract.A test principal with unlimited privileges.
DatabaseCompeting reservations cannot both spend the same unit.Using only an in-memory fake.
OperationsUnknown results and stuck reservations can be found and recovered.Treating a timeout as proof of rejection.

Do not require the team to automate every unknown before learning anything. A short spike may reveal the real warehouse contract. Record the finding and settle the acceptance rule before treating the implementation as complete. A prototype is useful evidence about feasibility, not permission to hide an unresolved business decision.

6. Accept the right guarantee

-- Conceptual SQL for a single authoritative stock row:
UPDATE stock SET available = available - :quantity
WHERE tenant_id = :tenant AND sku = :sku
  AND :quantity > 0 AND available >= :quantity;
-- Inspect affected rows and commit before claiming durable acceptance.

This illustrates where the arithmetic decision belongs when requests compete. Zero affected rows needs interpretation under the service contract, including nonexistent products and authorization. The database engine, transaction isolation and data model still need verification. This SQL is a teaching fragment, not the implementation used by the runnable Java tests.

If the write commits but the response is lost, the buyer has an unknown outcome. Before retrying, the system needs stable command identity and a durable way to discover the original reservation. Add an example for that timeline if repeat-safe requests are in scope. An acceptance suite that excludes it cannot justify a retry-safety claim.

7. Keep acceptance useful in CI

Store the agreed examples near the code and review rule changes with their owner. Run fast domain checks on every change, then adapter and database checks at the boundaries they substantiate. A small deployed acceptance flow should use the built artifact and representative configuration.

For an asynchronous reservation, acceptance and completion need separate observations. Replace a fixed sleep with bounded polling of the reservation status, reporting the last observed state on failure. Choose the deadline from the agreed test environment, and make cleanup safe for committed fixtures. Never make a green run depend on a previous scenario creating the next scenario’s stock.

8. Keep the claim honest

ATDD earns its cost when acceptance is ambiguous or crosses roles. It is less useful as a second paperwork layer for a settled internal helper. A compact table with meaningful counterexamples often communicates more than a long feature file.

Business acceptance is not exhausted by a green test suite. Accessibility, security, capacity, recovery and user usefulness may need other evidence. State which checks were automated, against what boundary, and which decisions remain open.

Practice: add an expiring reservation. Agree what happens exactly at expiry, after payment succeeds late and after a duplicate release. Write one acceptance example for each disagreement before selecting a timer or queue.

9. Explain acceptance with evidence

FoundationalDoes ATDD require Gherkin?

No. A table, readable code or another shared notation can express the examples. The important order is agreement before implementation, followed by useful checks.

FoundationalHow does it differ from UAT?

User acceptance testing commonly evaluates an implemented product. ATDD uses acceptance examples to guide development beforehand; later user evaluation can still reveal unmet needs.

IntermediateWhy include the exact-stock row?

It distinguishes the intended inclusive boundary. A test that only asks for one unit from ten cannot detect rejecting equality.

IntermediateCan an in-memory example prove no overselling?

It can prove selected domain decisions and sequential state changes. It cannot establish the correctness of concurrent database transactions or multiple service instances.

AdvancedWhat is the acceptance result after a lost commit response?

Unknown until the original operation can be reconciled. Define stable identity and a durable outcome lookup; a timeout alone is not a rejected reservation.

AdvancedWhat would you include in a release decision?

The agreed examples, boundary-specific evidence, known exclusions, operational recovery and owner approval of remaining risks. A passing example count is not the release argument.
