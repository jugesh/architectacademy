Library/Testing & Quality/Property-Based Testing

Property-Based Testing · fundamentals to production judgment

Test a rule across many generated cases

Move from a few stock-reservation examples to generated invariants, constrained inputs and small counterexamples. Run Java properties and learn their limits around models, overflow, randomness and concurrency.

Technical definitionProperty-based testing checks general statements about behavior over many generated inputs. A useful failure report identifies a counterexample; shrinking attempts to simplify it while preserving the failure.
Before you begin. Read TDD test design and the stock examples. Understand Java assertions and the meaning of an invariant.

Learning outcome: Write a meaningful property, design valid generators and interpret a failure without confusing sampled cases with a proof of all possible behavior.

1. Four examples leave a large input space

The reservation table covers ten units and an empty store. Production receives quantities ranging across many values. One example per familiar case cannot explore every combination of current stock and requested units. A property asks what must remain true across that wider space.

Imagine checking that a weighing scale conserves weight across many combinations of objects. You do not need to know every reading in advance to say adding an object must not make the combined weight lower. Similarly, an accepted reservation must not create stock, and a rejected one must leave stock unchanged.

Keep concrete examples for important business boundaries. Generated cases complement the named equality, empty-stock and invalid-input cases; they do not replace the conversation that established what the correct rule means.

2. Separate the property from its generator

PartQuestionInventory example
PropertyWhat general relation must hold?Available stock never becomes negative or increases after reserve.
GeneratorWhich inputs and distributions do we explore?Nonnegative stock and positive quantities in a declared range.
OracleWhy is the expected relation valid?A reservation consumes units or changes nothing.
ShrinkerCan a failing case become easier to understand?Reduce a large failing pair to a small boundary case.
SeedHow is this generated run reproduced?Record the seed, generator configuration and library version.

Avoid an expected result that simply repeats the production condition. Independent relations often reveal more. Conservation, monotonicity, round trips under a defined domain and idempotency of a completed operation can be useful properties. Each needs assumptions: compress/decompress may be a round trip, while a lossy normalization is not reversible.

3. Run two Java properties

The project pins QuickTheories 0.26 and runs it inside ordinary JUnit tests. These properties exercise the same Inventory class as the acceptance table. Fixed seeds keep this teaching run reproducible; they are not a claim that these are the latest library versions or that two seeds cover the domain.

package academy.testing;

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;
import static org.quicktheories.QuickTheory.qt;
import static org.quicktheories.generators.SourceDSL.longs;

class InventoryPropertiesTest {
    @Test void reservingCannotCreateOrMakeNegativeStock() {
        qt().withFixedSeed(73).withExamples(1000)
            .forAll(longs().between(0, 1_000_000), longs().between(1, 1_000_000))
            .checkAssert((before, quantity) -> {
                var inventory = new Inventory(before);
                boolean accepted = inventory.reserve(quantity);
                long after = inventory.available();
                assertTrue(after >= 0 && after <= before);
                if (accepted) assertEquals(before, after + quantity);
                else assertEquals(before, after);
            });
    }

    @Test void splittingAnAffordableReservationPreservesItsTotal() {
        qt().withFixedSeed(91).withExamples(1000)
            .forAll(longs().between(1, 500_000), longs().between(1, 500_000))
            .checkAssert((first, second) -> {
                long total = first + second; // bounded generators avoid overflow
                var split = new Inventory(total);
                var combined = new Inventory(total);
                assertTrue(split.reserve(first));
                assertTrue(split.reserve(second));
                assertTrue(combined.reserve(total));
                assertEquals(combined.available(), split.available());
            });
    }
}

Runnable Java 17+ examples live in the shared Maven project. From the repository root:

mvn -B -f v4/examples/testing/pom.xml test

The first property checks bounds and conservation for accepted operations, and unchanged stock for rejection. It does not insist every affordable request is accepted: an implementation that always rejects would pass that property. The named acceptance examples and the second property provide additional evidence. This is why the strength of the oracle matters as much as the number of generated inputs.

The second property compares two affordable sequential reservations with one combined reservation. Its generators deliberately bound the sum to avoid overflow. It relies on our simple unit-reservation rules; a bulk discount, per-order minimum or reservation fee could make the analogous property invalid in a different domain.

4. Design inputs that reach the interesting behavior

Generator decisionGood reasonRisk to inspect
Restrict stock to nonnegative valuesValid-state properties have a clear domain.Invalid constructor input still needs separate checks.
Generate positive quantitiesExercise valid requests without excessive discarded cases.Zero and negative cases are excluded, so add them explicitly.
Bias toward equality and adjacent valuesFind boundary defects quickly.Uniform random generation may rarely reach a particular boundary.
Generate structured domain valuesReach valid combinations intentionally.A generator that excludes difficult states can hide defects.
Bound arithmetic intentionallyAvoid accidental overflow in the test oracle.The bounded test proves nothing about untested extreme values.

Prefer constructing valid inputs directly over filtering almost everything out. Heavy assumptions can produce a passing run with very little useful exploration. Track discarded cases and distributions where the tool supports it. Generate invalid inputs separately when rejection is part of the contract.

For full-range arithmetic, decide whether overflow should be rejected or represented through a larger numeric type. Add named cases around Long.MAX_VALUE and Long.MIN_VALUE as appropriate. A test that overflows its own expected value can approve the same bug as the implementation.

5. Read a small failure carefully

Illustrative failure, not a captured run:
Property: an affordable reservation succeeds
Original case: stock=73492, quantity=73492
Simplified counterexample: stock=1, quantity=1
Possible cause: quantity >= available was used for rejection
Expected business rule: equality is allowed

Shrinking searches for a simpler failing case under the generator and shrink strategy. It does not guarantee the mathematically smallest example or diagnose the cause automatically. Reproduce the case, understand the rule, then add a clear named regression test if it communicates a valuable boundary.

Preserve the seed, tool version and relevant generator settings. A seed alone may not reproduce the same sequence after generator or framework changes. The actual input is often the most durable diagnostic artifact, especially when an external state or timing schedule contributed to the failure.

6. Generate sequences when order matters

A single reserve call cannot establish a whole reservation lifecycle. A richer model might include reserve, release, expire and repeat command. Generate sequences against a simple reference model, checking allowed transitions and conservation after every step.

Conceptual stateful model, not in the runnable example:
initial available = 10
reserve(R7, 3) → available 7, R7 active
repeat reserve(R7, 3) → available 7
release(R7) → available 10, R7 released
repeat release(R7) → available 10
Invariant: active holds + available = total stock
Assumptions: no replenishment, consumption or loss in this model

The reference model must be simpler or independently specified enough to avoid copying the same defect. Define how rejected commands, unknown outcomes and replay relate to the model. If a release can race a successful shipment, the valid state machine needs a business decision before property generation can resolve it.

Sequential generated commands do not explore concurrent database interleavings. For concurrency, combine a justified consistency mechanism with controlled competing transactions, history checking or another appropriate verification technique.

7. Use randomness as evidence, not noise

Use a stable, quick property set for routine feedback and an intentionally varied run to explore other seeds when useful. Record failing seeds and counterexamples as artifacts. Give larger runs a clear budget so an expensive search cannot stall every change indefinitely.

Failure sourceUseful diagnosisWrong response
A real counterexampleReplay the input and inspect the violated rule.Change the seed until green.
Environment dependencyIsolate clocks, external state and fixtures.Assume every generated failure is a random flake.
Bad property assumptionReview it with the domain owner.Modify production code to satisfy an invalid theorem.
Generator excludes edge casesAdd structure/bias and explicit examples.Increase sample count without improving input relevance.

The included Maven project runs two fixed-seed properties with 1,000 generated examples each. These are sampled sequential checks over bounded inputs. Report that scope explicitly rather than claiming complete coverage or mathematical proof.

8. Challenge the oracle

A property that output is non-null is rarely enough. An always-empty result can pass many weak properties. Add properties or examples that distinguish doing useful work from simply avoiding obvious failure. Conversely, avoid asserting a relation that is only accidentally true for the current implementation.

Property-based testing explores a defined input space with a defined oracle. A flawed property or generator can miss every important defect even after millions of cases.

Practice: define properties for pagination without duplicates under a stated snapshot model. Explain why the same property can fail legitimately on a changing live dataset. Then write a generator that includes equal sort keys.

9. Explain generated evidence

FoundationalExample-based versus property-based tests?

An example names a concrete expected case. A property describes a relation checked across generated cases. Useful suites often combine both.

FoundationalWhat is shrinking?

An attempt to simplify a failing generated case while preserving the failure. It makes diagnosis easier, but does not guarantee a globally minimal counterexample.

IntermediateWhy can an always-reject implementation pass a property?

If the property only asserts no negative stock or no change on rejection, rejecting everything satisfies it. Add liveness/useful-behavior examples and stronger independent relations.

IntermediateIs a fixed seed enough to reproduce a failure?

Not always after generator or library changes. Preserve the actual counterexample, relevant versions and configuration too.

AdvancedDo generated sequential tests prove concurrent safety?

No. They exercise generated inputs and orderings within the stated execution model. Database races require evidence at the concurrency boundary.

AdvancedHow do you avoid mirroring the implementation?

Use independently justified invariants, metamorphic relations or a simpler model, and check important concrete examples. Review whether the oracle can share the same defect.
