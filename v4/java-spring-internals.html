1. Follow one checkout request

A request reaches a controller, validates a DTO, invokes an application service, opens a database transaction, runs statements, commits and serializes a response. HTTP-client calls, executor handoffs and event listeners can insert additional boundaries. Draw where the transaction begins and where each resource is held. Latency accumulates in waits as well as execution.

The servlet request thread and a database connection are different resources. A thread may wait for a connection, or hold one while waiting for a remote provider. Increasing the request executor can admit more waiting work without increasing database throughput. Instrument pool acquisition and statement time independently.

2. Thread pools and connection pools

A bounded executor limits active tasks; a bounded queue limits waiting tasks. Rejection must have an explicit caller-visible or durable recovery policy. An unbounded queue can turn overload into delayed failure and memory pressure. HikariCP pools reusable database connections, but its maximum does not mean the database can execute that many expensive queries efficiently.

Budget across the fleet: twenty pods with a pool maximum of twenty can request 400 connections, plus administration, migrations and other services. A larger pool can increase lock contention and query time, keeping connections occupied longer. Determine a useful operating point through workload measurement, not by setting every pool to the server limit.

3. Spring transaction boundaries

In ordinary proxy-based Spring transaction management, an external call through the proxy applies the transaction advice. Calling another annotated method on this bypasses that proxy boundary. The annotation expresses a policy; it does not make arbitrary code transactional. Use an explicitly proxied application-service boundary or a deliberate programmatic transaction when the control flow requires it.

// Teaching fragment: caller invokes this Spring-managed service.
@Transactional
public Reservation reserve(Command command) {
    int changed = inventory.reserveIfAvailable(
        command.sku(), command.positiveQuantity());
    if (changed != 1) throw new InsufficientStock();
    Reservation saved = reservations.insert(command);
    outbox.append(saved.toEvent());
    return saved;
}
// Call the payment provider outside this lock-holding transaction.

The repositories must participate in the intended transaction manager and data source. Default rollback rules commonly differ for unchecked versus checked exceptions; configure and test the intended policy. Catching a database exception does not necessarily restore a usable transaction. JPA flush can surface a constraint violation later than the method that staged the write.

4. Virtual threads, reactive code and blocking

Virtual threads make many waiting Java tasks cheaper to represent; they do not increase database connections, provider capacity or CPU. Do not use a pool of virtual threads as the concurrency control for a scarce dependency. Use explicit admission or permits around the resource while creating virtual threads according to the supported execution model.

Reactive pipelines coordinate nonblocking work and backpressure when the participating components support it. Blocking a small event-loop pool can stall unrelated requests. Wrapping blocking JDBC in a reactive type does not change JDBC into nonblocking I/O. Conversely, a virtual-thread approach may simplify blocking code but still requires cancellation, context and resource limits. Choose for the actual workload and team, not as a universal throughput upgrade.

5. Memory, GC and context propagation

A growing heap may reflect retained pending work, cache growth, oversized payloads or a leak. GC activity is evidence to interpret, not the root cause by definition. Compare allocation rate, live set after collection, pauses, queue lengths and payload distribution. Bound collections and request bodies before merely enlarging memory.

MDC is commonly thread-bound. Executors, reactive pipelines and message boundaries need supported context capture, restoration and cleanup. ScopedValue can carry scoped in-process values but does not propagate HTTP headers or create distributed spans. Keep security context, trace context and business operation identity distinct and avoid leaking one request’s state into another.

6. Worked diagnosis: low CPU, slow requests

Observe 90% database-pool occupancy, long acquisition waits and moderate query execution time. A code change placed an HTTP provider call inside @Transactional after the first query. Connections are now held across remote waits. Verify the timeline using tracing plus transaction/pool metrics, then move the remote step behind a durable state boundary without losing recovery identity.

Bound provider waits, use a persisted payment state and reconcile unknown outcomes. Do not simply move the call earlier if that creates an unrecorded remote effect. Validate resource release on timeout and exception, mixed load across endpoints and total fleet connection usage.

7. Runtime interview ladder

FoundationalDoes @Transactional include a remote REST call?
It does not enlist an ordinary remote HTTP service in the local database commit. The remote effect can succeed even if the local transaction rolls back.
IntermediateWhy did self-invocation not start a new transaction?
Under normal proxy mode the call did not cross the transaction proxy. Refactor the boundary or use an explicit supported transaction mechanism; do not rely on an annotation that was never intercepted.
AdvancedDo virtual threads remove backpressure needs?
No. They reduce the cost of many waiting tasks, which can actually make it easier to overload finite dependencies. Bound admissions and scarce resources separately.
