Contract-First Development · fundamentals to production judgment

Agree on the interface before both sides implement it

Design an order-cancellation HTTP contract before the client and server diverge. Work through schemas, error semantics, security, compatibility and a realistic implementation-verification pipeline.

Technical definitionContract-first development reviews and versions an interface agreement before implementing its participants. Machine-readable schemas describe the wire format; explicit semantics and executable checks connect that agreement to actual behavior.
Before you begin. Read API Design and the BDD cancellation examples. JSON and basic HTTP are enough to begin.

Learning outcome: Review a contract for both syntax and meaning, identify breaking changes and distinguish schema validation from business or integration correctness.

1. Two teams implement different agreements

The frontend sends POST /orders/O7/cancel and expects 204. The backend implements POST /orders/O7/cancellations and returns a JSON outcome. Both teams can pass local tests while integration fails immediately. Agreeing on the boundary first prevents this avoidable mismatch.

Think of choosing the plug and socket dimensions before manufacturing both sides. A shared drawing helps independent work, but it does not prove the wiring is safe. In an API, the drawing includes path, method, headers and schemas; the wiring includes authorization, durable effects and failure semantics.

For our cancellation example, a 200 result means the synchronous operation has a durable cancellation outcome under the documented identity policy. A claimed order returns conflict. If the design instead accepts background work, the contract must describe 202, a status resource and terminal outcomes; changing only the status code would be incomplete.

2. Start from observable behavior

Contract partQuestion to settleExample
AddressingWhich operation represents the intention?POST /orders/{orderId}/cancellations.
InputWhat must every caller supply?Authenticated identity and a scoped Idempotency-Key.
SuccessWhat fact is durable at the response?Cancellation completed or a recognized repeated cancellation.
FailureWhat may the caller safely do next?Conflict means too late; timeout means outcome unknown.
EvolutionWhich existing clients must keep working?Explicit compatibility/support policy, including generated clients.

Collaborate with the domain owner and actual consumers. A schema created from an internal DTO can be a useful starting point, but generated documentation after implementation is not evidence that the interface was agreed beforehand.

3. Read a concrete OpenAPI contract

This operation comes from a complete, downloadable OpenAPI 3.1.1 teaching document. It is an interface artifact, not a running endpoint. The response outcome deliberately maps the domain decision CANCEL to the public state label CANCELLED.

{
  "post": {
    "summary": "Cancel an unclaimed order",
    "operationId": "cancelOrder",
    "security": [
      {
        "bearerAuth": []
      }
    ],
    "parameters": [
      {
        "name": "orderId",
        "in": "path",
        "required": true,
        "schema": {
          "type": "string",
          "minLength": 1
        }
      },
      {
        "name": "Idempotency-Key",
        "in": "header",
        "required": true,
        "schema": {
          "type": "string",
          "minLength": 1
        }
      }
    ],
    "responses": {
      "200": {
        "description": "A durable cancellation or replayed cancellation result",
        "content": {
          "application/json": {
            "schema": {
              "type": "object",
              "required": [
                "orderId",
                "outcome"
              ],
              "properties": {
                "orderId": {
                  "type": "string"
                },
                "outcome": {
                  "type": "string",
                  "enum": [
                    "CANCELLED",
                    "ALREADY_CANCELLED"
                  ]
                }
              }
            }
          }
        }
      },
      "401": {
        "description": "Missing or invalid authentication"
      },
      "403": {
        "description": "Caller is not permitted by the resource policy"
      },
      "404": {
        "description": "Order is not visible under the agreed disclosure policy"
      },
      "409": {
        "description": "Warehouse claim prevents cancellation"
      }
    }
  }
}

A bearer security scheme describes how a credential is presented. It does not validate a token or enforce order ownership. The server must validate the credential under the intended issuer/audience policy and check resource-level permission before changing state. The 403/404 descriptions also require an agreed disclosure policy.

4. Write what the schema cannot prove

ConcernAgreement beyond the schemaRequired implementation evidence
Retry identityScope keys by principal/tenant and operation; define payload mismatch and retention.Duplicate and concurrent request tests against durable storage.
DurabilityDefine the commit represented by 200.Read committed state through a separate transaction after response.
OwnershipA caller may act only on permitted orders.Cross-customer request is denied and changes no state.
Unknown outcomeTimeout is not proof of rollback.Original-key replay or a documented status lookup.
Information disclosureDecide whether forbidden/not-found resources are distinguishable.Consistent policy in lookup and error mapping.

Do not encode a promise only in an example payload and assume every tool enforces it. Examples illustrate intended values; schemas define structural constraints; prose/state-machine rules define additional behavior. Review those pieces together and state which checks validate each one.

If a provider cannot support your desired retry policy, contract-first work has exposed a design conflict early. Resolve it through an operation resource, workflow or different acceptance point rather than publishing a contract the system cannot uphold.

5. Use mocks without trusting them blindly

After review, the client can develop against a contract-based mock while the provider implements the endpoint. A useful mock produces agreed success and failure shapes, including missing optional fields and documented error responses. It should not become a hand-edited second specification.

Contract review → versioned specification
  Client: real API client + specification-based mock
  Provider: implementation + request/response verification
  CI: schema validation + compatibility diff + semantic examples
  Release: verify supported deployed client/provider combinations

Generated server interfaces can enforce method signatures but not transaction behavior. Generated clients can also make compatibility assumptions, such as exhaustive enum handling. Compile and exercise representative clients; do not assume that adding a response enum member is harmless because the JSON remains valid.

Tools such as Specmatic can connect specifications to mocks and verification, subject to their supported dialects and configuration. Choose and pin tools for the project’s specification version. The downloadable artifact here is not presented as having run through a full live-provider verification suite.

6. Review changes in both directions

ChangeLikely riskReview action
Require a new request fieldOld clients cannot produce it.Add a compatible default or migrate/version deliberately.
Remove/rename a response fieldExisting readers lose a dependency.Observe usage and preserve overlap during migration.
Add an optional response fieldUsually additive, but strict readers may reject it.Check actual client parsing and tolerance.
Add an outcome enum valueExhaustive readers may fail.Define unknown-value behavior or a version transition.
Change 200 to 202The meaning of completion changes.Treat as a semantic contract change, not cosmetic schema editing.

Compatibility depends on a direction and a population. Can an old client send to the new provider? Can a new client run against the old provider during rollout? Which versions are still supported? A green final-state integration test says little about mixed versions during deployment.

For events, also consider retained history, delayed messages and replay. A new reader may need to understand old facts long after the old writer is gone. A live HTTP compatibility diff does not establish that event-history requirement.

7. Verify the implementation boundary

In a Java/Spring service, keep transport DTO validation separate from the domain policy. Verify JSON binding, required headers, error envelopes, configured security and request limits at the HTTP boundary. Verify state transitions and unique identities at the repository/transaction boundary.

CI should fail on malformed specifications and unintended incompatible changes. It should also run selected semantic examples: the last allowed cancellation, claimed-order conflict, duplicate identity and denied owner. A schema validator will not discover that an error response was returned after the database already changed.

EvidenceProves something aboutDoes not establish
Specification parses/validatesDocument structure and supported constraints.A deployed endpoint exists.
Response matches schemaSelected wire representation.Correct order, tenant or committed result.
Provider semantic testA selected behavior in the configured application.All client compatibility.
Deployed smoke checkBuilt artifact/routing for a critical path.Every failure or workload.

8. Keep one maintained agreement

Avoid maintaining an OpenAPI file, a separate mock JSON library and controller annotations that disagree. Choose the authoritative artifact and verify generated or derived outputs. Review intentional changes with affected consumers and define a retirement process for obsolete behavior.

A machine-readable contract is a powerful agreement about an interface. It is not a proof of end-to-end security, useful business behavior, capacity or resilience. Keep those claims attached to their own evidence.

Practice: change cancellation to asynchronous processing. List the required changes to acceptance meaning, response schema, status lookup, retry behavior and client UX before editing the OpenAPI file.

9. Defend the agreement

FoundationalContract-first versus code-first?

Contract-first agrees the boundary before implementation; code-first derives a description from code. Either can maintain useful contracts, but the timing and collaboration differ.

FoundationalDoes OpenAPI enforce authorization?

It can describe security requirements. Actual credential validation and resource policy remain implementation responsibilities and need tests.

IntermediateWhy can a schema-compatible change break clients?

Semantics, enum handling, strict parsing, ordering, limits and status meanings can change without a structurally invalid payload.

IntermediateCan teams develop in parallel with a mock?

Yes, if the mock derives from the agreed contract and both real participants are verified. A passing mock test alone proves neither provider behavior nor real integration.

AdvancedHow do you review a rollout?

Check old/new client-provider combinations, supported versions, durable data changes and the removal schedule. Verify the overlap rather than only the final new-new pair.

AdvancedWhat does a response validator miss after a timeout?

Whether the original effect committed and how the caller can recover it. That needs stable operation identity and durable outcome semantics beyond shape validation.
