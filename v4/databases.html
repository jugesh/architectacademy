Databases · fundamentals to production judgment

Choose storage by the questions and invariants it must serve

Build an order store step by step: access patterns, keys, indexes, transactions, replication, and partitioning. Follow the data before choosing a database brand.

Technical definitionA database manages durable data and supplies defined operations for reading and changing it. A data model describes entities, relationships and constraints; a storage engine and access paths determine how those operations are executed.
Before you begin. Know JSON objects and the basic meaning of an SQL table. Read requirements and workload measurements if latency or throughput terms are unfamiliar.

Learning outcome: Select a storage model for an access pattern, explain its consistency boundaries, and diagnose the cost of a query or concurrent update.

1. An order is more than a JSON document

Start with facts, questions and forbidden outcomes, not a database brand.

The API lesson defined the contract and Scalability counted the work. Now follow the facts the order service must preserve. An order has identity, a customer, line items and a lifecycle. A reservation changes stock. A retry may represent an already accepted intention. Storing a JSON payload durably does not by itself decide whether two competing changes are legal.

Write the questions and mutations separately. “Find the latest 25 orders for this tenant and customer” specifies a filter, ordering and result bound. “Reserve two units if enough remain” specifies a conditional mutation. “Never reuse a partner order ID within a tenant” specifies a uniqueness invariant. These become inputs to access paths, constraints and transaction design.

We will first choose the authority for those facts, then make its important operations correct, then reduce their access cost. This order avoids selecting a fast lookup that permits an unsafe update or an attractive storage model that cannot meet the required ownership boundary.

2. Derive correctness before choosing a storage product

Read this slowly: it establishes the distinction used in the implementation sections.

A database stores committed facts, but the application decides which combinations of facts are legal. An invariant is a rule that must remain true after every allowed transition. A constraint checks a rule in the database. A transaction groups changes into one commit. Isolation determines which concurrent observations and outcomes are permitted. These terms solve related but different parts of correctness.

Two buyers see stock=1. If both make a decision in Java and later write stock=0, two orders can exist for one item. Begin with one atomic conditional update that subtracts only when enough stock remains. Inspect affected-row count and insert the reservation in the same local transaction. The business decision now happens where competing mutations are coordinated. An index can accelerate access to that row; it cannot replace the rule.

Check your understanding
FoundationalWrapping check-then-write in a transaction always prevents overselling.
Not at every isolation level and not for every read/write pattern. Use an appropriate conditional mutation, lock or serializable protocol, account for conflicts and retry the entire required transaction with stable operation identity.
IntermediateWhy is a replica a poor default for a post-create lookup?
An asynchronous replica can lag behind the committed writer. The absence is then stale evidence, not proof creation failed. Choose the read path according to the promised freshness and use the original identity on retries.

3. Follow one operation before adding patterns

Carry this concrete operation through the later mechanisms.

Suppose two checkout requests both read the last available item. Each sees stock=1 and each decides the purchase is valid. Storing both orders durably would preserve the wrong business outcome. Durability answers whether committed data survives; isolation and atomic conditional mutation determine whether concurrent decisions can commit safely. This small example explains why database selection starts with invariants as well as query speed.

4. List operations and invariants

Separate the access pattern, invariant, freshness and recovery promise.

An access pattern is a precise operation over data, including its expected frequency, result size and freshness. Record its key distribution as well: one large merchant can dominate traffic even when most tenants are small. Distinguish the authoritative acceptance path from analytics or search views that can be delayed.

An invariant describes a forbidden committed state. Uniqueness of a partner reference, nonnegative available stock and a legal order transition are different rules and may need different enforcement mechanisms. A unique constraint guards identity; a conditional update or suitable locking/isolation protocol guards a concurrent stock decision. A fast query is an efficiency requirement rather than a substitute for either rule.

Durability and recovery need their own definitions. State what a successful acknowledgement means in the chosen store/configuration, the tolerated data-loss window and the tested restore process. A running replica can reproduce an accidental delete, while an older backup can omit a later external payment. Database correctness includes recovery evidence, not only successful inserts.

Functional requirements

  • Create order and line items.
  • Read one order; list recent orders for a customer.
  • Reserve stock and expose payment state.

Targets and invariants

  • No duplicate partner order within a tenant.
  • Stock must not become negative.
  • Illustrative p95 order lookup below 100 ms.
  • Durable accepted order; recovery point defined explicitly.

An invariant is a condition that must hold after every allowed transition. “Never negative stock” needs an atomic mutation; a fast eventual view is insufficient. “Revenue dashboard updated within a minute” can use an asynchronous projection. Different operations can therefore use different storage paths without changing the source of truth.

5. Keys and constraints before indexes

Choose identity and ownership before optimizing how rows are found.

Begin with identity. A primary key uniquely identifies a stored row under the database’s constraint semantics. A business key such as tenant plus partner reference recognizes an externally meaningful order. They can coexist because they answer different questions. If two requests race, only an authoritative uniqueness guard can decide which insert may commit; a Java existence check alone has a gap between its read and write.

Next decide which facts belong together. Order and line items may need one atomic creation, while a historical customer display name can intentionally be copied into an order. A foreign key can enforce that a referenced identity exists, but cannot decide whether an order may transition from cancelled to shipped. Normalization reduces duplicated mutable facts; denormalization deliberately duplicates data for a read or historical requirement and requires an owner for updates.

Before committing to embedding or separate rows, walk an update and a query. Which fields change together? Can a collection grow without bound? Is the copied field a historical snapshot or a current truth? This makes the model’s consistency cost visible before it becomes a production synchronization problem.

CREATE TABLE orders (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  external_id text NOT NULL,
  customer_id uuid NOT NULL,
  created_at timestamptz NOT NULL,
  status text NOT NULL,
  UNIQUE (tenant_id, external_id)
);

The primary key identifies a row. The unique constraint enforces one external order ID per tenant even when two requests race. Checking existence in Java first is useful for a friendly error but cannot replace the constraint. Relational foreign keys can enforce referenced identity; domain transitions still require application rules.

Normalize when it protects shared facts and useful relationships. Embed or denormalize when an access pattern benefits and you can own the update rules. Duplicating customer display name into an order may preserve a historical snapshot; duplicating live account credit can create an invariant problem.

6. Derive an index from a query

Derive an access path from this query, then inspect what the engine actually does.

A table stores rows, while an index supplies an additional access structure. For the example query, tenant and customer identify a subset and created_at plus ID order that subset. A suitable composite B-tree index can let PostgreSQL locate the relevant range and traverse it in the required order, rather than examining and sorting the whole table. The ID gives deterministic ordering when timestamps tie.

The column order must be justified by actual predicates and ordering. An index optimized for equality on tenant/customer followed by recent time is not automatically the best path for an unrelated status-only query. PostgreSQL planning and multicolumn access have nuances, so inspect the chosen plan rather than treating “leftmost column” as a universal rule that predicts every possible optimization.

An index costs storage and mutation work; updates to indexed values may require additional maintenance. Inspect representative data, selectivity, estimated versus actual row counts, sort behavior and buffers. EXPLAIN describes a plan; EXPLAIN ANALYZE executes the statement to collect measurements. Be deliberate about executing writes or expensive queries during diagnosis. A sequential scan can be the right plan when much of the table is needed.

SELECT id, created_at, status
FROM orders
WHERE tenant_id = :tenant AND customer_id = :customer
ORDER BY created_at DESC, id DESC LIMIT 25;

CREATE INDEX order_customer_recent
ON orders (tenant_id, customer_id, created_at DESC, id DESC);

An index is an additional access structure. The ordering above lets the engine locate a tenant/customer range and return recent rows without sorting the whole order table. It costs storage and work on inserts/updates. A low-selectivity index or incompatible leading columns may not help the actual query.

Use EXPLAIN to inspect the plan; use EXPLAIN ANALYZE carefully because it executes the statement. Compare estimated and actual row counts, scanned rows, sorts and buffer activity with representative data. A sequential scan is sometimes the correct choice for a large fraction of a table.

7. What a transaction protects

Place the concurrent decision at the authoritative commit boundary.

Atomicity means a defined set of changes commits together or not at all. Isolation describes the concurrent observations and anomalies the transaction protocol permits. Durability describes survival under the specified failure/acknowledgement model. These properties are related, but one does not imply every business decision is safe.

Follow the last item under PostgreSQL Read Committed. A reads available=1; B reads available=1; both decide in Java that a sale is allowed. Merely putting each read and later unconditional write in a transaction does not make that decision exclusive. Move the check into the authoritative mutation: decrement only where enough stock remains, check affected rows, and insert the corresponding reservation in the same local transaction.

Keep quantity validation and duplicate identity explicit. A negative decrement can increase stock; a repeated valid command must not reserve again. For several items, use a consistent acquisition/update order and roll back the intended group when a prerequisite fails. Deadlocks or serialization failures require a bounded retry of the relevant transaction, with stable business identity and no duplicated external effects.

In Spring, the transaction boundary must actually be intercepted under the selected transaction mechanism and use the intended resource/manager. A proxied @Transactional method does not enlist an ordinary HTTP payment provider. Keep remote calls outside lock-holding work and persist recovery state across that boundary. Exceptions and JPA flush timing can move when a failure is observed; test the commit outcome rather than assuming a repository call returning means the transaction committed.

BEGIN;
UPDATE inventory SET available = available - :qty
WHERE sku = :sku AND available >= :qty;
-- Continue only if exactly one row changed; qty must be positive.
INSERT INTO reservations (...);
COMMIT;

In Spring, a transaction interceptor normally surrounds a proxied method invocation. Self-invocation can bypass proxy interception. Keep the data-source and transaction-manager relationship explicit, avoid long remote calls while holding locks, and understand rollback rules. Catching an exception does not necessarily make a failed transaction usable again.

8. SQL and NoSQL as access-model choices

Compare the same operation and guarantee across storage models.

Only now compare storage models. Relational storage makes related rows, constraints and flexible indexed queries natural. Key-value access favors deliberately chosen keys and bounded known operations. Documents can keep aggregate-shaped data together. Search reorganizes derived facts for text retrieval and ranking. These are access/ownership choices, not a ranking from old to modern.

For each candidate, express the same operation and its failure boundary. Can the required conditional change be atomic? What is the transaction scope? Which exact read path can be stale? What happens to the busiest key? How are backups restored and migrations verified? SQL systems can partition/replicate, and NoSQL systems can provide transactions; the selected product, topology and access path determine the actual guarantee.

A hybrid can be appropriate when ownership is clear: authoritative orders in one write model, search in a derived index, large export bytes in object storage. It becomes dangerous when multiple stores independently act as authority for the same money or inventory fact without an explicit coordination/reconciliation protocol.

“NoSQL scales” is not a selection criterion. A badly chosen partition key can overload one partition. SQL databases can partition and replicate; NoSQL databases may offer transactions. State the specific operation, transaction boundary, consistency mode and operational cost.

9. Replication and partitioning solve different problems

Choose where a reader may look and who may accept writes.

Another copy and another owner solve different problems. Replication maintains copies of a logical dataset; partitioning divides the dataset or work across keys/ranges. A readable replica may absorb eligible reads but can lag the writer. If order creation commits and the next lookup reaches a delayed copy, not found is stale evidence rather than proof creation failed.

Define the promised observation for each journey. The caller retrieving a newly created order may need a writer path or another explicit read-your-writes mechanism. A revenue dashboard may tolerate delay. Do not turn either choice into an assumption that all indexes, replicas or regions behave identically in a managed service.

Partitioning introduces locality and distribution trade-offs. Tenant-based routing keeps many queries local, but a giant tenant can remain hot. Splitting it may require fan-out or a new projection. Rebalancing must preserve write ownership while routes change; an old process does not stop acting merely because another node became leader. The dedicated replication lesson develops these protocols further.

10. Worked design: order store and revenue view

Keep correctness local where possible and derive the delayed revenue view.

Design the order write model from the earlier requirements: a scoped unique partner reference, an atomic reservation decision, the order facts and a durable outbox intent. Keep the customer/recent-order access path indexed. A response is successful only according to the transaction’s actual outcome; a lost response is recovered using the original operation identity.

Now add daily revenue. Its one-minute freshness requirement allows a projection rather than an expensive synchronous scan in every checkout. Each source event needs identity and ordering/version semantics appropriate to the projection. Replaying a paid event must not count revenue again, and a later refund or correction must adjust the view under an explicit rule.

Backfill is another concurrent protocol: connect a consistent baseline to subsequent changes using a known position or an equivalent supported mechanism. Otherwise updates during the scan can be lost or overwritten by older copied values. Validate counts and critical business totals, not merely whether the pipeline is running. Keep operational order acceptance independent of a temporarily delayed dashboard.

Test unique-key races, concurrent last-item purchases, replica lag after create, transaction deadlocks, and projection replay. Observe pool waits, query latency, locks, slow-query plans and replica lag. Adding an ORM does not remove database behavior: JPA flush timing and N+1 queries still need measurement.

11. Tricky failures to rehearse

Classify scan cost, lock wait, pool wait and stale observation separately.

Investigate a symptom by separating access cost, contention and freshness. A query can be slow because it scans too much, waits for a lock, waits for a connection, or receives a resource-starved execution plan. An ORM method name does not distinguish those cases. Measure generated SQL, plan, transaction duration and acquisition wait before selecting a fix.

Also examine changes over time: index growth, data skew, long-running snapshots, schema overlap and restore compatibility. A clean small dataset can hide an N+1 read pattern or an expensive count. A successful backup job is not a demonstrated restore. Test representative volume, competing mutations and recovery paths against the actual engine/configuration.

FailureCommon mistakeBetter response
Replica lag after writeTreat a missing replica row as a failed creationUse authoritative lookup and retry identity.

Record recovery time objective (RTO: acceptable recovery duration) and recovery point objective (RPO: acceptable data-loss window). Availability of a running replica is not the same as recoverability after corruption or an operator mistake.

12. Interview ladder

FoundationalPrimary key versus index?
A primary key identifies a row and enforces uniqueness/non-null semantics. An index is an access structure; databases commonly implement key constraints with indexes, but not every index defines identity.
FoundationalDoes an index always make a query faster?
No. Selectivity, column order, result size, data distribution and plan choice matter. Indexes also increase write and storage cost.
IntermediateWhy is check-then-insert unsafe?
Two transactions can both observe absence before either commits. A unique constraint or equivalent atomic conditional operation is the final concurrency guard.
IntermediateCan a read replica show stale data?
Yes when replication is asynchronous or the selected read path lags. Define freshness requirements and route operations accordingly.
AdvancedHow do you migrate without a write outage?
Choose an initial consistent copy plus change capture/catch-up and verification, control the write switch, define rollback and conflict ownership, and test failure windows. The exact protocol depends on source/target capabilities.
AdvancedWhen would you avoid a distributed transaction?
When a durable state machine, outbox and compensation can meet the business contract with less coordination. That introduces temporary intermediate states and recovery work rather than making cross-system atomicity disappear.
IntermediateWhy can a transaction still allow an unsafe last-item purchase?
A transaction groups changes, but the isolation/protocol may allow both callers to read stock=1 before either writes. Put the stock condition into an authoritative atomic mutation or use an appropriate lock/isolation protocol. Inspect affected rows and commit the reservation with the decrement. Distinct purchase keys still compete; idempotency alone does not solve that race.
AdvancedThe index exists but production is slow. What do you inspect?
The actual query and parameters, chosen plan, estimated/actual rows, selectivity/skew, sorts and buffer work, plus lock and pool waits. Verify representative data and query frequency, including ORM-generated N+1 and count queries. An index can be present yet irrelevant to the bottleneck, and a sequential scan may be a rational plan.

13. Further reading and practice

Know the authoritative read before adding a cached copy.

Use the PostgreSQL references to check the exact isolation and plan behavior used in your design. Use Spring’s transaction documentation to check proxy boundaries and rollback policy. For other stores, read the documentation for the specific operation, index and topology rather than transferring guarantees from a different engine.

Before moving to Caching, explain which database operation is authoritative and how much it costs. A cache adds a separate copy with its own identity and freshness policy; it should not hide an undefined transaction boundary or turn a stale browse answer into permission to sell stock.

  • PostgreSQL isolation: statement snapshots, anomalies and retry requirements.
  • PostgreSQL EXPLAIN: read real query plans before optimizing.
  • Spring transactions: proxy boundaries and transaction behavior.
  • DynamoDB read consistency: table/index-specific guarantees.
