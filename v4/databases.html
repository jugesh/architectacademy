Databases · fundamentals to production judgment

Choose storage by the questions and invariants it must serve

Build an order store step by step: access patterns, keys, indexes, transactions, replication, and partitioning. Follow the data before choosing a database brand.

Technical definitionA database manages durable data and supplies defined operations for reading and changing it. A data model describes entities, relationships and constraints; a storage engine and access paths determine how those operations are executed.
Before you begin. Know JSON objects and the basic meaning of an SQL table. Read requirements and workload measurements if latency or throughput terms are unfamiliar.

Learning outcome: Select a storage model for an access pattern, explain its consistency boundaries, and diagnose the cost of a query or concurrent update.

1. An order is more than a JSON document

The API lesson treated persistence as the place where accepted orders survive. We now open that box. A row or document stores facts; keys identify them; queries retrieve them; constraints and transactions determine which changes are legal. Keep these responsibilities separate while reading. The first goal is to describe what the application needs, not to memorize a list of database products.

The first order endpoint accepts a customer, items, and a total. Storing that JSON looks sufficient until the next requirements arrive: find recent orders for one customer, prevent two orders with the same external ID, reserve stock, and calculate daily revenue. These are different access patterns and correctness requirements.

An access pattern is a specific question or mutation: “latest 25 orders for tenant T and customer C” is useful; “we need flexible queries” is too vague to choose an index. Write frequency, result size, ordering and freshness beside each pattern.

2. Follow one operation before adding patterns

Carry this concrete operation through the later mechanisms.

Suppose two checkout requests both read the last available item. Each sees stock=1 and each decides the purchase is valid. Storing both orders durably would preserve the wrong business outcome. Durability answers whether committed data survives; isolation and atomic conditional mutation determine whether concurrent decisions can commit safely. This small example explains why database selection starts with invariants as well as query speed.

3. List operations and invariants

Functional requirements

  • Create order and line items.
  • Read one order; list recent orders for a customer.
  • Reserve stock and expose payment state.

Targets and invariants

  • No duplicate partner order within a tenant.
  • Stock must not become negative.
  • Illustrative p95 order lookup below 100 ms.
  • Durable accepted order; recovery point defined explicitly.

An invariant is a condition that must hold after every allowed transition. “Never negative stock” needs an atomic mutation; a fast eventual view is insufficient. “Revenue dashboard updated within a minute” can use an asynchronous projection. Different operations can therefore use different storage paths without changing the source of truth.

4. Keys and constraints before indexes

The requirements identify duplicate order identity; express that rule in a durable constraint.

CREATE TABLE orders (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  external_id text NOT NULL,
  customer_id uuid NOT NULL,
  created_at timestamptz NOT NULL,
  status text NOT NULL,
  UNIQUE (tenant_id, external_id)
);

The primary key identifies a row. The unique constraint enforces one external order ID per tenant even when two requests race. Checking existence in Java first is useful for a friendly error but cannot replace the constraint. Relational foreign keys can enforce referenced identity; domain transitions still require application rules.

Normalize when it protects shared facts and useful relationships. Embed or denormalize when an access pattern benefits and you can own the update rules. Duplicating customer display name into an order may preserve a historical snapshot; duplicating live account credit can create an invariant problem.

5. Derive an index from a query

A correct model still needs an efficient access path. Derive it from one exact query.

SELECT id, created_at, status
FROM orders
WHERE tenant_id = :tenant AND customer_id = :customer
ORDER BY created_at DESC, id DESC LIMIT 25;

CREATE INDEX order_customer_recent
ON orders (tenant_id, customer_id, created_at DESC, id DESC);

An index is an additional access structure. The ordering above lets the engine locate a tenant/customer range and return recent rows without sorting the whole order table. It costs storage and work on inserts/updates. A low-selectivity index or incompatible leading columns may not help the actual query.

Use EXPLAIN to inspect the plan; use EXPLAIN ANALYZE carefully because it executes the statement. Compare estimated and actual row counts, scanned rows, sorts and buffer activity with representative data. A sequential scan is sometimes the correct choice for a large fraction of a table.

6. What a transaction protects

A transaction groups operations into an atomic commit. Isolation controls which concurrent observations and anomalies are permitted. Under PostgreSQL Read Committed, each statement sees a snapshot from the start of that statement; two statements can see different committed data. Repeatable Read gives a stable transaction snapshot but does not make every business invariant automatic.

BEGIN;
UPDATE inventory SET available = available - :qty
WHERE sku = :sku AND available >= :qty;
-- Continue only if exactly one row changed; qty must be positive.
INSERT INTO reservations (...);
COMMIT;

In Spring, a transaction interceptor normally surrounds a proxied method invocation. Self-invocation can bypass proxy interception. Keep the data-source and transaction-manager relationship explicit, avoid long remote calls while holding locks, and understand rollback rules. Catching an exception does not necessarily make a failed transaction usable again.

7. SQL and NoSQL as access-model choices

ModelGood fitBoundary to examine
Relational (PostgreSQL/RDS)Relations, constraints, transactions, flexible indexed queriesJoin/query cost, locks, write capacity.
Key-value (DynamoDB)Known partition-key access and conditional item changesKey distribution, secondary-index behavior, transaction scope.
Document (MongoDB)Aggregate-shaped documents read/updated togetherDocument growth, multi-document invariants and index cost.
Search indexRelevance and text searchProjection freshness; not an automatic authority for orders.
Object storage (S3)Large immutable blobs and exportsObject lifecycle and metadata/query service.

“NoSQL scales” is not a selection criterion. A badly chosen partition key can overload one partition. SQL databases can partition and replicate; NoSQL databases may offer transactions. State the specific operation, transaction boundary, consistency mode and operational cost.

8. Replication and partitioning solve different problems

Transactions explain one database boundary. Copies and partitions introduce new boundaries.

Replication keeps copies of data. A read replica can absorb reads but may lag behind the writer. If checkout writes an order and immediately reads a replica, the customer can see “not found.” Route that read to an appropriate authoritative path or offer a documented read-your-writes mechanism.

Partitioning divides data across ranges or keys. It can distribute capacity, but now a cross-partition operation may require more coordination. Choose a key from access locality and load distribution together: tenant ID is convenient, yet one enormous tenant can remain hot. Backups are separate from replicas because a bad delete can replicate perfectly.

For RDS, inspect the selected engine and deployment type: traditional Multi-AZ standby behavior differs from readable replicas and Multi-AZ DB cluster configurations. For DynamoDB, verify consistency support for the exact table/index and topology; do not assume every read path supports strongly consistent reads.

9. Worked design: order store and revenue view

Keep orders, reservations and outbox in the relational write model because stock and duplicate-order rules need local atomicity. Use the customer/recent index for customer pages. Publish committed outbox changes to an analytics projection keyed by date and merchant. The dashboard can be one minute behind; order acceptance cannot depend on its freshness.

Each projection update carries an event identity or source position so replay does not double revenue. If order states can change, the projection must handle corrections/refunds, not just increment on every event. Backfill from a consistent snapshot plus a change position or an equivalent reconciliation strategy so concurrent changes are neither lost nor counted twice.

Test unique-key races, concurrent last-item purchases, replica lag after create, transaction deadlocks, and projection replay. Observe pool waits, query latency, locks, slow-query plans and replica lag. Adding an ORM does not remove database behavior: JPA flush timing and N+1 queries still need measurement.

10. Tricky failures to rehearse

FailureCommon mistakeBetter response
Replica lag after writeTreat a missing replica row as a failed creationUse authoritative lookup and retry identity.
Schema rolloutNew writer breaks old readers during rollbackExpand, migrate, verify, then contract.
Hot partitionAdd partitions without changing skewMeasure key distribution and choose a split/aggregation policy.
Backup existsAssume recovery is provenRestore into isolation and measure recovery time/data loss.

Record recovery time objective (RTO: acceptable recovery duration) and recovery point objective (RPO: acceptable data-loss window). Availability of a running replica is not the same as recoverability after corruption or an operator mistake.

11. Interview ladder

FoundationalPrimary key versus index?
A primary key identifies a row and enforces uniqueness/non-null semantics. An index is an access structure; databases commonly implement key constraints with indexes, but not every index defines identity.
FoundationalDoes an index always make a query faster?
No. Selectivity, column order, result size, data distribution and plan choice matter. Indexes also increase write and storage cost.
IntermediateWhy is check-then-insert unsafe?
Two transactions can both observe absence before either commits. A unique constraint or equivalent atomic conditional operation is the final concurrency guard.
IntermediateCan a read replica show stale data?
Yes when replication is asynchronous or the selected read path lags. Define freshness requirements and route operations accordingly.
AdvancedHow do you migrate without a write outage?
Choose an initial consistent copy plus change capture/catch-up and verification, control the write switch, define rollback and conflict ownership, and test failure windows. The exact protocol depends on source/target capabilities.
AdvancedWhen would you avoid a distributed transaction?
When a durable state machine, outbox and compensation can meet the business contract with less coordination. That introduces temporary intermediate states and recovery work rather than making cross-system atomicity disappear.
