API design · fundamentals to production judgment

Design APIs that clients can trust

An API is a long-lived contract between independently changing systems. Good design makes normal behavior obvious, failure behavior recoverable, and operational guarantees explicit.

Single lesson · V4Study in sections · 3 worked designsExamples: REST · Spring Boot · AWS
Continue learning. Browse the V4 lesson library: Scalability, Databases, Caching, Messaging, Reliability, and Observability. Each follows the same problem-to-implementation lesson structure.
Technical definitionAPI design is the deliberate specification of an interface’s resources or operations, schemas, semantics, security, failure behavior, and operational guarantees so that independent clients and servers can evolve without ambiguity.
How to use this lesson. Start with the contract and requirements. Then choose semantics and storage from the guarantees you need. The implementation examples are teaching fragments: adapt authentication, error mapping, transaction configuration, and observability to your service.

1. Start with the contract

Before choosing REST, gRPC, a database, or a cloud service, write what a caller can ask for and what the service promises in return. A contract includes syntax and behavior: status codes, side effects, retries, consistency, and failure states.

Syntax

Methods, paths, headers, media types, schemas, required fields, and examples. OpenAPI can describe much of this mechanically.

Semantics

What the operation means, when it commits, whether it is safe to repeat, and how a caller discovers the final state.

Compatibility

Which additions are safe, which changes break clients, and how deprecated behavior will be retired.

Operational promise

Latency, availability, limits, freshness, consistency, and observability expectations that clients rely on.

The contract documents the identity key, replay behavior, conflict behavior, and asynchronous possibility. Those details matter more than whether the handler is written in Spring or Node.

2. Separate functional and non-functional requirements

Functional requirements describe what the API does. Non-functional requirements describe the conditions under which it must continue doing it. Add invariants: statements that must remain true even during retries, crashes, and concurrent requests.

Functional

  • Create, retrieve, update, cancel, or delete a resource.
  • Validate fields and enforce business transitions.
  • Return a stable error shape and status.
  • Notify downstream systems or expose job status.

Non-functional

  • p95 read latency under 200 ms; p99 write latency under 800 ms.
  • 99.95% monthly availability and bounded blast radius.
  • Never charge one order twice; isolate tenants.
  • Trace every request and recover from dependency timeouts.

3. Model resources, actions, and state

Use resources for durable nouns and actions for business commands that cannot be expressed safely as a generic update. A payment is a resource; “capture payment” is a command with a distinct invariant and side effect.

NeedGood shapeReason
Read a resourceGET /orders/{id}Safe and cacheable when authorized.
Create with client intentPOST /orders + idempotency keyServer assigns identity; retries do not duplicate.
Replace a known representationPUT /profiles/{id}Repeatable replacement semantics.
Partial changePATCH /orders/{id} with explicit rulesAvoid accidental field resets.
Business commandPOST /payments/{id}/captureNames a state transition and its authorization.

State machines beat boolean flags

Define legal transitions before writing update code. For an order, CREATED → PAID → FULFILLING → SHIPPED is clearer than independently toggling paid, cancelled, and shipped. Reject impossible transitions with a conflict response and record who or what attempted them.

Common modeling trap. POST /orders/{id}/status with an arbitrary string moves validation into every client. Prefer a named command or a constrained transition endpoint with a documented state graph.

4. Reliability is part of the API

Most production API bugs appear between the request and the response: a client times out after the server commits, a proxy retries a body, or a dependency returns slowly. Design the uncertain path explicitly.

  1. Can the operation be repeated safely? Use naturally idempotent methods where possible. For a non-idempotent command, define an idempotency key or a domain identity such as orderId.
  2. Where is the effect committed? Put request identity and the local effect in one transaction. A cache lock alone cannot prove that a charge or shipment happened.
  3. Can the dependency be queried? Persist a durable intent and reconcile an IN_DOUBT state when the provider result is unknown.
  4. How should a caller retry? Publish timeout, retryable status, backoff, jitter, and key-retention behavior. Never tell callers to blindly retry every 500.
  5. Can work be asynchronous? Return 202 plus a status resource when completion exceeds the request budget. Make terminal states and expiry clear.

Practical REST + Spring pattern

Use a unique key in the database, a transaction around the ledger and local effect, and an explicit replay response. The key is scoped to the principal and operation, and the request fingerprint detects accidental reuse with a different payload.

Illustrative Spring JDBC fragment

@Transactional
public PaymentResult create(String accountId, String key, CreatePayment cmd) {
  String hash = fingerprint(cmd);
  int inserted = jdbc.update("""
    INSERT INTO api_idempotency(account_id, idem_key, request_hash, status)
    VALUES (?, ?, ?, 'IN_PROGRESS')
    ON CONFLICT (account_id, idem_key) DO NOTHING
    """, accountId, key, hash);
  if (inserted == 0) return replayOrConflict(accountId, key, hash);
  Payment payment = paymentRepository.insert(cmd); // same transaction
  jdbc.update("UPDATE api_idempotency SET status='SUCCEEDED', response=? WHERE ...", serialize(payment));
  return PaymentResult.created(payment);
}

This fragment assumes one relational database and no remote charge inside the transaction. If a provider call is involved, use an outbox or durable intent plus reconciliation; do not pretend a database transaction spans the provider.

Practical AWS mapping

API Gateway can enforce auth, throttling, and request shape; Lambda or ECS runs the handler; DynamoDB conditional writes reserve a key; SQS buffers work; Step Functions models long-running recovery; CloudWatch and X-Ray expose outcomes. The managed service does not remove the need to define ownership, deduplication scope, retention, and replay semantics.

5. Security, abuse, and data boundaries

Authentication answers “who is calling?” Authorization answers “may this caller perform this operation on this resource?” Enforce both at the service boundary and again at sensitive data access points.

6. Implementation choices in context

Spring Boot building blocks

  • @RestController for transport; DTOs for input/output; Bean Validation for shape checks.
  • @ControllerAdvice for a stable error envelope and correlation ID.
  • @Transactional for local atomicity, with awareness of proxy/self-invocation boundaries.
  • Spring Security method/resource authorization; WebClient/RestClient timeouts and bounded retries.
  • JdbcTemplate or JPA plus a database uniqueness constraint for idempotency and concurrency.
@PostMapping("/v1/orders")

    @RequestHeader("Idempotency-Key") String key,
    @Valid @RequestBody CreateOrderRequest request) {
  return ResponseEntity.status(CREATED).body(service.create(key, request));
}

HTTP / REST building blocks

Use method semantics, status codes, conditional requests, cache controls, content negotiation, and a documented error format. ETags with If-Match protect against lost updates; Location points to a new resource; Retry-After communicates throttling or delayed retry.

412 Precondition Failed  // If-Match version is stale
429 Too Many Requests   // include Retry-After
409 Conflict             // valid request conflicts with current state
202 Accepted             // work is queued; provide status URL

AWS building blocks

API Gateway or ALB terminates traffic; Cognito or an external issuer supplies identity; WAF filters abuse; Lambda/ECS/EKS executes business logic; RDS supplies relational constraints; DynamoDB supplies conditional writes; SQS/EventBridge decouple work; CloudWatch metrics and X-Ray traces show the path.

Selection rule: choose a service because it supplies a required guarantee—conditional write, durable queue, isolation, or operational scale—not because its name appears in an architecture diagram.

7. Tricky use cases to reason through

Case A — “The client did not send an idempotency key”

tricky A mobile client retries a payment after a timeout, but the original request had no key.

Reasoning: Do not hash the whole payload and assume equal payload means equal intent: two legitimate ₹499 payments can look identical. Prefer a server-issued checkout/order ID, a prior create-intent, or require a key for operations with irreversible side effects. If no identity exists, expose an inquiry/reconciliation path and make the ambiguity visible.

Case B — “The queue says exactly once”

tricky An SQS FIFO message is delivered once within its deduplication window, but the worker crashes after shipping and before acknowledging.

Reasoning: Delivery deduplication is not effect deduplication. Keep an inbox keyed by event ID or business command ID, commit the shipment state and inbox record atomically, then acknowledge. Make redelivery safe beyond the queue’s five-minute content-dedup window.

Case C — “The PATCH succeeded but the response was stale”

tricky A client updates an address while another device updates the same profile.

Reasoning: Require If-Match: "v17". The server applies the change only when the version matches and returns a new ETag. A 412 tells the client to refetch and merge. Last-write-wins is acceptable only when the product explicitly accepts lost updates.

Case D — “The provider is IN_DOUBT”

tricky Your timeout budget expires while a remote payment provider may have captured the card.

Reasoning: Persist intent before calling the provider, use the provider’s idempotency key, record the provider request ID, and reconcile by lookup or webhook. Return 202 or a documented pending state. Never turn uncertainty into an automatic second charge.

8. Interview ladder: questions and answers

Answer in layers: define the concept, state the invariant, choose a mechanism, explain failure behavior, then name a trade-off.

EasyWhat makes an HTTP method idempotent?
Repeating the same request has the same intended server-side effect as sending it once. It does not require the same response bytes. GET, PUT, and DELETE are defined as idempotent by HTTP semantics; a POST can be made safely repeatable with an application-level key.
EasyWhen would you return 201, 202, 204, 409, and 422?
201 means a resource was created; 202 means accepted for later processing; 204 means success with no body; 409 means a state conflict such as a duplicate identity or stale workflow; 422 is useful for semantically invalid input when your API convention distinguishes it from malformed syntax.
EasyWhy use DTOs instead of returning JPA entities?
DTOs keep persistence shape, security, and API compatibility separate. They prevent accidental lazy-loading or secret exposure and let the API evolve without making database refactoring a breaking change.
IntermediateOffset pagination or cursor pagination?
Offset is simple and useful for small, stable datasets. Cursor pagination scales better and avoids skipping or repeating rows when data changes, provided the cursor encodes a stable ordering and is treated as opaque. Always cap page size and define ordering.
IntermediateHow do you prevent lost updates?
Use optimistic concurrency: return a version or ETag, require If-Match, and update only when the version still matches. Return 412 or a documented conflict. A lock may be appropriate for short local transactions, but it is not a safe cross-request or cross-service coordination mechanism by itself.
IntermediateWhere should retry logic live?
Retry transient, bounded failures at the caller that understands the operation and can preserve identity. Use deadlines, exponential backoff, jitter, and a retry budget. Do not stack independent retries in gateway, client, service, and SDK until one request becomes dozens.
AdvancedHow do you design a payment API across a remote provider?
Create a durable local intent keyed by the business operation, validate the request fingerprint, call the provider with a stable provider key, persist the provider reference and result, and reconcile unknown outcomes through lookup/webhook. The local database transaction cannot atomically include the provider; model IN_DOUBT and recovery explicitly.
AdvancedWhy is an outbox useful, and what does it not solve?
An outbox commits a domain change and an event record in one local transaction, then publishes the event asynchronously. It closes the database-to-broker dual-write gap. It does not automatically provide global ordering, exactly-once effects, consumer idempotency, or a transaction across a remote API.
AdvancedHow would you evolve an enum without breaking clients?
Treat unknown values as possible, document forward compatibility, and avoid clients switching on an exhaustive set unless the contract supports it. Add values only when consumers tolerate them; use capability negotiation or a new version when semantics change, not merely because an implementation changed.
AdvancedWhat would you measure for an API?
Traffic, error rate by route and cause, p50/p95/p99 latency, saturation, throttles, dependency latency, queue age, retry count, idempotency replays/conflicts, and business outcomes such as duplicate prevention. Correlate logs and traces with a request ID while redacting sensitive values.

9. HATEOAS: make the next action discoverable

DefinitionHypermedia as the Engine of Application State means a client follows links and action metadata supplied by a resource representation to discover the next permitted interaction. The client still needs to understand link relations and media-type semantics.

Why it arises: a checkout workflow changes as an order moves from awaiting payment to shipped. Clients that construct every action URL and duplicate every transition rule become coupled to server internals. Hypermedia can expose the actions currently available.

GET /orders/ord_123
Content-Type: application/hal+json

{
  "id": "ord_123", "status": "AWAITING_PAYMENT",
  "_links": {
    "self": { "href": "/orders/ord_123" },
    "payment": { "href": "/orders/ord_123/payment" },
    "cancel": { "href": "/orders/ord_123/cancellation" }
  }
}

A HAL link identifies a related target; it does not by itself define the HTTP method or request schema. Document the relation, or use an action-capable format such as HAL-FORMS. After shipment the cancellation action may disappear, but the server must still enforce authorization and legal transitions when a stale client submits a command.

Spring HATEOAS · representation assembly fragment

EntityModel<OrderView> model = EntityModel.of(view);
model.add(Link.of("/orders/" + view.id()).withSelfRel());
if (policy.mayCancel(principal, order)) {
  model.add(Link.of("/orders/" + view.id() + "/cancellation")
                .withRel("cancel"));
}
return model;
Choose it whenCost / pitfall
Several clients navigate changing business workflows; relations have durable meaning.Clients must actually follow relations. Adding unused links gives little benefit.
Discovery and evolving resource relationships are valuable.More payload and media-type tooling; it does not eliminate semantic versioning.
Personalized action links affect caching. A shared cached representation must not expose another user's available actions. Generate external links using a configured public base URL or trusted proxy information, never arbitrary forwarded headers.

10. Pagination, filtering, and stable ordering

DefinitionPagination bounds a collection response. Offset pagination addresses a position; cursor pagination carries continuation state. Keyset pagination implements continuation using ordered field values.

Offset works well for small administrative tables with page-number navigation. Deep offsets become expensive and concurrent inserts can shift page boundaries. Keyset pagination is a better fit for feeds and large tables, but arbitrary page jumps and snapshot consistency require additional design.

GET /orders?status=PAID&limit=25&cursor=opaque-token

SELECT id, created_at, status FROM orders
WHERE tenant_id = :tenant AND status = :status
  AND (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT :limit_plus_one;

Use a supporting index such as (tenant_id, status, created_at DESC, id DESC) after validating the actual query plan. Fetch one extra row to determine whether another page exists. The unique ID breaks timestamp ties; timestamp alone can skip records.

{ "items": [{ "id": "ord_123" }],
  "nextCursor": "opaque-token", "hasMore": true }
Link: </orders?status=PAID&limit=25&cursor=opaque-token>; rel="next"
  • Bind the token to tenant, filters, sort order, and token version; reject incompatible or expired tokens. Base64 encoding provides neither integrity nor confidentiality. Sign the token or keep server-side state when appropriate.
  • Allowlist filter operators and sort fields. Cap page size and query complexity. Parameterize values and never concatenate raw user sort expressions into SQL.
  • Keyset traversal is not a frozen snapshot. Updating the sort field can still cause repeats or omissions. For exports, use immutable ordering plus a snapshot strategy, materialized result set, or explicit consistency contract.
  • Exact totals can be more expensive than the page itself. Make them optional, approximate, or omit them with a clear contract.

Spring mapping: Spring Data Page commonly entails a count query; Slice exposes whether another slice exists without requiring a total. Verify repository behavior and use a custom keyset query or supported scrolling API when that is the required contract.

11. Caching: freshness, validation, and isolation

DefinitionHTTP caching reuses stored responses according to freshness and validation rules. A fresh response can be reused directly; a stale response may be revalidated against the origin using a validator.
Directive / headerMeaning and use
Cache-Control: public, max-age=60A public catalog may be reused for 60 seconds, subject to other cache rules.
private, max-age=30Permit private client caching; shared caches must not store the response.
no-cacheStorage is allowed, but reuse requires successful validation.
no-storeInstruct caches not to store this response. It does not erase previously stored copies.
ETag + If-None-MatchValidate a representation; an unchanged conditional GET can return 304 without a body.
Vary: Accept-LanguageSeparate representations selected using this request header. Configure the actual CDN cache policy too.
GET /catalog/products/p7
→ 200 OK
  Cache-Control: public, max-age=60
  ETag: "product-p7-v8"

GET /catalog/products/p7
If-None-Match: "product-p7-v8"
→ 304 Not Modified  // no representation body

For writes, a strong ETag with If-Match can protect against stale updates. A weak ETag (W/) is unsuitable for strong If-Match comparison. The check and database update must be atomic; checking a version in Java and then issuing an unconditional update leaves a race.

Implementation choices: Spring ResponseEntity supports cache-control and ETag headers. Service-level @Cacheable caches method results and is a separate layer from HTTP caching. CloudFront can cache public reads, but TTLs, cache keys, authorization handling, and invalidation must match the contract.

Tricky case: a product price changes while cached pages remain fresh. Decide whether bounded staleness is acceptable. Always revalidate authoritative price and inventory at checkout; a cache TTL is not a business invariant.

12. Headers are part of the contract

Headers carry representation metadata, control information, credentials, and request context. Prefer standard fields where their semantics fit. Document custom fields, their limits, and whether intermediaries must preserve them.

FieldPurposeNuance

AuthorizationCredentials such as a bearer token.Redact from logs; never use an unverified token claim as authority.

Proxy boundary: strip or validate incoming forwarding headers at the trusted edge. Otherwise generated links, redirect URLs, client IP controls, and audit records can be spoofed. Header names are case-insensitive; header values follow their own field-specific rules.

13. Traceability from HTTP to background work

DefinitionDistributed tracing connects spans across service boundaries. A correlation/request ID helps search related records; a trace also records parent-child relationships, timings, and propagation context. An audit record captures a business or security action and has different retention and integrity needs.
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

Structured log:
{ "route": "/orders/{id}", "method": "GET", "status": 200,
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736", "durationMs": 42 }

Use OpenTelemetry instrumentation or Spring Boot's Micrometer Tracing integration to extract inbound context and inject outbound context. Configured framework HTTP client builders usually preserve instrumentation; manually constructed clients and thread/executor boundaries need verification. Propagate context through SQS message attributes using an agreed carrier rather than assuming HTTP headers travel with a message.

  • Validate incoming context; generate new context when invalid. A public caller must not control sampling cost or impersonate an internal actor through metadata.
  • Use route templates in metrics. Raw URLs, user IDs, request IDs, and trace IDs create unbounded metric cardinality.
  • Sampling means some requests have no retained trace. Keep essential outcome metrics and appropriate error/audit records independently.
  • Exclude tokens, card details, and personal data from headers, baggage, and log fields. Baggage can propagate far beyond the original service.

AWS mapping: an OpenTelemetry collector/ADOT pipeline can export to AWS observability services. Verify propagation and identifier conversion across API Gateway, application instrumentation, and workers; do not assume every service uses one native trace format.

14. Versioning and compatibility beyond URLs

A version identifies a contract boundary. Breaking changes include removing fields, changing types, tightening validation, changing defaults, or changing behavioral guarantees. Even adding an enum value can break a client that assumes an exhaustive set.

StrategyWhen usefulTrade-off
Path: /v1/ordersPublic APIs needing visible routing and documentation.Parallel surfaces and lifecycle ownership.
Header or media typeClients explicitly negotiate a representation/contract.Less visible in URLs; gateways, docs, and caches need correct handling.
Compatible evolutionAdd optional data while preserving semantics.Requires tolerant clients and automated compatibility checks.

Choose one primary mechanism and document what “v1” guarantees. Avoid a new major version for every additive release. For a breaking migration, publish both contracts, track usage by client/version, provide examples and a sunset plan, and retire the old contract only after the agreed migration process.

Tricky migration: integer money becomes decimal

Changing amount: 49900 from minor units to 499.00 silently changes meaning even if JSON parsers accept both. Introduce an explicitly named field or new contract, keep old semantics during migration, and test old clients against new server releases.

Implementation: OpenAPI diff checks identify many structural breaks; consumer/provider contract tests (for example Pact) exercise agreed interactions. Neither detects every semantic change. Include replay, authorization, pagination, and default-behavior examples in regression review.

15. Response mechanisms and error contracts

Choose response behavior from completion time, payload size, and interaction needs. Specify when work is committed, how the caller learns the final outcome, and what disconnecting means.

16. Documentation is an executable contract

OpenAPI describes operations, schemas, security schemes, and responses. Readers also need the behavioral rules it cannot fully enforce: consistency, idempotency retention, ordering, pagination stability, and recovery from uncertainty.

  1. Start: a working authenticated request, required scopes, environment URLs, and sample credentials acquisition.
  2. Define: field units, null versus absent, time zones, defaults, limits, enum extensibility, and money precision.
  3. Demonstrate: success, validation failure, authorization denial, conflict, rate limiting, duplicate replay, and async completion.
  4. Explain recovery: timeout behavior, retryable errors, status lookup, support request ID, and webhook replay.
  5. Maintain: changelog, compatibility policy, deprecation schedule, and SDK version support.

Practical toolchain: springdoc-openapi can generate a Spring API description; Swagger UI/Redoc renders it; OpenAPI Generator builds clients; Spectral lints conventions; Pact checks selected consumer interactions; Karate/REST Assured exercise runtime behavior. Use framework-compatible library versions and review generated schemas—generation does not prove the running API matches the document.

Additional interview questions

EasyIs no-cache the same as no-store?
No-cache permits storage but requires validation before reuse. No-store instructs caches not to store the response. Use an explicit policy appropriate for the data and verify browser and shared-cache behavior.
IntermediateDoes HATEOAS replace documentation and authorization?
No. Links expose relationships and potentially available transitions; clients still need relation and payload semantics. The server checks authorization and current state on every command because links can be cached or become stale.
IntermediateHow can pagination still duplicate records with a cursor?
A cursor with mutable sort fields can cross changed ordering boundaries. A timestamp without a unique tie-breaker is also ambiguous. Use a deterministic tuple and specify whether traversal is live or snapshot-based.
AdvancedA CDN leaks one user's action links to another. What failed?
A personalized representation was reused across security contexts. Stop shared storage of those responses, correct the cache policy/key and invalidate affected cached objects as needed. Verify authorization at the command endpoint; hidden links never enforce access.
AdvancedHow do you trace a retried command through SQS without double-counting business outcomes?
Propagate tracing context through message metadata and record attempt-level spans. Separately use a stable business command/event ID for deduplication and outcome accounting. Trace IDs identify observations; they are not durable idempotency keys. Count the committed business transition once and retries separately.

17. REST, gRPC, or GraphQL?

An API style determines how clients express intent and how contracts evolve. Select it from the interaction and consumer constraints; one system can expose public REST while using gRPC internally.

StyleChoose whenCosts and traps
REST / HTTPPublic integrations, resource operations, HTTP caching, broad client support.Over/under-fetching and many round trips may require a tailored read model or BFF.
gRPC / ProtobufControlled service clients, typed code generation, streaming, explicit deadlines.Browser use needs appropriate tooling such as gRPC-Web; proxies must support the protocol. Never reuse removed Protobuf field numbers.
GraphQLSeveral UIs need different projections of related data.Resolver N+1 queries, query cost, field-level authorization, and less straightforward shared HTTP caching.

Implementation choices: Spring MVC for REST, grpc-java for typed RPC, Spring for GraphQL with GraphQL Java for schema/resolvers. DataLoader can batch resolver reads, but its cache should normally be scoped to a request/security context. Bound depth, complexity, execution time, and list sizes; one GraphQL HTTP request can still create thousands of backend reads.

Decision exercise: a mobile screen needs ten downstream calls. First consider an aggregated endpoint/BFF or a purpose-built projection. GraphQL is useful when flexible client-selected queries justify its operational cost; adopting it does not repair slow databases or missing authorization.

18. Validation, precision, and PATCH semantics

Validation has layers: transport syntax, schema shape, domain rules, and transactional invariants. Bean Validation can reject a blank address; it cannot prove available stock remains sufficient between a read and a later write.

Input nuanceContract choiceFailure to avoid
Missing versus nullMissing means no change for a partial update; explicit null has documented removal/clearing semantics.A DTO that collapses missing and null can accidentally erase stored values.
MoneyInteger minor units plus currency, or decimal strings plus an explicit scale/rounding policy.Floating-point rounding and assuming every currency has two decimal places.
TimeUTC instants for events; local date plus IANA zone for future civil-time appointments.A fixed offset cannot describe future daylight-saving rules.
Unknown fieldsChoose strict write validation or tolerant parsing deliberately; document it.Silent misspellings or breaking an older server with a newly added client field.
Cross-field ruleValidate start before end, permitted currency, and immutable fields at the domain layer.Only validating field types and accepting impossible business state.
PATCH /profiles/u7
Content-Type: application/merge-patch+json
If-Match: "profile-v12"

{ "nickname": null, "address": { "city": "Delhi" } }

Under JSON Merge Patch, null removes an object member and arrays are replaced as whole values. JSON Patch instead uses explicit operations such as add/remove/replace/test with application/json-patch+json. Neither format grants permission to edit protected fields. Allowlist writable paths and apply validation to the resulting representation. A custom PATCH format is possible, but its rules must be explicit.

Spring fragment: @NotBlank, @Positive, nested @Valid, and a class-level validator handle input shape. Use BigDecimal from decimal strings where decimal arithmetic is required; enforce scale and rounding intentionally. Persistence constraints remain the final guard for uniqueness and concurrent invariants.

19. Concurrency and inventory reservations

DefinitionA race condition occurs when correctness depends on the timing of concurrent operations. An invariant such as available stock ≥ 0 must be enforced atomically at the authoritative store.

Reading stock=1 in two requests and then independently decrementing permits overselling. Use a conditional update rather than a check followed by an unconditional write.

UPDATE inventory
SET available = available - :quantity
WHERE sku = :sku AND available >= :quantity;
-- affected rows = 1: reserved; 0: insufficient stock or missing SKU
-- Require quantity > 0 and scope by warehouse/tenant where applicable.

In one local transaction, create a unique reservation, update inventory, and record the result. A duplicate command must replay the reservation rather than decrement again. For several SKUs, acquire locks/update in a deterministic order, roll back the entire reservation if any item fails, and retry deadlocks only within a bounded policy.

Expiry race: payment completion and reservation expiry can arrive together. Make RESERVED → CONFIRMED and RESERVED → EXPIRED conditional transitions. Only the winning expiry transition releases stock. Provider success after expiry needs a defined compensation policy, such as refund or a new reservation; do not silently mark an unfulfillable order confirmed.

Mapping: RDS transactions/row locks or optimistic updates; DynamoDB condition expressions and transactions when the access model fits. Redis is useful for fast admission control, but an expiring distributed lock alone does not replace a durable inventory invariant.

20. Security beyond a valid JWT

A signed token proves only the claims verified under a trusted issuer and validation policy. Validate allowed algorithms, issuer, audience, expiry and other relevant time claims. Then authorize the requested action on the actual resource.

// Illustrative resource lookup: tenant comes from verified security context.
Order order = repository.findByTenantAndId(currentTenant(), orderId)
    .orElseThrow(NotFoundException::new);
policy.requireCanRefund(currentPrincipal(), order);
// A scope such as orders:write does not imply ownership of every order.
  • OAuth scopes: express granted capabilities; combine them with tenant, ownership, roles, and business state. Use authorization-code + PKCE for appropriate interactive clients and client credentials for appropriate machine clients.
  • Token rotation: cache trusted signing keys with a rotation strategy; handle unknown key IDs without unbounded issuer fetches. JWT revocation requirements may call for short lifetimes, introspection, or explicit revocation state.
  • mTLS: authenticates peers at the transport boundary. It does not automatically authorize a user's refund or tenant access.
  • SSRF: callback URLs can make a server reach internal services. Validate destinations, DNS/IP results and redirects; restrict egress, block metadata/internal addresses, and account for DNS rebinding.
  • Mass assignment: bind writable DTO fields explicitly. A caller must not set role, tenantId, or payment status by adding JSON properties.

Spring/AWS: Spring Security resource-server JWT support supplies token verification machinery; configure audience and authorization policies explicitly. Cognito or another identity provider supplies tokens; API Gateway/WAF can enforce edge controls, while application-level resource authorization remains necessary.

21. Deadlines, retry budgets, and overload

A timeout limits one wait; an end-to-end deadline bounds the caller's useful time. Allocate time for connection acquisition, dependency work, retries, serialization, and returning a response. Cancel work that no longer has a useful consumer where safe, while preserving recovery for already-committed side effects.

Illustrative 800 ms request budget:
  50 ms admission/validation
  500 ms dependency work (including any retry)
  150 ms persistence and response
  100 ms safety margin
Each downstream deadline must fit the remaining budget.
MechanismProtects againstDoes not guarantee
Timeout/deadlineWaiting indefinitely.Cancellation or rollback of a remote side effect.
Circuit breakerRepeated calls to an unhealthy dependency.Concurrency isolation or idempotency.
Bulkhead/concurrency limitOne dependency consuming all worker connections.More backend capacity.
Bounded queueShort bursts beyond service rate.Sustained overload; backlog grows if arrival exceeds processing.
Retry budget + jitterRetry amplification and synchronized bursts.Safe repetition of an unsafe command.

Implementation: Resilience4j offers retry, circuit-breaker, rate-limiter and bulkhead modules; configure HTTP connection/read timeouts separately and verify whether cancellation reaches the client implementation. gRPC supports deadlines. For REST, define an internal deadline propagation convention at trusted boundaries. Gateway throttles are one protection layer, not a complete fair-use policy.

Three layers making three attempts each can create 27 leaf attempts. Pick retry ownership and count the initial call consistently. Do not hedge a charge across two providers unless the business protocol guarantees a single effect.

22. Bulk APIs and partial success

Batching reduces round trips, but complicates atomicity, authorization, limits, and retries. State whether the batch is one transaction, independently committed items, or an asynchronous job. Do not let a generic batch silently span arbitrary remote services.

POST /order-imports → 202 with job URI  // large import

// Example contract for a small independently processed batch:
200 OK
{ "results": [
  { "clientItemId": "a", "status": 201, "id": "ord_7" },
  { "clientItemId": "b", "status": 422, "code": "INVALID_CURRENCY" }
] }

The outer 200 above means the batch was processed according to this contract; it does not mean every item succeeded. An invalid envelope can fail as a whole. Preserve a stable item identifier and per-item idempotency identity; retry failed items without recreating successful ones. Bound item count, body bytes, response bytes and execution time. Do not adopt WebDAV's 207 without deliberately defining the media type and semantics for your API.

Tricky case: a client times out after 60 of 100 items commit. A single batch key with no durable per-item outcomes leaves it unable to recover safely. Store per-item results or expose the job ledger. A database transaction can give local all-or-nothing behavior, but holding it across a huge import can exhaust locks and connections.

23. File APIs and direct S3 uploads

Large file bodies should often travel directly between the client and object storage. Your API authorizes the intent and tracks the file lifecycle instead of holding an application worker for every byte.

  1. Create an upload intent after checking tenant, file purpose, quota and allowed size/type. Generate a random tenant-scoped storage key.
  2. Issue a short-lived presigned upload URL or POST policy with applicable restrictions. The URL is a bearer capability: keep it out of logs and analytics.
  3. Client uploads with the required signed headers/checksum. For large objects, use multipart upload and persist upload ID/parts as needed.
  4. Verify stored object metadata/checksum and expected ownership. Quarantine until malware/content inspection completes.
  5. Publish the file as READY only through a conditional lifecycle transition. Abort abandoned multipart uploads and expire orphaned intents.

AWS SDK for Java v2 · illustrative presigning fragment

PutObjectRequest put = PutObjectRequest.builder()
    .bucket(bucket).key(serverGeneratedKey)
    .contentType("application/pdf").build();
PresignedPutObjectRequest signed = presigner.presignPutObject(
    PutObjectPresignRequest.builder()
      .signatureDuration(Duration.ofMinutes(5))
      .putObjectRequest(put).build());
// Return signed.url() and signed.signedHeaders() to the authorized caller.

A presigned URL can generally be reused until expiry, and an upload to the same key can overwrite an object. Temporary credentials can expire before the chosen URL duration. Do not claim one-time or immutable upload semantics without extra controls. A checksum verifies integrity, not that the file is harmless; a MIME header is not proof of content type. Verify actual bytes and enforce size through an appropriate upload policy and finalization checks.

24. Webhooks: delivery is a protocol

A webhook is an outbound HTTP event notification. Network uncertainty means the sender may retry even after the receiver committed. Design event identity, authentication, retention and recovery on both sides.

POST /partner-events
Webhook-Id: evt_91
Webhook-Timestamp: 1793275200
Webhook-Signature: v1=...

{ "eventId": "evt_91", "type": "payment.captured",
  "resourceId": "pay_7", "resourceVersion": 18 }

These header names are an example application contract. Sign a documented canonical input such as timestamp plus the exact raw body bytes using HMAC-SHA256; compare signatures in constant time. Check an allowed clock window and deduplicate the stable event ID. Signature verification after JSON reserialization can fail because whitespace and property ordering changed.

  1. Authenticate and validate within strict size/time limits.
  2. Persist the event to a durable inbox before returning a successful acknowledgement.
  3. Process asynchronously with idempotent business transitions; acknowledge duplicates consistently.
  4. Retry transient failures with backoff/jitter and a bounded delivery horizon. Preserve the event ID across attempts; follow the documented retry rules for status codes.
  5. Expose delivery history, dead-letter handling and authorized replay. Rotate secrets with overlap and a key identifier if the protocol supports it.
Events can arrive out of order. A receiver can apply a version guard or fetch the authoritative current resource. A replay of an old signed event should not roll a payment from REFUNDED back to CAPTURED. Validate callback destinations as SSRF-sensitive input.

Contract-first means reviewing the intended interface before implementing it. Code-first can also work when generated contracts are reviewed and checked against behavior. Either approach needs an owner and a compatibility policy.

Migration trap: deploy a server that writes a new database representation, then roll back to code that cannot read it. Use expand/migrate/contract changes and verify both old and new binaries during the transition. API rollback and data rollback are different problems.

26. SLOs, capacity, load tests, and cost

An SLO is a measurable service target over a time window. Define eligible requests, successful outcomes and measurement boundaries. A health endpoint returning 200 while all checkout attempts fail is not business availability.

Illustrative targets (validate against product needs):
  99.9% eligible checkout requests receive a valid acceptance/outcome per month
  95% of status reads complete within 200 ms
  99% of accepted exports finish within 5 minutes
  duplicate business effects = 0 (invariant, not a latency percentile)

With average in-flight duration 0.2 s and 1,000 requests/s, Little's Law suggests roughly 200 concurrent requests in steady state. It is an average relationship, not a sufficient connection-pool setting; fan-out, variance, bursts and downstream limits matter. A 1 GB response costs bandwidth even when the compute endpoint is cheap.

  • Load-test realistic payloads, hot keys, tenants, cold starts and cache misses. Measure tail latency and rejection behavior, not only average throughput.
  • Exercise dependency slowdown, DB-pool exhaustion, queue backlog and retry storms. Verify bounded memory and graceful rejection.
  • Budget request charges, compute, database reads/writes, storage, egress, logs and traces. Sampling/retention must preserve required auditability.
  • Separate API acceptance SLO from asynchronous completion SLO; alert on queue age and oldest pending business operation.

27. Worked design: checkout and payment

Functional requirements

  • Create checkout and reserve several SKUs.
  • Authorize payment, expose status, cancel/refund when permitted.
  • Emit confirmation and fulfillment events.

Targets and invariants

  • Illustrative: p95 acceptance under 800 ms.
  • No negative stock; one committed capture per payment intent.
  • Recover after worker crashes and unknown provider outcomes.
POST /checkouts   Idempotency-Key: purchase-91
{ "items": [{ "sku": "p7", "quantity": 2 }], "currency": "INR" }
→ 201 { "id": "chk_7", "status": "AWAITING_PAYMENT" }

POST /checkouts/chk_7/payment-attempts   Idempotency-Key: attempt-1
{ "paymentMethodToken": "provider-token" }
→ 202 { "id": "pat_7", "status": "PROCESSING" }
GET /payment-attempts/pat_7 → current durable state

Implementation and rationale

  1. Derive tenant/customer from verified identity. Resolve current authoritative price; reject changed or unavailable items according to the contract.
  2. Within a Spring/RDS transaction, reserve stock conditionally, create checkout and idempotency outcome, and add an outbox record. Commit all or roll back all.
  3. Publish outbox events to SQS. A worker uses the durable payment-attempt ID as a provider retry identity when supported.
  4. Record success/failure through conditional transitions. Deduplicate provider webhooks and reconcile IN_DOUBT attempts through provider lookup.
  5. Confirm inventory and emit fulfillment intent only when business prerequisites hold. Compensation/refund is a new durable action with its own identity.
FailureRecovery
HTTP response lost after checkout commitReplay the stored outcome using the scoped key/fingerprint.
Outbox published, publisher crashes before marking sentRepublish safely; consumer inbox/conditional transition prevents duplicate effect.
Provider timeout after captureMark unknown, query with original identity, reconcile webhook; never create a new charge blindly.
Payment arrives after reservation expiresConditional transitions detect race; refund or re-reserve under explicit product policy.

Validation: concurrent last-item reservations, duplicate keys with mismatched payloads, crashes around every commit, provider timeout then delayed success, duplicate/out-of-order webhooks, and expiry races. Assert database invariants and provider-call identity, not just HTTP statuses.

IntermediateWhy not hold a transaction open during payment?
A local transaction cannot roll back a provider capture, and slow network calls hold database resources. Commit durable intent first and use an explicit state machine and reconciliation across the remote boundary.
ArchitectHow do you enforce “one capture” when the provider has no idempotency or lookup?
You cannot guarantee a single remote effect through arbitrary timeout/crash windows with local deduplication alone. Require a stronger provider protocol, reconcile through settlement/manual review, or restrict retry behavior and document the residual risk. A distributed lock does not solve the unknown-outcome boundary.

28. Worked design: large export and download

Functional requirements

  • Submit a filtered export; poll progress and download.
  • Cancel pending/running jobs; expire output.
  • Restrict access to the requesting tenant.

Targets and invariants

  • Illustrative: accept under 300 ms; 99% finish within 5 minutes.
  • Bound worker memory and tenant concurrency.
  • Export consistency is explicitly snapshot or best-effort live.
POST /exports
{ "format": "CSV", "filter": { "status": "PAID" } }
→ 202 + Location: /exports/exp_7
GET /exports/exp_7
→ { "status": "RUNNING", "rowsWritten": 50000 }
POST /exports/exp_7/download-links
→ 201 { "url": "short-lived-presigned-url", "expiresAt": "..." }
  1. Validate/allowlist filters, record tenant and query specification, reserve quota, and persist job plus outbox atomically.
  2. Choose consistency: a maximum-ID watermark bounds new inserts but does not freeze updates/deletes. For a true snapshot, use an appropriate DB snapshot/materialized dataset and budget its cost.
  3. Read bounded chunks, stream to multipart S3 upload, and checkpoint only according to a tested resume protocol. Restarting a whole file may be simpler and safer than appending after an uncertain chunk.
  4. Complete upload and verify output before conditionally marking SUCCEEDED. Keep partial/failed objects inaccessible and clean them up.
  5. Authorize each download-link request using current permissions. A previously issued presigned URL is still a bearer capability until its effective expiry or underlying access changes.

Spring/AWS: Spring Batch for chunked jobs/checkpointing where appropriate; ECS workers or a suitable batch runtime for long workloads; SQS for dispatch; private S3 for output. A Step Functions workflow can coordinate phases. Choose execution runtime from actual duration/memory limits rather than assuming every export fits a request handler.

Failure walkthrough: a cancellation and completion race uses conditional job transitions. Define whether cancellation is best-effort and whether completed output is deleted. Queue redelivery must not create two published results. CSV exports need spreadsheet-formula injection protection for untrusted cells, plus an explicit encoding/escaping policy.

Validation: mutate source data between pages, kill workers mid-upload, retry completion, revoke tenant access, expire links, cancel at each phase, and verify bounded memory and orphan cleanup.

EasyDoes 202 mean the export will succeed?
No. It means accepted for processing. The job resource reports eventual success or failure, and the contract states retention, polling and recovery behavior.
ArchitectIs a cursor enough for a consistent financial export?
No. Stable traversal does not freeze changing values. Agree on a consistency point and use a suitable snapshot, ledger cutoff semantics, or materialized export dataset. Explain the storage/DB retention cost and how retries reproduce the same dataset.

29. Worked design: partner integration

Functional requirements

  • Partner submits an order and reads status.
  • Receive signed lifecycle events and request replays.
  • Rotate credentials and migrate contract versions.

Targets and invariants

  • Per-partner quota and concurrency isolation.
  • No cross-partner access; durable delivery history.
  • Eventual recovery after partner outages without infinite retries.
POST /partner/v1/orders
Authorization: Bearer ...
Idempotency-Key: partner-order-781
{ "externalOrderId": "781", "items": [...] }
→ 201 { "id": "ord_7", "status": "ACCEPTED" }

Event evt_91: order.shipped, resourceVersion: 4
GET /partner/v1/orders/ord_7  // authoritative reconciliation path
  1. Issue machine credentials through the chosen OAuth flow. Map the verified principal to a partner; enforce scopes plus partner/resource ownership in Spring Security and repository access.
  2. Scope external IDs and idempotency keys by partner and operation. Rate-limit admission and bound per-partner concurrent work; return documented 429/Retry-After behavior.
  3. Persist business change plus outbox; maintain separate event and delivery-attempt IDs. Each retry retains the event ID while timestamps/signatures may be refreshed per the contract.
  4. Verify callback ownership, restrict egress, and deliver through bounded workers. Durable failed-delivery records allow operator review and authorized replay after the retry horizon.
  5. Publish versioned examples and migration dates; track partner version usage. Keep secrets out of audit records while recording actor, resource, action and outcome.

Tricky failures: an expired token causes bounded refresh rather than a retry loop; partner 200 before durable persistence can lose events; a slow partner must not exhaust every delivery thread; a valid old webhook cannot revert newer state. Rotate signing secrets with overlap and test both sides before retiring the old key.

Spring/AWS mapping: Spring Security resource server, RDS delivery ledger/outbox, SQS dispatch, API Gateway/WAF admission controls, Secrets Manager for signing material, and structured logs/traces for diagnosis. Evaluate EventBridge API Destinations when its auth, retry and delivery contract matches your integration; a managed delivery feature still needs business-level reconciliation.

Validation: cross-partner object access, secret rotation, duplicate external IDs, callback SSRF, out-of-order delivery, prolonged outage, quota fairness, version migration and replay auditability.

IntermediateWhy keep event ID and delivery-attempt ID separate?
The event ID deduplicates one business notification; attempt IDs explain retries and delivery diagnostics. Generating a fresh event ID for every retry defeats receiver deduplication.
ArchitectCan webhook delivery guarantee the partner processed an event exactly once?
An HTTP acknowledgement proves only the receiver's documented acceptance behavior. The receiver needs durable intake and idempotent effect processing. Provide replay/status reconciliation and state the guarantee at each boundary rather than claiming end-to-end exactly once.
