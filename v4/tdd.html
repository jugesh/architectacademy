TDD · fundamentals to production judgment

Let one failing example guide the next code change

Learn red–green–refactor through a Java order-cancellation policy. Then choose useful test boundaries for Spring, databases, time, retries and concurrent requests.

Technical definitionTest-driven development is a programming feedback loop: express a small expected behavior in an automated test, observe the intended failure, implement enough behavior to pass, then improve the design while the tests remain green.
Before you begin. Read basic Java methods, enums and assertions. No mocking framework is required. The BDD example map explains where the business rules in this lesson come from.

Learning outcome: Perform a small red–green–refactor cycle, explain what each test proves, and place extra checks at boundaries that a unit test cannot exercise.

1. Start with a rule, not a framework

A shop allows customers to cancel an order until the warehouse claims it. An unclaimed order may be cancelled; a claimed order is too late. A second cancellation should report that the order was already cancelled. Before writing a controller, start with the decision that all callers must share.

Imagine trying to assemble a shelf and checking each joint before adding the next piece. A failing test is a deliberately small check of the next joint. It is useful because it tells you which behavior is missing while the change is still easy to understand. It is not a prediction that the whole shelf will survive every load.

ApproachQuestion it helps answerTypical feedback
BDD — behavior-driven developmentHave we agreed on the behavior that matters?Collaborative examples and selected acceptance checks.
TDD — test-driven developmentWhat small behavior must the code support next?A failing test, a minimal implementation, then refactoring.
Testing after implementationDoes the existing implementation meet our expectations?Regression evidence; valuable, but does not show a test drove the design.

TDD is a way of developing code, not a test category. It can drive a pure function, a component or a boundary test. Unit tests written after implementation still have value. BDD can supply the examples used by TDD; you do not need to choose one practice for an entire project.

2. Read a test as a claim

A test needs a concrete starting state, an action and an observable outcome. Arrange–Act–Assert is a useful structure. Given–When–Then expresses a similar shape with a focus on behavior. Neither naming convention makes a weak assertion strong.

Given an order in CREATED state
When its cancellation policy is evaluated
Then the decision is CANCEL

Claim: one input maps to one expected decision.
Not yet proved: database commit, authorization or race handling.
TermPlain meaningCancellation example
AssertionThe comparison that can fail the test.Expected CANCEL, observed TOO_LATE.
FixtureThe data and collaborators prepared for a test.A newly created order; no unrelated customer biography.
Test oracleHow the expected outcome is determined.The agreed cancellation rule, not a second copy of the implementation.
RegressionA previously supported behavior stops working.A change permits cancellation after warehouse claim.

Choose expected results independently. If the test calculates its expected value with the same condition as the production method, both can share the same mistake. Name the business boundary explicitly, such as claimed orders are too late, rather than method_returns_correct_value.

3. Red, green, then refactor

StageWhat you doEvidence to inspect
RedWrite a test for CREATED → CANCEL, initially against a method that throws UnsupportedOperationException.The test runs and fails at the expected call. A broken import or missing test engine is an infrastructure failure, not useful behavioral feedback.
GreenReturn CANCEL for that first example.The selected test passes. A constant is acceptable as an intermediate step, not as the final policy.
Next redAdd CLAIMED → TOO_LATE.The constant now fails. Add only the distinction needed by the new example.
Next examplesAdd CANCELLED → ALREADY_CANCELLED and null rejection.Each example exposes a missing behavior before implementation.
RefactorReplace tangled conditions with a clear exhaustive switch.All earlier tests still pass; public outcomes are unchanged.

Do not force every edit into a theatrical one-line cycle. Keep the feedback small enough that the cause of a failure is clear. A short exploratory spike can help discover an unfamiliar API; discard or stabilize that exploration, then drive the agreed behavior with tests. Do not pretend that tests retrofitted afterward demonstrate the same process.

4. Work through the cancellation policy

Start with this single test in a class with the JUnit imports used in the final test below. Create the enums and method signature, but make the method throw UnsupportedOperationException. The test should fail at that call; then return CANCEL to make this first example pass.

@Test
void anUnclaimedOrderCanBeCancelled() {
    var policy = new CancellationPolicy();
    assertEquals(Decision.CANCEL, policy.decide(State.CREATED));
}

// First red implementation:
public Decision decide(State state) {
    throw new UnsupportedOperationException("not implemented");
}
// First green implementation: return Decision.CANCEL;

Next add an assertion that CLAIMED produces TOO_LATE. Run it while the method still returns the constant: the failure demonstrates why the next implementation needs to distinguish states. Add the remaining state and null examples, then refactor into the final switch below. The fragments above are successive edits, not additional methods to paste alongside the final implementation.

These are the final artifacts after those cycles. The policy makes a decision only; it does not mutate an order or contact the warehouse. Keeping that boundary small makes the examples fast and clear. The enum values are illustrative business states, not a universal order model.

package academy.testing;

import java.util.Objects;

public final class CancellationPolicy {
    public enum State { CREATED, CLAIMED, CANCELLED }
    public enum Decision { CANCEL, TOO_LATE, ALREADY_CANCELLED }

    public Decision decide(State state) {
        Objects.requireNonNull(state, "state");
        return switch (state) {
            case CREATED -> Decision.CANCEL;
            case CLAIMED -> Decision.TOO_LATE;
            case CANCELLED -> Decision.ALREADY_CANCELLED;
        };
    }
}

package academy.testing;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import static org.junit.jupiter.api.Assertions.*;
import academy.testing.CancellationPolicy.State;
import academy.testing.CancellationPolicy.Decision;

class CancellationPolicyTest {
    private final CancellationPolicy policy = new CancellationPolicy();

    @ParameterizedTest(name = "{0} produces {1}")
    @CsvSource({"CREATED,CANCEL", "CLAIMED,TOO_LATE",
                "CANCELLED,ALREADY_CANCELLED"})
    void decidesFromTheCurrentState(State state, Decision expected) {
        assertEquals(expected, policy.decide(state));
    }

    @Test
    void rejectsMissingState() {
        var error = assertThrows(NullPointerException.class,
                () -> policy.decide(null));
        assertEquals("state", error.getMessage());
    }
}

The parameterized rows document all three supported states. The null test makes an invalid input explicit instead of relying on a later accidental null dereference. If a new enum state is introduced, the exhaustive switch requires a design decision before compilation succeeds. That is a useful extra signal, not a replacement for examples.

Notice what is absent: a Spring application context, a repository mock and a controller. None is needed to prove this mapping. Keeping business decisions independent of delivery mechanisms makes tests faster and reveals a reusable boundary. It does not imply that the rest of the application is already tested.

5. Use doubles where they add evidence

A test double lets a test control a dependency. A stub returns configured results. A fake has a small working implementation, such as an in-memory repository. A mock can verify expected interactions. Different tools use these names differently, so explain the role rather than relying on the label.

DependencyUseful techniqueBlind spot
ClockInject java.time.Clock and use Clock.fixed in examples.A fixed clock does not exercise clock skew across services.
Warehouse clientStub accepted, rejected and unknown outcomes.A stub can drift from the real provider contract.
RepositoryUse a small fake for application-flow feedback.A HashMap does not reproduce SQL isolation, unique constraints or query behavior.
Audit/output portVerify an externally important call or persisted result.Verifying every internal call makes refactoring break tests unnecessarily.

Prefer observable business results over exact private call sequences. A test that verifies repository.find was called once may pass while the wrong customer receives the result. Conversely, verifying that a rejected command never calls a charge port can be a meaningful safety claim. Choose the interaction because it matters at the boundary.

A mock that always reports a successful commit cannot prove a transaction commits. Give fakes and real adapters shared contract examples where practical, then exercise database-specific behavior against the intended database engine.

6. Put Spring checks at the right boundary

A fast policy test and a full application test answer different questions. Keep both when both risks exist; do not require every arithmetic rule to boot the application. For a REST cancellation endpoint, trace the request through authentication, binding, application behavior, persistence and response mapping.

BoundaryCheckWhat remains outside it
Plain Java/JUnitCancellationPolicy maps states correctly.Serialization, wiring, transactions and concurrent writes.
Spring MVC test sliceRoute, JSON fields, validation, HTTP status and applicable security configuration.Real service/database behavior when collaborators are replaced.
Repository integrationA conditional state change and unique keys work against the target engine.End-to-end authorization and remote-service outcomes.
Application integrationA real request uses configured beans and commits durable state.Deployment routing and production capacity.
Small deployed smoke suiteThe built artifact starts and a critical path works through real routing.Every business combination or failure schedule.

Choose Spring test annotations and imports for the application’s actual Boot version; do not mix a current reference example into an older project blindly. A slice with security filters bypassed supplies no evidence of authorization. Check both an authorized owner and another customer, and distinguish 401/403 behavior according to the API contract.

For a commit claim, read through a separate transaction after the application operation commits. A test-managed transaction that rolls back afterward can mask commit-time constraints and after-commit behavior. HTTP handlers may also run on different threads and transactions from the test. Cleanup must cover committed test data; rollback on the test method is not a universal cleanup strategy.

7. Make races and time controllable

Suppose cancellation and warehouse claim both read CREATED. Both then write a new state. The policy test remains green while the system loses an update. Correctness must be protected at the write boundary, for example with a conditional update or version check in the same authoritative transaction.

-- Illustrative SQL; adapt to the schema and database.
UPDATE orders SET state = 'CANCELLED', version = version + 1
WHERE tenant_id = :tenant AND id = :id
  AND state = 'CREATED' AND version = :observedVersion;
-- One changed row: this transition won.
-- Zero: re-read and map the current state under the contract.

Test two independent transactions or connections against the real engine. Use a barrier or latch to coordinate competing attempts at a known point; do not rely on Thread.sleep to create a race. Assert the final business state and allowed outcomes, not that a particular thread always wins. Capture the losing result too: a timeout with an unknown commit is different from a clean conflict.

CaseControlAssertion
Expiry exactly at a deadlineInjected fixed Clock plus just-before/equal/just-after inputs.The agreed inclusive or exclusive boundary is honored.
Concurrent cancel/claimIndependent transactions and coordinated start.Exactly one allowed transition wins; no impossible combined state.
Same cancellation retriedStable command identity and repeat requests.No second business effect; documented repeated response.
Remote response lost after successProvider stub records the effect, then times out.Recovery preserves identity and reconciles rather than blindly creating another effect.

A finite race test samples schedules. It can expose defects and validate a proposed boundary; it is not a mathematical proof for every interleaving. Combine it with constraints, transaction reasoning and production evidence.

8. Choose examples that can expose a mistake

Start with equivalence classes: groups of inputs expected to behave alike. Add boundaries where the rule changes, invalid inputs and one contrasting example. For a cancellation deadline, far-before and just-before are less informative together than just-before and exactly-at.

TechniqueUseful questionLimit
Example testsDoes this concrete state produce the agreed result?Only selected inputs and schedules are exercised.
Property-based testsAcross generated cases, does a general invariant hold?Generators and properties can both omit important behavior.
Mutation testingDo tests notice a deliberately changed condition?A surviving mutant needs analysis; equivalent changes may not matter.
CoverageWhich lines or branches ran?Executed code can still be asserted incorrectly or not asserted at all.

A useful mutation exercise here is changing CLAIMED to return CANCEL. The claimed-order example must fail. If it stays green, check whether the test was discovered and whether it asserts the actual result. Do not optimize for a coverage percentage by writing assertions that merely repeat whatever the code returned.

Refactor test fixtures as well as production code, but keep the important inputs visible in each test. A giant factory with dozens of hidden defaults can make one failing example incomprehensible. A few explicit repeated fields may communicate better than a clever test DSL.

9. Adopt TDD in a working service

For legacy code, first preserve important observed behavior with characterization tests. Mark a known defect as a defect instead of silently blessing it. Add a seam around the dependency you need to control, make one small change, and keep unrelated cleanup separate.

For the cancellation change, first capture current HTTP behavior. Then extract the policy and drive the new claimed-order rule in a fast test. Retain an adapter test that proves the controller uses it, and add a database race check before claiming the invariant survives concurrency. This makes adoption incremental instead of demanding that a large service be rewritten.

CI laneTypical scopeFailure policy
Fast feedbackPure rules and focused application checks.Block changes that violate agreed behavior.
Boundary integrationReal database constraints, serialization and provider contracts.Run on relevant changes and before release.
Broader assuranceCritical deployed paths, failure exercises and performance.Report the environment and reproducible evidence.

Keep fixtures isolated so tests can run independently and in parallel. A flaky test is one whose result varies without a relevant change; investigate shared state, uncontrolled clocks, eventual consistency and environment limits. A retry can help diagnose a transient condition, but a passed retry must not erase the initial failure. Any quarantine needs an owner, reason and removal deadline.

10. Avoid test-shaped false confidence

TemptationWhy it misleadsBetter evidence
Write the implementation, then call it TDDThe test did not guide that design change.Describe it honestly as regression testing; use a real next-behavior cycle for the next change.
Mock every layerAssertions prove your configured story.Keep pure-rule tests, then exercise real high-risk boundaries.
Assert only no exceptionThe operation can do the wrong thing successfully.Assert state, returned decision and forbidden side effects.
Refactor and change a rule togetherA failure has multiple plausible causes.Separate behavior changes from structural cleanup.
Always add tests before learning the requirementAn automated guess can harden the wrong rule.Resolve examples with product/domain input first.

TDD is especially useful for rules with clear examples and code that benefits from small design feedback. Exploratory UI work, unfamiliar integrations and performance investigations can need spikes or measurements first. Choose the practice for the risk; do not claim TDD replaces security reviews, load tests, exploratory testing or architectural judgment.

11. Explain and defend the approach

FoundationalIs TDD just writing unit tests first?

The order alone is incomplete. Observe a useful failure, implement enough to satisfy the behavior, and refactor while preserving earlier behavior. Unit tests are common, but the practice is a feedback loop rather than a file type.

FoundationalWhy run the test before implementing?

To check that it is discovered and can fail for the intended missing behavior. A test that already passes may describe existing behavior, assert too little, or never execute the relevant path.

IntermediateWhen is verifying a mock call useful?

When the interaction is part of an important boundary claim, such as no charge request after rejection. Verifying private sequencing everywhere makes harmless refactoring expensive and can miss incorrect outcomes.

IntermediateCan 100% line coverage prove cancellation is safe?

No. It shows execution, not complete assertions, business agreement or concurrent correctness. Add contrasting examples and check the authoritative write boundary.

AdvancedAll unit tests pass, but cancel and claim both succeed. What next?

Trace the read/write transactions. Reproduce competing operations with independent connections, verify the invariant with a conditional write or equivalent concurrency mechanism, and assert final state plus both caller outcomes.

AdvancedHow would you introduce this into a fragile legacy service?

Capture critical current behavior, isolate one change behind a controllable boundary, drive the next rule with small tests, and retain adapter/integration evidence. Avoid combining a broad rewrite with the first rule change.

12. Run, practice and read further

The complete examples use Java 17+ and JUnit Jupiter 5.13.1, with pinned Maven compiler and test plugins. From the repository root run:

mvn -B -f v4/examples/testing/pom.xml test

The command executes the final TDD policy tests and BDD-style acceptance examples. There is no Spring server, database, broker or Cucumber runner in this small example. HTTP, persistence and concurrency require the additional checks described below. A green final suite cannot prove the historical order in which tests and implementation were written.
