Consumer-Driven Contract Testing · fundamentals to production judgment

Prove that a provider still speaks its consumers’ language

Follow an Order client and Billing provider through consumer tests, published interactions, provider verification and release decisions. Learn what Pact-style contracts cover and where business integration tests remain necessary.

Technical definitionConsumer-driven contract testing captures the interactions a consumer depends on and verifies that a provider can satisfy them. Consumer-side execution and provider-side verification form complementary evidence for specific participant versions.
Before you begin. Read contract-first development and understand the difference between a real API client and a hand-written mock response.

Learning outcome: Design a useful consumer interaction, explain provider states and matching, and make a version-aware deployment argument without claiming full end-to-end correctness.

1. A green mock can tell the wrong story

Order needs Billing to return payment P7 with status CAPTURED. Its local mock returns that string, so the client tests pass. Billing renames the field from status to state, but its own endpoint tests also pass. Production fails when the real client reads a missing field.

The problem is not that either team lacks tests. Their tests assert independent assumptions. A consumer contract connects the expectations exercised by the actual client to a check of the provider. Think of checking that a supplier still delivers the part dimensions your assembly uses, rather than assuming its internal quality checks cover your dependency.

This is particularly useful for independently released services. It does not mean every internal method needs a published contract, or that provider business rules can be delegated to its consumers.

2. Follow the two-sided evidence

StepImportant detailFailure detected
Consumer testInvoke the production HTTP client against a controlled contract mock.Wrong request construction or response parsing.
Contract publicationAttach immutable consumer version and branch/release metadata.Missing/stale expectations can be identified.
Provider verificationPrepare the named state, call the provider and match the response.Provider no longer satisfies the interaction.
Deployment checkUse verification evidence for the versions in the target environment.A new-new pass hides an old consumer still deployed.

Do not manually construct the same request in a test while leaving the real client unused. That can generate a plausible contract without testing the code that production executes. Keep business orchestration outside a focused client contract test so failures remain attributable.

3. Specify one real dependency

Illustrative interaction, not a runnable Pact file:
Consumer: Order service
Provider: Billing service
Provider state: payment P7 belongs to tenant T7 and is captured

Request:
  GET /payments/P7
  Authorization: a valid test credential for T7

Expected response:
  200 application/json
  id: exact value P7
  status: exact value CAPTURED (the branch Order needs)
  amountMinor: an integer matching the agreed money representation

Consumer assertion:
  invoke the real BillingClient against the contract mock
  assert the parsed result drives the captured-payment branch

The exact captured status matters because Order branches on it. For unrelated generated identifiers or timestamps, suitable type/format matchers reduce brittleness. Matchers are not a license to accept any value for a field whose meaning determines the consumer’s action.

This lesson shows the protocol rather than a copy-paste Pact-JVM runner. Framework APIs and setup depend on the pinned Pact/JUnit versions, HTTP client, authentication adapter and provider lifecycle. No Pact Broker or live Billing provider is included in the Java example project.

4. Be strict about needs, loose about accidents

Field/detailUseful expectationOverconstraint or blind spot
Payment identifierMatch P7 when the client requests P7.Accepting any identifier can hide a wrong-resource response.
Status used for branchingExplicit captured/failed cases the client supports.A string matcher alone misses an unsupported status.
Extra response fieldsTolerate additions when the real parser tolerates them.Exact whole-body matching can reject safe additions.
TimestampFormat and relevant semantics where supported.An arbitrary fixed time makes unrelated changes break verification.
MoneyInteger/decimal representation, units and required fields.A numeric type alone does not establish currency or accounting correctness.

Include relevant negative interactions such as not found or a documented conflict if the consumer handles them. Do not reproduce the provider’s entire functional suite through the contract. The contract should expose what this consumer needs, while provider tests remain responsible for the rules producing those outcomes.

Request matching and response matching can have different tolerance rules. Read the selected Pact specification/tool’s matching behavior rather than assuming an extra request field and an extra response field are equivalent changes.

5. Prepare state without scripting a journey

A provider state names the starting facts required by an interaction, such as payment P7 is captured. Provider verification arranges those facts deterministically. It should not require a previous contract test to have created P7 or rely on uncontrolled production data.

Use isolated test storage or appropriately controlled fixtures, and run the configured provider boundary that serves the interaction. Replacing the whole application with another hand-written response merely compares two mocks. Replacing an external payment processor can be reasonable when the intended verification scope is the Billing API, but label that scope.

ProblemConsequenceCorrection
State setup depends on scenario orderParallel or selected verification fails.Make every state self-contained.
Credentials expire during verificationCompatibility failures become environment noise.Use a controlled test-auth configuration with explicit limits.
A test-state endpoint is deployed openlyTest setup becomes a security capability.Keep setup isolated from production exposure.
Provider state over-specifies internal tablesRefactoring breaks contracts without changing behavior.Name domain facts; hide fixture mechanics behind the state handler.

6. Verify the versions that actually meet

Suppose Order v12 and Billing v8 are deployed. Billing v9 passes a contract published by Order v13, but v12 still needs a removed field. The v13-v9 result does not justify deploying v9 while v12 remains live.

ConsumerProviderResultDeployment implication
Order v12Billing v8PassExisting supported pair.
Order v12Billing v9FailDo not infer safety from the newer consumer’s success.
Order v13Billing v9PassOnly this pair’s interaction evidence is established.
Order v12Billing v10UnknownNeeds verification or an explicit policy for missing evidence.

A Pact Broker can record contract versions, verification results and deployments; can-i-deploy evaluates the relevant matrix. Publish meaningful immutable application versions and record what reaches each environment. Incorrect metadata makes a sophisticated gate answer the wrong question.

Treat unknown verification as unknown. A team can have an explicit workflow for pending contracts or early development, but that policy must not silently promote unverified production compatibility. Retire old consumer versions using actual support/deployment evidence.

7. Separate compatibility from delivery

For asynchronous integration, a consumer can exercise its message handler with the agreed message while the producer verifies the event it generates. This checks payload compatibility at selected boundaries. It does not send the message through the real broker, validate retention or prove acknowledgement safety.

ClaimSuitable evidenceContract check alone?
Consumer parses ReservationAcceptedReal handler/client plus representative message.Useful for that interface dependency.
Producer creates the expected messageProducer verification at its output boundary.Useful for the selected representation.
Duplicate delivery has one effectDurable receipt/effect transaction and repeated delivery.No.
Old events replay safelyHistory/version policy and replay tests.No.
Checkout completes through all servicesSelected real integration/deployed flow.No.

A syntactically compatible CAPTURED response can still report the wrong tenant’s payment. Keep authorization and provider business correctness tests. Contract testing reduces a class of integration failures; it does not remove the need to reason about authority, identity or failure recovery.

8. Use contracts for real boundaries

Avoid publishing contracts from tests that never call the production client, matching every incidental field or copying the provider’s entire functional suite. Those patterns increase maintenance without protecting the dependency that matters.

A successful contract verification is evidence for selected interactions and versions under the verification setup. It is not proof of production networking, security, throughput or complete business correctness.

Practice: design a contract for Subscription consuming Billing’s invoice response. Name two fields that need exact semantic values, two that can use tolerant matchers, and a provider business rule that belongs outside this contract suite.

9. Explain the evidence chain

FoundationalWho writes the consumer contract?

The consumer team captures its actual client/handler needs. The provider verifies it; cooperation is still needed to agree on supported behavior.

FoundationalIs a hand-written mock enough?

No. A mock can drift from the provider. Provider verification supplies the complementary evidence, and the consumer test must exercise the real consuming code.

IntermediateWhat is a provider state?

A named prerequisite fact for an interaction, arranged independently by the verifier. It is not a required sequence of earlier user actions.

IntermediateWhy avoid exact matching every field?

Incidental fields can turn safe provider changes into failures. Be precise about what the consumer depends on and tolerant where its real behavior is tolerant.

AdvancedBoth newest versions pass. Is deployment safe?

Not necessarily. Check the consumer/provider versions still deployed or supported in the destination environment, including mixed-version rollout.

AdvancedCan message contracts prove exactly-once effects?

No. Payload compatibility is separate from broker delivery and the consumer’s durable effect boundary. Test duplicates, crashes and replay using those mechanisms.
