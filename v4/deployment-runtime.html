Deployment & Runtime · fundamentals to production judgment

Release new code without losing accepted work

Connect Java process behavior to container lifecycle, Kubernetes routing, rolling delivery and data-compatible rollback.

Technical definitionDeployment changes the running version/configuration of a service. The runtime lifecycle governs startup, readiness, serving, draining and termination; safe delivery preserves the API and data contract across versions and failures.
Before you begin. Read Networking and message acknowledgement. A container packages a process; orchestration schedules and manages it.

Learning outcome: Design probes, shutdown and rollout limits from actual workload behavior, and explain what rollback can and cannot undo.

1. A healthy rollout loses a background task

A deployment is a transition through overlapping execution and data versions. For a period, old and new instances may both serve requests, consume events and write state. A green health endpoint proves little about whether an old reader can interpret a new status value.

Follow one order through a rollout and termination. The application must stop admitting work, finish or durably hand it off, and recover if termination becomes abrupt. Container packaging and orchestration make lifecycle controllable; they do not replace compatible contracts or crash-safe business protocols.

2. Treat a rollout as overlapping versions

Read this slowly: it establishes the distinction used in the implementation sections.

A container packages a process; a deployment controller manages its lifecycle. During a rolling update, old and new versions often coexist. Readiness determines eligibility for traffic. Liveness decides when restarting may help. Graceful shutdown coordinates stopping new work and finishing or handing off existing work. None replaces application compatibility.

Version B writes a new order status while A is still serving reads. If A rejects that status, the rollout fails even when every health probe is green. First deploy readers that tolerate the future state, then enable writers, and only later remove old behavior. For shutdown, remove readiness, account for routing propagation and drain active work within the platform grace period.

Check your understanding
FoundationalRolling back an image rolls back the data.
Committed schema and business-state changes survive an image change. Define rollback compatibility and a forward-repair route for writes old code cannot understand.
IntermediateShould liveness fail whenever a dependency is down?
Usually that creates restart storms without repairing the dependency. Distinguish a stuck process from temporary downstream unavailability; readiness and admission policies require their own capacity analysis.

3. Define release safety

State what a successful release preserves: supported clients keep working, committed facts remain readable, accepted work survives interruption, and failure capacity stays within target. Define canary signals and rollback/forward-repair boundaries before enabling new writers.

Budget resources during overlap. Deployment surge can create more database connections and cold-cache fills than the ordinary replica count. A rollout losing one availability-zone share also differs from a healthy steady state. Capacity and compatibility are both release requirements.

Functional requirements

  • Roll out a Spring service and route to ready instances.
  • Drain in-flight HTTP and reclaim interrupted jobs.
  • Roll back code when necessary.

Targets and invariants

  • No lost accepted intent or duplicate protected effect.
  • Keep enough capacity during rollout/failure.
  • Use least-privilege runtime identity and bounded resources.
  • Old/new code must coexist with schema changes.

A release may change code, database schema, configuration and message contracts. These components do not automatically roll back together. Plan the compatibility interval explicitly.

4. Startup, readiness and liveness

Readiness controls eligibility for traffic; liveness asks whether restart is appropriate; startup handling gives initialization its intended conditions. A shared dependency outage does not automatically mean every process should be restarted. Choose probes that distinguish a stuck process from unavailable external capacity.

For shutdown, stop advertising readiness, allow routing state to propagate and drain bounded active work. New requests can arrive briefly while intermediaries update. A worker must finish a durable unit or let repeat-safe redelivery recover it, not acknowledge unfinished work. Graceful termination is an optimization over a crash-safe design, not permission to ignore crash windows.

Probe/stateQuestionPitfall
StartupHas initial startup completed?Aggressive liveness restarts a legitimately slow startup.
ReadinessShould this instance receive intended traffic now?Marking all pods unready for a shared temporary outage can worsen recovery.
LivenessIs restart likely to repair this process?Restarting healthy processes because a database is down creates churn.

A pod can be alive but not ready. A process can also be ready for status reads but unable to accept a costly operation; coarse readiness cannot express every route’s admission policy. Use application-level rejection where needed.

5. Requests, limits and graceful shutdown

CPU and memory requests/limits influence scheduling and runtime behavior under the chosen platform. A Java heap is only part of process memory: native buffers, thread stacks and runtime metadata also consume resources. Choose headroom from representative measurements rather than setting heap equal to the container limit.

Capacity policies must consider startup, garbage collection, connection acquisition and dependency waits. More pods can remain pending without node capacity; more runnable pods can overload a shared database. Inspect useful completions and saturation rather than assuming a desired replica count has already become usable capacity.

Illustrative shutdown protocol:
  stop admitting new application work
  allow endpoint/routing changes to propagate
  drain in-flight requests within a bounded grace period
  commit/abandon work with a durable reclaim protocol
  close clients and exit before forced termination

Termination hooks, endpoint updates, load-balancer deregistration and application shutdown can overlap. Test their ordering in the actual platform; a fixed sleep alone is not proof of graceful draining. Worker acknowledgement/leases must tolerate hard termination as well as polite shutdown.

6. Spring and deployment strategies

Use explicit deployment configuration for readiness, shutdown grace, resource budgets and rollout strategy. In Spring, verify server and worker shutdown behavior for the actual runtime. HTTP draining does not automatically stop every scheduled task or safely transfer every consumer lease.

Apply expand/migrate/contract sequencing to schema and state changes: make readers compatible, migrate under a restartable protocol, enable new writes, and remove old behavior after the support/rollback window. Feature flags can control exposure, but disabling a flag does not erase new data already committed.

StrategyBenefitRisk
RollingIncrementally replaces replicasOld/new versions coexist; surge consumes shared DB/provider budget.
Blue/greenSwitch between complete environmentsExtra capacity; routing rollback does not undo new data writes.
CanaryExpose a subset and compare outcomesSmall samples can miss rare failures or tenant-specific paths.

On EKS/ECS, account for node/task startup, AZ placement, connection pools and dependency quotas. A PodDisruptionBudget constrains certain voluntary disruptions; it is not a universal guarantee against node failure, overload or every rollout behavior.

7. Worked design: add an order state safely

Version B adds a payment state while A still serves reads. First deploy readers that understand or deliberately tolerate the future value. Then enable B’s writers for a controlled population and compare customer outcomes, errors and completion age. A probe that never reads the new state cannot validate this compatibility.

Interrupt the rollout and exercise rollback against data already written by B. If A cannot handle it, image rollback is not a safe recovery. Disable unsafe new writes if supported and use a compatible reader or forward repair. Also kill a worker after a local commit but before acknowledgement to prove interruption recovery remains correct.

8. Operational pitfalls

A rollout can fail without a process crash: enum interpretation, default changes, incompatible serializers or a new scheduled job can break older instances. Test mixed versions and delayed messages, and identify every writer rather than only the web deployment.

A restart storm, synchronized cold fills or an oversized surge can turn a small problem into fleet-wide saturation. Keep a safe mitigation path, operational capacity and observable release identity. Declare success from the intended business journeys over an appropriate interval, not solely from all pods being Ready.

FailureMitigation
OOM during warmupBudget heap plus native memory; observe real startup/steady-state.
All pods restart togetherSeparate dependency health from process liveness.
Surge exhausts DB connectionsInclude deployment replicas in shared-resource budgets.
Rollback breaks data readersExpand/migrate/contract with tested compatibility windows.

Deploy immutable versioned artifacts and track image digest, config version and schema/event compatibility. Store secrets outside image layers and source. Know the difference between restarting, replacing an instance, rolling back code and restoring data.

9. Interview ladder

FoundationalReadiness versus liveness?
Readiness controls traffic eligibility; liveness indicates whether restarting may recover a process. They should not be identical dependency checks by default.
FoundationalDoes a container limit equal JVM heap size?
No. Native allocations, stacks, metaspace, buffers and instrumentation also consume memory.
IntermediateWhy can a rolling deployment overload a database?
Surge replicas open extra pools and startup/cache-fill work. Count peak rollout resources, not only steady-state replicas.
IntermediateDoes a PDB prevent outages?
It governs specified voluntary disruptions under its semantics; it does not prevent all failures or ensure application correctness.
AdvancedWhy is code rollback not data rollback?
New versions may have committed states/schema/events older code cannot interpret. Plan compatibility before enabling writers.
AdvancedHow do you verify graceful shutdown?
Exercise real routing/endpoint propagation and hard/soft termination under load, assert bounded draining and durable job recovery, and inspect client-visible outcomes.
IntermediateWhy is image rollback not necessarily safe?
The newer version may have committed states or representations that old readers cannot interpret. Verify mixed-version/data compatibility and retain a forward-repair route; changing the binary does not reverse those facts.
AdvancedWhat must a shutdown test include?
Late routed requests, bounded drain, forced termination after grace, worker commit/ack gaps and repeat-safe reclamation. Graceful shutdown should improve behavior while abrupt interruption remains recoverable.
