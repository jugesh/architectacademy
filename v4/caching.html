Library/Data & Consistency/Caching

Caching · fundamentals to production judgment

Make repeated reads cheaper without hiding the truth

Start with one repeated product lookup. Build a cache, then follow what happens when data changes, entries expire together, or the cache disappears.

Technical definitionA cache stores a reusable copy of data or computation to reduce the cost of retrieving it again. The source of truth remains authoritative; cache design defines identity, freshness, eviction and failure behavior for the copies.
Before you begin. Know a database lookup and an HTTP response. Indexes reduce lookup cost without creating an application cache; understand that distinction first.

Learning outcome: Choose a read/write pattern, define freshness and isolation, and protect the source during a cache incident.

1. Why repeat the same read?

The database lesson improved the cost of a query with an index. The same popular product can still cause that query to run thousands of times. A cache keeps an answer for reuse, often nearer the caller. We first save repeated work, then ask what happens when the authoritative product changes while an older answer remains available.

Keep browsing and purchasing separate. A customer may tolerate a slightly old description while scrolling, but accepting a purchase at an invalid price or against unavailable stock is a different decision. The right cache policy follows the operation’s correctness and freshness requirements. It does not follow simply from having Redis available.

2. Derive freshness from the operation

Read this slowly: it establishes the distinction used in the implementation sections.

An index finds the authoritative row faster; a cache answers from a separate copy. That distinction introduces time into correctness. A TTL limits how long an entry is reusable under a policy. Eviction removes an entry for capacity or policy reasons. Invalidation reacts to a change. None of those words alone specifies how stale the answer can become during concurrent fills or failed updates.

Follow a race. A reader loads product version 7. A writer commits version 8 and deletes the cached entry. The earlier reader then stores version 7 after that deletion. The cache is stale despite invalidation. Depending on the freshness contract, use a bounded expiry, version-aware updates or a coordinated strategy. For checkout, revalidate the price against an authoritative rule instead of assuming a cached browse price is a purchase guarantee.

Check your understanding
FoundationalA high hit ratio means the cache is working correctly.
It measures reuse, not freshness, tenant isolation or total cost. Observe stale-answer incidents, source load during misses, refill concurrency, eviction and key distribution alongside hit ratio.
IntermediateWhat must happen when Redis becomes unavailable?
The policy depends on the operation. Browsing may use bounded stale data or constrained database fallback. An authoritative safety rule must not silently disappear. Limit fallback concurrency so a cache outage does not become a database outage.

3. Follow one operation before adding patterns

Carry this concrete operation through the later mechanisms.

Request A reads product version 7 and stores a copy. Request B arrives one second later and can use it without SQL. A merchant then publishes version 8. If B continues reading the copy, the shop has two representations of the product. Decide which operations may see version 7. Browsing can often tolerate delay; charging a price or checking permission may require another policy. This is why freshness belongs in the requirement, before a TTL or Redis command is selected.

4. Define the freshness contract

A freshness contract states what observations are permitted, under which conditions and failure modes. “Cache for sixty seconds” describes an entry policy; “no answer more than sixty seconds behind a committed update” is a stronger end-to-end claim. A reader can fetch an old source version and publish it late, or another cache layer can reuse it longer. Explain those intervals before claiming a staleness bound.

Define identity before expiry. The same product ID can produce different views for tenants, languages, currencies or permission contexts. Reuse is safe only across callers entitled to the same representation. A fast wrong-tenant hit is a security failure, not a cache-performance improvement. State whether the cache is disposable and what the service will do when it cannot reach it.

Functional requirements

  • Read product details and update them as a merchant.
  • Share popular data across application instances.
  • Return a controlled response when a cache read fails.

Targets and invariants

  • Illustrative display staleness: at most 60 seconds under the stated policy.
  • Never reuse one tenant’s private representation for another.
  • Checkout revalidates authoritative price/stock.
  • Cache loss must not overload the database.

A TTL by itself is not necessarily a bound on staleness relative to the latest write: a slow reader can refill an old value after invalidation. State which races and refresh failures your guarantee covers. If an invariant requires current data, enforce it at the authoritative mutation path.

5. Walk through cache-aside

The freshness requirement defines which answers are reusable; follow the simplest miss path next.

Follow a cold lookup: build the complete representation key, ask the cache, and on a miss load the authoritative data and publish a reusable value with its policy. A miss is expected. The source path must therefore be bounded and observable in normal operation, not only during an outage. Distinguish a missing product, an unavailable source and an undecodable cached value.

Now let a hundred callers miss the same popular key. The basic pseudocode can send a hundred identical database reads before any fill becomes visible. A local single-flight mechanism lets equivalent callers share one in-progress fill inside that process; other processes may still refill independently. Bound waiting and fill concurrency, and define what happens if the fill fails. Do not let a slow fill hold every caller indefinitely.

Fill publication is a separate event from the source read. Carry source/version information when the freshness protocol needs it. A method returning a value does not establish that it is still the latest value when the cache write completes. That is the race explored next.

Product getProduct(TenantId tenant, ProductId id) {
  String key = "product:v2:" + tenant + ":" + id;
  Product cached = cache.get(key);
  if (cached != null) return cached;
  Product value = repository.find(tenant, id);
  cache.put(key, value, Duration.ofSeconds(60));
  return value;
}
// Teaching pseudocode: add timeouts, missing values, failure policy and metrics.

Include every dimension that changes the reusable value: tenant, locale, currency, schema version or permission scope where relevant. Avoid using raw credentials as keys. A user-specific representation often belongs in a private or per-user cache rather than one shared product key.

6. What happens after a write?

The read path works until the source changes. Now trace a reader and writer together.

Place a reader and writer on the same timeline. The reader loads version 7; the writer commits version 8 and invalidates the key; the reader then publishes version 7. The delete was successful, yet an older value reappeared. This is why write-then-invalidate needs an explicit concurrent-fill policy rather than a slogan.

A versioned immutable key prevents one version from overwriting another, but the caller still needs a trustworthy way to find the current version. A version-aware publication rule needs durable knowledge or a marker that survives an absent key; comparing only against a cache value that has already been deleted does not preserve that knowledge. A delayed second delete can reduce particular races without proving a general bound.

Choose the least coordination that meets the contract. A browse view may tolerate bounded stale answers under documented assumptions. An inventory or permission decision can use the authoritative mutation path. Durable invalidation intent, such as an outbox row committed with the update, helps recover lost invalidations but still does not make a source transaction atomic with all cache readers.

Race to reason about:
1. Reader misses and reads DB version 7.
2. Writer commits version 8, then deletes cache key.
3. Reader finishes late and caches version 7.
4. New readers temporarily see version 7 again.

Options include tolerating bounded staleness, caching under immutable/versioned keys, and using version-aware conditional publication tied to durable version knowledge. A compare-and-set only against an existing cache value does not solve the absent-key race unless the protocol preserves a newer version marker. “Delete twice after a delay” reduces some races but is not a general proof of consistency.

7. A stale fill after deletion

Cache-aside has a race that “delete after write” does not close. Reader A misses, reads product version 7 from the database and pauses. Writer B commits version 8 and deletes the cache entry. A resumes and puts version 7 into the now-empty cache. Every step succeeded, yet the cache is old immediately after invalidation. The problem is the order of observations and publication, not a failed Redis command.

TimeReader AWriter BCache
1Miss; read source version 7Empty
2PauseCommit version 8Empty
3Delete cached productEmpty
4Publish delayed version 7Version 7

Choose a freshness contract before choosing a repair. If a catalog description may be stale briefly, bounded fill duration plus a hard entry lifetime may be sufficient. If a price or authorization decision must reflect the current authoritative fact, the checkout/authorization path must validate that fact through its appropriate authority. A best-effort invalidation event cannot turn a stale browse cache into a transaction boundary.

Conceptual version-aware cache publication, NOT a Redis client API:
  candidate = source.readWithVersion(product)
  cache.atomicForThisKey(() -> {
    if (candidate.version < invalidationFloor) rejectFill();
    if (current != null && candidate.version < current.version) rejectFill();
    else store(candidate, remainingFreshnessLifetime);
  });

On a committed invalidation for source version v:
  atomically raise invalidationFloor to max(invalidationFloor, v);
  remove any cached representation older than v;

The comparison and publication must be atomic in the cache authority. A Java read of the floor followed by a separate SET has another race. Events must carry a comparable authoritative version; wall-clock timestamps from arbitrary machines are not automatically an ordering rule. Duplicate or reordered invalidations must not move the floor backward. Deletions also need a tombstone/version rule so an old fill cannot resurrect a removed product.

This protocol is conditional on its metadata surviving and on invalidations arriving. If eviction or failover loses the floor, an old loader can publish again. If the source commits but publication of its invalidation is lost, the cache does not know version 8 exists. A durable outbox/change stream can make delivery recoverable, but its delay still creates a stale window. To promise a strict bound, include delivery delay, loader lifetime, source-read freshness and all downstream cache layers, or use authoritative validation at the decision boundary.

A second delayed delete is a mitigation with an assumed maximum loader delay, not a universal proof. A paused process can resume later than that delay. Similarly, a 60-second TTL begins when the value is installed, not necessarily when the underlying snapshot was observed. A loader delayed for ten minutes can otherwise install a ten-minute-old value for another minute. Bound the loader or carry trusted observation/expiry metadata and refuse an already-expired candidate.

AdvancedDoes a higher cached version guarantee that the value is current?
No. It prevents a known older publication under the cache protocol. A source update whose invalidation has not arrived can still be newer. Distinguish monotonic cache publication from authoritative freshness.
IntermediateCan I use the same version floor for every representation?
Only if the source version and invalidation semantics cover those representations. A product description, tenant-specific price and permission decision can have different authorities and lifetimes.

8. Local, distributed, and edge caches

A local Caffeine cache belongs to one Java process; another process can hold a different copy. A Redis/Valkey cache is shared through a network dependency and serialization contract. A CDN stores HTTP representations under HTTP/cache-key rules. These layers can reduce different costs and can coexist, but every extra copy needs an identity and freshness policy.

Trace an update through all layers. If Redis refreshes but a process keeps an older local copy, the shortest TTL does not automatically govern the user’s observation. A freshly fetched lower-layer entry can already contain stale data. Use source/version or age evidence appropriate to the contract and avoid stacking independent TTLs without analyzing the resulting lifetime.

Spring’s cache annotation expresses interception and lookup behavior, while the selected provider defines expiry, serialization and operational details. Under normal proxy mode, self-invocation bypasses the cache interceptor. Review key construction and configuration as part of correctness. A cached method result and a shared HTTP response are different layers with different privacy and validation rules.

@Cacheable(cacheNames = "products", key = "#tenant + ':' + #id")
public ProductView load(String tenant, String id) {
  return repository.loadView(tenant, id);
}
// Provider config supplies expiry/serialization; invoke through the Spring proxy.

9. Cache the right representation

A key is a claim that every request mapped to it may reuse the same representation. The URL path alone rarely establishes that. The same product can have a locale-specific description, currency-specific display and tenant-specific price. A response filtered by a user’s entitlements may vary even within one tenant. Missing a dimension can return a fast, validly encoded response to the wrong audience.

Illustrative logical key, serialized with unambiguous encoding:
  schema = catalog-view-v3
  tenant = authorized tenant identity
  product = validated product identity
  locale = normalized supported locale
  currency = normalized supported currency
  priceList = authorized pricing context/version

Do NOT derive authorization from a caller's cache-key string.
Do NOT concatenate arbitrary fields without length/escape rules.
Do NOT put bearer tokens or personal payloads into readable keys.

The key schema is versioned so a representation change does not reinterpret old bytes. Normalize only what is semantically equivalent: lowercasing a case-sensitive identifier can merge distinct resources. Bound key length and allowed variants so arbitrary query strings cannot create an uncontrolled cache working set. Protect key/value visibility because cache administration and telemetry often expose more than the application response.

Authorization must precede reuse of a protected value, or the cached value itself must be partitioned and validated under an explicit authorization policy. A tenant prefix prevents one class of collision; it does not prove the current actor may read every object in that tenant. An administrator-only field cached inside a general customer representation can leak even when the tenant is correct.

Cached itemSafe question to answerAdditional requirement
Public descriptionMay this reusable public text still be shown?Freshness and representation identity.
Tenant price listWhich authorized pricing context owns this value?Tenant/context identity and checkout validation policy.
Negative lookupWas not-found observed for this exact scope?Short deliberate lifetime; creation/invalidation behavior.
Permission resultHow quickly must revocation take effect?Bounded decision freshness or current-authority check.

Negative caching helps repeated absent lookups, but can hide a newly created object. A not-found observed through a lagging replica may not mean authoritative absence at all. Do not cache a transient timeout as a permanent not-found. Classify absence, authorization denial and dependency failure separately; their reuse and disclosure policies differ.

At HTTP/CDN layers, review actual cache-control and variation behavior, not just the Redis key. A private response stored by an intermediary under a public cache rule can bypass an otherwise correct application cache. Conversely, varying on every arbitrary header can destroy reuse or explode cardinality. Test the end-to-end path with two tenants, two roles and a revoked permission, including warm caches and repeated conditional requests.

IntermediateIf every key includes tenant ID, have we solved multi-tenant caching?
No. The tenant must come from trusted authorization context, the actor must still be allowed the resource/action, variants must not collide, and every cache layer must honor the same disclosure policy.
AdvancedWhy is a stale permission cache more dangerous than a stale product description?
It can permit an operation after authority was revoked. The permitted revocation delay is a security requirement; a convenient TTL cannot silently choose that requirement.

10. Expiration, eviction, and stampedes

Expiration makes an entry ineligible according to time policy; eviction removes it because of capacity or another policy. Both produce misses, but neither guarantees that a business subscriber receives a durable deletion event. Estimate the working set using realistic key/value encoding, metadata and copies, then measure memory and eviction under the real popularity distribution.

A stampede is many callers refilling equivalent data concurrently. Coalesce same-key work where appropriate, spread mass expiry with jitter and cap total source-facing fills. Jitter distributes expiry times; it does not supply capacity for one extremely hot missing key. Coordination needs timeout/ownership rules so a failed filler does not strand future callers.

Negative caching stores an intentional not-found result for a defined interval. Use a distinct representation and appropriate invalidation after creation. A database timeout is uncertainty, not proof that the product does not exist. Caching the timeout as absence can turn a transient dependency incident into persistent incorrect answers.

11. Stampedes and refill leases

A popular key expires while 2,000 requests are waiting. If every miss independently reads the database, a cache that normally saves work becomes a synchronized load multiplier. First use single-flight within one process: callers for the same key share one bounded loader. Across ten pods, that can still mean ten loaders. A distributed refill lease can reduce duplicate work further, provided losing the lease does not compromise business correctness.

# Redis command shape; token is random and unique to THIS acquisition.
SET cache-refill:{product-42} <owner-token> NX PX 3000

-- Lua release: KEYS[1] is the lease key; ARGV[1] the owner token.
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end

The token comparison and delete occur atomically. A plain DEL in finally is unsafe: A’s lease expires, B acquires it, then A deletes B’s lease. The token distinguishes acquisitions; it is not merely a pod name. The braces illustrate a Redis Cluster hash tag for this key, not a requirement to place every product in one slot. Multi-key scripts have additional placement constraints.

Three seconds is illustrative. If A pauses beyond the lease, B may start another refill while A still runs. A conditional release prevents A from deleting B’s lease; it does not stop A publishing stale data or writing a remote effect. Combine refill publication with the freshness/version contract where needed. Never use this optimization as the sole authority for stock deduction, money transfer or tenant authorization.

Caller situationBounded behaviorWhat must not happen
Won leaseLoad within a deadline; publish eligible value; conditional releaseHold an unbounded request while the source stalls.
Lost lease; permitted stale value existsReturn stale within the hard policy; let owner refreshReset the hard lifetime on every stale hit.
Lost lease; no usable valueBrief bounded wait/recheck or controlled rejectionSpin, poll indefinitely or send every waiter to the source.
Redis unavailableFollow a finite fallback/admission policyUnlimited bypass that overloads the database.

Jitter entry lifetimes or refresh thresholds so unrelated keys do not all refresh at the same instant. Jitter must stay within the permitted freshness envelope. A soft refresh threshold can trigger background work while the value is still allowed; a hard expiry forbids serving it. Separate the two explicitly. “Stale while refreshing” is only valid for operations whose contract permits that stale representation.

A Redis failover can weaken lease exclusion under the selected replication protocol. For a cache refill, occasional duplicated work may be acceptable if source load and publication are bounded. That is a different requirement from exclusive ownership of an irreversible action. Measure duplicate fills, waiters per key, source work per miss and hard-expired serves rather than treating successful lease acquisition as proof of correctness.

AdvancedWhy can renewal still fail to make a lease a correctness lock?
A paused or partitioned owner may continue after renewal fails or after another owner takes over. The protected resource needs an appropriate fencing/atomic authority protocol. Extending a cache key alone cannot revoke an old process’s ability to act.
  • Redis lock documentation: ownership tokens, expiry and failover assumptions.

12. Worked design: catalog during a flash sale

Combine identity, invalidation and refill protection under one realistic traffic spike.

For the flash-sale catalog, define which view is reusable before choosing layers. Public images can use an edge cache; tenant/locale product descriptions can use a shared view; personalized discounts must have a separate representation policy. Checkout independently validates authoritative pricing and stock. Browsing freshness is not permission to commit the purchase.

Commit merchant changes and a durable invalidation intent together. The invalidator retries its own work under stable identity. Refill must account for the reader/writer race and protect the database with bounded concurrency. If Redis fails, decide which reads may use a permitted stale copy, which may use constrained fallback, and which must fail/defer. An unconditional “catch exception and query SQL” path can multiply source traffic catastrophically.

Prove recovery with more than hit ratio: examine source work, fill latency, age/version, eviction, error rate and useful checkout completions. Repeat with a cold start, a slow old reader, an invalidation outage, a hot key and an intentionally wrong tenant/locale key. These experiments test distinct correctness and capacity boundaries.

13. Survive cache loss

Model the cold path before deciding to bypass Redis on failure. An illustrative catalog receives 1,000 requests/s. With 90% hits and two source reads per miss, ordinary source demand is 1,000 × 0.10 × 2 = 200 reads/s. Total cache loss makes that 2,000 reads/s before retries, background fills and checkout traffic. A source sized near the warm-cache baseline cannot absorb the bypass simply because the application has spare CPU.

ConditionCalculated source demandInterpretation
90% hit ratio200 reads/sWarm illustrative baseline.
50% hit ratio1,000 reads/sFive times the baseline.
Cache unavailable2,000 reads/sTen times the baseline before amplification.
Validated spare read budget = 400 reads/sAt most 200 two-read misses/sOther required work is already reserved outside this budget.

The last line is a demand budget, not a recommended connection-pool setting. The source might execute some expensive queries much more slowly than others. Measure useful throughput, lock waits and latency for the actual mix. Fleet-wide admission must respect the aggregate budget: giving each of ten pods a 200-miss/s fallback budget would overspend it tenfold.

Conceptual cache-failure branch:
  if reusable cached value exists within allowed hard lifetime:
      return it only for operations that permit stale data
  if source admission and deadline budgets permit:
      perform bounded authoritative read; publish only if eligible
  else:
      reject/degrade optional browsing under the API contract

Checkout stock/permission decisions retain their authoritative path.
A cache outage must not manufacture inventory or permission success.

Separate caches by the value of the work they protect where appropriate. Optional browse traffic should not consume every connection needed for order acceptance or reconciliation. Bound refill concurrency during a recovery, since all entries may be cold simultaneously. Prewarming can reduce a known working set but also creates load; an uncontrolled scan is another stampede.

Inject a lost cache, a slow cache and a partially recovered cache as different failures. A slow cache consumes deadline before the source fallback even starts. Inspect time spent acquiring cache connections, waiting on Redis and waiting on source admission. Ensure one request cannot retain both scarce resources indefinitely. On recovery, ramp fills and observe useful completions rather than celebrating hit ratio while accepted orders are stalled.

AdvancedWhat proves a cache-outage plan works?
The source stays within its validated operating budget, critical invariants hold, optional work follows its documented degradation policy and recovery age remains bounded under a cold-cache drill. A successful Redis reconnect or high hit ratio afterward is not enough.
  • Redis replication: acknowledgement, replication and failover limitations.

14. Tricky cases and recovery

Cache recovery can be as demanding as cache failure. Reconnecting processes may all refill at once, and a serialization rollout may make old entries unreadable across the fleet. Version representations and roll readers/writers compatibly. Bound fallback and refill before enabling traffic after a cold start.

If the cache holds the only copy of an accepted business fact, it is functioning as a primary data store and needs a corresponding durability/recovery design. Likewise, keyspace notifications cannot become the only durable trigger for required work. Choose mechanisms according to what loss or duplication the business can tolerate.

CaseRiskPolicy
Redis unavailableAll traffic falls through to SQLBound fallback; shed noncritical reads.
Serializer changesOld values cannot be decodedVersion key/value format; roll safely.
Permission revokedOld cached authorization still allows accessEnforce sensitive checks authoritatively or design an explicit revocation bound.
Delete notification lostA consumer assumes every expiration is observedUse a durable event mechanism for required business work.
Redis keyspace notifications are not a durable business-event log. A disconnected subscriber can miss notifications. Use them for suitable best-effort observations, not as the only proof that an order must be processed.

15. Interview ladder

FoundationalCache hit versus miss?
A hit finds a reusable eligible value; a miss requires another source or a controlled fallback. Miss performance matters during normal expiry and incidents.
FoundationalTTL versus eviction?
TTL is time-based eligibility; eviction is capacity-policy removal. Entries can be evicted before TTL. Neither guarantees a reliable deletion event.
IntermediateWhy delete after DB commit rather than before?
Deleting first lets a concurrent reader refill the old DB value before the write commits. Deleting after commit avoids that specific ordering, but a late reader can still refill old data, so state the remaining race.
IntermediateWould you cache account permissions?
Only with a documented revocation/freshness policy and suitable isolation. For a sensitive mutation, use authoritative validation or a protocol that enforces the required revocation bound.
AdvancedHow do you survive loss of a 99% hit-rate cache?
The source may see up to 100 times usual miss traffic. Use bounded fallback/refill, headroom, permitted stale responses, admission control and recovery tests.
AdvancedDoes a distributed lock solve consistency?
It only coordinates participants that obey it during its valid lease. Expiry, stale holders, crashes and outside writers remain; durable version/invariant enforcement may still be required.
IntermediateDoes a 60-second TTL prove an answer is at most 60 seconds behind the latest write?
Not by itself. Identify when the source value was observed, when it was published, concurrent invalidation/refill and other cache layers. A late old fill can create a fresh entry containing old data. State the assumptions behind the bound or use an authoritative/coordinated path.
AdvancedWhat must a cache outage policy protect?
The business invariant, tenant isolation and source capacity. Bound fallback/refill concurrency, use stale data only where permitted, and reject/defer optional reads when necessary. A universal catch-and-query fallback can move the outage to the database.

16. Further reading and practice

Carry the operation and its guarantee into the next lesson.

Read the provider documentation to verify what expiry, eviction, persistence, notifications and coordination actually mean. Read Spring’s cache documentation to locate the interception boundary. Then compare those mechanisms against one precise operation and its failure contract rather than treating @Cacheable as an end-to-end consistency guarantee.

The next lesson makes a different kind of copy durable: an intent or fact passed to another process. Unlike a disposable cached view, accepted asynchronous work must survive the producer’s lifetime and have an explicit completion/recovery protocol.

  • Spring cache abstraction: proxy semantics and provider responsibilities.
  • Redis keyspace notifications: delivery limitations and event configuration.
  • Redis eviction: memory policy and eviction behavior.
  • HTTP caching: freshness and validation for edge/client caches.
