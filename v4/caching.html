Caching · fundamentals to production judgment

Make repeated reads cheaper without hiding the truth

Start with one repeated product lookup. Build a cache, then follow what happens when data changes, entries expire together, or the cache disappears.

Technical definitionA cache stores a reusable copy of data or computation to reduce the cost of retrieving it again. The source of truth remains authoritative; cache design defines identity, freshness, eviction and failure behavior for the copies.
Before you begin. Know a database lookup and an HTTP response. Indexes reduce lookup cost without creating an application cache; understand that distinction first.

Learning outcome: Choose a read/write pattern, define freshness and isolation, and protect the source during a cache incident.

1. Why repeat the same read?

The database lesson improved a query with an index. That reduces the work for each lookup, but repeated requests still cross the application/database boundary. Caching reuses an earlier answer. We will first make that repeated read cheaper, then deliberately change the source while a copy exists. The difficulty becomes visible at that moment: a fast answer can be an old answer.

Every product-page request reads the same description from SQL. The query is indexed, but a popular product still generates thousands of identical reads. A copy kept near the caller avoids repeating network and database work. That is the opportunity a cache addresses.

Now a merchant changes the description. The database is correct immediately; the copy may not be. Caching exchanges repeated-work cost for ownership of copy freshness. Before choosing Redis, ask how stale the product page may be and whether checkout must use the same answer. A five-minute-old description may be acceptable; a five-minute-old permission or stock decision may not be.

2. Follow one operation before adding patterns

Carry this concrete operation through the later mechanisms.

Request A reads product version 7 and stores a copy. Request B arrives one second later and can use it without SQL. A merchant then publishes version 8. If B continues reading the copy, the shop has two representations of the product. Decide which operations may see version 7. Browsing can often tolerate delay; charging a price or checking permission may require another policy. This is why freshness belongs in the requirement, before a TTL or Redis command is selected.

3. Define the freshness contract

Functional requirements

  • Read product details and update them as a merchant.
  • Share popular data across application instances.
  • Return a controlled response when a cache read fails.

Targets and invariants

  • Illustrative display staleness: at most 60 seconds under the stated policy.
  • Never reuse one tenant’s private representation for another.
  • Checkout revalidates authoritative price/stock.
  • Cache loss must not overload the database.

A TTL by itself is not necessarily a bound on staleness relative to the latest write: a slow reader can refill an old value after invalidation. State which races and refresh failures your guarantee covers. If an invariant requires current data, enforce it at the authoritative mutation path.

4. Walk through cache-aside

The freshness requirement defines which answers are reusable; follow the simplest miss path next.

Cache-aside means the application first checks the cache, reads the source on a miss, then fills the cache. A hit returns the copy. A miss is normal—it is not an error—and must have a working bounded path.

Product getProduct(TenantId tenant, ProductId id) {
  String key = "product:v2:" + tenant + ":" + id;
  Product cached = cache.get(key);
  if (cached != null) return cached;
  Product value = repository.find(tenant, id);
  cache.put(key, value, Duration.ofSeconds(60));
  return value;
}
// Teaching pseudocode: add timeouts, missing values, failure policy and metrics.

Include every dimension that changes the reusable value: tenant, locale, currency, schema version or permission scope where relevant. Avoid using raw credentials as keys. A user-specific representation often belongs in a private or per-user cache rather than one shared product key.

5. What happens after a write?

The read path works until the source changes. Now trace a reader and writer together.

The simplest policy is commit the authoritative update, then delete the cached copy. Next read repopulates it. If deletion fails after the DB commit, the old entry can survive until expiry; an outbox-driven invalidation can make retries durable. It still requires a policy for reads racing with the write.

Race to reason about:
1. Reader misses and reads DB version 7.
2. Writer commits version 8, then deletes cache key.
3. Reader finishes late and caches version 7.
4. New readers temporarily see version 7 again.

Options include tolerating bounded staleness, caching under immutable/versioned keys, and using version-aware conditional publication tied to durable version knowledge. A compare-and-set only against an existing cache value does not solve the absent-key race unless the protocol preserves a newer version marker. “Delete twice after a delay” reduces some races but is not a general proof of consistency.

Cache-asideRead-heavy data; misses are acceptableStale copies and refill races.
Write-throughWrites go through a component that updates cache/sourceFailure ordering and authority must be explicit.
Write-behindBuffering asynchronous persistence is acceptableLoss/durability and ordering become core requirements.

6. Local, distributed, and edge caches

A Caffeine local cache avoids a network hop, but each Java process holds its own copy. Redis/Valkey provides a shared remote cache, adding network latency, serialization and an operational dependency. A CDN such as CloudFront caches HTTP representations near readers; HTTP cache headers and key policy decide reuse.

These layers can coexist, but their freshness periods can compound. Inspect the age/source version instead of assuming the shortest TTL controls every layer. Redis persistence or replicas can improve recovery, but a cache replica is not automatically the authoritative database. Decide whether the cache is disposable; if it holds unique business data, you have designed a data store with different durability requirements.

Spring mapping: the cache abstraction can use a local or Redis-backed CacheManager. With proxy-based caching, self-invocation does not pass through the interceptor. Choose cache names, key generation, serialization and TTL in provider configuration rather than assuming the annotation defines them all.

@Cacheable(cacheNames = "products", key = "#tenant + ':' + #id")
public ProductView load(String tenant, String id) {
  return repository.loadView(tenant, id);
}
// Provider config supplies expiry/serialization; invoke through the Spring proxy.

7. Expiration, eviction, and stampedes

Expiration makes an entry ineligible after time. Eviction removes entries to satisfy capacity policy. Neither is a business deletion notification. Size the working set from key count, key/value bytes, metadata overhead and replication; test with realistic serialization rather than payload size alone.

A stampede occurs when many requests miss the same key and all refill it. Collapse same-key work locally, use bounded distributed coordination when necessary, and add expiry jitter so many keys do not expire together. Coordination locks need leases and failure rules; do not hold a global lock around every product lookup.

Negative caching stores “not found” briefly to suppress repeated misses. Use a distinct marker and short policy, and avoid turning temporary database failure into a cached “not found.” Hot-key pressure can remain even with many cache shards because one key still has one primary ownership path.

8. Worked design: catalog during a flash sale

Combine identity, invalidation and refill protection under one realistic traffic spike.

Product descriptions are cacheable for 60 seconds; prices shown in browse responses are indicative; checkout uses the current authoritative pricing rule. Use CloudFront for public media, Redis for shared product views and a small local cache only if its additional staleness is acceptable. Put tenant and locale in the key, and keep personalized discounts separate.

Merchant update commits to SQL with an outbox invalidation event. The invalidator retries failed deletes. Refill uses per-key work collapse and a database concurrency budget. On a cache outage, permit a limited miss-path load; serve an allowed stale display copy or reject nonessential reads after the budget is exhausted. Never allow every request to bypass the failed cache simultaneously.

Observe hit/miss rate together with source load, fill latency, entry age/version, eviction, memory and cache error rate. Test a cold start at peak, invalidation delayed behind a slow reader, one hot product, tenant-key mistakes and cache timeouts. Verify checkout rules independently of page freshness.

Redis keyspace notifications are not a durable business-event log. A disconnected subscriber can miss notifications. Use them for suitable best-effort observations, not as the only proof that an order must be processed.

10. Interview ladder

FoundationalCache hit versus miss?
A hit finds a reusable eligible value; a miss requires another source or a controlled fallback. Miss performance matters during normal expiry and incidents.
FoundationalTTL versus eviction?
TTL is time-based eligibility; eviction is capacity-policy removal. Entries can be evicted before TTL. Neither guarantees a reliable deletion event.
IntermediateWhy delete after DB commit rather than before?
Deleting first lets a concurrent reader refill the old DB value before the write commits. Deleting after commit avoids that specific ordering, but a late reader can still refill old data, so state the remaining race.
IntermediateWould you cache account permissions?
Only with a documented revocation/freshness policy and suitable isolation. For a sensitive mutation, use authoritative validation or a protocol that enforces the required revocation bound.
AdvancedHow do you survive loss of a 99% hit-rate cache?
The source may see up to 100 times usual miss traffic. Use bounded fallback/refill, headroom, permitted stale responses, admission control and recovery tests.
AdvancedDoes a distributed lock solve consistency?
It only coordinates participants that obey it during its valid lease. Expiry, stale holders, crashes and outside writers remain; durable version/invariant enforcement may still be required.
