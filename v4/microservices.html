Microservice Boundaries · fundamentals to production judgment

Split ownership only when the boundary earns its cost

Grow a modular order application into independently owned services without creating a distributed monolith.

Technical definitionA service boundary assigns responsibility for business behavior and data to an independently operated component. A modular monolith enforces internal boundaries in one deployment; microservices make selected boundaries remote and independently deployable.
Before you begin. Understand data ownership and remote messaging. Start with one codebase; a service-per-table design is not assumed.

Learning outcome: Choose a boundary using invariants, change patterns, team ownership and operational cost, then migrate it safely.

1. One change requires six coordinated deployments

The application now has orders, inventory, payment and fulfillment behavior. Those names do not require four deployable services. Start with who owns each rule, which facts change together and which team needs independent change. A module can create a useful boundary without adding a network or separate deployment.

Extracting a module changes failure semantics. A method call becomes remote admission, serialization, communication and an uncertain response. If an inventory reservation was formerly part of the order transaction, extraction introduces a visible interval and recovery protocol. The service boundary must justify that cost through ownership, scaling or deployment needs.

2. Find an ownership boundary before adding a network call

Read this slowly: it establishes the distinction used in the implementation sections.

A module groups behavior behind an interface. A service adds independent process, deployment and operational boundaries. A bounded context supplies a consistent domain model and vocabulary. Those boundaries can align, but they are not identical. First ask which team owns a rule and which facts it must change atomically.

Orders and inventory may begin as modules sharing a local transaction. Extracting inventory creates an interval between accepting an order and confirming a reservation. The API must now represent that interval and recover when the reservation response is lost. If the product cannot tolerate the intermediate state, splitting processes requires more coordination or a revised boundary. Network separation does not erase the original invariant.

Check your understanding
FoundationalEach database table should become a service.
A table is a storage detail. Splitting by tables can force every business operation into chatty distributed coordination. Group by domain responsibility, change patterns, invariants and team ownership.
IntermediateWhen is a modular monolith a reasonable endpoint?
When coherent modules, acceptable release coupling and one operational unit meet the workload and team needs. Extraction should solve a measured ownership, scaling or deployment problem with a sustainable operational cost.

3. Define autonomy and invariants

Collect change patterns as well as request rates. Which features repeatedly modify the same business rules? Which operations must commit atomically? Which team can operate and evolve the behavior independently? Those answers often reveal a more coherent boundary than a table-by-table split.

Include operating constraints: on-call ownership, contract evolution, identity, telemetry and data migration. Independent deployment is useful only when the team can preserve compatibility and diagnose failures across the new boundary. A diagram with many small boxes can conceal tightly synchronized releases and a shared database that nobody owns.

Functional requirements

  • Own checkout, catalog, payment and notifications explicitly.
  • Change receipt behavior without deploying checkout.
  • Expose supported contracts instead of shared-table writes.

Targets and invariants

  • Each critical invariant has an owner.
  • Bound synchronous fan-out and failure propagation.
  • Independent delivery requires compatible contracts.
  • Teams can observe and operate what they own.

A bounded context defines a model in which terms have precise meaning. “Customer” in billing may differ from “customer” in marketing. A domain boundary is not inferred from matching noun names alone. Analyze workflows, shared invariants and reasons for change.

4. From modules to service ownership

A bounded context supplies a consistent domain model and vocabulary. The word customer may mean a payer in billing and a delivery recipient in fulfillment; forcing one universal entity can couple unrelated changes. Define the facts each context owns and the interfaces through which others learn or request changes.

In a modular monolith, enforce module interfaces and data access discipline before distributing execution. Private data ownership makes later extraction safer. If every module can mutate every table, adding REST endpoints does not create independent domain ownership. Keep business invariants cohesive even when the storage representation spans several tables.

EvidenceBoundary implication
Two operations must commit together for a hard invariantKeep an appropriate common transactional owner or design explicit coordination.
A capability changes independently and has distinct load/lifecycleCandidate for independent deployment.
Every request needs many chatty calls across the boundaryRevisit boundary or introduce a suitable projection/BFF.
Another service directly updates its tablesOwnership is bypassed regardless of repository layout.

Start with module interfaces and restricted data access in the monolith. Integration tests enforce allowed calls. Extract only when deployment, scaling, fault isolation or organizational autonomy benefits exceed extra operational complexity. A well-structured monolith is not a failure state.

5. Synchronous decisions and asynchronous facts

Follow one customer journey across proposed services and count sequential dependencies. Every required synchronous response contributes latency and availability constraints. A call from orders to inventory may be justified for reservation, while email or analytics may use durable asynchronous progress. Choose from completion semantics rather than a blanket “everything is an event” rule.

An event records a fact owned by its source, not permission for any consumer to rewrite that source’s data. A command has a responsible action owner. Publish stable domain contracts rather than leaking internal table schemas without an evolution policy. Consumers needing local views must own their freshness, backfill and replay behavior.

Avoid sharing one giant DTO/entity jar across all services. A schema contract or generated client can be useful, but forced lockstep dependency updates undermine compatibility. Publish versions and behavioral guarantees at the boundary.

6. Modular Spring and AWS choices

Place an application interface around a cohesive module, test its contract and identify its data authority. Then extract a bounded path if independent operation is needed. Spring controllers and messaging listeners adapt transport; they should call explicit domain/application boundaries rather than exposing repository methods as the public service contract.

For AWS/EKS deployment, separate scaling and identity policies by the actual service responsibility, and propagate evidence across calls/events. Network access is not domain authorization. Each new service needs bounded dependencies, rollout compatibility and a recovery runbook. Sharing a library can reduce boilerplate, but shared domain schemas can also force lockstep upgrades.

Boundary contract:
 Checkout publishes OrderAccepted(eventId, orderId, receiptAddressRef)
 Notifications owns delivery status and retry policy
 Notifications cannot UPDATE checkout.orders
 Checkout does not wait for email provider completion

Store only the data a consumer needs under the applicable privacy rules. A replicated reference is not permission to treat stale copied data as authority for another owner’s invariant.

7. Worked migration: extract notifications

Extract fulfillment first when delayed shipping work can proceed independently of order acceptance. Commit an order-side event durably; fulfillment creates its own task and uses a stable warehouse identity. Orders exposes progress under the agreed contract without directly mutating fulfillment tables.

If inventory is extracted later, model reservation, expiry and late payment before cutover. Migrate write ownership deliberately and avoid two active authorities for the same stock. Compare the extra intermediate states with the organizational/scaling benefit. It is reasonable to retain a cohesive local boundary where distribution does not solve a measured problem.

8. Trade-offs and tricky cases

A distributed monolith has network-separated processes that still require coordinated releases or chatty shared-state access for ordinary work. Diagnose change coupling and critical-path fan-out rather than counting services. A shared database can be a migration stage, but independent uncontrolled writers undermine the claimed boundary.

Review failure and cost after extraction. More telemetry, deployments, contracts and on-call paths are real obligations. Keep rollback compatible with data already produced by the new service, and retire old jobs/routes only when no supported path depends on them.

TrapConsequenceResponse
One service per entityChatty distributed transactionsModel business capability/invariant ownership.
Shared DB without ownershipIndependent deployments break each otherRestrict writes and migrate through explicit contracts.
Event choreography everywhereWorkflow state/ownership becomes invisibleUse an orchestrator or an explicit end-to-end ledger where useful.
Premature extractionOperations overhead exceeds benefitEnforce module boundaries first.

Measure lead time, coordinated deployments, dependency failures and operational workload. Service count is not a success metric. A shared team can operate several services, but ownership and on-call capacity must be credible.

9. Interview ladder

FoundationalMonolith versus microservices?
A monolith deploys as a unit; microservices make selected responsibilities independently deployed/operated. Internal modularity is a separate property.
FoundationalWhat is data ownership?
One capability controls authoritative mutation and invariants for its data; others use supported contracts or projections.
IntermediateWhen should you keep a modular monolith?
When clear modules deliver change isolation and there is no sufficient need for remote deployment/scaling autonomy to justify its cost.
IntermediateWhy can shared entity jars cause coupling?
Persistence changes and lockstep versions can spread across services, exposing internals rather than a stable contract.
AdvancedHow do you extract a side-effecting capability safely?
Establish durable intent/identity, shadow without effects, switch ownership deliberately, preserve compatibility and test rollback/duplicates.
AdvancedHow do you detect a distributed monolith?
Frequent coordinated releases, shared writes, synchronous chatty chains and inability to tolerate one component’s outage indicate boundaries lack autonomy.
IntermediateWhy can splitting by tables create a distributed monolith?
One business rule can require several tables and atomic decisions. Splitting them into separate owners without changing the protocol creates chatty coordination and lockstep releases rather than coherent autonomy.
AdvancedWhat should an extraction prove before routing all traffic?
Clear write ownership, compatible contracts/data, recovery for new remote boundaries, acceptable critical-path capacity/latency and an operating owner. Test cutover and rollback with facts already committed by the new path.
