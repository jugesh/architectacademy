Networking & HTTP · fundamentals to production judgment

Follow a request from a hostname to a response

Understand the layers beneath an API call before diagnosing connection failures, slow requests and gateway timeouts.

Technical definitionNetworking provides addressing, transport and communication between processes. HTTP defines request/response semantics above the transport; DNS resolves names, TCP provides an ordered byte stream, and TLS protects the connection’s confidentiality and authenticated peer identity.
Before you begin. Know an HTTP endpoint from API Design. No prior TCP, DNS or TLS knowledge is assumed.

Learning outcome: Locate delay or failure at the correct network layer and configure connection reuse, trust and time budgets intentionally.

1. Why “the API is slow” is not a diagnosis

A Spring service calls https://payments.example.com/capture. Before the provider can process the JSON, the caller needs an address, a reachable peer, an appropriate secure connection and permission to send the request. An error at any earlier layer can look like “payment failed” in a badly designed log.

Follow a new connection first. DNS maps the name to records containing addresses. TCP establishes a connection to a selected IP/port. TLS negotiates protection and validates the peer under a trust policy. HTTP then sends the method, target, headers and body. An existing pooled connection may skip most of that setup; a proxy may perform some steps on the caller’s behalf.

2. Follow the time, not just the URL

Read this slowly: it establishes the distinction used in the implementation sections.

You know that an API receives an HTTP request. Before its controller can run, the caller must find a destination and establish a usable connection. DNS translates a name into an address; a connection joins endpoints; TLS authenticates the peer and protects traffic; HTTP describes the operation. These layers have separate state and separate failure signals. A successful DNS lookup therefore proves neither that a port is reachable nor that the certificate is trusted.

Consider an order lookup taking two seconds although its controller timer records 30 ms. First ask what that timer excludes. The client may have waited for a pooled connection, performed DNS resolution, negotiated TLS, or waited at a proxy before the controller began. Reusing a connection avoids some setup work, but does not make its lifetime unlimited. Idle connections can be closed by either endpoint or an intermediary. Diagnose the stage before changing the read timeout.

Check your understanding
FoundationalAn HTTP timeout means the server did not execute the operation.
No. The response can disappear after the database commits. Connection failure before sending and timeout after sending convey different evidence, and even client instrumentation may not establish the remote outcome. Use business identity and reconciliation for a mutating operation.
IntermediateWhy can a connection pool be exhausted while CPU is idle?
Connections remain occupied while requests wait on downstream work. Inspect lease wait, active connections and remote latency. More CPU cannot release those connections; bound waits and concurrency before increasing the pool.

3. Write connectivity and user-facing requirements

Functional requirements

  • Reach the intended provider and send a valid HTTP request.
  • Reuse suitable connections and return meaningful failures.
  • Drain connections safely during deployment.

Targets and invariants

  • Verify TLS peer identity; no disabled certificate checks.
  • Bound connect, pool-wait and response time within a total deadline.
  • Illustrative p95 status call below 200 ms.
  • Never infer remote rollback from a connection failure.

The user cares about an outcome, but operators need a layer-specific error: DNS resolution, connection refusal, TLS validation, pool exhaustion, HTTP rejection or application timeout. Preserve that distinction without leaking credentials.

4. Walk through the layers

LayerWhat it establishesWhat it cannot prove
DNSA name-to-record answer, subject to caching and resolver behaviorThat the returned address is healthy or the application is authorized.
TCPA connection and reliable ordered bytes while viableThat the business operation executed exactly once.
TLSEncrypted transport and peer identity under configured validationThat an authenticated user may refund a particular order.
HTTPMethods, representations, status and metadataThat a timeout means the remote side effect did not happen.

A port selects a listening service on a host; an IP identifies a network destination, not a specific Java object. A Kubernetes Service routes to eligible endpoints; a pod may listen on 8080 while the Service exposes port 80. Keep listener, Service and externally exposed ports distinct.

5. Connection pools and HTTP versions

Opening TCP/TLS repeatedly consumes time and resources. A client pool reuses eligible connections and bounds concurrent use. Requests can wait for a connection even when network latency is low. Track pool-acquisition time separately from provider processing.

HTTP/1.1 commonly uses multiple reusable connections for parallel requests. HTTP/2 multiplexes streams over a connection, reducing some connection overhead; TCP packet loss can still delay streams sharing that connection. HTTP/3 uses QUIC and has different transport behavior. Neither protocol automatically fixes an overloaded handler or an N+1 query.

DNS records may change while connections remain open. Idle timeouts on clients, ALBs and proxies can disagree, creating stale-connection failures. Configure reuse, idle eviction and connection lifetime deliberately; retry only when the operation’s semantics permit it.

6. Implement clear budgets and trust

Conceptual client configuration (client-specific APIs differ):
  pool acquisition timeout: 50 ms
  TCP connect timeout: 100 ms
  response/read timeout: 400 ms
  total logical-call deadline: 600 ms including any retry
  TLS: verify certificate chain AND intended hostname
  connection pool: bounded per destination

Spring RestClient/WebClient uses an underlying HTTP client whose pool and timeout configuration must be inspected. Construct clients through configured/instrumented builders where appropriate. A WebClient reactive return type does not guarantee every invoked dependency is nonblocking. Do not put a blocking SOAP call on an event-loop thread.

On AWS, map client → DNS → ALB/API Gateway → ECS/EKS/Lambda → provider. Distinguish security-group routing/access from application authentication. If TLS terminates at the ALB, decide explicitly how the next hop is protected. Trust forwarding headers only from your controlled edge.

7. Worked diagnosis: intermittent gateway timeouts

After scaling to 20 pods, provider calls intermittently wait for seconds, but provider execution remains 80 ms. Inspect per-pod pool wait and connection count before blaming DNS. Each pod opened its own large pool; the provider now hits a connection quota. Bound fleet-wide pressure and reduce pools/concurrent calls based on measured capacity.

Next separate a 504 generated by the gateway from an exception generated by the client. Compare gateway access records, application trace and provider request reference. If capture may have committed before the gateway timed out, reconcile using the original intent; do not fix the symptom by blindly increasing every timeout.

Validate with fresh and reused connections, idle gaps, DNS rotation, certificate rotation and controlled packet/delay faults in a nonproduction test environment. Confirm hostname validation remains enabled throughout.

Only first call slowDNS/connect/TLS phase timingsEvaluate connection reuse and startup warmup.
Connection reset after idleClient/proxy idle policiesAlign eviction/reuse and safe retry rules.
Client disconnect or cancellation does not undo work already accepted by the server. Connectivity and idempotency are related operationally but solve different problems.

9. Interview ladder

FoundationalWhat does DNS do?
It resolves names to records through a resolver/cache hierarchy. It does not guarantee application health or authorization.
FoundationalIs HTTPS simply HTTP on another port?
HTTPS adds TLS protection and peer validation. Port conventions alone do not create encryption or prove identity.
IntermediateWhy can pool wait dominate latency?
Connections are finite. Slow calls or excessive concurrency can exhaust them, making later requests queue locally before reaching the provider.
IntermediateDoes HTTP/2 eliminate head-of-line blocking?
It multiplexes HTTP streams but runs over TCP; loss can delay all streams on that connection. Application queues and downstream contention also remain.
AdvancedHow do you distinguish a gateway timeout from an application timeout?
Use phase timing, gateway logs, trace boundaries and provider references. Identify which component ended its wait and preserve unknown write outcome recovery.
AdvancedShould certificate validation be disabled during an incident?
No. Diagnose the chain, hostname, clocks and trust configuration. Disabling validation removes the peer-identity guarantee and creates a different failure/security mode.
