Mutation Testing · fundamentals to production judgment

Check whether your tests notice the wrong behavior

Deliberately alter a stock rule and see which tests fail. Run a scoped PIT report, interpret surviving mutants and learn why mutation scores, coverage and business correctness are different claims.

Technical definitionMutation testing introduces small program changes and runs tests to see whether they detect the altered behavior. It evaluates aspects of test sensitivity against selected mutation operators, rather than proving the implementation satisfies all requirements.
Before you begin. Read test design and the stock examples. The runnable report uses Maven, JUnit and PIT.

Learning outcome: Explain killed, surviving and uncovered mutants, investigate a useful survivor and adopt mutation testing without gaming a percentage or treating every mutation as a real bug.

1. Executed code can still be weakly tested

A reservation test calls reserve(1) on ten units and checks only that no exception was thrown. Coverage reports that the subtraction line ran. Now replace subtraction with addition: the test may stay green while stock is created from nothing.

Mutation testing asks whether the checks sound the alarm when a selected small mistake is introduced. It is like testing a smoke alarm with a controlled signal rather than merely confirming the light is on. The controlled signal represents a class of faults, not every possible fire.

Our example uses Inventory and its named acceptance tests. The report is deliberately scoped to that class, so readers can inspect each change. It does not measure the entire textbook, all Java examples or the correctness of a deployed inventory service.

2. Separate coverage from sensitivity

EvidenceQuestion answeredImportant limit
Line coverageDid the test execute this line?Execution can happen without a meaningful assertion.
Branch coverageWere selected control-flow alternatives exercised?The asserted outcome can still be wrong or incomplete.
Mutation resultDid a test detect a selected artificial code change?The operator set and tests cover only selected fault classes.
Business acceptanceDoes the behavior meet the agreed rule?Requires a correct rule and suitable observation boundary.

PIT mutates compiled Java bytecode and selects relevant tests using coverage information. The report maps results back to source. The displayed source-level interpretation can be approximate, so inspect the operator and observable effect rather than assuming every line description is literal source editing.

3. Run a scoped PIT report

The shared Maven project pins PIT 1.18.2 and its JUnit 5 plugin 1.2.2. This configuration mutates Inventory and uses InventoryExamplesTest as the detecting suite. The property tests still run in ordinary Maven tests; they are deliberately outside this small mutation scope.

mvn -B -f v4/examples/testing/pom.xml test
mvn -B -f v4/examples/testing/pom.xml test-compile \
  org.pitest:pitest-maven:mutationCoverage

# Open locally after the command completes:
# v4/examples/testing/target/pit-reports/index.html
<targetClasses>
  <param>academy.testing.Inventory</param>
</targetClasses>
<targetTests>
  <param>academy.testing.InventoryExamplesTest</param>
</targetTests>
<timestampedReports>false</timestampedReports>

CI runs the analysis and retains its HTML/XML report as an artifact. It does not impose a universal mutation-score threshold or promise that every generated mutant is killed. Read the actual report from the run; example calculations below are hypothetical and are not claimed report results.

4. Interpret each result before changing code

ResultMeaningNext step
KilledAt least one relevant test detects the altered program.Inspect whether the failure is meaningful rather than incidental infrastructure breakage.
SurvivedThe selected tests did not detect this mutation.Check missing assertions, missing cases and possible equivalent behavior.
No coverageNo selected test executes the mutated location.Decide whether the path belongs in scope and add relevant tests if needed.
Timed outThe mutation exceeded the configured execution budget.Inspect the operator and baseline stability; do not equate every timeout with a useful assertion.
Tool/run errorThe analysis could not establish a normal result.Fix infrastructure or compatibility before drawing conclusions.

A survivor is a question, not an automatic instruction to add a test. The altered code may be equivalent for every valid input, or the code itself may be unnecessary. Removing redundant production code can be better than writing a test for an unobservable implementation detail.

A killed mutant also has limits. A test may fail because an error message changed while the business outcome is wrong in both versions. Review the quality of the detecting assertion, especially for critical rules.

5. Investigate a boundary mutation

Illustrative source-level change:
Original: if (quantity > available) return false;
Mutation: if (quantity >= available) return false;

Test case: available=10, quantity=10
Agreed result: accepted=true, available=0
Mutated result: accepted=false, available=10

The equality row in InventoryExamplesTest distinguishes these versions. If the row were absent and all successful quantities were comfortably below stock, a boundary mutation could survive. The useful response is an example for the agreed rule, not an assertion about a private branch variable.

Hypothetical survivorPossible gapUseful investigation
Subtraction behaves as additionOnly response success is asserted.Assert remaining stock and conservation.
Rejection condition is removedNo insufficient-stock example.Add a rejected request and check unchanged state.
Invalid-input guard disappearsOnly positive quantities tested.Check zero/negative input and no mutation.
A redundant null guard changesValid inputs cannot distinguish the versions.Determine equivalence; simplify or document narrowly.

These are illustrative fault hypotheses. The exact mutants generated depend on the PIT version, operators, compiler and source. Do not write a report claiming a particular survivor without running and reading the configured analysis.

6. Use percentages with a declared denominator

For an illustrative report with 20 killed, 5 survived and 5 uncovered mutants, the simple killed/all total is 20/30, about 67%. Excluding uncovered mutants gives 20/25, or 80%, which answers a different question. Tools can distinguish mutation coverage from test strength and classify other outcomes differently.

Always inspect the report’s definitions and included statuses. A percentage without target classes, operator set, excluded code and baseline is hard to interpret. Comparing two teams’ scores can be meaningless if one targets a small pure policy and the other includes large generated adapters.

TemptationWhy it misleadsBetter decision
Set 100% as a universal targetEquivalent or irrelevant mutants can consume effort.Review high-risk survivors and set a justified project policy.
Exclude every difficult classScore improves while evidence shrinks.Record exclusions and the alternative assurance.
Treat a rising score as fewer production defectsFault model and requirements may be incomplete.Combine sensitivity with acceptance and boundary evidence.
Use only the summary numberOne missed money/security rule can matter more than many trivial kills.Inspect critical mutants individually.

7. Start small and keep the baseline trustworthy

Begin with a stable domain policy or calculation where failures are cheap and meaningful. Run ordinary tests first, then mutation analysis on the target. Preserve reports so reviewers can see whether the change improves assertions or merely changes scope.

For larger repositories, use a bounded changed-code or critical-module strategy where supported, and schedule broader analysis separately if it earns its cost. Record plugin/compiler/JDK versions. A slow, flaky baseline amplifies costs when many mutated executions repeat it.

Do not run real payments or notifications inside mutation tests. An altered guard can remove protection against side effects. Keep test collaborators isolated and safe, and use dedicated integration evidence for real external contracts. The included Inventory target has no network or persistence side effects.

When adding thresholds, choose how new uncovered code, equivalent mutants and tool errors are handled. A failed analysis should be visible; silently skipping the mutation lane is not the same as meeting the policy.

8. Avoid tests that only defend implementation

A test that asserts the exact private helper call order can kill mutants while making harmless refactoring expensive. Favor business-visible outcomes and invariants. Mutation analysis should help discover weak evidence, not force the implementation to remain structurally frozen.

Mutation testing challenges a finite set of artificial changes. It cannot identify missing requirements, prove authorization or discover every possible race. Keep independent business, integration and concurrency evidence.

Practice: temporarily remove the exact-stock acceptance row, run the scoped report and inspect whether a relevant boundary mutation survives. Restore or improve the test based on the observed report; do not assume a particular operator is always generated.

9. Defend the report

FoundationalWhat does killed mean?

A selected test detects the mutated program. Inspect the actual failure before treating it as strong evidence for the business rule.

FoundationalWhy is line coverage insufficient?

A line can execute while its result is never asserted. A deliberate arithmetic or boundary change may still pass the suite.

IntermediateMust every survivor lead to a new test?

No. Investigate equivalent behavior, redundant code, scope and missing meaningful assertions. Some survivors warrant simplification or a documented exclusion instead.

IntermediateCan two mutation percentages be compared directly?

Only with compatible scope, operators, status definitions and exclusions. Different denominators and target code can make the comparison misleading.

AdvancedWhy start from a green, deterministic baseline?

Otherwise ordinary failures and timing noise contaminate repeated mutated runs, making the detecting evidence unreliable and analysis costly.

AdvancedCan mutation testing prove concurrent reservation safety?

No. It evaluates selected program changes under selected tests. Concurrency guarantees still need a sound authoritative write mechanism and evidence about competing executions.
