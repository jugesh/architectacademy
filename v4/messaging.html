Library/Messaging & Pipelines/Messaging

Messaging · fundamentals to production judgment

Move work asynchronously and own every delivery boundary

Follow one paid order from an API to a background worker. Learn the words first, trace successful delivery, then add crash recovery, duplicates, queues, Kafka, retries and replay one step at a time.

Technical definitionMessaging lets one component send a request or fact for another component to handle separately. A broker carries/retains messages under its contract; the application still defines what successful business processing means.
Before you begin. Know what an HTTP request and a database commit are. No Kafka or SQS knowledge is assumed. If local transactions are new, read what a transaction protects first.

Learning outcome: Explain producer, broker and consumer in plain language; choose a queue or retained log from reader needs; and defend one order workflow through duplicate delivery, crashes and recovery.

1. Start with one order

Keep order O7 and event E91 in mind throughout the lesson.

Alice buys a mug. Order O7 is paid, and the shop must prepare one parcel. Alice should not have to keep the checkout connection open while a warehouse worker packs it. We want to accept the order now and finish the packing work later. For this running example, assume payment is already confirmed; recovering an unknown payment is a separate problem in the Reliability lesson.

Think of a restaurant order ticket. The counter records the accepted order, then a kitchen worker picks up the ticket. The customer and cook do not need to remain in the same conversation. The analogy explains the handoff, but a computer needs something a paper-ticket picture hides: a record that survives a crash, a way to recognize copied tickets and a rule for when a ticket may be considered finished.

A background Java thread changes when work happens, but the thread disappears if its process dies. A durable message or pending-work record lets another process continue. This buys time independence; it does not make work instant or guarantee success. A paid order left waiting forever is still a customer failure.

Read in two passes.

First pass: learn the words, follow O7, compare queue and log readers, then understand acknowledgement and the outbox.

Second pass: study the relay SQL, consumer transaction, offset recovery, retry decisions and compatible replay.

2. Learn the five words

A message is a small envelope of data. In our example it says that order O7 was paid. The order service creates the message; another service uses it to prepare fulfillment work. Start with the five words below before choosing a product.

WordPlain meaningO7 example
ProducerThe component that sends the messageOrder service.
BrokerThe service that accepts and makes messages available under its storage/delivery contractA selected SQS queue or Kafka deployment.
ConsumerThe component that reads and handles the messageFulfillment worker.
Acknowledgement (ack)A confirmation about a particular step; its scope must be statedProducer send accepted, or consumer processing acknowledged. These are different confirmations.
RedeliveryThe same logical message is made available againE91 is received again after a lost acknowledgement or worker failure.
{
  "eventId": "E91",
  "eventType": "OrderPaid",
  "schemaVersion": 1,
  "tenantId": "T7",
  "orderId": "O7"
}

The identifiers here are readable placeholders. eventId identifies this recorded fact; orderId identifies the order it concerns. Retrying publication of E91 keeps E91. A later refund of O7 is a different fact and needs a different event identity. Do not use one new random event ID for every retry, or one event ID for every event in the order’s whole life.

A command requests an action, such as PrepareParcel. An event reports a fact, such as OrderPaid. Several independent services can react to one fact, but each owns its reaction. Naming something an event does not make its payload trustworthy: authenticate the producer path, validate the schema and authorize tenant/resource access in the consumer.

Synchronous means the caller waits for the chosen result in that interaction. Asynchronous means completion can happen separately. The API still needs to say what its response proves: “order accepted” is different from “parcel prepared.” Provide a durable status identity rather than implying all work is complete because the HTTP handler returned.

FoundationalIs the broker the code that packs the parcel?
No. The broker carries/retains the message under its contract. The consumer runs the business handler. Keeping those roles separate helps identify whether a failure is publication, delivery or processing.
FoundationalIs a message ID the same as an order ID?
No. One order can have many distinct events. Keep a stable event ID across repeats of the same fact, and a stable order ID across the order lifecycle.

3. Separate delivery from completion

Ask what each confirmation actually proves.

Use three questions whenever someone says “the message succeeded.” First, did the sender get evidence that the broker accepted it? Second, did a consumer receive it? Third, did the required business work commit or reach its explicitly defined completion boundary? These answers can differ.

ObservationWhat it can tell usWhat it cannot tell us alone
Send acknowledgementThe broker accepted the send according to its configured contractThe fulfillment consumer committed.
Consumer received E91A handler has a delivery to inspectThe handler finished or a parcel exists.
Local fulfillment task committedRecoverable local work now existsA remote warehouse has completed the shipment.
Consumer ack / offset commitThe consumer reports progress to the brokerAny arbitrary external effect is part of that same transaction.

We will first protect a local database effect: create one fulfillment task for O7. Later, a separate worker may call a warehouse API. That remote call has another failure boundary. Do not start by trying to guarantee every possible side effect at once; name the current effect and the durable evidence that proves it.

FoundationalThe send call succeeded. Is O7 packed?
No. It tells you about the sender/broker boundary, according to the actual send contract. The consumer may not have received or processed E91 yet.
IntermediateWhy do we expect redelivery instead of treating it as an impossible error?
A consumer can commit useful work and crash before the broker sees its acknowledgement. Redelivery recovers uncertain progress, so the consumer must recognize and safely handle repeats.

4. Follow O7 through five steps

First the happy path; then stop the process between steps.

Here is the successful O7 path before introducing the failure fixes. The order service records the paid order and the need to notify fulfillment. A sender publishes E91. A fulfillment worker receives E91 and creates a local task. Only after that task is durably recorded does it report the delivery as processed.

StepWhat happensEvidence after the step
1Commit O7 and pending event E91 locallyOrder and pending publication survive a process restart.
2Publish E91 and observe broker acceptanceThe broker has accepted the event under its contract.
3Fulfillment receives E91A delivery attempt exists; no effect is yet proved.
4Commit receipt for E91 and fulfillment task togetherA repeat can be recognized without another task.
5Acknowledge/delete or commit the permitted consumed positionThe broker can apply its progress/redelivery rules.

The pending publication in step 1 is called an outbox. The consumer’s durable “I applied E91” receipt in step 4 is often called an inbox or deduplication receipt. Those names describe two small records on opposite sides of the handoff. The later SQL sections implement them; first understand why each record exists.

Now remove power after each step. Before step 1 commits, no accepted fact should escape. After step 1 but before step 2, the pending event needs a sender that can resume. After step 4 but before step 5, the broker may deliver E91 again. We cannot make those gaps disappear by calling a method “reliable”; we need an explicit recovery action for each.

Notice what we have not claimed: one local fulfillment task is not the same as one completed remote shipment. If a warehouse accepts the task and its response disappears, the runner needs the original warehouse operation identity and an inquiry/reconciliation policy. The complete fulfillment design returns to that harder boundary.

5. Define acceptance and completion separately

Name the business acceptance point and the final effect. “No lost receipt intent after order commit” requires a durable connection between the local change and publication; “no duplicate shipment” requires protection at the effect boundary. These are separate guarantees. A broker feature solving delivery does not automatically solve either local atomicity or remote-provider uncertainty.

A command requests an action from a responsible owner; an event describes a fact that interested consumers can interpret. SendReceipt is a command, while OrderAccepted is an event. Define their identity, schema, ownership, retry horizon and completion expectations. Independent consumers need independent progress and failure handling so analytics cannot accidentally govern shipping availability.

Functional requirements

  • Accept an order and schedule receipt work.
  • Allow fulfillment and analytics to react independently.
  • Retry transient delivery errors and recover failed work.

Targets and invariants

  • No lost receipt intent after order commit.
  • Duplicate delivery must not duplicate protected business effects.
  • Illustrative oldest receipt age under two minutes.
  • One broken message must not block all healthy work.

A command asks someone to act, such as SendReceipt. An event records a fact, such as OrderAccepted. Events often have several independent consumers. Commands should have clear ownership; events should carry enough identity and contract information for consumers to interpret them safely.

6. Choose the reader model

A queue shares work; independent subscribers share facts, not one completion cursor.

Choose the delivery model from how readers must behave. For one pool of workers sharing packing jobs, use a work-queue model. For fulfillment and analytics to react independently, give them independent delivery/progress. For consumers that must reread retained history, a log model is useful. These are requirements before they are product names.

ModelReader behaviorQuestion to ask
Work queueCompeting workers share pending jobsWhich durable effect permits acknowledging/removing a job?
Publish/subscribeIndependent subscribers each get their own reaction pathDoes each subscriber have independent retries and recovery?
Retained partitioned logReaders track positions while history remains retainedWhat ordering, replay and retention scope is required?

Kafka supplies a partitioned log and independent consumer-group progress. SQS supplies queue behavior with different standard/FIFO contracts. Products add more capabilities than this introductory table shows; choose the exact service mode and client configuration. The next section makes reader behavior concrete using only E91 and two fulfillment workers.

7. Two workers, two reader models

Imagine E91, E92 and E93 represent three paid orders. Fulfillment has workers F1 and F2. We want the workers to share the work, while an analytics service separately counts all three orders. “Add another consumer” can mean a competing worker or another independent reader; confusing them can make analytics steal fulfillment work.

SetupF1/F2 behaviorAnalytics behavior
One work queue for fulfillmentWorkers compete for deliveries; repeats remain possibleNeeds its own subscription/queue/path for an independent reaction.
Kafka: F1/F2 in the same fulfillment groupAssigned partitions divide progress among the groupA separate analytics group reads its own copy of the retained history.
Kafka: F1 and F2 in different groupsEach group independently reads the recordsThis is not load sharing for one fulfillment reaction.
Illustrative Kafka topic: order-events
  partition 0: offset 10 = E91(order O7), offset 11 = E93(order O9)
  partition 1: offset 20 = E92(order O8)

Consumer group fulfillment:
  F1 assigned partition 0; F2 assigned partition 1
Consumer group analytics:
  A1 has its OWN positions for partitions 0 and 1

An offset is a position within one partition.
Offset 20 in partition 1 is not globally "after" offset 11 in partition 0.

With this two-partition illustration, adding a third fulfillment member does not create a third partition to own. Actual assignment depends on the configured assignor and subscriptions. More partitions can help parallelize different keys, but do not split an inherently ordered single key’s effect safely without a different domain protocol.

Kafka progress and retention are separate. A consumer group advancing past E91 does not itself delete E91 from the topic; retention/compaction policies govern what history remains. A new analytics group can read older retained records under its configured start behavior. A queue job that was deleted is not automatically available for a future independent subscriber: plan retained source/archive or another delivery path if historical replay is required.

Ordering is smaller than “the system.” Kafka orders records within a partition. Two records in that order can still finish in the opposite order if the application offloads them concurrently. SQS standard queues can redeliver and do not promise strict order; FIFO has specific message-group/order/deduplication rules, which still do not atomically commit a warehouse HTTP effect. Draw the exact scope before claiming order or exactly once.

IntermediateWhy did F1 and F2 each create a task for every event after we gave them different group IDs?
They became independent Kafka reader groups, not two workers sharing one group’s assigned work. Use the intended grouping and still protect the local business effect from repeats.
FoundationalIf analytics crashes, should fulfillment stop?
Not inherently. Independent progress lets analytics catch up from its allowed retained source while fulfillment continues, subject to shared broker/dependency capacity and the business contract.
  • Kafka design: partitioned logs, reader progress and delivery scope.
  • SQS redelivery: why consumers still need repeat-safe effects.

8. Ack only after durable work

Use one database effect first; add external providers later.

Acknowledging too early can lose work; acknowledging after a durable commit can cause a repeat. Compare two attempts to create one local task for E91. The “safe” column is safe only when the receipt and effect truly share the same local commit and the duplicate branch is implemented correctly.

Crash momentAck first, then databaseDatabase commit first, then ack
Before database workBroker may already stop redelivering; task missingNo ack yet, so redelivery can retry.
After local commit, before ackThis gap was skipped by the unsafe orderingTask exists; repeat must recognize E91.
On repeatCannot recover a message already discarded without another ledgerReceipt finds completed local work; skip another task and acknowledge.
Conceptual consumer protocol:
  begin local transaction
  try to insert receipt keyed by (consumerName, eventId)
  if an existing COMPLETED receipt matches the original event:
      do not apply the same local effect again
  else:
      create the fulfillment task / allowed state transition
      record the receipt in THIS transaction
  commit
  only then acknowledge the delivery / safe contiguous position

If local work fails, roll back the receipt with it.
A separately committed "seen" flag is not proof the effect completed.

Idempotent processing means repeating the same logical operation does not repeat its protected effect. Here we achieve it with stable identity and a database uniqueness/transaction protocol, not by assuming only one delivery arrives. Scope receipts by the intended consumer: analytics must be allowed to process E91 even after fulfillment did.

Retain the receipt for the supported redelivery/replay horizon or preserve equivalent durable business uniqueness. Deleting it after a day makes a two-day-old replay potentially new again. If one event ID arrives with different content, treat that as a contract conflict instead of silently applying the changed event.

The consumer SQL section adds hash comparison and state/version conditions. For now, remember the reason for the ordering: a repeat is repairable when durable identity tells us what committed; missing work after premature ack may have no remaining trigger.

9. Commit the consumer effect

In plain language. Before the SQL: the consumer needs a receipt that means “my local E91 effect committed,” not merely “I saw E91.” Put that receipt and the task in the same database commit. The SQL below adds the concurrent-duplicate and stale-state checks.

Now let fulfillment consume OrderPaid event E. The local effect is to make an order ready for packing. We need one committed local effect per consumer/event identity even if E is delivered repeatedly. The consumer name matters: fulfillment and analytics must each be allowed to process the same event. Do not globally mark E consumed for every subscriber.

CREATE TABLE consumer_receipt (
  consumer_name text NOT NULL,
  event_id uuid NOT NULL,
  payload_hash text NOT NULL,
  completed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer_name, event_id)
);

-- Consumer transaction, AFTER schema and authorization validation:
BEGIN;
INSERT INTO consumer_receipt (consumer_name, event_id, payload_hash)
VALUES ('fulfillment-v1', :event, :hash)
ON CONFLICT (consumer_name, event_id) DO NOTHING
RETURNING event_id;
-- Duplicate branch: compare stored hash; do not repeat the effect.
-- New branch only:
UPDATE fulfillment_order
SET state = 'READY', version = :event_version
WHERE tenant_id = :tenant AND order_id = :order
  AND state = 'AWAITING_PAYMENT'
  AND version = :expected_previous_version;
-- Require the domain-approved result. A gap/conflict may need rollback.
-- Insert any next external-work intent into this database's outbox.
COMMIT;
-- Only after this commit, advance the broker acknowledgement/offset.

This is a protocol outline: the fulfillment table and event-version contract belong to the domain model. A version predicate is useful only when producers and consumers agree what the version counts. If the consumer receives only selected event types, source aggregate versions can skip legitimately; “previous + 1” would then reject valid events. Define either a complete per-aggregate stream, a dedicated consumer sequence or a transition rule that can safely skip irrelevant source changes.

If the new-event update cannot apply, do not commit a completed receipt merely because an INSERT succeeded. Roll back and classify the conflict: missing prerequisite, stale event, invalid transition or a real incompatible schema. A business-idempotent transition may deliberately regard a known already-completed state as success, but establish that it belongs to the same business intention. “It is already READY” is not enough if the event refers to a different payment or order version.

Crash pointDatabaseBrokerRecovery
Before local commitEffect and receipt absentUnacknowledgedRedelivery runs the transaction.
After commit, before acknowledgementEffect and receipt presentMay redeliverDuplicate branch verifies identity and skips the effect.
After acknowledgementEffect and receipt presentPosition advancedNo recovery required for that delivery.
Acknowledged before commit, then crashEffect may be absentPosition advancedLost work: this order of operations is unsafe.

The receipt is evidence of completed local work because it commits in the same transaction as that work. A preliminary receipt committed separately breaks that meaning. Its payload hash also detects illegal reuse of one event identity for changed content. Define a canonical event representation for the comparison, and quarantine a mismatch instead of overwriting the old receipt.

Sending a shipment request or email inside this transaction does not extend database atomicity to the remote service. Persist a shipment intent, then use a stable provider request identity and reconciliation. If the remote service cannot deduplicate or answer an inquiry, expose the weaker guarantee. A correct local inbox is not proof of exactly-once real-world shipment.

If a blocked event must be parked to allow progress, atomically store the complete recoverable event and its PARKED state before advancing the source. The recovery handler needs a distinct state transition from PARKED to APPLIED; a generic duplicate check that treats every stored receipt as completed would strand it forever. Monitor parked age and give it an owner.

IntermediateCan I keep consumed IDs in Redis while effects are committed in PostgreSQL?
Only if the resulting cross-store failure protocol meets the requirement. A cache eviction or a crash between the independent writes can permit repeats or lose work. A receipt in the same local transaction is easier to reason about for this database effect.

10. Record the message with the order

Outbox = durable intent; relay = recoverable sender.

The sender has a similar two-step problem. It needs both a committed order and a message. If it commits the order first, it can crash before sending. If it sends first, it can later roll back the order. Writing to two independent systems is often called a dual write. Merely placing the two Java calls next to each other does not make them atomic.

AttemptFailureWrong outcome
Commit order, then sendCrash before sendPaid order has no recoverable fulfillment notification.
Send, then commit orderOrder transaction rolls backConsumer sees a fact that never became true locally.
Commit order + outbox togetherCrash before relay sendA durable pending event remains to be sent.
// Application orchestration outline; repositories use one DB/manager.
// Call this through the managed transaction boundary.
@Transactional
public Order recordPaidOrder(ConfirmedOrder command) {
  Order order = orders.recordPaid(command); // stable command identity
  outbox.insert(eventWithStableId("E91", "OrderPaid", order.id()));
  return order;
}
// E91 is a readable example ID, not a constant for ALL orders.
// Successful outward response depends on the actual commit outcome.
// A separate relay sends committed outbox records.

An outbox is a local table of messages that still need publication. A relay is a worker that publishes those committed records. Committing order and outbox in one database transaction means both exist or neither does. It does not make the later broker send part of that same transaction.

The relay can send E91 successfully, crash before marking it published and send it again after restart. That is why the consumer protocol already learned to recognize E91. An outbox trades an unrecorded lost notification for recoverable, potentially repeated publication. It is a good fit when the business change and intent really can share a local atomic boundary.

An after-commit callback without durable intent still has a crash gap. If the relay reconstructs an old event from mutable current data, it can also change what E91 means. Store the intended event representation or a carefully versioned reconstruction rule. The relay SQL then adds bounded claims, acknowledgement handling and stale-worker protection.

11. Build an outbox relay

In plain language. Before the SQL: imagine the relay putting a temporary “I am sending E91” label on a pending row. If it dies, another sender must be able to recover that row. The lease/epoch below coordinates that claim; it still cannot make a network send and a database marker one atomic action.

An outbox makes the need to publish durable alongside the business mutation. It does not make publication and the later “sent” marker atomic across a database and broker. Follow event E: the checkout transaction commits a reservation and E in the same database. A relay discovers E, sends it, waits for the configured broker acknowledgement, and then records publication. If the process dies after the broker accepted E but before the marker commits, the next relay sends E again. Duplication is the expected recovery path, not an exceptional violation of the outbox pattern.

-- Illustrative PostgreSQL outbox; same transaction as business writes.
CREATE TABLE order_outbox (
  event_id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  aggregate_id uuid NOT NULL,
  aggregate_version bigint NOT NULL,
  event_type text NOT NULL,
  payload jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz,
  lease_until timestamptz,
  claim_epoch bigint NOT NULL DEFAULT 0
);
CREATE INDEX outbox_pending ON order_outbox (created_at, event_id)
WHERE published_at IS NULL;

Claim a bounded batch in a short transaction, release database locks, then perform network I/O. The following is an unordered, lease-based dispatcher. It is suitable only where consumers can tolerate/detect reordering or another ordering protocol is added. Simply sorting claims does not guarantee per-order publication order when several relay workers run.

BEGIN;
WITH candidates AS (
  SELECT event_id FROM order_outbox
  WHERE published_at IS NULL
    AND (lease_until IS NULL OR lease_until < now())
  ORDER BY created_at, event_id
  FOR UPDATE SKIP LOCKED
  LIMIT 50
)
UPDATE order_outbox o
SET lease_until = now() + interval '30 seconds',
    claim_epoch = o.claim_epoch + 1
FROM candidates c
WHERE o.event_id = c.event_id
RETURNING o.*;
COMMIT;
-- Send the returned events OUTSIDE this database transaction.
-- On a confirmed broker acknowledgement for the claimed epoch:
UPDATE order_outbox SET published_at = now(), lease_until = NULL
WHERE event_id = :event AND claim_epoch = :claimed_epoch
  AND published_at IS NULL;

Thirty seconds and fifty rows are illustrative, not recommended defaults. Size the lease and batch from publish duration, process pauses and renewal behavior. A recovered worker increments claim_epoch. The old worker cannot mark a newer claim as published, but it may still send to the broker after its lease expired. Database fencing protects this database update; it does not retroactively cancel a network send. Consumers must still recognize E by its durable event identity.

WindowRiskProtocol response
Commit business/outbox failsNo accepted business state or intentTransaction rolls back; original command may retry.
Claim commits, worker dies before sendEvent waits until reclaimableLease expiry and bounded rediscovery.
Broker accepted, acknowledgement lostPublication outcome unknownRepublish E with the same identity.
Publish acknowledged, marker write failsEvent remains pendingRepublish E; consumer deduplicates the local effect.

Store the event’s business representation or a deliberately versioned reconstruction contract. If a relay rereads a mutable order after the fact, it may publish today’s state as yesterday’s event. For strict per-aggregate sequence, choose a compatible approach such as ordered source-log capture or serialized dispatch of an aggregate’s next event, and test it through takeover. A Kafka partition preserves the order actually appended to it; it does not repair two relay workers sending version 8 before version 7.

Operate from oldest unpublished age, claim failures, broker acknowledgement latency and repeated publication, not only pending count. Cleanup must respect replay/audit needs and downstream retention. Deleting a row because a send method returned before its acknowledgement future completed can permanently lose the intent.

AdvancedDoes claim_epoch make the relay exactly once?
No. It prevents a stale worker from completing a newer database claim under this condition. A stale or uncertain send can still reach the broker. Stable event identity and a safe consumer protocol handle the duplicate effect.
  • PostgreSQL SELECT: locking clauses and SKIP LOCKED behavior.

12. Ordering, schema evolution, and replay

Arrival order, business event order and effect completion order can differ. One handler may finish slowly while a later event’s asynchronous effect finishes first. Include an aggregate identity and a version/ordering rule where the business requires one. A delayed old state should not blindly overwrite a newer state merely because it arrived later.

Schema compatibility must cover retained history and delayed work, not only the newest producer and consumer. Define how readers treat optional additions, unknown event types and incompatible versions. A poison event may require quarantine, but skipping it can let later events for the same aggregate overtake a prerequisite. Choose that ordering/recovery policy explicitly.

Replay is safe only for the effects being rebuilt. Reconstructing a search projection can use a replay-specific path that suppresses external email or shipment. Keep stable source identities, define the starting snapshot/log position and verify completeness. Resetting an offset alone does not prove a correct reconstruction or restore history that retention already removed.

13. Change events without breaking readers

Messages can outlive a deployment. Version 2 of the producer may run while a version 1 consumer is still processing yesterday’s events. A reader also meets old schemas during replay. Compatibility is therefore a relationship among retained records, overlapping processes and the actions each reader can safely take—not just whether today’s JSON deserializes.

Earlier event, schema version 1:
{"eventId":"E91","eventType":"OrderPaid","schemaVersion":1,
 "tenantId":"T7","orderId":"O7"}

Compatible optional extension, ONLY if readers tolerate unknown fields
and the new field really is optional for their business decision:
{"eventId":"E94","eventType":"OrderPaid","schemaVersion":1,
 "tenantId":"T7","orderId":"O10","salesChannel":"WEB"}

Potential breaking change:
rename orderId to purchaseId, change amount units, or change the
meaning of OrderPaid from "captured" to "authorization requested".

A field addition is not universally safe. A strict reader can reject unknown fields, a schema registry has its own configured compatibility checks, and an old reader cannot enforce a newly required business rule merely by ignoring a field. Test semantic behavior as well as serialization. Never silently change an immutable E91 payload and republish it under E91’s identity to “upgrade history.”

ChangeReader questionControlled migration
Optional display fieldCan old readers ignore it without changing their decision?Test old/new producer-reader combinations.
New required decision inputWhat should old readers do when they lack it?Deploy compatible readers before enabling writers; define absence behavior.
Renamed/type-changed fieldCan retained history still be interpreted?Version the contract and use an explicit adapter/upcaster if appropriate.
New event typeIgnore, reject or quarantine under which policy?Make unknown-type handling and ownership visible.

An upcaster translates a historical representation into the internal model a current reader uses. It should preserve the original fact’s meaning and identity, not invent missing business evidence. If an old event lacks a required value, choose an explicit lookup, legacy rule or unresolved path. Filling in a convenient current price can rewrite historical meaning.

Replay also needs an effect policy. Rebuilding a revenue/search projection may intentionally reprocess history while suppressing email, shipment and payment effects. A normal inbox receipt can skip events already applied to the old projection, so a rebuild may need a new projection generation or an isolated target with its own progress/receipt scope. That does not authorize a new shipment consumer identity to repeat irreversible work.

Before switching to the rebuilt projection, connect the baseline to a known source position, handle concurrent changes/deletes, compare critical facts and expose the intended freshness. Rewinding a Kafka offset supplies retained input; it does not by itself prove the new output is complete or correct.

AdvancedCan a schema registry prove the new event means the same business fact?
No. Its configured structural compatibility rules are useful evidence, but units, state meaning, authorization context and allowed effects still require domain tests and a migration policy.
IntermediateWhy does a projection rebuild sometimes use a new receipt scope?
The new target needs to apply historical events even if the old target already did. Isolate the new projection generation and its effects; do not bypass deduplication for unrelated external operations.

14. Offsets and ownership

In plain language. Before the offset arithmetic: a bookmark must not move beyond a page of unfinished work. If offset 250 is unfinished, finishing 251 does not make it safe to resume from 252 after a crash. Follow the two records below and keep the partition identity attached.

A Kafka offset is a position in one partition, not a global business sequence. For a consumer group, committing offset 252 declares that the next record to resume from is 252. If record 250 is still being processed while 251 completed, committing 252 skips unfinished 250 after a crash. Parallel handlers need a contiguous completion frontier for each partition; the highest finished offset is not sufficient.

Partition 3 delivery:
  offset 250 -> slow database transaction, NOT committed yet
  offset 251 -> local transaction committed

Safe committed next offset: 250
Unsafe committed next offset: 252

After 250 also commits, contiguous frontier becomes 252.
If the process crashes at frontier 250, 250 and 251 may replay.
The local receipt handles the already-committed 251 repeat.

This example assumes every record below the frontier was either applied durably or handed to a defined durable recovery path. The commit mechanism, worker handoff and group lifecycle must agree on that meaning. Keep the Kafka consumer’s ownership/commit operations under the client’s supported threading model. Offloading work does not remove poll interval, buffer size and rebalance obligations.

When ownership moves, stop handing new work to the revoked partition, fence or drain the old tasks according to the framework contract, and commit only what is safely completed while ownership permits it. A paused JVM can resume an old task after another consumer acquired the partition. Broker ownership helps delivery coordination; a conditional database transition and receipt still defend the effect against stale or overlapping work.

Partition key selection connects throughput and order. Keying by order ID brings that order’s events to one partition under the chosen routing, while unrelated orders can progress elsewhere. One very active order/key still has a sequential bottleneck. Increasing partition count can change key-to-partition mapping for future records, so a migration requiring strict key order must manage old and new histories rather than assuming automatic continuity.

SQS visibility windowTemporary delivery invisibility while a worker operatesA proof that no duplicate will arrive or that the worker finished.
SQS delete after local commitRemove the processed delivery through its receipt handleUndo a committed local effect if the delete response is lost.

For SQS, extend visibility for legitimate long work under a bounded policy, and plan for extension failure or a stalled worker. A very long visibility timeout delays recovery after a crash; a short one raises concurrent redelivery risk. Neither replaces repeat-safe processing. For Kafka, a retained log permits intentional replay only while the required records remain available; retention is part of the recovery contract.

AdvancedCan Kafka exactly-once processing make the database transaction and a topic output atomic?
Not by itself for an arbitrary external database. Kafka’s transaction protocol covers its participating records/offsets. Use an explicitly supported connector/protocol or a database outbox/inbox design, and state precisely which boundary has the guarantee.
AdvancedShould I commit a poison record so the partition can continue?
Only after an allowed terminal decision or durable recovery handoff has been recorded. Skipping without retaining enough evidence sacrifices the business work. Whether later same-key events may proceed is a domain ordering decision.
  • Kafka design: partition positions, delivery semantics and transactional scope.
  • SQS visibility: delivery visibility, extensions and failure recovery.

15. SQS and Kafka operational choices

Acknowledge/delete and commit-position APIs expose broker-specific progress. In SQS, visibility temporarily hides received work; expiration can make it available to another worker. In Kafka, consumer positions and group participation have their own poll/processing rules. Neither replaces effect idempotency. Configure the actual Spring listener/client behavior rather than assuming return from a method always means the same acknowledgement boundary.

Use bounded retries for transient failures and a deliberate path for deterministic failures. Quarantine preserves the event, error, schema and business identity for diagnosis. A dead-letter queue is a location for unresolved work, not resolution. Fix the reader or data under policy, replay with original identities and prove the business state recovered.

Measure age and useful completions alongside broker counters. A decreasing queue can mean successful processing, expiration, quarantine or loss under a bad acceptance contract. Scale consumers only within database/provider capacity and ordering constraints. Backlog per worker is useful only when its relationship to processing cost and the completion target is understood.

SQS visibility timeout is a lease-like hiding period, not exclusive ownership forever. A second worker may receive the message when it expires. Bound processing time, extend visibility when appropriate, and keep effects idempotent anyway. Kafka lag counts how far a consumer is behind; also measure oldest-event age and actual processing failures.

A poison message fails repeatedly because of its data or a deterministic bug. After a bounded policy, quarantine it with diagnostics and ownership. A DLQ is not resolution: operators need a fix, replay authorization, and proof the replay cannot duplicate earlier effects.

16. Decide what to retry

The worker cannot treat every failure as “try again now.” A temporary connection problem, malformed message and unknown warehouse outcome have different remedies. Start with E91’s intended local effect and classify the evidence before selecting backoff, quarantine or inquiry.

Illustrative retry timing, NOT service defaults:
  attempt 1 fails transiently
  wait a jittered interval near 1 second
  attempt 2 fails transiently
  wait a jittered interval near 2 seconds
  attempt 3 still fails
  stop/park under the declared policy; preserve E91 and its evidence

Every repeat must fit the remaining completion and resource budgets.
A deterministic schema error is not repaired by these delays.

Jitter varies wait times so many workers do not retry in lockstep. It does not add downstream capacity. If 100 deliveries each get three total attempts, up to 300 handler attempts can reach the dependency; SDK and client retry layers can multiply that further. Count useful completed effects separately from delivery/attempt counts.

A dead-letter queue (DLQ) or quarantine stores work the normal path could not finish. It needs the original identity/payload or a secure recoverable reference, classified error, schema/reader version, attempt history and an owner. Moving E91 there is not fulfillment. A paid order’s unresolved age still matters even if the primary queue becomes empty.

Ordering changes the retry decision. If O7’s version 8 failed and version 9 depends on it, sending 8 to a delayed retry path can let 9 overtake it. Pause the relevant ordered scope, park dependent work durably, or use a domain transition that safely handles the gap. “Use a retry topic” describes transport; it does not decide which business state transitions are legal.

For SQS, ensure the visibility policy and any extensions fit the real processing duration, while retaining repeat safety if visibility expires or duplicates occur. For Kafka, commit only the safe contiguous progress described in offset recovery. In both cases, a local committed effect followed by a failed acknowledgement is a repeat-recognition case, not a reason to execute the effect again.

IntermediateShould the consumer acknowledge a poison event just to unblock the queue?
Only after the business contract permits a terminal decision or a durable, owned recovery handoff. Dropping it with no recovery evidence can lose accepted work, and later same-key events may still depend on it.
AdvancedHow do we prove replay recovered the incident?
Reconcile the original affected cohort to allowed business outcomes without duplicate effects, then verify unresolved age, useful throughput and resource budgets. A falling DLQ count alone is not proof.

17. Worked design: fulfillment after checkout

Use the outbox and inbox together, then identify the remote warehouse boundary they do not cover.

Commit the confirmed order transition and OrderPaid intent locally. A relay publishes the stable event. A fulfillment consumer commits its receipt and a local fulfillment task together, then acknowledges. A separate runner performs the remote warehouse interaction using a durable fulfillment identity. Each boundary has a ledger that survives the current process.

Now lose the warehouse response after acceptance. The local task becomes UNKNOWN until provider lookup, supported repeat-safe retry or reconciliation establishes the result. Creating a fresh shipment because the worker timed out would discard the identity needed to prevent duplication. Analytics and receipt delivery use independent progress so their failures cannot consume fulfillment’s entire budget.

Validate every gap: order commit/before publication, publish/before sent mark, local consumer commit/before ack, and remote acceptance/before result recording. Include duplicate, delayed, out-of-order and incompatible-schema deliveries. Assert durable fulfillment identity and state, while monitoring oldest business-state age and unresolved recovery work.

18. Check the whole recovery path

Queue health and customer completion are different measurements.

A queue buys time only if useful completion can catch up within the business deadline. If new accepted jobs arrive faster than sustainable processing, the backlog grows even when HTTP acceptance remains fast. The backlog workbook calculates the recovery budget; distinguish arrivals, delivery attempts and useful completed effects.

“Exactly once” always needs a scope. A supported broker transaction may coordinate selected broker operations, not an arbitrary database, email provider and warehouse together. For every claim, name the participating resources, stable identity, durable evidence and recovery action. Keep critical fulfillment capacity separate from optional analytics or receipt delivery where their failure budgets differ.

Ask before releaseWhat a defensible answer contains
What survives a crash?Order/outbox, consumer receipt/effect and remote intent under their actual commit boundaries.
What may repeat?Publication, delivery, callbacks and recovery attempts, with identities preserved.
Who owns unresolved work?An observable durable state, age bound and authorized recovery path.
What if the queue shrinks?Verify useful business completion rather than assuming deletion, expiry or quarantine is success.

19. Backlog recovery budget

In plain language. Before the calculation: a queue drains only with capacity left after new arrivals. If workers finish 800 jobs/s while 600 new jobs/s arrive, only 200 jobs/s reduce the old backlog. Use useful completed jobs, not repeated delivery attempts.

A queue trades immediate coupling for a recovery obligation. Estimate how quickly it can clear accepted work while new work continues. Use comparable units: completed business jobs per second, not polls or delivery attempts. If a job produces three downstream calls, the provider budget must include that fan-out and all retries.

Illustrative steady recovery:
  existing backlog B = 120,000 jobs
  new arrivals lambda = 600 jobs/s
  sustainable useful completion mu = 800 jobs/s
  net drain = mu - lambda = 200 jobs/s
  time to clear = B / (mu - lambda) = 600 s = 10 min

If arrivals rise to 900 jobs/s at the same capacity:
  backlog grows by 100 jobs/s; it never drains in steady state.
If redelivery doubles handler attempts but useful mu stays 800:
  attempt throughput is not a doubling of recovery capacity.

The ten-minute estimate assumes a stationary mix, no new failure and enough capacity for each partition, database and downstream dependency. A hot ordered key can violate the fleet-average assumption. A few permanently failing jobs can also dominate the oldest-age signal while most work is current. Report age and count by bounded workload class, plus the size and age of parked/unresolved work.

Set recovery targets from the business deadline and retention. If the oldest job has already spent 20 minutes waiting and the completion deadline is 25 minutes, a ten-minute drain estimate is insufficient for that cohort. Decide whether to prioritize urgent eligible work, acquire validated capacity, degrade optional work or explicitly expire an operation. Expiry must define the business outcome; dropping an accepted paid order is not just queue housekeeping.

IncidentUnsafe reactionControlled response
Database slowsDouble all consumers immediatelyReduce/hold admitted concurrency; inspect locks and useful completion.
Poison payload repeatsRetry forever with no ownerClassify and preserve it through a durable quarantine policy.
Recovered providerRelease the entire accumulated backlog at onceRamp within provider and database budgets; reserve capacity for new critical work.
Operator requests replayGenerate new IDs for all eventsRetain original identities, authorize scope and reconcile expected effects.

A dead-letter queue is a place to retain failed deliveries, not a business resolution. Record why the item moved, what parser/schema failed and what the recovery operator may safely do. Managed broker redrive and a custom publish-then-delete routine have different guarantees. In a custom routine, a crash between those independent operations can duplicate or lose the intended handoff unless the protocol accounts for the window.

Before a replay, define the source range, consumer version, original event identities, expected duplicate behavior, ordering impact and stop criteria. Dry-run comparisons can expose incompatible old schemas, but a dry run cannot prove remote side effects are safe. Begin with a bounded cohort, observe useful completions and invariants, then expand. Keep a reconciliation report of applied, already applied, rejected and still unresolved work.

AdvancedWhich graph proves the incident is over: queue depth falling or consumer error rate zero?
Neither alone. Verify timely useful completion, correct final business state, bounded unresolved age and safe resource use. A queue can shrink because messages expired or were discarded, while errors become zero because consumers stopped.
IntermediateWhy can adding workers reduce completion throughput?
More concurrent attempts can increase lock contention, connection waits, retries and provider throttling. Measure the operating point of the constrained dependency and bound the fleet’s aggregate pressure.

20. Interview ladder

FoundationalWhy use a queue?
To decouple timing, persist pending work and buffer bursts. It introduces delayed completion, consumer operations and delivery semantics.
FoundationalCommand versus event?
A command asks for an action and has an owner; an event describes a fact that can have independent consumers.
IntermediateWhy acknowledge after commit?
Acknowledging first risks losing work if the commit never happens. Commit first can cause redelivery, so make the effect idempotent through a shared local transaction or another appropriate protocol.
IntermediateWhat does an outbox guarantee?
The local business change and pending event are committed together. Publication can repeat, so consumers still need safe duplicate handling.
AdvancedHow do you rebuild a projection safely?
Use retained events/snapshot plus a consistent change position, handle versions, isolate rebuild traffic and suppress external business effects. Verify completeness against the source.
AdvancedWhat if FIFO messages still create duplicates?
Send deduplication, visibility and redelivery are different boundaries. Protect the consumer effect with stable business identity, conditional transitions and appropriate retention.
IntermediateWhy does an outbox still require consumer deduplication?
The relay can publish successfully and crash before recording publication. Republishing is the safe recovery for that uncertainty. A stable event identity plus the consumer’s atomic receipt/effect boundary handles the repeat.
AdvancedCan a dead-letter queue prove the business recovered?
No. It isolates unresolved work. Preserve identity, establish failure cause and ordering impact, repair under policy, replay safely and verify the intended durable business state. Queue depth alone cannot establish completion.
