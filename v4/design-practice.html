Turn requirements into a defensible architecture

Apply the V4 foundations to six systems. Make each decision traceable to a requirement, invariant, failure or operating constraint.

Technical definitionSystem design composes interfaces, data models, processing paths and operating policies to meet explicit requirements. A defensible design explains why each mechanism is needed and what happens when its assumptions fail.
Before you begin. Use API Design plus Databases, Messaging and Reliability. Follow the linked specialist lessons when a mechanism is unfamiliar.

Learning outcome: Conduct a structured interview/design review, then pressure-test six systems with concrete failure and implementation questions.

1. Start with the user outcome, not a box collection

A familiar product name does not define its requirements. “Design chat” might mean a small team inbox or a global messenger with offline delivery. Ask who uses it, what must work, what may be delayed and what must never happen. Draw the simplest path that meets those answers before adding caches, shards and streams.

Each case below begins with a narrow contract and a primary invariant. The examples are teaching baselines with illustrative targets, not production blueprints for every scale. A design becomes stronger when it states what evidence would force a different choice.

2. Build an argument, not a product diagram

Read this slowly: it establishes the distinction used in the implementation sections.

A design starts with required behavior, measurable targets and invariants. An invariant rules out an unsafe outcome; a target allows a measured degree of degradation. Constraints include team skills, existing infrastructure and migration cost. A diagram is useful only after these choices explain why each boundary exists.

Take booking one remaining seat. A fast browse projection can show availability, but acceptance needs an atomic claim. A payment timeout creates an unknown external outcome, while a reservation expiry changes local ownership. Define who wins that race and how late payment success is refunded or reconciled. Only then select SQL conditional updates, a durable coordinator and messaging for side effects.

Check your understanding
FoundationalA named pattern is a complete design justification.
An outbox explains reliable publication from a local commit; it does not decide reservation duration, payment uncertainty or authorization. Tie every mechanism to a requirement and name the boundary it leaves uncovered.
IntermediateHow should you answer an unfamiliar design prompt?
Clarify one user journey and its invariants, estimate workload, define authoritative state and trace a happy path. Then introduce concurrency and one crash at each commit boundary before scaling or selecting products.

3. Use one review template

Functional requirements

  • Define core operations and access patterns.
  • Choose authorities, identity and state transitions.
  • Explain errors, recovery and rollout.

Targets and invariants

  • Set workload, latency/availability and retention targets.
  • State invariants and acceptable staleness.
  • Identify dependency/resource budgets and cost.
  • Plan security, observability and recovery ownership.
Interview sequence:
 1. clarify users, scope and invariants
 2. estimate workload and data shape
 3. define APIs/state and authoritative model
 4. explain read/write paths
 5. pressure-test concurrency/failure/abuse
 6. choose scaling and operating policies
 7. state trade-offs and unresolved assumptions

During an interview, answer the actual follow-up before adding another technology. A small correct design with a clear evolution path is more useful than a large diagram with unexplained guarantees.

4. Case 1: URL shortener

Requirements: create a short alias and redirect it; optionally expire or disable it. Illustrative workload is read-heavy. Invariant: one active alias maps to its intended destination, and private/disabled links follow policy.

Baseline: POST /links returns an alias, GET /{alias} resolves it. Use an atomic unique alias insert; random collisions are retried or IDs are allocated under a defined scheme. Store destination, owner, expiry and status. Cache public mappings with an explicit invalidation/freshness policy.

Decision: 301/308 permanence can create durable client/intermediary caching, complicating revocation. Use redirect/cache behavior matching the product contract. Never trust arbitrary callback/fetch destinations; if the service previews URLs, that fetch path is SSRF-sensitive. Block abuse and limit creation.

Spring/AWS: Spring REST plus DynamoDB conditional writes or SQL unique constraints; CloudFront for appropriately cacheable redirects; WAF/admission controls. Test collisions, stale disabled links, expiry and open-redirect abuse. Scaling reads is easy only if the revocation guarantee permits the cache policy.

5. Case 2: notification service

Requirements: send email/SMS/push from business events, honor preferences and expose delivery status. Separate accepted, provider-accepted and actually delivered where the provider reports that distinction.

Baseline: use an outbox from business producers, stable notification/event identities, a per-channel worker budget and a durable delivery ledger. Resolve templates/preferences under an explicit policy; do not replay historical marketing sends blindly after a rebuild.

Failure: provider accepted but response vanished. Reuse provider identity or query delivery evidence; where unsupported, document residual duplicate risk. Rate-limit by tenant/channel and quarantine invalid destinations. Spring consumers plus SQS/SNS/SES or another provider can implement selected pieces; inspect each provider’s actual delivery semantics.

Test: duplicate event, provider outage, opt-out change before delayed delivery, secret rotation and bounded backlog drain. Audit delivery without storing unrestricted personal message bodies in logs.

6. Case 3: chat with offline delivery

Requirements: send to a conversation, retrieve history, reconnect and show receipt states. Define whether ordering is per conversation and whether “delivered” means stored, device-received or read.

Baseline: assign a stable client message ID and server sequence under a conversation authority. Persist before acknowledging durable acceptance. WebSocket carries live updates, while a history/resume API recovers missed data after disconnect. Presence is an expiring observation, not proof a message was read.

Data/scaling: index by conversation and sequence; route conversation writes to an appropriate owner/partition. Large groups introduce fan-out/backpressure and membership-change rules. Authorize history and live subscriptions, not only the initial socket connection.

Spring/AWS: WebSocket-capable runtime or API Gateway WebSocket with explicit connection registry/lifecycle, durable storage and workers. Test duplicate sends, reconnect from last sequence, stale membership, out-of-order arrivals and slow clients. A connected socket alone does not guarantee durable delivery.

7. Case 4: booking scarce inventory

Requirements: hold one seat/room interval, confirm payment and expire holds. Invariant: at most one confirmed booking for the protected resource/time scope.

Baseline: a conditional mutation/constraint in the authoritative store creates the hold with expiry and stable command identity. Confirmation and expiry compete through conditional transitions. Use the database’s appropriate interval/exclusion or equivalent domain constraint when the rule is about overlapping ranges, not just an exact seat ID.

Failure: late payment after hold expiry needs rebooking, void or refund policy. Redis locks can assist contention control but do not replace durable invariant enforcement. Read replicas/search show availability estimates; confirmation uses the authority.

Spring/AWS: local Spring/RDS transactions and outbox; SQS schedules recoverable work; an orchestrator can coordinate payment. Test simultaneous last-seat attempts, hold expiry races, duplicate confirmation and a paused worker waking after lease loss. Do not sell “exactly once” from a lock alone.

8. Case 5: private file storage

Requirements: upload large files, scan them, authorize downloads, version/delete objects and clean abandoned uploads. Invariant: only authorized clean/eligible content becomes visible.

Baseline: create a tenant-scoped upload intent and random object key, issue a short-lived presigned capability, verify stored metadata/checksum, scan in quarantine and conditionally mark READY. For multipart uploads, track finalization and abort or expire abandoned parts.

Failure: duplicate object events or scan callbacks must not publish twice or revive deleted versions. Presigned URLs can be reused until effective expiry and are bearer capabilities; do not claim immediate revocation or one-time access without extra controls.

Spring/AWS: Spring metadata API, private S3, asynchronous scanning and lifecycle policies. Test checksum mismatch, MIME spoofing, cross-tenant key access, replacement of an object under an existing key and download after permission changes. See API Design’s upload/export sections for a longer implementation walk-through.

9. Case 6: payment system walkthrough

Requirements: create a payment intent, capture once per allowed business intent, query status and refund under policy. Separate authorization, capture, settlement and refund; they are not interchangeable states.

Baseline: scope the caller key, validate fingerprint, persist intent, call the provider with stable identity, and store outcome conditionally. A timeout becomes UNKNOWN when the effect may have happened. Authenticated duplicate/out-of-order webhooks use event identity and state/version guards.

Failure: a provider without retry identity or inquiry cannot offer the same single-effect guarantee through arbitrary crashes. State that constraint rather than hiding it behind a distributed lock. Reconciliation uses provider references and settlement records with controlled operator actions.

Implementation: Spring/RDS ledger and outbox, SQS reconciliation tasks, provider SDK with explicit retry/timeouts, protected status reads and auditable refund commands. Test every commit/call boundary, repeated refund, restore from an older backup and late success. See the detailed API checkout design.

10. Cross-case review and trade-offs

Design questionEvidence expected
Where is authority?One named owner/store for each invariant.
What can repeat?Stable command/event identity and retention horizon.
What can be stale?Operation-specific freshness and cache/replica policy.
What happens after a crash?Commit/ack/call boundaries and recoverable state.
How does it scale?Measured bottleneck and workload distribution.
How do we operate it?SLOs, auditability, runbooks, safe rollout and recovery.

Finish each design by changing one assumption: a hot tenant, regional failure, strict revocation or a tenfold burst. Explain which part must change and which requirement drives that change. This tests understanding better than memorizing a diagram.

11. Interview ladder

FoundationalWhat should you clarify first?
Core users/operations, scale, invariants and acceptable delays. The product name alone does not define the design.
FoundationalWhy not start with a technology list?
It hides the reason for choices. Establish the operation and guarantee, then choose mechanisms that supply them.
IntermediateWhen should you introduce a cache?
When measured repeated-read cost and a clear freshness/isolation policy justify it, with a protected miss/failure path.
IntermediateHow do the six cases share an identity problem?
Retries/replays need stable intent/event identity, while each domain defines which repetitions are legitimate new work.
AdvancedHow do you answer a region-failure follow-up?
Specify authority, replication/RPO, recovery/RTO, dependency readiness and external-effect reconciliation before claiming multi-region safety.
AdvancedWhat makes a design defensible?
Every component traces to a requirement, its guarantee has a stated scope, and failure/recovery paths are testable with honest limitations.

12. References and deliberate practice

  • HTTP semantics: redirect and method behavior.
  • S3 presigned URLs: capability and expiry behavior.
  • API Gateway WebSocket: connection-oriented service behavior.
  • AWS idempotent APIs: intent and retry recovery.

Practice: take 40 minutes for one case. Spend the first five clarifying, then write a contract, data/invariant model, request paths and two failure timelines. Review against the table above.
