Domain-Driven Design · fundamentals to production judgment

Model the business before splitting the services

Follow stock reservation across Sales, Inventory and Billing. Learn the language, context boundaries and invariants first, then use aggregates, value objects and domain events with clear transaction limits.

Technical definitionDomain-driven design develops software models in close collaboration with domain experts. It makes the business language and model boundaries explicit, and uses those models to guide code and architectural decisions.
Before you begin. Read service boundaries and understand a local transaction. The reservation examples supply a concrete business rule.

Learning outcome: Draw a context map, identify a consistency boundary and explain why a domain model, database schema and microservice deployment need not have identical boundaries.

1. One word can mean different things

Sales calls an order confirmed when the customer finishes checkout. Inventory calls it reserved when units have been held. Billing calls a payment captured when the provider reports a completed capture. A shared status string called CONFIRMED cannot safely express all three facts.

Think of departments using different dictionaries for the same word. DDD makes those dictionaries explicit and asks the people who know the work to refine the model with developers. Start by listening to actual decisions and exceptions. Do not begin by generating classes called Entity, Aggregate and Repository.

Our shop’s Inventory model owns available stock and reservation decisions. Sales owns purchase intention and order lifecycle. Billing owns payment/refund facts. A customer-facing order view can combine those facts without becoming the authority that changes all of them in one local transaction.

2. Move from language to boundaries

TermPlain meaningShop example
DomainThe area of activity the software serves.Selling and fulfilling purchases.
SubdomainA problem area within that activity.Stock reservation or tax calculation.
Bounded contextA boundary within which a model and its terms have defined meanings.Inventory defines available and reserved units.
Ubiquitous languageThe model’s language used consistently in discussions and code within its context.reserve, release and expire rather than arbitrary status updates.

A subdomain describes a problem area; a bounded context describes a model boundary. Their relationship is a design decision, not a rule requiring one service per noun. A bounded context can initially be a module in one process. Separating deployables later adds network and operational costs without automatically improving the model.

3. Map ownership and translation

RelationshipContract in this shopFailure question
Sales → InventoryReserve units under a stable reservation identity.If the response is lost, how does Sales find the reservation?
Inventory → SalesReservationAccepted or ReservationRejected facts.Can duplicates or older facts regress an order?
Sales → BillingRequest payment for the same purchase intention.What if payment succeeds after the reservation expires?
Billing → providerTranslate the provider’s statuses and identifiers.Which outcomes remain unknown after timeout?

An anti-corruption layer translates an external model into the local one. For example, a warehouse status ALLOCATED might mean a non-expiring commitment there while our RESERVED state is an expiring hold. Copying the external enum into the order model hides that disagreement. Translation must decide semantics, not merely rename a JSON field.

Record who owns each contract, whether the downstream team can influence it and how breaking changes are coordinated. A diagram of boxes without ownership or failure behavior is not enough to guide independent changes.

4. Use tactical patterns selectively

PatternPurposeExample or caution
EntityKeep identity despite changing attributes.Reservation R7 remains R7 when its status changes.
Value objectRepresent meaning through values and validation.Quantity or Money with explicit units/currency.
Aggregate rootControl changes within an invariant boundary.A stock authority prevents spending the same available unit twice.
RepositoryLoad/save domain roots through a domain-oriented boundary.It does not make remote writes part of one database transaction.
Domain serviceExpress a domain operation that belongs to no single entity/value.Avoid moving every entity’s behavior into a giant service class.

Choose an aggregate because facts must change consistently together. Putting all products, customers and payments under Order creates a huge lock and persistence graph. Conversely, scattering every field into an independently written object can destroy the invariant. Ask which updates must be decided together and how contention will be bounded.

Framework annotations are an implementation choice. A model can contain JPA mappings deliberately, or use an adapter that maps persistence records to domain objects. The important question is whether the choice makes domain rules clear and preserves the intended transaction boundary.

5. Put a small invariant in code

This runnable class isolates the core behavior of one inventory authority: no accepted reservation makes available units negative. A full aggregate would also need product identity, reservation identity, versioning and persistence. Those are intentionally absent from this arithmetic example.

package academy.testing;

// In-memory domain example; persistence, deduplication and locking are external.
public final class Inventory {
    private long available;

    public Inventory(long available) {
        if (available < 0) throw new IllegalArgumentException("negative stock");
        this.available = available;
    }

    public boolean reserve(long quantity) {
        if (quantity <= 0) throw new IllegalArgumentException("positive quantity required");
        if (quantity > available) return false;
        available -= quantity;
        return true;
    }

    public long available() { return available; }
}

The method validates the request before mutation and refuses an unaffordable reservation without changing state. A caller cannot bypass the rule by calling setAvailable. That improves local encapsulation, but the object is not thread-safe and two database copies can still disagree. Encapsulation in Java is not a distributed concurrency mechanism.

mvn -B -f v4/examples/testing/pom.xml test

The acceptance examples exercise selected rules. The property tests explore broader input combinations.

6. Keep events and commits distinct

Suppose Inventory accepts R7 and wants to announce it. Update stock, record the reservation and append an outbox fact in the same local transaction. Publishing after a commit without a durable outbox can lose the notification; publishing before commit can announce a reservation that rolls back.

Local Inventory transaction:
  recognize reservationId R7 or validate a new intention
  conditionally reserve units
  record R7 and its outcome
  append ReservationAccepted(eventId E7, reservationId R7)
Commit

Relay may deliver E7 more than once.
Sales consumes it using its own duplicate/version rules.

A domain event expresses a meaningful occurrence. An integration event is a deliberate published contract between contexts; it need not expose every internal event or entity field. Include stable identity and the information readers need, while preserving the freedom to change the internal model.

A saga coordinates progress across contexts through local commits and explicit recovery. A compensating release is another business operation; it cannot make a remote capture never have happened. Define the late-success policy, especially when payment succeeds after stock expiry.

7. Evolve the model with evidence

Start with a modular monolith when one team and one deployment can support the workload. Enforce module APIs and prevent direct writes to another context’s tables even if the database is shared. Later extraction should follow ownership, scaling and release needs rather than a desire to maximize service count.

SignalInvestigatePossible change
Every checkout change touches Inventory internalsLeaking model or unclear command contract.Expose a domain command and explicit outcome.
One stock aggregate becomes hotContention and the true inventory unit of ownership.Partition independent stock authorities, preserving cross-location semantics.
One term has conflicting meaningsA context boundary or translation is missing.Split meanings and publish a translation contract.
Simple lookup code is buried in abstractionsPatterns exceed the domain complexity.Use a simpler implementation for that supporting capability.

Not all parts of a system deserve the same modeling effort. Invest deeply where business distinctions and change create risk. A simple administrative lookup can remain simple; it need not imitate the core reservation model’s structure.

8. Check the model under failure

A useful model makes failure decisions explainable. If two buyers compete for the last unit, which authority serializes the decision? If Sales retries R7, which durable record recognizes it? If the provider’s payment state is unknown, which local state communicates uncertainty instead of inventing success or failure?

An aggregate is not a promise that arbitrary distributed operations are atomic. Define the real persistence and concurrency boundary, then test it. A bounded context is also not automatically one microservice, one database or one team.

Practice: map a subscription purchase across Catalog, Subscription and Billing. Define the meaning of active in each context, the authority for each fact and one translation that would be unsafe as a shared enum.

9. Defend the model

FoundationalIs DDD a test-first approach?

No. It concerns business modeling and explicit model boundaries. It can work with BDD, ATDD and TDD, which provide complementary feedback.

FoundationalEntity versus value object?

An entity has identity that persists through change. A value object represents a value with meaningful validation/equality; it is usually treated as immutable.

IntermediateDoes each bounded context need its own service?

No. A context can be a module. Independent deployment is a separate decision with operational and distributed-consistency costs.

IntermediateWhy not share the warehouse enum everywhere?

The same label can carry different promises. Translate external meaning into the local model and make uncertainty explicit rather than spreading an accidental dependency.

AdvancedHow do you choose an aggregate boundary?

Identify the invariant and the facts that must change consistently together, then evaluate contention, loading and persistence. Avoid both a giant graph and boundaries that split one atomic decision.

AdvancedWhat happens when payment succeeds after reservation expiry?

The local commits cannot be undone as if nothing happened. A coordinated workflow needs a product policy such as re-reservation or refund, stable identity and durable recovery.
