Search & Data Pipelines · fundamentals to production judgment

Build useful projections without losing the source of truth

Follow committed order changes into search and analytics, then handle duplicates, old events, backfills and rebuilds.

Technical definitionA data pipeline moves/transforms data between systems. A projection is a derived representation optimized for a read/use case. Change data capture (CDC) observes source changes; stream processing updates results as records arrive, often using event-time and window semantics.
Before you begin. Read event ordering and replay and source-of-truth storage. We introduce search as a derived read path.

Learning outcome: Design snapshot-plus-change ingestion, choose ordering/late-data rules, and rebuild a projection safely.

1. A database filter is not relevance search

The order database is authoritative, but product search needs relevance, text analysis and retrieval shapes different from the write model. A projection derives a read representation from source facts. It can make queries useful without becoming the authority for inventory, current price or permission.

Follow one source change until it is searchable. There is an interval between commit and projection visibility, and failures can extend that interval. Define freshness and recovery before adding a search engine; otherwise a fast search result can be mistaken for a current business decision.

2. Treat a projection as a derived answer

Read this slowly: it establishes the distinction used in the implementation sections.

The order database records authoritative transactions. A search index reorganizes facts for retrieval, ranking or filtering. A projection is a derived representation maintained from source changes. CDC captures changes from a source mechanism; event time is when the business event happened, while processing time is when the pipeline handled it.

An order changes from pending to paid. If a delayed pending event arrives after paid, a blind overwrite moves the projection backward. Carry source versions or an equivalent ordering rule, handle deletion records and define replay identity. For a backfill, connect the snapshot to a change position so updates during the scan are not lost. Refresh delay is visible in search even when the source commit succeeded.

Check your understanding
FoundationalReplaying all events always reconstructs the correct view.
Only with complete retained history, compatible interpretation, correct ordering/deduplication and a defined starting state. Some sources retain only a bounded log. Schema evolution and external enrichment can also change replay results.
IntermediateCan search results authorize a purchase?
Use the authoritative path for current inventory, price and permissions when the invariant requires it. A stale projection can suggest candidates without authorizing the final business mutation.

3. Define freshness and authority

Write both the retrieval need and the freshness contract. Text ranking, filters, facets and exact lookups are different operations. Bound result size and query cost, enforce tenant/security policy, and identify which decisions must be rechecked authoritatively after search returns candidates.

For the pipeline, define source identity, versions, deletion handling, retained history and recovery ownership. A backfill must coexist with live updates, and replay must not repeat external side effects. Measure age/version lag and reconciliation errors alongside indexing throughput.

Functional requirements

  • Index product/order views for search.
  • Build daily totals and support correction/backfill.
  • Rebuild projections while changes continue.

Targets and invariants

  • Authoritative writes remain in the owning system.
  • Duplicate/out-of-order data must not corrupt derived state.
  • Illustrative search freshness under one minute.
  • Deletes, privacy rules and schema evolution propagate.

A source row appearing in a search result does not authorize access. Include tenant/visibility filtering and enforce sensitive access at the appropriate authoritative boundary. A search result is not proof of current price or stock.

4. Understand the search representation

A search index reorganizes documents and terms for retrieval. Analysis/tokenization changes what queries mean; an exact identifier lookup and a relevance-ranked description search need different field/query choices. Model filters, sorting and access control explicitly rather than indexing raw database rows without a retrieval contract.

Index publication and refresh can delay visibility after ingestion. That is separate from source commit success. A search hit is evidence from a derived view; authorize the final resource operation and validate current inventory/price through the required authority. Restrict fields and query complexity so one flexible search cannot create unbounded work or disclose other tenants.

5. Snapshot plus changes without a gap

Change data capture (CDC) obtains changes through a supported source mechanism. It is not automatically a complete domain event contract: row changes may require interpretation, ordering and transaction-context handling. State which source position and identity let the consumer recognize progress and repetition.

Join a consistent baseline to subsequent changes using a known position or equivalent supported protocol. A bulk scan followed by an arbitrary later subscription can miss intervening updates; applying an old copied row after a newer event can regress the projection. Carry version/ordering guards, handle deletions and verify reconciliation under concurrent source writes.

Illustrative projection event:
 eventId, aggregateId, aggregateVersion, operation, occurredAt, payload
 apply only when the version/order policy permits
 record durable progress after committed projection work
 include tombstones/deletes and schema version handling

CDC can expose low-level row changes, while an outbox can publish intended domain events. Select based on what consumers need and which producer coupling is acceptable. Neither eliminates duplicate delivery. Retention and source-log cleanup must exceed expected outages/catch-up time or require a resnapshot plan.

6. Event time, windows and corrections

Event time describes when the business event happened; processing time describes when the pipeline handled it. A delayed event can arrive after a later business fact. Windowed aggregates need an explicit late-data and correction policy rather than treating arrival order as business order.

Choose what a watermark or lateness threshold means for your source and result contract. Closing a window is a policy decision, not proof that no earlier event can ever appear. Retractions/corrections, deduplication and replay must preserve the intended aggregate when historical data changes or arrives late.

Work the boundary through a failure

Suppose a five-minute event-time window closes at 10:05, but an event timestamped 10:03 arrives at 10:08. A watermark is a progress estimate used by the processing system; it does not prove that every older event has arrived. Choose an allowed-lateness and correction policy based on source disorder and the business result. Processing time tells when the worker handled the event, which answers a different question.

PolicyTrade-off
Drop beyond the boundFinal results arrive sooner, but omitted facts need a declared tolerance and a count.
Update/retract a published aggregateMore correct under late data, but consumers must support revisions and identities.
Send to a correction pathKeeps the fast path bounded; requires an owner and a deadline for corrections.

Replaying a source can resend an old fact after a newer update or deletion. Use source identity and a supported ordering/version rule at the projection boundary; arrival order alone can resurrect stale data. A tombstone must survive the replay/correction window or be replaced by an equivalent durable deletion rule. Test duplicate, delayed, reordered and deleted facts, then rebuild the projection from a known source position and compare business invariants.

7. Spring, AWS and pipeline tools

Use a pipeline with explicit source positions, repeat-safe writes and observable failure/quarantine state. On AWS, managed stream/search services can supply parts of ingestion and storage; framework connectors can manage checkpoints. Verify the actual retention, delivery, ordering and schema behavior rather than transferring guarantees between services.

For Spring consumers, keep local processing and acknowledgement boundaries clear. Separate a projection rebuild from external business effects, budget its load and support compatible schema evolution. If retained changes are insufficient for replay, establish another baseline instead of assuming an offset reset can reconstruct lost history.

8. Worked rebuild: change product search mappings

Rebuild order search while customers continue updating orders. Establish a source baseline and continuation position, populate an isolated target view, then apply subsequent changes with the chosen version/deletion rules. Compare critical identities, counts and sampled/domain-specific results before routing reads.

Exercise an update during the scan, a delete, duplicate events, old schemas and a lagging consumer. Confirm that no older copy overwrites a newer fact and no deleted/unauthorized resource leaks through the final access path. After cutover, retain an explicit rollback/reconciliation plan and observe freshness under real load.

Test duplicate events, out-of-order updates, deletion during snapshot, connector outage beyond retention and a corrected refund. A low consumer lag can coexist with a broken projection if bad records are silently discarded. Measure end-to-end source-to-query freshness and reconciliation differences.

9. Backfills and failure recovery

A healthy ingestion process can still produce wrong search: stale permissions, missing deletes, incompatible analysis or silent rejected documents can all escape a throughput graph. Inspect failure records, result correctness and source-to-view reconciliation.

Do not make a projection the accidental authority for an invariant merely because it is fast. Rebuilds, lag and retention gaps must have declared behavior, and expensive queries need admission/limits independent of source-write capacity.

CaseRequired policy
Backfill replays old side effectsSeparate projection rebuilding from email/payment execution.
Late event changes a closed reportDefine correction, versioning and re-publication semantics.
Source log expiresDetect the gap; resnapshot/reconcile rather than claiming continuous progress.
Deleted data reappearsPreserve delete/version ordering and purge derived/retained copies per policy.

Budget backfill I/O, source reads and write load separately from live traffic. Throttle and pause safely. Record source position and transformation version so a result can be reproduced and compared.

10. Interview ladder

FoundationalWhat is a projection?
A derived representation optimized for a use case, with its own freshness/update behavior and an identified authoritative source.
FoundationalEvent time versus processing time?
When the fact happened versus when the system handles it. Late delivery can make them far apart.
IntermediateWhy is snapshot plus CDC tricky?
A consistent relationship between snapshot contents and the change position is needed to avoid gaps/duplicates and stale overwrite races.
IntermediateDoes low consumer lag prove search is correct?
No. Records may be dropped, mis-transformed or invisible due to mappings/refresh. Check end-to-end freshness and reconciliation.
AdvancedWhat does a watermark guarantee?
It supports the engine’s configured event-time progress/late-data policy; it is not a universal assertion that older events cannot arrive.
AdvancedHow do you rebuild without an outage?
Build a versioned projection, combine snapshot/change capture correctly, validate/catch up, switch routing, and retain a tested rollback/freshness plan.
IntermediateWhy can a backfill lose an update even when every scan query succeeds?
The source changes while scanning. Without a baseline/change-position protocol and correct apply ordering, an intervening update can be missed or overwritten by an older copied row. Verify concurrent changes, deletes and versions.
AdvancedCan a retained log alone guarantee a correct projection rebuild?
Only under explicit assumptions about complete retained history, starting state, compatible interpretation, ordering and deduplication. Retention gaps or changed external enrichment can require another baseline and reconciliation.
