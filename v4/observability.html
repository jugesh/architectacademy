Observability · fundamentals to production judgment

Explain what happened to one request and one business outcome

Start with a customer asking where an order went. Build a useful evidence trail from logs to metrics, traces, asynchronous work, audit records and actionable alerts.

Technical definitionObservability is the ability to infer a system’s internal behavior from its emitted evidence. Logs describe events, metrics summarize measurements, traces connect timed operations, and audit records preserve accountable business/security actions.
Before you begin. Know the request contract and asynchronous delivery boundary. No monitoring platform is assumed; the lesson defines the signals before naming tools.

Learning outcome: Trace a customer outcome across HTTP, SQL and messaging without leaking secrets or creating unbounded telemetry cost.

1. The endpoint is green, but the customer has no order

The order API returns acceptance, messaging handles later work, caches serve copies and payments can be unknown. A generic health check cannot explain which state a customer encountered. Observability connects emitted evidence to hypotheses about those states; it does not make the evidence a substitute for the authoritative ledger.

Begin with one question: why did a paid order not ship? Identify the expected transitions and the evidence needed to distinguish publication failure, consumer failure and a remote unknown outcome. Add signals for those decisions rather than collecting every possible field without a question or retention policy.

2. Connect evidence to a customer question

Read this slowly: it establishes the distinction used in the implementation sections.

A metric summarizes measurements over dimensions; a log records an event; a trace relates timed operations through propagated context. A business ledger records durable facts needed for correctness and recovery. These are complementary. A trace can be sampled out, while a ledger entry still proves an accepted order exists.

A customer asks why a paid order never shipped. Start with order identity, verify payment state, locate the outbox event, inspect consumer receipt and quarantine state, then find the shipment transition. A trace may shorten the search but must not be the only evidence. Measure age from paid to shipped; HTTP success rate would count the earlier acceptance as healthy even while fulfillment is broken.

Check your understanding
FoundationalA correlation ID provides idempotency.
An ID that links logs does not coordinate concurrent writes or remember a prior result. Idempotency needs a recognized operation identity and durable atomic enforcement over the effect being protected.
IntermediateWhy not put every order ID in a metric label?
Unbounded identity creates unbounded series and cost. Use bounded labels for aggregate detection and controlled logs/traces/ledgers for individual diagnosis. Redact credentials and sensitive payloads.

3. Follow one operation before adding patterns

Carry this concrete operation through the later mechanisms.

An API returns 202 for order ord_7. The HTTP request succeeded at acceptance, but the order may still be waiting for a message consumer. A request ID finds the initial HTTP attempt, an order ID finds the durable business state, and an event ID follows the notification. A trace can show timings where it was recorded. These identifiers answer different questions; treating them as interchangeable makes both diagnosis and duplicate prevention unreliable.

4. Decide the questions evidence must answer

Define detection and investigation separately. Aggregate indicators should reveal customer-impacting delay or failure, while controlled identities let an operator investigate one journey. Specify retention, sampling, redaction and audit integrity according to purpose. A sampled trace cannot be the only record needed for business recovery.

Measure acceptance and completion over explicit eligible populations and deadlines. Pending work must not disappear from the indicator merely because it has not finished. Also observe the telemetry pipeline itself: exporter failures or dropped data can make an unhealthy service look quiet.

Functional requirements

  • Find an accepted order and its current lifecycle state.
  • Locate latency/error causes across services and workers.
  • Audit who changed a sensitive business state.

Targets and invariants

  • No credential/card payload in telemetry.
  • Bound metric cardinality and storage cost.
  • Illustrative accepted-to-fulfilled SLO measured separately from HTTP.
  • Essential audit evidence survives trace sampling.

A service-level indicator (SLI) is the actual measurement, such as the fraction of eligible orders completed within five minutes. An SLO is the target for that measurement. Specify eligible events, time windows, missing evidence and where timestamps come from. Otherwise teams can appear reliable by dropping failed requests from the denominator.

5. Use the right signal for each question

The customer question spans acceptance and completion. Choose which signal supplies each part of the evidence.

Metrics summarize measurements over bounded dimensions; logs describe events; traces relate timed execution through propagated context. Profiles can show where runtime resources are spent. A durable order/event ledger records facts required for correctness. Choose the signal that can establish the required evidence, and connect them with appropriately scoped identifiers.

For latency, align boundaries before comparing values: gateway time, local queue wait, handler execution and provider work can measure different intervals. Aggregate compatible histograms/distributions instead of averaging pod percentiles. Use bounded route/failure/version cohorts to expose skew without creating an unbounded metric series for every customer.

SignalGood questionLimitation
MetricsIs error rate rising? How old is the backlog?Aggregates do not reconstruct every request.
LogsWhat error/state transition was recorded?Unstructured text and missing context make joins difficult.
TracesWhere did elapsed time go across this path?Sampling or missing propagation can leave gaps.
Audit recordsWho approved this refund and what changed?Need deliberate integrity, access and retention policies.

A span is one timed operation in a trace, such as an HTTP handler or database call. Parent/child relationships explain a call path. Metrics summarize populations; labels split those populations into dimensions. A trace ID belongs in a log field or exemplar, not a metric label that creates one series per request.

6. Separate request, trace, and business identity

Signals become useful together when identities have precise meanings and lifetimes.

An order ID identifies a durable entity; an operation key recognizes one intended mutation; an event ID recognizes one fact; an attempt ID distinguishes one execution; a trace context connects recorded spans. A retry can have another trace while retaining the same business identity. Treating these as one identifier makes both diagnosis and duplicate protection ambiguous.

Propagate trace context across supported HTTP/message carriers and validate untrusted incoming metadata. Keep durable business references where recovery needs them even when traces expire. Context is not authority: a caller-supplied trace ID cannot grant access, prove a committed effect or dictate unlimited sampling cost.

{
  "service": "checkout", "route": "/orders/{id}",
  "requestId": "req_82", "traceId": "trace-example",
  "orderId": "ord_7", "eventId": "evt_91",
  "operation": "payment.confirm", "outcome": "SUCCEEDED",
  "durationMs": 42
}

Request ID identifies one ingress attempt; trace context connects observed execution; order/payment/event identity identifies durable business work. A retry may have a new request/trace while acting on the same payment intent. Using trace ID as an idempotency key confuses these different lifetimes.

W3C traceparent carries standard trace context between HTTP services. It is metadata, not authentication. Validate untrusted incoming context and apply your sampling policy. Do not accept a client-provided tenant or actor as authoritative simply because it is in a header.

7. Java context and structured logging

Logging context such as MDC is commonly associated with execution threads. An executor handoff, reactive pipeline or message boundary may lose it unless the supported framework/instrumentation captures and restores context. Cleanup matters too: reused threads must not retain another request’s identity.

ScopedValue provides scoped in-process value access under its runtime rules; it does not create spans, inject HTTP headers or decide sampling. Use instrumentation suited to the actual stack and verify propagation through custom executors and manually constructed clients. Business identity remains separate from logging convenience.

// Illustrative synchronous logging scope; use your logging API correctly.
MDC.put("requestId", validatedOrGeneratedId);
try {
  handler.process();
} finally {
  MDC.remove("requestId");
}
// This alone does NOT propagate context to another thread or message.

OpenTelemetry Context provides execution-scoped trace propagation abstractions; Spring Boot Micrometer Tracing integrates with supported instrumentation. Use configured HTTP client builders/instrumentation so outbound context is injected. Verify executor, Reactor and messaging boundaries explicitly.

Java ScopedValue provides lexically scoped immutable context binding in supported Java versions, useful for deliberate request-context design. It is not a logging adapter or distributed propagation protocol. MDC integration, instrumentation and task-boundary behavior still require an explicit strategy; do not assume replacing ThreadLocal changes every library.

8. Build metrics that stay affordable

Start with a precise numerator, denominator and measurement window. An acceptance SLI might count eligible valid requests durably accepted within a deadline. A completion SLI might count accepted orders reaching fulfillment within their target age. These populations differ; HTTP success alone can hide a broken asynchronous flow.

Choose bounded labels such as route template, operation class, release or controlled error category. Order IDs and raw URLs can create unbounded cardinality. Preserve essential audit/ledger facts separately when sampling or telemetry retention would discard individual execution details.

MeasurementUseful interpretation
HTTP latency + DB pool waitDistinguish slow execution from waiting for a connection.
Accepted-to-completed durationCapture asynchronous user experience.
Retry attempts / original commandsDetect amplification hidden by final success.
Outbox age / DLQ countFind durable work that is not progressing.

Sampling can keep traces affordable, but head sampling may miss rare errors and tail sampling has buffering/collector cost. Keep essential operational metrics and required audit outcomes independently of sampled traces.

9. Spring and AWS instrumentation map

Instrument inbound and outbound boundaries using configured Spring/Micrometer/OpenTelemetry support appropriate to the stack. Check custom HTTP clients, message attributes, executor handoffs and exporter failure behavior. Seeing one local span does not prove end-to-end propagation.

On AWS, map the complete collection/export path and its trust/retention rules. Telemetry is workload and cost too: bound payloads, redact credentials and avoid putting sensitive data in baggage that travels to unrelated services. Core business metrics and recovery records should not depend on every trace being retained.

Work the boundary through a failure

Trace one Spring request through HTTP, a durable message and a worker as separate execution spans. At each boundary, inject/extract the supported trace context using the instrumentation contract rather than inventing a private header. Keep the stable business operation identity as a separate correlation field: a retry, replay or reconciliation may have a new trace while still belonging to the same order.

SignalUseful fieldsAvoid
Trace spanOperation, dependency, outcome and bounded error classificationRecording secrets or complete customer payloads.
Structured logTrace/span correlation where present, business identity, release and state transitionAssuming thread-local context automatically crosses every executor boundary.
MetricLow-cardinality route/operation/outcome and latency distributionOrder IDs or trace IDs as unbounded metric labels.

Validate propagation with a controlled request whose producer completes before the consumer starts, and with a retry after the original request has ended. Check that the trace explains execution and the durable operation identity connects all attempts. Sampling can omit a trace; the business status and recovery record must still exist. A dashboard showing only successful sampled requests is not evidence that the unresolved tail is healthy.

10. Worked design: missing fulfillment investigation

Investigate a missing shipment using durable identity even when a sampled trace is unavailable.

For an accepted paid order, inspect the durable order state, its outbox event, relay evidence, consumer receipt/quarantine and fulfillment task. If the consumer rejected an unsupported schema, a healthy broker delivery graph does not mean shipping completed. The missing state transition explains the customer impact.

Repair the reader compatibly and replay under the original event identity with conditional/repeat-safe effects. Confirm the final fulfillment state and audit the recovery action. A trace may speed the investigation, but the procedure must still work when that trace was sampled out or expired.

11. Alerts and tricky interpretation

Alert on actionable customer symptoms and risk to a defined SLO, with a responsible owner and diagnostic path. Queue depth alone can fall because events moved to quarantine; CPU can be low while the database pool is exhausted. Combine outcome/age signals with evidence useful for the likely causes.

Error-budget burn compares observed bad-event consumption with the allowed budget over the selected window. Use appropriate short and long perspectives to distinguish sudden and sustained problems. Recovery proof needs restored business outcomes, not merely an alert returning green after its data pipeline failed.

TrapWhy it misleadsBetter practice

Alert on actionable symptoms and SLO risk, then attach diagnostic context. Error-budget burn compares observed bad-event consumption to the allowed budget. Use suitable short and long windows so fast incidents and slow persistent degradation are both visible. A runbook should name the invariant, safe mitigation and evidence needed to confirm recovery.

12. Interview ladder

FoundationalLogs versus traces?
Logs record events; traces connect timed operations across execution boundaries. Shared IDs can link them, but neither automatically replaces the other.
FoundationalWhat is an SLO?
A target over a defined SLI and measurement window, such as 99% of eligible accepted orders completing within five minutes.
IntermediateWhy did MDC disappear in an async task?
Thread-bound logging state does not automatically cross executor/reactive/message boundaries. Use scoped context capture/restore through supported mechanisms and test cleanup to avoid leakage.
IntermediateWhy not label metrics with order ID?
It creates a growing time series for every order and can expose sensitive identity. Put it in controlled logs/traces; metrics need bounded dimensions.
AdvancedHow do you investigate with no retained trace?
Use durable business state, event IDs, structured outcomes and audit records. Traces are sampled evidence, not the only recovery ledger.
AdvancedDoes ScopedValue replace distributed tracing?
No. It can carry scoped in-process state. HTTP/message propagation, span creation, sampling, logging integration and durable business identity are separate responsibilities.
IntermediateWhy can all HTTP requests succeed while the business SLO fails?
Acceptance may be prompt while asynchronous completion is delayed or stranded. Define and measure completion over accepted operations with explicit deadlines and pending-state handling.
AdvancedHow do you investigate when the trace is missing?
Follow durable business, operation and event identities through authoritative state, outbox/inbox and controlled outcome/audit records. Traces are sampled execution evidence, not the only recovery ledger.
