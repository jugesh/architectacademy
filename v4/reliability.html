Reliability · fundamentals to production judgment

Keep useful work recoverable when dependencies fail

Follow a checkout request through slow services, lost responses and process crashes. Derive deadlines, retries, idempotency, circuit breakers and recovery from those failures.

Technical definitionReliability is the ability to perform the required function correctly over time under stated conditions. Availability concerns whether the service can be used; recoverability concerns restoring correct operation and data after failure.
Before you begin. Understand an API contract, local transactions, and acknowledgement windows. We introduce each resilience mechanism before combining them.

Learning outcome: Assign retry and recovery ownership without confusing a timed-out request with a rolled-back business action.

1. A slow provider consumes the whole service

Checkout calls a pricing service and a payment provider. Usually both are fast. One morning the provider takes 30 seconds. Request threads and connections accumulate, queues grow, and eventually healthy status reads also fail. The first failure was remote slowness; the second was allowing that slowness to consume all local resources.

A distributed call has several outcomes: succeeded, definitely rejected, or unknown. If the response is lost after a capture, the caller cannot infer that capture failed. Recovery starts by representing uncertainty honestly rather than retrying every exception as a new business action.

2. Identify what must remain correct

Functional requirements

  • Accept checkout, expose payment status and reconcile uncertain attempts.
  • Keep status reads usable during provider problems.
  • Let operators recover failed/unknown work safely.

Targets and invariants

  • One capture per payment intent under the provider protocol.
  • Illustrative p95 status read below 200 ms.
  • Bound dependency concurrency and queue length.
  • Explicit RTO/RPO and durable intent retention.

An SLO is a measurable reliability target over a window. An invariant is a condition that must hold, such as not shipping an unpaid order. A fallback can preserve availability while violating an invariant if chosen carelessly. Serving a stale product description can be acceptable; fabricating payment success cannot.

3. First bound waiting time

A timeout bounds one wait. A deadline bounds the total useful time remaining for the request. Give downstream calls a share of the remaining budget, including connection acquisition, retry delay and response processing. A 500 ms client timeout with a 30-second backend call wastes work after the client has gone.

Example 800 ms total budget:
  validation/admission: 50 ms
  provider + any allowed retry: at most 500 ms
  persistence/response: 150 ms
  safety margin: 100 ms
Do not reset to a fresh 800 ms at every downstream hop.

Configure connect, pool-acquisition and response/read timeouts for the actual HTTP client. Cancellation may interrupt local waiting without stopping remote work. A timeout cannot roll back an already-committed provider action. Use durable state and status lookup to resolve it.

4. Retry an identity, not a new intent

A retry repeats an attempt because an earlier attempt did not produce a definitive outcome. Use it for selected transient failures only when repetition is safe. Exponential backoff spaces attempts; jitter spreads clients so they do not all retry on the same clock tick.

Set a maximum attempt count, total elapsed deadline and retry budget. A budget limits the extra load retries can create. If the gateway, application and SDK each make three attempts, a request can fan out to 27 leaf attempts. Pick an owner and account for other layers explicitly.

For a payment, persist a business intent and pass the same provider identity across retries if supported. Scope the client key by tenant/operation and reject a changed payload. Key retention must cover the replay horizon. A new random key per retry makes every attempt look like new intent.

5. Add circuit breaking and bulkheads

MechanismMeaningWhat it does not do
Circuit breakerTemporarily stop calls after evidence of dependency trouble; probe recoveryIt does not make a command idempotent.
BulkheadLimit resources assigned to one dependency/work classIt does not increase downstream capacity.
Rate limiterBound arrivals over timeIt does not necessarily bound concurrent slow work.
Bounded queueLimit waiting work and expose overloadIt does not solve sustained excess demand.

Circuit breakers usually move among closed, open and half-open states. Half-open probes should be bounded; releasing every waiting caller when one probe succeeds can overwhelm a recovering dependency. Choose thresholds from real traffic, not arbitrary defaults.

Separate payment-call concurrency from status-read resources. Reject early with a documented response when a budget is exhausted. Keep fallback behavior visible in metrics; a service can report 200 while returning unusable substitute data.

6. Spring and AWS implementation boundaries

Resilience4j offers independent retry, circuit-breaker, bulkhead and rate-limiter components. Decorator order changes what is counted and retried: ask whether the breaker sees every attempt or one logical call. Test the actual configuration rather than assuming a list of annotations composes correctly.

// Teaching pseudocode: explicit semantic order, not a library API signature.
requireRemainingDeadline();
return boundedPaymentConcurrency.execute(() ->
    retryBudget.executeSafeAttempts(() ->
        breaker.call(() -> provider.capture(stableIntentId, request))));
// HTTP client timeouts and durable UNKNOWN-state recovery remain separate.

Use Spring transaction management for durable intent and outcome updates, with remote calls outside long-held DB transactions. RDS holds the ledger; SQS can schedule retry/reconciliation work; Step Functions can coordinate explicit states when its execution model fits. ALB/API Gateway limits and SDK retry policies must be included in the end-to-end budget.

A multi-AZ deployment addresses a failure domain; it does not protect against a bad release, corrupt writes or region-wide dependency failure. Test backup restoration and failover routing, and define who can initiate recovery.

7. Worked design: provider outage during checkout

Persist a payment attempt as PENDING and expose its status resource. A worker calls the provider with the stable attempt identity. Success becomes SUCCEEDED; a definitive decline becomes DECLINED; transport ambiguity becomes UNKNOWN. A reconciler queries the provider or handles authenticated callbacks. Each transition is conditional so stale callbacks cannot overwrite a later terminal outcome.

While the breaker is open, accept durable intents only if the product permits delayed processing and capacity is available; otherwise reject before promising acceptance. Show “payment processing” to the customer, never “paid” based on a timeout fallback. Status reads remain on a protected local path.

Recovery is paced. Limit reconciliation concurrency and prioritize old unknown attempts. Compare local and provider records, quarantine discrepancies, and retain operator evidence. The warehouse acts only on a durable paid transition through an outbox. Replaying a recovery task must not create another payment or shipment.

8. Failure drills and recovery evidence

DrillAssertion
Kill worker immediately after provider captureAttempt becomes resolvable with original identity.
Provider stays slow for an hourPools/queues stay bounded; status reads remain usable.
Duplicate success after refundConditional state/version policy prevents regression.
Breaker recovers at traffic peakProbe and release policy avoids a new surge.
Restore ledger backupMeasured RPO/RTO meet the declared recovery contract.

Track timeout rate, attempt count, retry amplification, breaker state, rejected concurrency, oldest unknown age and business discrepancy count. A green CPU chart is insufficient if payments remain unknown for hours.

9. Interview ladder

FoundationalTimeout versus failure?
A timeout means the caller did not receive a result in time. The remote side effect may have completed, so classify the outcome as unknown when appropriate.
FoundationalCircuit breaker versus retry?
Retry performs another attempt. A circuit breaker suppresses attempts when a dependency appears unhealthy and probes for recovery. Their composition must not amplify overload.
IntermediateWhy use both a rate limit and a concurrency cap?
A rate limit bounds arrivals per time; slow operations can still accumulate. A concurrency cap bounds simultaneous resource use.
IntermediateWhat makes a fallback safe?
Its result and side effects must preserve the operation’s business contract. Stale display data can be acceptable; invented payment success is not.
AdvancedWhat if the provider has no key or status inquiry?
Local coordination cannot prove a single remote effect across arbitrary lost-response windows. Require a stronger protocol or explicitly accept bounded retry/manual-settlement risk.
AdvancedHow do you prevent recovery from causing another outage?
Bound probes, retry/reconciliation rate, queue drains and concurrency. Keep resource headroom and separate critical paths, then test a prolonged outage and synchronized recovery.
