Scalability · fundamentals to production judgment

Grow an application without moving the bottleneck blindly

Follow an order service from one instance to a load-balanced system. Learn to measure demand, find the constraint, and preserve correctness while adding capacity.

Technical definitionScalability is a system’s ability to handle increasing workload by adding resources while maintaining acceptable performance, cost, and correctness. Capacity is how much it can currently sustain; elasticity is how quickly resources adapt to changing demand.
Before you begin. Know what an HTTP request and database query are. The API requirements section explains latency, throughput, and invariants. No Kubernetes knowledge is required.

Learning outcome: Explain why adding application replicas helps some workloads and hurts others, then propose a measured scaling plan.

1. One service meets a sale-day spike

Our shop begins with one Java process and one SQL database. At 50 requests per second, orders respond quickly. During a sale, traffic reaches 1,000 requests per second. Requests wait; customers retry; more work arrives. A larger queue does not create processing capacity—it mostly delays the moment callers discover overload.

Before adding replicas, ask where time is spent. If CPU is saturated, more application compute may help. If every request waits for a slow query, more replicas can send even more competing queries to the same database. The visible symptom is slow HTTP; the limiting resource may be somewhere else.

A bottleneck is the resource that limits useful throughput for the current workload. It can shift after every improvement. Treat scaling as a sequence of measured changes rather than one architecture diagram.

2. State demand and success first

Functional requirements

  • Accept orders and expose status.
  • Serve product reads and stock checks.
  • Keep already-accepted work recoverable.

Targets and invariants

  • Illustrative peak: 1,000 requests/s, 80% reads.
  • Illustrative read p95 below 200 ms.
  • No duplicate order or negative inventory.
  • Continue after losing one application instance.

These are example targets, not universal defaults. Measure payload size, read/write mix, dependency fan-out, and burst duration. A peak lasting one second may be buffered; a peak lasting an hour needs sustainable service capacity. Distinguish offered traffic, admitted traffic, and successfully completed business work.

3. Connect throughput, latency, and concurrency

Throughput counts completed work per unit time. Latency measures elapsed time for an operation. Concurrency counts work in progress. At steady state, Little’s Law relates averages: in-flight work ≈ arrival rate × average time in the system. At 1,000 requests/s and 0.2 s average response time, roughly 200 requests are in flight.

That estimate does not set your thread-pool or database-pool size. Some requests wait without holding threads; one request can make several downstream calls; tail latency and bursts differ from averages. Measure queue wait separately from execution time so a fast handler does not hide an overloaded admission queue.

Measure per route:
  admitted/completed requests per second
  p50 / p95 / p99 response time
  active requests and queue wait
  CPU, GC pauses, DB pool wait, dependency latency
  rejection and retry rates

A percentile describes a distribution: p99 of 800 ms means 99% of measured observations are at or below 800 ms for that window/population. Do not average per-instance percentiles to obtain a global percentile.

4. Vertical first, then horizontal when justified

ChoiceWhat changesConstraint
Vertical scalingGive one instance more CPU/memory.Simple but finite; failure domain remains large.
Horizontal scalingRun more application instances.State, shared dependencies and load distribution must support it.
PartitioningDivide data/work by a key.Cross-partition operations and hot keys become harder.

Horizontal scaling works best when any healthy instance can process a request. Keep durable order state in the database rather than a Java field. A local cache can still exist, but its contents may differ between instances. Sticky sessions can ease a migration; they do not make session state survive instance loss.

A load balancer routes traffic; health checks determine eligible targets. Readiness should indicate that the instance can handle intended traffic, while liveness answers whether restarting may help. Marking every instance unready for a short shared dependency outage can amplify the outage.

5. Implement a bounded scaling change

In Spring Boot, configure bounded HTTP/dependency timeouts and monitor the data-source pool. With an ALB and ECS service, distribute tasks across appropriate failure domains and use target tracking on a metric related to useful load. In EKS, HPA changes pod replicas; node provisioning and scheduling are separate steps. Neither makes RDS write capacity infinite.

Illustrative capacity guard:
  8 app instances × 15 DB connections = 120 possible connections
  Reserve DB headroom for operations, jobs, and failover.
  Scaling to 20 instances without a pool policy → 300 connections.
  Verify throughput under contention before increasing either limit.

Use rolling delivery with graceful shutdown: stop admitting new requests, drain in-flight work, then terminate. Background workers need leases or queue acknowledgement rules so interrupted work can be reclaimed. Configure deployment surge and replica limits against shared-resource budgets.

Autoscaling reacts after measurement and startup delay. Pre-scale known events and keep headroom where startup is slow. For queue workers, backlog per worker and oldest-message age may be better signals than CPU alone.

6. Choose the next intervention

EvidenceInterventionCheck afterward
App CPU saturated; database has headroomMore/faster app compute, reduce expensive CPU workCPU/request and latency under the same load.
Slow query dominatesIndex/query/model correctionQuery plan, lock time, write overhead.
Repeated read workCache or read modelFreshness contract and miss-path capacity.
Remote service limitsConcurrency cap, queue, negotiated quotaQueue age and completed outcomes.
One tenant/key dominatesFair admission or split workloadPer-tenant impact and hot partition behavior.
A cache hit rate of 95% does not prove resilience: if cache loss sends all reads to the database, the miss path may need 20 times its usual capacity. A read replica may help reads but introduces freshness and failover considerations.

7. Worked design: twenty times the traffic

The baseline service sustains 100 requests/s. The target is 2,000. Profile first: product reads dominate and run the same indexed lookup; checkout writes are a small share. Cache public product descriptions with a documented freshness bound, keep stock/price validation authoritative at checkout, and separate admission budgets for browsing and purchase.

Load-test the app fleet against a representative database. Increase replicas only while useful throughput improves. Apply a per-route concurrency cap to prevent the browsing surge from consuming every DB connection. Queue noncritical receipt work after a durable outbox commit. Keep the order command synchronous only to its bounded acceptance point.

Test loss of one app instance and a cold cache at peak. If the database cannot sustain the cold path, limit refill concurrency, return permitted stale data or shed browsing load. Verify duplicate retries do not create extra orders. Success is meeting latency and correctness targets during these transitions, not reaching a replica count.

8. Tricky cases and operations

CaseWhy it happensResponse
All replicas start togetherEmpty local caches and connection establishment spikeStagger rollout; bound refill/connections.
CPU low, requests slowWaiting for DB locks or remote connectionsInspect wait metrics and traces before scaling CPU.
Scale-in kills active workTermination occurs before drain completesDrain requests, reclaim durable jobs, test interruption.
Average latency looks fineA small customer segment suffers extreme waitsBreak down route/tenant cohorts without unbounded metric labels.

Keep a baseline cost per completed request. More replicas can increase cost while reducing throughput if contention dominates. Use a soak test to find memory leaks and backlog growth that a five-minute spike test misses.

9. Interview ladder

FoundationalLatency versus throughput?
Latency measures time per operation; throughput measures completed work per time. High concurrency can raise throughput until contention makes both latency and efficiency worse.
FoundationalDoes a load balancer make a service scalable?
It distributes traffic across targets. The targets and their shared dependencies must have capacity, and durable state must survive routing changes.
IntermediateWhy can HPA make a database incident worse?
More pods can create more connections and concurrent queries against the same constrained database. Bound shared-resource use and address the limiting query/lock before raising replicas.
IntermediateHow do you scale a stateful application?
Identify which state must survive instance loss. Move or replicate it with an appropriate ownership/durability model, or partition ownership deliberately. Routing affinity alone is not durable state management.
AdvancedHow would you prove a 20× scaling claim?
Use representative data and load, explicit SLOs, steady-state and burst tests, failure injections, and correctness assertions. Report offered/admitted/completed work, saturation, and cost; record the first bottleneck.
AdvancedWhat if one key remains hot after sharding?
More shards do not split one unsplittable operation. Consider caching, aggregation, salting with merge semantics, a single-writer model, or a product limit, according to the invariant.
