Scalability · fundamentals to production judgment

Grow an application without moving the bottleneck blindly

Follow an order service from one instance to a load-balanced system. Learn to measure demand, find the constraint, and preserve correctness while adding capacity.

Technical definitionScalability is a system’s ability to handle increasing workload by adding resources while maintaining acceptable performance, cost, and correctness. Capacity is how much it can currently sustain; elasticity is how quickly resources adapt to changing demand.
Before you begin. Know what an HTTP request and database query are. The API requirements section explains latency, throughput, and invariants. No Kubernetes knowledge is required.

Learning outcome: Explain why adding application replicas helps some workloads and hurts others, then propose a measured scaling plan.

1. One service meets a sale-day spike

Keep the contract fixed; change the workload and follow resource use.

Keep the API contract from the previous lessons unchanged: the shop accepts an order, enforces inventory rules and lets the caller recover a lost response. Now increase the number of callers. Scaling should preserve those promises under more demand. It is not simply running the same code on more machines, because those machines may compete for the same database, lock or provider quota.

Follow one request before following a thousand. It executes some instructions, waits for a database connection, runs statements and possibly waits for another service. Each stage consumes a different resource. CPU capacity helps execution; a query improvement reduces database work; a connection limit bounds admitted pressure. Requests look equally slow from outside even when the required interventions differ.

The goal is useful completed work at an acceptable latency and cost. A system receiving twice as many HTTP attempts because clients keep retrying has not doubled business throughput. We will distinguish demand from admission and completion, locate the current constraint, then change one part of the system and measure again.

2. Account for where one request spends time

Read this slowly: it establishes the distinction used in the implementation sections.

A service is a collection of finite resources. CPU executes instructions, connections carry requests, memory holds active work, and storage serves reads and writes. Throughput is completed work per unit time. Latency includes execution and waiting. Increasing one resource helps only when it limits the operation or removes work from the limiting resource.

At 100 requests per second and 0.2 seconds average time in the measured system, about 20 requests are present on average in steady state. If a dependency slows to one second at the same admitted arrival rate, that becomes about 100. Those requests occupy memory and connections even if CPU is quiet. Once a limit is reached, waiting grows further. This feedback explains why replicas, bounded queues and admission control must be considered together.

Check your understanding
FoundationalDoubling replicas doubles capacity.
Only when the divided work and shared dependencies allow it. Two application replicas can contend on the same database lock or overwhelm the same connection limit. Measure useful throughput and tail latency after each change.
IntermediateWhy might autoscaling make a database incident worse?
Each new replica can open more database connections and add retries. If the database is already the constraint, scaling callers increases pressure. Cap fleet-wide concurrency and preserve headroom before scaling.

3. Follow one operation before adding patterns

Carry this concrete operation through the later mechanisms.

Imagine ten customers arrive together. If each request needs 100 ms of CPU and there is one available CPU core, they cannot all finish in 100 ms. Some work must wait. If most time is instead waiting for a remote response, there may be spare CPU but exhausted connections. Both look like a slow API from outside, yet need different fixes. First classify service time and waiting; then measure which resource is scarce. Only after that does choosing a larger instance, another replica or a queue become meaningful.

4. State demand and success first

Describe the demand and allowed degradation before selecting capacity.

Write a workload description before a machine count. For the shop, specify reads versus writes, route mix, average and large payloads, requests per second, burst duration and how much work each request triggers. One list request returning 25 rows is not equivalent to a checkout modifying five inventory items. A total RPS number without that mix is difficult to reproduce or use for capacity planning.

Next separate a target from a forbidden outcome. A read p95 target means a stated fraction of eligible observations must meet the latency bound over a defined window. No negative inventory remains an invariant even when the latency target is missed. An instance-loss requirement defines a condition under which the system must still meet its stated operating contract; it is not satisfied merely because a second instance exists.

Finally define the overload policy. If the system cannot sustainably process the offered work, it must bound waiting, reject/defer some requests, reduce optional work or provide a permitted degraded response. Choose which operations receive scarce capacity first. Durable order acceptance and optional catalog browsing need not have identical admission rules.

Functional requirements

  • Accept orders and expose status.
  • Serve product reads and stock checks.
  • Keep already-accepted work recoverable.

Targets and invariants

  • Illustrative peak: 1,000 requests/s, 80% reads.
  • Illustrative read p95 below 200 ms.
  • No duplicate order or negative inventory.
  • Continue after losing one application instance.

These are example targets, not universal defaults. Measure payload size, read/write mix, dependency fan-out, and burst duration. A peak lasting one second may be buffered; a peak lasting an hour needs sustainable service capacity. Distinguish offered traffic, admitted traffic, and successfully completed business work.

5. Connect throughput, latency, and concurrency

Define one measurement boundary, then derive average work and inspect waiting.

Begin with a stable boundary: from admitting a request until returning its result. Throughput counts completions per second, latency measures elapsed time, and concurrency counts work currently inside that boundary. Little’s Law relates long-run averages in a stable system: average work present equals average arrival rate multiplied by average time present. It does not predict a particular tail percentile.

At 1,000 admitted requests/second and 0.2 seconds average time, about 200 requests are present on average. If a dependency slows and average time becomes one second while admissions remain at that rate, the average approaches 1,000 under stable conditions. Those waits retain memory and other resources. If arrivals continue to exceed completions and the queue keeps growing, the steady-state assumptions no longer describe a finite stable queue.

Then separate queue time from execution. A controller timer beginning after admission may look healthy while callers spend most of their deadline in a gateway or local queue. Record the boundaries of every timer, use compatible latency distributions across instances, and examine route/cohort differences. An average of per-pod p99 values is not the fleet’s p99.

Read a load curve as evidence. At low load, more admissions produce more completions with little waiting. Near saturation, waiting rises faster than useful throughput. Beyond that point, added attempts can reduce useful work through retries, contention or garbage collection. Repeat the measurement after each proposed change: the limiting resource can move.

Measure per route:
  admitted/completed requests per second
  p50 / p95 / p99 response time
  active requests and queue wait
  CPU, GC pauses, DB pool wait, dependency latency
  rejection and retry rates

A percentile describes a distribution: p99 of 800 ms means 99% of measured observations are at or below 800 ms for that window/population. Do not average per-instance percentiles to obtain a global percentile.

Healthy stable operation1,000/s × 0.2 sAbout 200 requests present on average.
Stable slower dependency1,000/s × 1 sAbout 1,000 present; waiting consumes resources.
Arrivals persistently exceed completionsBacklog grows over timeDo not describe an unbounded growing queue as a finite steady state.

6. Vertical first, then horizontal when justified

Choose which resource or ownership boundary actually changes.

Vertical scaling changes the resources available to one instance. It can be an effective first step when a larger instance removes a measured CPU or memory limit without changing ownership. It remains finite and does not by itself make the instance survive failure. Horizontal scaling adds instances, which helps only if requests can be distributed and shared dependencies can support the resulting work.

Now let two application instances accept orders. A Java map of accepted operation keys on instance A is invisible to B and disappears if A fails. A local session also follows that ownership problem. Move durable authority to an appropriate shared store or design explicit partition ownership. “Stateless application” means the instance does not privately own the durable state needed to preserve the contract; it does not forbid temporary local caches.

A load balancer distributes eligible traffic but cannot split every coordination point. Both instances may still update the same popular SKU or use the same database writer. Partitioning can distribute different keys, at the cost of cross-partition work, rebalancing and skew. A single last-item claim still needs a coordinated authoritative decision. Choose the scaling dimension from the actual constraint.

ChoiceWhat changesConstraint
Vertical scalingGive one instance more CPU/memory.Simple but finite; failure domain remains large.
Horizontal scalingRun more application instances.State, shared dependencies and load distribution must support it.
PartitioningDivide data/work by a key.Cross-partition operations and hot keys become harder.

Horizontal scaling works best when any healthy instance can process a request. Keep durable order state in the database rather than a Java field. A local cache can still exist, but its contents may differ between instances. Sticky sessions can ease a migration; they do not make session state survive instance loss.

A load balancer routes traffic; health checks determine eligible targets. Readiness should indicate that the instance can handle intended traffic, while liveness answers whether restarting may help. Marking every instance unready for a short shared dependency outage can amplify the outage.

7. Implement a bounded scaling change

Budget the whole fleet, including reaction delay, failure and rollout.

Convert the measured limit into budgets across the fleet. If eight instances may each open fifteen database connections, they can request 120 connections collectively, before jobs, operations or rollout surge. Twenty instances with the same setting can request 300. Each local pool can be within its configured limit while the database is overwhelmed by the aggregate.

In Spring, measure acquisition waits separately from query time and choose bounded dependency waits. In Kubernetes, the Horizontal Pod Autoscaler (HPA) adjusts desired pod replicas from configured metrics; scheduling and obtaining node capacity are further steps. A CPU-based policy may not react appropriately when the service is waiting on database locks with low CPU. Select a metric that represents the workload and verify its behavior under failure, not just a clean traffic ramp.

Autoscaling has a control-loop delay: observe demand, decide, provision/schedule, start, initialize and become ready. Keep enough headroom or pre-scale known bursts when that delay exceeds the workload’s tolerance. Include rollout surge in connection/capacity budgets. During scale-in, drain active requests and reclaim durable queued work; killing a process cannot be the normal completion signal for an accepted order.

Illustrative capacity guard:
  8 app instances × 15 DB connections = 120 possible connections
  Reserve DB headroom for operations, jobs, and failover.
  Scaling to 20 instances without a pool policy → 300 connections.
  Verify throughput under contention before increasing either limit.

Use rolling delivery with graceful shutdown: stop admitting new requests, drain in-flight work, then terminate. Background workers need leases or queue acknowledgement rules so interrupted work can be reclaimed. Configure deployment surge and replica limits against shared-resource budgets.

Autoscaling reacts after measurement and startup delay. Pre-scale known events and keep headroom where startup is slow. For queue workers, backlog per worker and oldest-message age may be better signals than CPU alone.

8. Choose the next intervention

Make one hypothesis, change one constraint and compare the same workload.

Use the evidence below to choose one hypothesis and a falsifiable intervention. If a query dominates latency, adding callers can increase the same expensive work. An index may reduce it, but increases write/storage cost and needs representative plan evidence. If repeated public reads dominate, caching may reduce source work, provided the miss path and freshness policy remain safe.

Keep correctness in the comparison. A read replica can distribute permitted stale reads but cannot automatically serve a read-your-writes promise. A queue can defer work but cannot make sustained arrivals above processing capacity disappear. A quota increase can help only if the downstream system really supplies more useful capacity. After the change, compare the same workload, data distribution, useful completion rate and latency boundaries.

EvidenceInterventionCheck afterward
App CPU saturated; database has headroomMore/faster app compute, reduce expensive CPU workCPU/request and latency under the same load.
Slow query dominatesIndex/query/model correctionQuery plan, lock time, write overhead.
Repeated read workCache or read modelFreshness contract and miss-path capacity.
Remote service limitsConcurrency cap, queue, negotiated quotaQueue age and completed outcomes.
One tenant/key dominatesFair admission or split workloadPer-tenant impact and hot partition behavior.
A cache hit rate of 95% does not prove resilience: if cache loss sends all reads to the database, the miss path may need 20 times its usual capacity. A read replica may help reads but introduces freshness and failover considerations.

9. Worked design: twenty times the traffic

Demonstrate the target under the cold path and lost capacity, not just healthy peak.

Start with the twenty-times claim and make it testable. Suppose the baseline completes 100 business operations/second under a recorded mix; the target is 2,000 under that same mix. Keep payloads, data size, hot keys and completion criteria explicit. A test using only cached status reads cannot validate a target that includes concurrent checkouts.

Assume measurement shows public product reads dominate. Reuse permitted product descriptions while checkout still validates authoritative price and stock. Separate browsing and order admission so optional reads cannot consume every database connection. Move receipts after a durable outbox handoff. Then increase application replicas while checking that useful throughput still improves and the shared database retains safe headroom.

Now remove one failure-domain share of capacity and lose the cache. A system sized exactly for the warm healthy path may fail both tests. Bound refill/fallback concurrency, serve stale data only where the contract allows it, and shed lower-priority work before accepted orders become unrecoverable. Verify database invariants and duplicate-command recovery alongside latency. Report the first limiting resource and the operating margin, not merely the final replica count.

Warm cache, healthy fleetLose cacheBounded refill/source load; allowed freshness; useful checkout completions.
All instances availableLose one failure-domain shareLatency/rejection under the failure contract; no lost accepted work.

10. Tricky cases and operations

Examine transitions and sustained behavior as well as averages.

Transitions often matter more than the comfortable steady state. A rollout can create many empty local caches at once. A recovered dependency can receive a synchronized backlog. Scale-in can concentrate hot traffic on fewer instances. Test these changes deliberately because a five-minute healthy peak test may not expose them.

Keep a cost measure tied to useful completions and inspect longer runs. If memory, backlog age or retries keep rising under supposedly stable load, the system has not demonstrated sustainable capacity. Fleet averages can hide one slow route or tenant cohort; choose bounded diagnostic dimensions rather than creating a metric series for every customer ID.

CaseWhy it happensResponse
All replicas start togetherEmpty local caches and connection establishment spikeStagger rollout; bound refill/connections.
CPU low, requests slowWaiting for DB locks or remote connectionsInspect wait metrics and traces before scaling CPU.
Scale-in kills active workTermination occurs before drain completesDrain requests, reclaim durable jobs, test interruption.

Keep a baseline cost per completed request. More replicas can increase cost while reducing throughput if contention dominates. Use a soak test to find memory leaks and backlog growth that a five-minute spike test misses.

11. Interview ladder

FoundationalLatency versus throughput?
Latency measures time per operation; throughput measures completed work per time. High concurrency can raise throughput until contention makes both latency and efficiency worse.
FoundationalDoes a load balancer make a service scalable?
It distributes traffic across targets. The targets and their shared dependencies must have capacity, and durable state must survive routing changes.
IntermediateWhy can HPA make a database incident worse?
More pods can create more connections and concurrent queries against the same constrained database. Bound shared-resource use and address the limiting query/lock before raising replicas.
IntermediateHow do you scale a stateful application?
Identify which state must survive instance loss. Move or replicate it with an appropriate ownership/durability model, or partition ownership deliberately. Routing affinity alone is not durable state management.
AdvancedHow would you prove a 20× scaling claim?
Use representative data and load, explicit SLOs, steady-state and burst tests, failure injections, and correctness assertions. Report offered/admitted/completed work, saturation, and cost; record the first bottleneck.
AdvancedWhat if one key remains hot after sharding?
More shards do not split one unsplittable operation. Consider caching, aggregation, salting with merge semantics, a single-writer model, or a product limit, according to the invariant.
IntermediateCan Little’s Law choose the database pool size?
No. It relates average work over a stated stable system boundary. HTTP requests can wait without holding a database connection and can issue multiple queries. Derive the database budget from its own workload, useful execution concurrency and fleet-wide capacity; then measure acquisition, query and lock waits.
AdvancedA 95% cache hit ratio looks excellent. Why test cache loss?
Normal misses are only 5% of read demand. Losing the cache can send roughly 20 times that usual miss traffic toward the source before refresh amplification. Bound fallback/refill and choose permitted stale responses or load shedding; do not assume application autoscaling supplies database capacity.

12. Further reading and practice

Carry the measured database work into the storage lesson.

Read HPA and cloud scaling documentation as control-loop behavior, not as a promise that replicas will appear instantly. Check the selected metric, stabilization, limits, startup/readiness and downstream capacity. Use the capacity guide to calculate an initial hypothesis, then replace assumptions with measurements.
