Migration & Modernization · fundamentals to production judgment

Change the system while old and new versions coexist

Follow an overlapping-version change from inventory and compatibility through backfill, cutover and the point where rollback needs data reconciliation.

Technical definitionA migration is a controlled transition of behavior, state or ownership between implementations. Correctness depends on compatibility during overlap, reconciliation of changes and a defined rollback or forward-repair boundary.
Before you begin. Read mixed versions, transaction boundaries and recovery.

Learning outcome: Plan schema, runtime, database and service migrations with evidence-based cutover gates.

1. Inventory the change before moving anything

Begin with consumers, data writers, scheduled jobs, runtime dependencies, message schemas and operational tooling. A Java upgrade changes more than a compiler target; a database migration changes more than a connection string. Capture the current contract and failure behavior so improvements do not silently break existing consumers.

Separate reversible routing/configuration changes from irreversible or difficult-to-reverse data changes. Define which source owns each fact at every stage. A rollback plan that says “point back to the old database” is incomplete if new writes exist only in the target.

2. Expand, migrate, verify, contract

Suppose full_name becomes given_name and family_name. Add nullable new columns first and deploy readers that tolerate incomplete backfill. Define the transformation honestly: many names cannot be split reliably by spaces. Backfill in bounded, restartable batches using stable progress identity and conditional updates so a concurrent edit is not overwritten.

During overlap, define which representation is authoritative and how old writers remain compatible. When all readers and writers are upgraded, verify reconciliation and stop the old path. Remove old columns only after the rollback/support window ends. If two representations are stored, their consistency is a protocol to own, not an incidental implementation detail.

Do not treat a successful deployment as permission to drop old columns immediately. Old instances, batch jobs, delayed messages and rollback paths may still require them.

3. Java and Spring upgrade sequence

Inventory application server support, bytecode targets, libraries, reflection, removed APIs, build plugins, agents, TLS providers and test tooling. Choose a supported target combination using the actual vendor support matrix. Upgrading Spring and changing the deployment runtime at once can make failures harder to isolate; stage changes where compatibility allows.

Compile and test business paths, integration protocols, serialization, security, database behavior and startup/shutdown. Benchmark representative CPU, allocation, latency and memory with comparable limits. A lower GC pause in a microbenchmark does not prove a safe production migration. Canary the new runtime, retain compatible images and define observable rollback triggers.

If an application server does not support the required JDK, evaluate a supported framework/JDK combination, a server upgrade or moving the application to an independently supported runtime. Do not assume putting newer bytecode in a container makes the host application server support it.

4. Database copy and catch-up

An online migration usually needs a consistent baseline plus a position from which subsequent changes can be captured. A bulk copy without a matching change stream can miss or reorder updates during the scan. Preserve deletions, transaction/order semantics required by the target and schema transformations. Measure lag by relevant source positions and business freshness, not merely whether a process is running.

Verify counts, keys, sampled/full checksums where meaningful, query results and critical invariants. Define a controlled write-ownership switch using fencing or a brief write pause when necessary. “Zero downtime” must specify what readers and writers can observe and whether bounded retries or deferred acceptance are allowed.

5. Extract a service with a strangler route

Choose one cohesive behavior and place an explicit interface around it. Route a limited operation or tenant population to the new implementation while retaining ownership rules. Shadow reads can compare outputs if authorization, side effects and sensitive data are controlled. Shadow writes to real business providers are unsafe without a separate harmless environment.

Avoid long-lived uncontrolled dual writes. If local commit and remote publish are required, use a durable handoff and reconciliation protocol. Move data ownership deliberately; leaving every service able to mutate the same tables undermines independent boundaries. Retire old routing and jobs only when no supported path still depends on them.

6. Worked cutover: new account and new database cluster

Assume one authoritative writer and a target cluster in a new account. Establish identity/network/secret access, copy a consistent baseline, capture changes, apply idempotently and compare critical records. Rehearse full recovery before scheduling cutover. Freeze schema changes or handle them through an explicit migration-compatible process.

At cutover, stop or fence source writers, record the final change position, wait for target application and invariant checks, then enable the target writer and redirect traffic. If the target is unhealthy before accepting writes, routing back may be straightforward. After target-only writes begin, rollback requires reverse synchronization, a bounded write pause plus merge/reconciliation, or forward repair. Never enable both writers merely to reduce downtime.

Gate completion on business paths, queue consumers, scheduled jobs, access control and telemetry in the new account. Record unresolved differences and retain the source according to the recovery plan. Cross-account DNS success does not prove that IAM, KMS, network policies and background jobs all function.

7. Worked plan: choose a bounded write pause and defend it

Assume the business permits a short, explicitly bounded write pause while reads remain available under a stated freshness contract. The source database has one writer; the target receives a baseline plus change capture. A bounded pause can simplify the final ownership transition compared with independently writable copies. It is a product/operating decision, not an automatically acceptable shortcut.

The key rollback boundary is the first target-only fact the source does not have or cannot interpret. Before that point, reverting controlled routing may be straightforward. After it, the plan must account for reverse synchronization, transformed data, conflict ownership and external effects. Never enable both writers merely to make the service appear available.

Bound the pause by evidence and a stop condition, not optimism. If final catch-up or validation exceeds the allowed interval, follow the rehearsed abort/recovery path. Keep critical comparisons restartable and ensure ongoing reads do not produce a misleading promise of current writable state.

This plan differs from a release that only changes binaries, but both require mixed-version compatibility. Record exactly which operations were deferred/rejected, which facts moved, and how accepted work survived. Completion means the intended journeys and recovery posture work in the target environment, not merely that a new connection string succeeds.

8. Migration interview

IntermediateWhy is dual write not an atomic migration strategy?
Two independent writes can fail separately. Define durable capture, ordering, retries and reconciliation, or constrain the transition so one authority remains clear.
AdvancedWhen does rollback become a data problem?
As soon as the new path commits facts the old path lacks or cannot interpret. Define that boundary before cutover and prepare reverse catch-up or forward repair with business reconciliation.
