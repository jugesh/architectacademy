Agree on behavior through concrete examples

Turn an ambiguous cancellation request into shared rules, Given–When–Then examples and executable acceptance checks. Learn where Cucumber helps and where deeper tests are still needed.

Technical definitionBehavior-driven development is a collaborative approach to discovering, expressing and checking valuable system behavior through concrete examples. Executable specifications can preserve that agreement; a feature file or test framework alone does not create it.
Before you begin. Know the idea of an API request and a stored order. Read the early sections without any testing-framework experience; the Java acceptance example follows the same cancellation rules as TDD.

Learning outcome: Lead a focused example conversation, write readable scenarios, choose an automation boundary, and explain what a passing acceptance example does and does not guarantee.

1. Begin with an ambiguous request

The story says: “As a customer, I want to cancel an order so I can stop an unwanted purchase.” A developer assumes cancellation is allowed until shipment. A warehouse operator considers a claimed order too late. QA expects repeated requests to succeed harmlessly. All three can build or test different versions of the same sentence.

BDD starts by exposing those differences before the implementation makes one assumption expensive. Think of agreeing on a delivery address before driving: faster driving does not fix a different destination. Bring a person who understands the business rule, a developer who understands implementation boundaries and a tester who probes counterexamples. These perspectives matter more than job titles.

ApproachQuestion it helps answerTypical feedback
BDD — behavior-driven developmentHave we agreed on the behavior that matters?Collaborative examples and selected acceptance checks.
TDD — test-driven developmentWhat small behavior must the code support next?A failing test, a minimal implementation, then refactoring.
Testing after implementationDoes the existing implementation meet our expectations?Regression evidence; valuable, but does not show a test drove the design.

For this teaching story, cancellation is allowed only while the order is CREATED. CLAIMED is too late; CANCELLED means the intention was already completed. Payment refund is a separate workflow and is not silently implied by a successful cancellation. These are explicit example rules, not claims about every shop.

2. Discovery, expression and checking

A useful discovery conversation asks: what changes for the customer, what must never happen, and which awkward case would distinguish two interpretations? Express only the rules you have actually agreed. Automate examples whose ongoing executable evidence is valuable; the conversation is still useful when an example is checked manually during discovery.

The output is a shared model of behavior, not a handoff document that QA receives after coding. When a new requirement changes the model, update the examples and implementation together. An executable example becomes living documentation only if people can find it, understand it and act on failures.

ConceptPlain meaningOur example
RuleA statement that covers a family of cases.Only an unclaimed order can newly transition to CANCELLED.
ExampleOne concrete illustration of a rule.Order O7 in CREATED is cancelled by its owner.
Acceptance criterionAn agreed condition for accepting the change.Repeated cancellation does not create another transition.
Open questionA decision still needed; not an assumption to hide in code.What should the caller see if the warehouse claim wins concurrently?

3. Build an example map

Use a short workshop to separate the story, its rules, examples and unanswered questions. The point is to find disagreement quickly. If the examples keep introducing unrelated workflows, slice the story. If a critical question has no owner, name one instead of letting a developer guess silently.

Rule for this storyConcrete exampleQuestion or boundary
Owner can cancel CREATEDAlice cancels O7, initially CREATED → CANCELLED.Which identity proves ownership? Decide before endpoint acceptance.
CLAIMED cannot be newly cancelledO8 was claimed by the warehouse → TOO_LATE, state unchanged.Does any privileged override exist? Excluded from this slice.
Repeat cancellation is harmlessO9 is already CANCELLED → ALREADY_CANCELLED.API status/body must be agreed separately.
Cancellation does not perform a refund hereO7 cancellation produces no immediate refund call.Refund workflow belongs to a separate story and contract.
A competing claim must not coexist with cancellationCancel and claim race on O10 → one allowed transition wins.Define loser response and recovery after an unknown commit.

During discussion, Alice and O7 are illustrative fixtures. The relevant facts are authenticated ownership and the order state. Do not clutter the examples with postal addresses, loyalty history or payment-card fields unless they affect the rule. Keep unknowns visible rather than giving a feature file an authoritative appearance before agreement.

For this lesson, settle the core domain outcomes first: CANCEL, TOO_LATE and ALREADY_CANCELLED. A cancellation policy does not by itself establish ownership or concurrency safety. Those become explicit API and repository acceptance work instead of invisible promises.

4. Write behavior in Given–When–Then

Gherkin is one structured notation for examples. Given establishes relevant context, When describes the event and Then states an observable outcome. And/But can continue the preceding kind of step. A Scenario Outline runs an example for each Examples row. A short Background can share context; avoid hiding the decisive setup in a long one.

Feature: Cancel an order before warehouse claim

  Scenario: An unclaimed order is cancelled
    Given Alice owns order O7 in state CREATED
    When Alice requests cancellation of O7
    Then O7 is in state CANCELLED
    And the cancellation outcome is CANCEL

  Scenario Outline: Cancellation does not change a closed decision
    Given Alice owns order O7 in state <initial>
    When Alice requests cancellation of O7
    Then O7 remains in state <initial>
    And the cancellation outcome is <outcome>

    Examples:
      | initial   | outcome           |
      | CLAIMED   | TOO_LATE          |
      | CANCELLED | ALREADY_CANCELLED |

Each scenario concentrates on one business event. The outline combines two cases because their shape is the same; the distinct outcomes remain visible. If a table needs dozens of unrelated flags, separate the rules instead. Avoid chaining login, catalogue search, checkout, cancellation and refund into one giant acceptance scenario.

A Then must assert a meaningful observation. “Then the service method is called” usually reveals implementation rather than customer behavior. “Then the order remains CLAIMED and the outcome is TOO_LATE” says what the system promises. Another customer’s cancellation must have a separate authorization example.

5. Execute the agreed examples in Java

You can automate the core acceptance examples without a Gherkin runner. Here a small in-memory order model receives the command and invokes the same policy developed in TDD. The acceptance test asserts both the decision and resulting state. It does not use HTTP and does not claim persistence, ownership or concurrent correctness.

package academy.testing;

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;
import academy.testing.CancellationPolicy.State;
import academy.testing.CancellationPolicy.Decision;

class CancellationAcceptanceTest {
    // Domain fixture only: no HTTP, authorization, persistence or concurrency.
    private static final class Order {
        private State state;
        private final CancellationPolicy policy = new CancellationPolicy();

        Order(State state) { this.state = state; }

        Decision cancel() {
            Decision decision = policy.decide(state);
            if (decision == Decision.CANCEL) state = State.CANCELLED;
            return decision;
        }
    }

    @Test
    void anUnclaimedOrderCanBeCancelled() {
        // Given
        var order = new Order(State.CREATED);
        // When
        var outcome = order.cancel();
        // Then
        assertEquals(Decision.CANCEL, outcome);
        assertEquals(State.CANCELLED, order.state);
    }

    @Test
    void aClaimedOrderCannotBeCancelled() {
        var order = new Order(State.CLAIMED);
        assertEquals(Decision.TOO_LATE, order.cancel());
        assertEquals(State.CLAIMED, order.state);
    }

    @Test
    void repeatingCancellationDoesNotRepeatTheTransition() {
        var order = new Order(State.CREATED);
        assertEquals(Decision.CANCEL, order.cancel());
        assertEquals(Decision.ALREADY_CANCELLED, order.cancel());
        assertEquals(State.CANCELLED, order.state);
    }
}

The in-memory Order is a fixture for the domain story, not a production repository. Its constructor records only the fact relevant to these examples. Each test owns a fresh fixture, so there is no reliance on scenario order or a shared static order. The repeated-request test is particularly useful: asserting only the first response would miss whether a second request causes a different transition.

This is BDD-style automation of already discussed examples, not proof that a team held the discovery conversation. The acceptance examples provide the outer behavior; the smaller TDD tests make changes inside that behavior easy to diagnose. Several small unit examples can support one acceptance rule without copying all the same tests at every layer.

6. Connect Gherkin to an adapter deliberately

Cucumber matches each step’s text to a step definition. The step definition arranges data, invokes an application boundary or asserts an observation. It should delegate repetitive HTTP or database mechanics to a test adapter so that business language stays readable. Framework glue does not replace assertions.

// Illustrative Cucumber-JVM adapter, not part of the runnable example.
// Scenario-scoped steps; orderApi is a test client with isolated fixtures.
@When("Alice requests cancellation of O7")
public void requestCancellation() {
    response = orderApi.cancel(aliceCredentials, orderId);
}

@Then("the cancellation outcome is {word}")
public void checkOutcome(String expected) {
    assertEquals(expected, response.outcome());
}

Choose the adapter based on the claim. A domain adapter is fast but bypasses security and HTTP mapping. An HTTP adapter can cover a genuine API contract but needs isolated data and a running application. A browser adapter is useful for a critical user journey; making every business permutation click through a browser usually slows feedback and adds irrelevant failure causes.

State/resourceIsolation ruleReason
Step stateKeep response and identifiers per scenario; no mutable statics.Parallel scenarios must not overwrite one another.
Database fixturesUse distinct tenant/order keys and clean committed data.A previous scenario must not create the next scenario’s precondition.
External providerUse an explicit stub or controlled test account with clear reset behavior.Do not accidentally send real orders, payments or notifications.
CredentialsUse test identities with relevant scopes and ownership.An always-admin fixture hides authorization defects.

If adopting Cucumber-JVM, pin mutually compatible Java, Cucumber, JUnit Platform and build-plugin versions for the project. The runnable example here deliberately uses only JUnit; the adapter above shows the boundary and needs the application’s real test client, assertions, imports and scenario lifecycle.

7. Turn domain examples into API evidence

An acceptance example must name the scope of its claim. A domain outcome CANCEL is not automatically HTTP 200, 202 or 204. For a synchronous durable cancellation, choose the documented success mapping. For a durably accepted asynchronous request, distinguish acceptance from final cancellation and provide a way to observe the outcome.

Acceptance concernConcrete observationAdditional boundary needed
Owner cancels CREATEDAllowed state transition plus agreed response.Authenticated HTTP request and committed database read.
Another customer attempts cancellationNo protected details or mutation beyond the disclosure policy.Authorization through the actual security configuration.
Order does not existAgreed not-found/disclosure behavior; no new order.HTTP mapping and tenant-scoped lookup.
Request retries after response lossSame intention has no second effect; result can be reconciled.Stable request identity and durable result handling.
Claim races cancellationExactly one valid transition wins.Concurrent real transactions and authoritative write constraints.

Do not let a scenario invent product decisions such as returning 404 instead of 403 without agreement. Record why the disclosure policy chooses a response. Similarly, a response code alone is not enough evidence: the database might still have changed after an error. Assert the protected state or effect as well as the returned representation.

Use provider/consumer contract checks for wire compatibility, integration tests for adapter behavior and a small deployed suite for the built system. These checks complement shared examples; they do not replace collaborative discovery.

8. Describe delayed and uncertain outcomes

Suppose cancellation is a durable command processed later. “Then the order is cancelled immediately” is now the wrong promise. Separate a scenario for durable acceptance from one for eventual completion and another for the worker’s failure or conflicting warehouse claim. An accepted command may still end as TOO_LATE under the agreed state machine.

Given order O7 is CREATED
When its cancellation command is durably accepted
Then the caller can retrieve that command by its stable identity
And the command status is PENDING or an already reached terminal result

Given that accepted command is PENDING
When a worker processes it before a warehouse claim wins
Then its terminal outcome is CANCEL
And the authoritative order state is CANCELLED

In an automated eventual-outcome test, poll a meaningful observation until a bounded deadline. Choose the bound from the test environment’s contract and report the last observed state on failure. Do not use a fixed sleep that is too short on a loaded machine and unnecessarily long on a fast one. Polling does not itself make production processing reliable.

Failure exampleExpected safety claimWhat to test
Message delivered twiceAt most one local business transition for that intention.Durable receipt/effect boundary, repeated delivery and stable identity.
Worker dies after commit before ackRedelivery recovers the committed result.Crash injection around commit/ack, not only a thrown exception before work.
External refund response is lostOutcome remains unknown until reconciliation; no blind new refund.Original provider key, status lookup and operational recovery path.
Event arrives out of orderOld information cannot reopen a final cancellation decision.Version/ordering rule at the consumer boundary.

The domain acceptance fixture cannot establish these delivery properties. Link the scenarios to the consumer transaction and unknown-outcome recovery designs, then exercise the actual mechanisms. “Eventually succeeds” without a deadline, failure outcome and owner is an incomplete requirement.

9. Keep the examples useful as rules change

Store selected executable examples beside the implementation and review their changes together. A product rule change should have a clear reason and owner. A red example can mean an implementation defect, an intentionally changed rule, stale fixtures or an unavailable dependency; investigate which before editing the expected result.

ChangeUseful review questionMaintenance action
Warehouse adds PACKING stateDoes packing mean already claimed, or is cancellation still safe?Agree a rule, add a contrasting example and update the implementation.
Endpoint response changesIs business behavior changing or only its representation?Keep the domain example; update the API contract check deliberately.
One scenario flakesIs there shared state, unbounded waiting or an uncontrolled dependency?Fix the cause; record first failures even if a diagnostic retry passes.
Feature is retiredWhich readers and recovery paths still depend on it?Remove or migrate the examples with the supported behavior, not months later.

Favor a compact set of examples that distinguish decisions over many near-identical scenarios. Detailed combinations often belong in parameterized or property-based tests. Use tags to select relevant suites if your tooling supports them, but prevent selective execution from silently omitting critical checks before release.

Measure whether conversations uncover questions earlier, whether feedback is quick enough to use and whether failures are actionable. A rising count of feature files is not evidence of shared understanding. A passing suite is evidence about selected checks in a specified environment, not a certificate that customers want the feature.

10. Know when BDD earns its cost

PatternProblemCorrection
QA writes Gherkin after developmentAmbiguities were already settled implicitly.Discuss rules before implementation and keep discovery collaborative.
Technical scripts in business syntaxReaders see click/type/SQL steps without the business rule.Use domain outcomes; hide adapter mechanics in test code.
Every test becomes a scenarioSpecification becomes slow, repetitive and hard to review.Keep representative acceptance examples; use lower-level tests for combinations.
A vague Then such as it worksThe example cannot distinguish competing interpretations.Name the observable state and forbidden side effect.
A passing fake is treated as full-system proofImportant adapters and commits were bypassed.Label the scope and add evidence at the missing boundaries.

BDD helps most when roles disagree about domain rules, exceptions, terminology or the meaning of completion. A narrow internal helper with an already settled contract may need a few direct TDD examples rather than a formal workshop. Start with a short conversation and one valuable behavior; add a framework only when readable executable specifications justify its ongoing maintenance.

11. Explain the differences with evidence

FoundationalIs BDD the same as Cucumber?

No. BDD is collaborative discovery and expression of behavior through examples. Cucumber is one automation tool that can connect structured scenarios to code. A team can use BDD without it, or use it without doing collaborative discovery.

FoundationalWhat belongs in Given, When and Then?

Relevant starting facts, one meaningful event and observable outcomes. Avoid hiding the decisive precondition in setup or expressing the outcome as private implementation calls.

IntermediateCan BDD and TDD be used together?

Yes. Shared acceptance examples can establish the outer goal while smaller TDD cycles evolve the internal implementation. They answer related questions at different scopes; neither mandates one test framework.

IntermediateShould every scenario run through the browser?

No. Pick the boundary needed to substantiate the claim. Pure rules can be checked directly, API behavior through HTTP, persistence through a real database, and a small critical journey through the browser.

AdvancedA cancellation scenario passes, but another customer can cancel the order. Why?

The original scenario may only exercise domain state. Add an unauthorized-owner example through the real security boundary and assert no state change. Do not infer authorization from a happy-path domain check.

AdvancedHow do you specify an asynchronous cancellation?

Separate durable acceptance from terminal outcome. Define stable identity, observable status, a bounded completion/recovery policy, conflicts and unknown outcomes. Test the actual commit/delivery mechanisms as well as the business decision.

12. Run, practice and read further

The complete examples use Java 17+ and JUnit Jupiter 5.13.1, with pinned Maven compiler and test plugins. From the repository root run:

mvn -B -f v4/examples/testing/pom.xml test

The command executes the final TDD policy tests and BDD-style acceptance examples. There is no Spring server, database, broker or Cucumber runner in this small example. HTTP, persistence and concurrency require the additional checks described below. A green final suite cannot prove the historical order in which tests and implementation were written.
