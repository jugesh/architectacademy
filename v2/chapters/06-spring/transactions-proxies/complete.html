Spring Transactions, Proxies and Consistency Boundaries

How @Transactional works, why self-invocation breaks expectations, and where database transactions stop.

ConceptsWorked LabInterviews

Concepts

1. The proxy mechanism

Why can self-invocation bypass @Transactional?

In conventional proxy-based Spring transaction management, a caller invokes a Spring-managed proxy, which starts or joins a transaction before invoking the target method. A direct call from one method to another on the same target object bypasses the proxy; @Transactional on the called method may not be applied. AspectJ weaving is a different mechanism with different interception behavior.

2. Propagation and isolation

What changes with REQUIRES_NEW?

REQUIRED joins an existing transaction or creates one; REQUIRES_NEW suspends the current transaction and uses an independent physical transaction, typically requiring another connection. NESTED uses savepoints where supported. Isolation determines which concurrent anomalies are permitted; exact behavior depends on database engine and SQL statements. Never assume SERIALIZABLE is free or that READ_COMMITTED prevents all lost updates.

3. Rollback semantics

What happens if an exception is swallowed?

By default Spring's declarative transactions roll back for unchecked exceptions and Errors, not ordinary checked exceptions, unless configured. Catching and suppressing an exception can lead to commit. An inner scope may mark a shared transaction rollback-only, causing UnexpectedRollbackException when the outer method attempts commit. Test rollback behavior explicitly for business exceptions.

4. Database versus network effects

Why is a remote call inside @Transactional risky?

A local database transaction cannot atomically commit an HTTP call or Kafka publish. Calling a payment provider while holding database locks creates long-lived transactions and still cannot guarantee atomicity. Use transactional outbox for durable event publication, inbox deduplication for consumers, and sagas/compensation for multi-service workflows. Reconciliation remains necessary for ambiguous external outcomes.

5. Connection pools and observability

Why does pool exhaustion happen before CPU saturation?

Long transactions retain connections, locks and row versions, increasing contention and exhaustion risk. Track active/idle/pending pool connections, transaction duration, lock waits, deadlocks and rollback counts. Keep transactions short; do not stream slow external responses inside a transaction. Bound concurrency to downstream capacity.

Implementation and diagnostics

Identify the invariant and the failure boundary.
@Service
class OrderService {
  private final OrderRepository orders;
  private final OutboxRepository outbox;

  @Transactional
  public void placeOrder(Command cmd) {
    orders.save(Order.from(cmd));
    outbox.save(OutboxEvent.from(cmd));
    // Both rows commit or roll back together in one database.
    // A separate publisher delivers outbox events with retries.
  }
}
// Consumers must be idempotent: publication may repeat.

Architecture review questions

Answer before expanding.
Does @Transactional work on a private method called from the same class?

Not with ordinary Spring proxy interception. The invocation does not pass through the proxy. Move the boundary to an externally invoked bean method or choose an explicit transaction mechanism.

Why can REQUIRES_NEW exhaust connections?

An outer transaction may retain its connection while the inner transaction requests another. With many concurrent callers, the pool can be exhausted or deadlock on connection acquisition.

Does @Transactional make Kafka and SQL atomic?

No. It controls the configured transaction manager and resource boundary. Use an outbox or a deliberately coordinated pattern for cross-system effects.

What isolation level should every service use?

There is no universal answer. Start from anomaly requirements, query patterns and database semantics; use constraints, optimistic locking or explicit locks where needed.

A lost-update timeline

Why doesn't @Transactional automatically prevent lost updates?

Two requests read account.version=7 and balance=100. Each calculates a new balance independently and writes it. Without an atomic predicate, the second write can overwrite the first even though both requests completed successfully. With optimistic locking, UPDATE account SET balance=?, version=8 WHERE id=? AND version=7 succeeds for only one transaction; the other must reload and retry or return a conflict. A @Transactional annotation alone does not enforce the invariant. In the presence of multiple database rows, consider locking order and constraints. Avoid holding locks across remote calls; move network effects behind an outbox and design consumer deduplication.

Why doesn't @Transactional automatically prevent lost updates?

Transactions provide a database isolation boundary, not necessarily serial execution. Under common isolation levels, read-modify-write races require version checks, atomic updates or locks.

6. Boot configuration and bean lifecycle

Why did this bean exist in one environment and disappear in another?

Spring Boot assembles a Spring application with conventions and conditional configuration. A starter brings dependencies; auto-configuration evaluates classpath, properties, existing beans and other conditions. A dependency change can therefore alter the effective bean graph without a source edit in your service. Treat the resolved dependencies, configuration sources and condition outcomes as part of the deployed system.

Use the condition evaluation report to investigate why a configuration applied or backed off. Defining an explicit bean can replace a conditional default, but it also transfers responsibility for the configuration that default supplied. Do not exclude a large auto-configuration merely to silence an unexplained startup error. Reduce the case and identify the exact condition or competing bean.

Bean definitions describe objects the container will create. Construction, dependency injection, initialization and post-processing form a lifecycle; AOP post-processors can expose a proxy instead of the raw target. Constructor injection makes required dependencies and cycles visible. Calling another annotated method during construction or initialization is not equivalent to entering through the fully configured proxy later. Objects created directly with new are not automatically container-managed.

Scopes and thread safety

A singleton bean is normally one shared instance per application context, not one per request and not one per cluster. Mutable request data in its fields can race across callers or leak between tenants. Keep services stateless where feasible and pass request-specific state through explicit parameters. Prototype/request scopes change creation and lifecycle rules; injecting a scoped dependency into a singleton requires the intended lookup or proxy behavior, not a remembered assumption.

Externalized configuration has precedence and binding rules. Validate a typed configuration object at startup, keep secrets out of logs and define whether values can change live. A feature flag changed mid-request can produce incoherent behavior unless the request captures a consistent decision. Configuration reload is a state transition, not merely replacing a string. Reference the configuration model for the pinned Boot release.

Worked failure: two DataSource beans after a starter change

A new starter introduces another candidate and injection becomes ambiguous, or an existing conditional configuration backs off. Inspect the bean/condition graph and dependency diff. Choose explicit qualifiers and transaction-manager ownership where multiple stores are intentional. Adding Primary without understanding which repositories use which manager can make startup pass while silently changing transaction boundaries.

7. MVC request and response internals

Where can a failure happen after the service committed?

A servlet-based request passes container and filter boundaries before DispatcherServlet selects a handler and adapter. Argument resolvers bind request values; conversion and validation can reject the call before the controller runs. The controller invokes domain services, and return-value handling chooses representation conversion or a view workflow. A RestController normally writes a body through HttpMessageConverter rather than rendering an HTML template.

Filters and MVC interceptors occupy different layers. Security can reject before a controller is selected; an MVC exception handler is not a universal catch-all for every filter failure. Trace IDs and safe logging context need cleanup on every exit and appropriate handling for asynchronous dispatch. Avoid reading a large body twice or logging authorization headers while adding diagnostics.

Controller success is not response success. Serialization can fail after the transactional service committed; a client can disconnect during transfer; a lazily loaded association can be accessed outside the intended persistence boundary. Prefer explicit response DTOs and deliberate queries rather than serializing an arbitrary entity graph. A gateway 500 or connection reset does not undo the order. Provide stable identity and lookup for effects whose response may be lost.

Validation and error mapping

Transport validation, authentication, object authorization and database invariants protect different contracts. A valid DTO can still reference an order belonging to another tenant. Validate the invariant inside the authoritative mutation boundary and return a documented conflict when current state invalidates the command. Keep public error types stable, map them consistently and preserve internal evidence without exposing stack traces.

Worked exercise: the JSON writer fails after checkout returns

The service transaction commits an order/outbox row, then the controller response traverses a recursive entity graph and serialization fails. An HTTP error is correct as a transport observation, but a blind retry with a new intent could create another order. Fix DTO mapping and serialization tests, and reconcile/replay by the original intent. A controller unit test returning a mock DTO would not expose the persistence/serialization boundary.

8. Proxies, advice and transaction participation

Which object and method did the caller actually invoke?

In proxy mode, advice runs when an eligible invocation crosses the proxy. Interface-based and subclass-based proxies impose different method constraints. A private method is not an externally interceptable boundary; final methods cannot be overridden by subclass proxies. Annotation placement, method visibility, proxy type and Spring version all matter. Inspect the actual bean and call path instead of diagnosing from the annotation alone.

Self-invocation uses the target's this reference. Moving the transaction boundary to a separately injected service often expresses ownership more clearly than self-injecting a proxy. TransactionTemplate can make a small programmatic boundary explicit. AspectJ weaving is a different interception model and must be configured/tested deliberately. The same general proxy caveat affects common caching and asynchronous advice, but each subsystem still has its own execution semantics.

Logical scopes and physical resources

REQUIRED participates in an existing transaction or starts one. Multiple logical scopes can therefore share one physical commit. An inner scope that marks rollback-only can make outer commit fail even when the outer method catches the original exception. REQUIRES_NEW requests an independent transaction while suspending the outer scope; the outer can retain its connection and locks. NESTED savepoint semantics depend on the transaction manager and resource, and are not equivalent to an independently committed transaction.

With 30 concurrent outer transactions holding all 30 pool connections, each requesting an inner independent connection can leave the fleet waiting for itself. More connections may avoid that acquisition cycle but can overload the database. Better boundary design can avoid nesting under load. Also consider lock dependencies: an independent inner transaction may wait for a row locked by its own outer transaction.

For the usual imperative model, transaction resources are associated with the current execution thread. Submitting work to another executor does not automatically transfer a JDBC transaction. Reactive transaction management uses a different context model and compatible resource stack. Do not combine arbitrary blocking JDBC work with a reactive annotation and assume the same participation rules. Name the manager and resource that owns the commit.

Worked exercise: an audit record survives a checkout failure

An independent audit transaction can commit even when checkout later rolls back. That may satisfy an audit requirement, but an audit record saying order created would then be false. Model the event as attempted/failed and ensure its semantics match the independent boundary. If the record is a domain fact that must exist only with the order, write it in the same local transaction instead.

9. Rollback, flush and concurrency

When did SQL run, and when did the transaction become durable?

Default declarative rollback rules usually roll back on RuntimeException and Error, while a checked exception needs an applicable rule to trigger rollback. These defaults can be configured, including global behavior in newer Spring releases. A swallowed exception does not cross the interceptor; rollback-only state may still be set by an inner participant or resource failure. Keep exception translation and rollback policy aligned with domain outcomes. See transaction rules.

With JPA, changing a managed entity need not execute SQL immediately. Flush synchronizes pending changes to the database but is not itself the final commit. A constraint or optimistic-lock failure can surface at flush or commit after application code appears to succeed. A read-only hint is not a universal prohibition on writes. Test the chosen provider, transaction manager and database instead of interpreting annotations as enforcement independent of those resources.

Lost updates and multi-row invariants

Two transactions can both read version 7 and calculate replacements. A version predicate makes one update succeed and the other detect conflict; retry must reload and recompute the business decision. Retrying only the final SQL with stale inputs preserves the bug. Pessimistic locking can serialize access but creates waits and deadlock possibilities. Use deterministic lock ordering, bounded lock waits and a clear conflict contract.

An invariant spanning several rows may not be protected by locking one row each transaction happened to read. For example, two on-call staff each observe the other available and independently go offline. Depending on isolation and access pattern, both can commit while violating the shared rule. Enforce a common serialization point, stronger isolation with retry, or a remodelled invariant. Transactional does not mean all business operations execute serially.

Failure exercise: catching a constraint exception inside the same transaction

Some resource errors leave the transaction unusable or rollback-only. Catching the Java exception cannot necessarily restore it. End the failed boundary and apply the documented recovery/retry policy in a new transaction. Do not log success merely because the method returned normally; observe the actual commit result and final state.

10. Events, async work and outbox ownership

Who recovers work after commit but before publication?

An in-process application event is not automatically durable messaging. A listener scheduled after commit can avoid observing rolled-back data, but the process can crash before it runs. Async execution also changes thread and transaction context. If the business requires eventual delivery after a committed state change, persist publication intent in the same database transaction and recover it independently.

An outbox row needs a stable event identity, aggregate identity, schema version, payload, ordering policy and publication metadata. Keep its creation atomic with the domain mutation. A relay claims bounded batches, publishes with retry and records progress; a crash after send but before marking can duplicate delivery. Consumer deduplication and domain invariants remain necessary. Cleanup must not delete work that a crashed relay still needs.

A transactional event listener after commit does not put subsequent writes into the already completed transaction. Work that needs a new durable transaction must request an appropriate new boundary and handle its failure. Email delivery, cache invalidation and webhook dispatch can all use outbox-like recovery where requirements justify it. Never mark a successful order failed merely because its notification is temporarily unavailable.

Worked duplicate-consumer exercise

The consumer inserts (consumer_name,event_id) and changes the local business row in one SQL transaction. It crashes after that commit but before acknowledging the message. On replay, the marker prevents a second effect. If the marker and effect use different databases or transactions, the guarantee no longer follows. External effects still require their own provider identity or reconciliation.

11. Executable boundaries and operational evidence

Which test proves interception and which proves database isolation?

The Maven lab pins Spring Framework 6.2.11, H2 2.3.232 and JUnit. Its three tests use an actual Spring transaction interceptor and JDBC transaction manager: an externally proxied runtime failure rolls back while self-invocation bypasses the advice; checked exceptions follow configured rollback rules; and local order/outbox writes commit or roll back together.

mvn -B -f v2/examples/ch06/pom.xml test

The lab targets Java 17+ and illustrates mechanisms, not a recommended production dependency baseline. It uses H2 and does not establish PostgreSQL isolation, pool exhaustion, Kafka coordination or a deployed Boot filter chain. Reproduce those contracts with the intended database and integration stack. A repository mock cannot prove commit/locking, while an H2 commit test cannot prove another engine's concurrency semantics.

Test transactions can hide the boundary

A test automatically wrapped in a transaction can make repository changes visible in the test while never exercising a real production commit. Deliberately separate setup, invocation and verification transactions. Trigger flush/commit failures, call the injected proxy, and avoid asserting only the state of an in-memory persistence context. Use two controlled sessions for races and verify after both complete.

Operational evidence should separate request queueing, connection acquisition, SQL execution, lock wait, transaction duration and response serialization. Track outbox age, relay retries and consumer duplicate suppression alongside final business state. Secure management endpoints and restrict access to configuration/bean diagnostics that can expose sensitive details. Keep readiness, liveness and graceful shutdown tied to the service's actual lifecycle.

Worked production case: low CPU, high latency after @Async change

A handler starts asynchronous work before its transaction commits. The worker sees missing state or blocks, retries accumulate and pool acquisition grows while CPU remains low. Verify thread and transaction boundaries, move required durable work behind an outbox, and bound worker concurrency. Then test commit-before-publication, duplicate delivery and a process crash. Adding threads alone increases offered database pressure.

Request pipeline in a JSON-only service

A typical request crosses servlet filters, DispatcherServlet, handler mapping, adapter, controller argument binding, controller, return-value handlers and HttpMessageConverters. @RestController ordinarily writes JSON using a converter such as Jackson, not an HTML ViewResolver template. Validation exceptions and domain exceptions must be mapped to deliberate status codes; do not leak stack traces or internal IDs.

Understand transactional proxies

Spring usually applies @Transactional via interception. An invocation that bypasses the proxy, such as this.someTransactionalMethod() in the same target object, bypasses this advice. Transaction scope is also about resource participation: a SQL transaction does not include an S3 upload or Kafka publish merely because the method has an annotation.

Caller enters the service proxy, order/outbox commit together, then the recoverable relay publishes. See the transaction boundary diagram.

Durable outbox skeleton

@Service
public class CheckoutService {
    private final OrderRepository orders;
    private final OutboxRepository outbox;

    public CheckoutService(OrderRepository orders, OutboxRepository outbox) {
        this.orders = orders;
        this.outbox = outbox;
    }

    @Transactional
    public void placeOrder(Order order) {
        orders.save(order);
        outbox.save(new OutboxEvent(order.getId(), "OrderPlaced",
                                   order.toEventJson()));
    }
}

This code assumes domain and outbox use one transactional database and mapper configuration. A real repository also needs uniqueness for event identity, serialization version, publication metadata and retry policy. The worker can publish twice if it crashes between Kafka send and marking delivered; consumer handlers must deduplicate business effects.

Isolation and propagation

Isolation defines which concurrent phenomena are permitted by the database, not by Spring alone. Default isolation generally delegates to the database. REQUIRES_NEW may demand a second connection while outer transaction resources are still held; this can exhaust pools under concurrency. Read-only is often a hint and not a guarantee that SQL writes will be impossible. Do not hold transactions around slow remote calls; transaction duration increases locking and pool occupancy.

Experiment: reproduce self-invocation

  1. Put @Transactional on a public method that inserts data and deliberately throws a runtime exception.
  2. Call through a Spring-managed proxy and verify rollback.
  3. Invoke that method via another method on the same object and observe that advice may be bypassed.
  4. Move the transactional method to another bean or use TransactionTemplate, and rerun.
  5. Test against the intended database engine; repository mocks are not isolation tests.

Design interview: answered

Why is @Transactional not enough for exactly-once Kafka delivery? A database commit and a Kafka publish do not share a single local atomic transaction. Use outbox and idempotent consumers.

What happens when an exception is swallowed? If no rollback rule or rollback-only flag applies, the transaction can commit.

How do you make an event handler idempotent? Insert a unique (consumer,event_id) marker in the same SQL transaction as the business mutation.

Why might @Async not run asynchronously? A self-call can bypass its proxy, or executor configuration may not be active.

Which tests prove locking behavior? Two real concurrent transactions on a faithful database with controlled synchronization points; unit mocks do not reproduce MVCC.

Production observability

Trace through request filters, transaction, outbox insert, worker publish and consumer apply. Alert on oldest unpublished event age, publish retry count, dead-letter backlog, pool waits, transaction duration and duplicate-event suppressions.

Interviews

1. What actually produces JSON in Spring MVC?

Explain the trade-off and test.

DispatcherServlet finds the handler, calls the controller through a HandlerAdapter and a return-value handler uses an HttpMessageConverter (often Jackson-backed) to serialize the response. A JSON REST API need not render a template View. Filters and interceptors surround different stages and have different exception behavior.

Follow-up / exercise: Trace where authentication, validation, serialization and error mapping occur.

Worked answer: Authentication commonly occurs in a filter chain before controller invocation. Argument resolution/validation can reject before the method; the service commits domain work; return-value handling serializes afterward. MVC exception resolvers handle their supported layer, while filter/security failures need that layer's response handling.

2. Why does @Transactional fail on self-invocation?

Explain the trade-off and test.

In common proxy-based Spring AOP, advice applies when an external call enters through the Spring proxy. this.innerMethod() invokes the target directly and bypasses the transactional interceptor. Extract a bean, call through the proxy intentionally, or use TransactionTemplate; beware changing public API merely to trick proxying.

Follow-up / exercise: Design a test that distinguishes proxied calls from self-calls.

Worked answer: Use the supplied Spring/H2 lab: an external call to inner inserts then throws and leaves zero rows; outer calls inner on the same target and the insert autocommits before the exception. Repeat through an extracted bean or TransactionTemplate to establish the intended boundary.

3. What determines transaction rollback?

Explain the trade-off and test.

Spring's default declarative behavior generally rolls back on unchecked exceptions and Errors, while checked exceptions may not trigger rollback unless configured. Swallowing an exception can permit commit unless the transaction is marked rollback-only. Database-side constraint violations may force rollback independently.

Follow-up / exercise: Contrast a caught RuntimeException with an escaping checked exception.

Worked answer: If a runtime exception is caught entirely inside the target and nothing marks rollback-only, normal return can commit. An escaping checked exception follows configured rollback rules; by default it often commits. Test database errors and global rollback configuration separately.

4. What is the danger of REQUIRES_NEW?

Explain the trade-off and test.

It starts an independent transaction and may acquire an additional connection while the outer context still holds resources. Under load, this can exhaust a small pool or increase lock conflicts. Its commit can survive an outer rollback, which may be intentional for audit records but surprising for domain effects.

Follow-up / exercise: Model 30 concurrent threads with a 30-connection pool and nested REQUIRES_NEW.

Worked answer: All thirty outer connections can remain held while each thread requests a second. No caller can make progress until an acquisition times out or capacity changes. Avoid that nesting pattern or establish a measured resource budget, and inspect inner/outer row-lock dependencies too.

5. Why can't @Transactional make SQL and Kafka atomic?

Explain the trade-off and test.

A Spring-managed SQL transaction typically covers one transactional resource; publishing to Kafka is outside that commit unless a specially coordinated protocol exists. The transactional outbox persists business state and event intent together, then publishes asynchronously with deduplicated consumption.

Follow-up / exercise: Enumerate crash before SQL commit, after commit and after Kafka send.

Worked answer: Before local commit both order and outbox roll back. After commit the outbox recovers publication. After Kafka send but before marking, publication can repeat, requiring consumer deduplication. The SQL transaction does not cover all three boundaries.

6. How do you build an idempotent Kafka consumer with Spring?

Explain the trade-off and test.

Handle a stable event ID and business update in one SQL transaction guarded by a unique processed-event marker. A successful SQL commit can precede offset commit; on replay, duplicate marker suppresses the second effect. Spring Kafka container and acknowledgment settings must preserve this ordering.

Follow-up / exercise: Explain why a Kafka transaction alone does not include arbitrary PostgreSQL writes.

Worked answer: Kafka transaction semantics cover participating Kafka records and offsets, not an arbitrary JDBC commit. A consumer that also mutates SQL needs a deliberate local marker/effect transaction and replay policy, or another explicitly coordinated design with its own failure analysis.

7. What is the difference between filters and HandlerInterceptors?

Explain the trade-off and test.

Servlet filters apply at the servlet infrastructure level and can wrap security, encoding and request body handling before DispatcherServlet. Spring MVC HandlerInterceptors operate around handler execution inside DispatcherServlet; they are not a replacement for comprehensive authorization across all entry points.

Follow-up / exercise: Place correlation IDs in a filter and explain exception behavior.

Worked answer: Create or accept a validated correlation value at the boundary, install it in logging context and restore/remove it in finally. Async dispatch needs deliberate propagation. A filter failure can occur before MVC exception handling is entered, so test the filter's actual error path.

8. How do connection pools constrain throughput?

Explain the trade-off and test.

A request waiting for a JDBC connection consumes latency and possibly a request thread. Increasing Hikari maximumPoolSize blindly may increase database contention. Measure active, pending and idle connections, acquisition latency and query service time before changing bounds.

Follow-up / exercise: Calculate aggregate maximum connections across all pod replicas.

Worked answer: Fifteen concurrently live instances at a pool cap of twelve can configure 180 connections, before other workers and reserve. Count old/terminating and rollout-surge instances. The configured maximum is not a guarantee the database performs well at that concurrency.

9. How does @Async interact with transaction context?

Explain the trade-off and test.

@Async usually executes in a different thread; thread-bound transactional context does not automatically follow it. Async self-invocation can bypass proxy advice. Pass immutable data and create deliberate new transactional boundaries rather than assuming the caller's transaction transfers.

Follow-up / exercise: Explain why an async email should be driven from an outbox after commit.

Worked answer: An in-memory async email task can be lost after order commit or run before state is visible. Persist notification intent with the order, deliver afterward with retry/deduplication as required, and keep notification failure separate from order success.

10. How should global error handling be designed?

Explain the trade-off and test.

Use a coherent exception contract via @ControllerAdvice or equivalent, distinguish validation errors from optimistic conflicts and transient server failures, and avoid exposing secrets. Make idempotent replays and tracing IDs consistent; serialization errors may happen after controller logic succeeds.

Follow-up / exercise: Test a failure during response serialization and discuss whether the domain mutation may already be committed.

Worked answer: A response serializer can fail after the service committed. Assert durable state and a safe same-intent retry/status lookup, then fix DTO boundaries. Do not infer rollback from an HTTP failure or return a misleading second independent operation.

11. What is the difference between optimistic and pessimistic locking in Spring Data?

Explain the trade-off and test.

Optimistic locking uses a version predicate and detects concurrent changes at update/flush, requiring an application retry or conflict response. Pessimistic locking acquires database locks and can block or deadlock. Choose based on contention, invariant complexity and user experience.

Follow-up / exercise: Explain why a transaction alone does not eliminate lost updates.

Worked answer: Common isolation levels permit some read-modify-write races. Use an atomic update/version predicate or explicit serialization that protects the invariant, then reload/recompute on conflict. JPA version failures may surface at flush or commit.

12. How do you validate transactional behavior?

Explain the trade-off and test.

Use integration tests against the actual database engine with simultaneous transactions, controlled barriers, forced rollbacks and crash-window tests. A Spring test framework may wrap tests in a transaction that masks commit behavior; configure boundaries intentionally.

Follow-up / exercise: Build a test for two checkouts racing on one inventory row.

Worked answer: Run two real transactions against the intended engine, coordinate reads/updates with barriers and assert inventory never becomes negative and only one reservation wins. Include losing transaction rollback and retries. Do not let a surrounding test transaction hide actual commit behavior.

Spring revision sheet

  1. Boot conditions depend on classpath, properties and existing beans. Inspect why configuration applied.
  2. Singleton is context-scoped, not request-scoped or inherently thread-safe.
  3. REST JSON uses return-value handling and message conversion; no template View is required.
  4. Serialization can fail after the domain transaction committed.
  5. Proxy advice needs an eligible invocation through the proxy; self-calls bypass it in proxy mode.
  6. REQUIRED can share one physical transaction. REQUIRES_NEW can retain outer resources while acquiring more.
  7. Rollback follows configured rules and rollback-only state, not the presence of an annotation alone.
  8. Flush executes pending SQL; it is not final durable commit.
  9. Constraints, version checks and isolation protect specific invariants.
  10. Imperative thread-bound transactions do not automatically cross executors.
  11. Order and outbox share one local transaction; relay delivery can repeat.
  12. Test actual commits deliberately; test-managed transactions and mocks can hide boundaries.

Worked recall

Thirty outer transactions holding thirty pool connections and each waiting for REQUIRES_NEW can exhaust acquisition capacity. Redesign resource ownership and bound concurrency before merely enlarging the pool.

Evidence

Verify proxy entry, checked/runtime rollback, local outbox atomicity, actual-engine concurrency, response loss and recovery. H2 mechanism tests do not prove PostgreSQL isolation or broker integration.
