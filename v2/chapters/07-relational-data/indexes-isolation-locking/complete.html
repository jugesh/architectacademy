SQL Indexes, Isolation and Locking

Why an index helps some queries but hurts writes, and how concurrent transactions produce subtle anomalies.

Index access paths Read the execution plan Isolation anomalies Optimistic and pessimistic locking Pagination and operational costs

1. Index access paths

Why might an index not be used?

A B-tree index orders keys and supports selective equality and range predicates, but its value depends on selectivity, covering columns and the optimizer's cost estimate. A composite index (tenant_id, status, created_at) often serves predicates on its leftmost prefix; index column order should reflect real query shapes and sorting needs. Too many indexes increase write amplification, storage and maintenance costs.

2. Read the execution plan

What does a row-estimate mismatch suggest?

EXPLAIN reveals estimated scan and join strategies; EXPLAIN ANALYZE executes the query and reports actual behavior in engines that support it. Compare estimated versus actual rows, index scans, sort operations, join loops and I/O. A query returning ten rows may still scan millions because of poor predicates or stale statistics. Benchmark with production-like data distribution.

3. Isolation anomalies

Can snapshot isolation allow write skew?

Read committed generally prevents dirty reads but can permit non-repeatable reads and phantoms. Snapshot-based isolation can prevent some read anomalies while allowing write skew unless constraints or locking address it. The SQL standard names levels, but implementations differ. Define the invariant first, then select isolation and constraints to enforce it.

4. Optimistic and pessimistic locking

How can two requests oversell one item?

Optimistic locking checks a version on update and retries or rejects conflicts; it works well when contention is low. Pessimistic locking acquires database locks earlier, reducing some races but increasing blocking and deadlock risk. For inventory reservations, a conditional atomic update can enforce nonnegative stock without a read-then-write race.

5. Pagination and operational costs

When is keyset pagination preferable?

OFFSET pagination becomes costly at deep pages and can shift results during concurrent writes. Keyset pagination uses a stable sort tuple, such as (created_at,id), and a matching index. Monitor slow-query distributions, lock wait time, deadlocks, buffer cache hit rate and replication lag. Avoid making all read traffic depend on replicas when read-after-write correctness is required.

Implementation and diagnostics

Identify the invariant and the failure boundary.
-- Atomic inventory decrement: prevents overselling on this row.
UPDATE inventory
SET available = available - 1
WHERE sku = :sku AND available > 0;
-- Require exactly one affected row; otherwise reject.

-- Composite index for tenant-filtered recent orders:
CREATE INDEX idx_orders_tenant_created_id
ON orders (tenant_id, created_at DESC, id DESC);

-- Keyset page (with matching ORDER BY):
SELECT id, created_at, total
FROM orders
WHERE tenant_id = :tenant
  AND (created_at, id) < (:cursor_time, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;

Validate the example against your exact runtime, database engine and deployment settings before production use.

Architecture review questions

Answer before expanding.
Why can an index make performance worse?

Every insert, update or delete may maintain the index. Low-selectivity scans or non-covering lookups can also be more expensive than sequential scans.

What is write skew?

Concurrent transactions read a shared invariant and update different rows so each sees a valid snapshot, but their combined committed effects violate the invariant.

How would you prevent lost updates?

Use a version predicate, atomic SQL update, row locking or suitable isolation depending on the invariant and contention profile.

What makes keyset pagination robust?

A stable total ordering, a matching index and a cursor carrying the full sort tuple. It avoids deep OFFSET scans but needs deliberate handling of mutable sort keys.

Composite indexes and selectivity worked example

Why must a pagination cursor contain the tie-breaker?

Consider orders(tenant_id,status,created_at,id) with 50 million rows. A query filtering one tenant and recent orders, ordered by created_at DESC, can benefit from (tenant_id,created_at DESC,id DESC) when status is optional. An index starting with status may be less useful if status has only three common values and the query does not filter it. A covering index can avoid heap/table lookups, but widening indexes increases write and storage cost. Compare actual plans for both common and rare tenants: skew changes estimates and plan quality. Use keyset pagination with the full (created_at,id) tuple to prevent duplicates when timestamps tie.

Why must a pagination cursor contain the tie-breaker?

Without a unique total order, records sharing a timestamp can be skipped or repeated between pages.

Inventory invariant under concurrency

Trace the invariant, failure boundary and recovery.

The invariant available >= 0 is better enforced by an atomic conditional update than by SELECT followed by UPDATE. Under concurrency, UPDATE inventory SET available=available-1 WHERE sku=? AND available>0 atomically checks and changes the row under database concurrency control. Check affected rows; zero means no stock or no matching SKU. For a reservation workflow, add a unique reservation identifier so retries cannot decrement twice. For multi-row invariants, snapshot isolation may permit write skew: two doctors each observe the other on call and independently go off duty, leaving nobody. Prevent it with a constraint or locking a shared guard row, or use appropriate serializable isolation and retry serialization failures. Diagnose query performance using actual plans and representative tenant cardinalities; index selectivity and column order are workload dependent.

Design review and interview follow-ups

Why is a transaction around SELECT and UPDATE insufficient for inventory?

Under common isolation levels two transactions may read the same stock and both act on it. A single conditional update, lock or version predicate enforces the invariant.

When is SERIALIZABLE a poor default?

When abort/retry overhead, contention or long-running transactions create unacceptable throughput or latency costs. It is a correctness tool, not a universal performance choice.

Join algorithms and plan instability

Why can the same query be fast for one tenant and slow for another?

Nested-loop joins are efficient when the outer side is small and the inner side has an index; hash joins often suit larger equijoins; merge joins can exploit sorted inputs. The optimizer chooses based on cardinality estimates, cost settings and statistics. Skewed tenant distributions can make a plan good for one parameter and poor for another. Compare estimated and actual rows, scan counts, loops, sort spills and buffer reads. Query latency is a distribution: report p95/p99 rather than only average.

Why can the same query be fast for one tenant and slow for another?

Tenant cardinality, data skew, parameter-sensitive plans and different index selectivity can change the chosen plan and amount of work.

Replication and consistency contracts

Why can a user fail to see an order they just created?

A primary/replica architecture scales some read workloads but introduces replication lag and failover complexity. A write acknowledged on the primary may not yet be visible on a replica, violating read-your-writes expectations. Route consistency-sensitive reads to the primary, use session consistency mechanisms where supported or expose a bounded-staleness contract. Replica promotion and split-brain protection depend on the database system. Define acceptable data loss and recovery time rather than assuming replication is equivalent to backups.

Why can a user fail to see an order they just created?

The write succeeded on the primary but the subsequent read was routed to a lagging replica.

Schema migration without downtime

Why is renaming a column in one deployment risky?

For rolling deployments, use expand-and-contract: add nullable or backward-compatible columns, deploy dual-compatible readers/writers, backfill safely in batches, switch reads, then remove obsolete fields only after all old binaries are gone. Large indexes and backfills can block or overload production depending on engine and DDL mode. Track migration progress, lock waits, replication lag and rollback path. Never assume an application rollback can undo a destructive schema change.

Why is renaming a column in one deployment risky?

Old application instances may still reference the original name during rolling deployment or rollback.

Index design for a real access pattern

Suppose a multi-tenant orders table contains 50 million rows and the API queries the newest PAID orders by tenant:

SELECT id, created_at, total
FROM orders
WHERE tenant_id = :tenant AND status = 'PAID'
  AND (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;

A candidate index is (tenant_id, status, created_at DESC, id DESC). Equality predicates precede the ordered range in this workload. Whether this is the *best* index depends on tenant cardinality, write overhead, columns returned, selectivity and database engine. Validate with EXPLAIN ANALYZE and real distributions, not synthetic tiny tables. The first page needs special handling instead of a null tuple comparison.

Keyset pagination versus OFFSET

OFFSET 100000 LIMIT 50 may require traversing and discarding many rows; keyset pagination starts after a known ordered tuple. Use a deterministic tie-breaker ID. Keyset pagination navigates relative to the prior page; it does not automatically promise a snapshot across separate requests. Concurrent inserts/deletes can change the result set, so define user-facing pagination semantics.

Atomic stock decrement

UPDATE inventory
SET available = available - 1
WHERE sku = :sku AND available > 0;

Require exactly one updated row to claim success. For a retryable reservation API, also persist a unique reservation ID so a repeated request cannot decrement again. A transaction around SELECT followed by UPDATE without appropriate locking can lose updates or violate invariants.

Write skew timeline

Constraint: at least one doctor must be on call.
T1 snapshot: A=on, B=on      T2 snapshot: A=on, B=on
T1 sets A=off                 T2 sets B=off
T1 commits                    T2 commits
Combined result: A=off, B=off -> invariant violated

This can occur under snapshot isolation in systems that allow write skew. Lock a shared invariant guard, enforce an appropriate constraint, or use suitable serializable isolation and retry serialization failures. Isolation behavior varies by engine; name the engine when discussing guarantees.

Replicas, failover and backups

Asynchronous replication may return an older value after a primary acknowledges the write. A read-your-writes contract can route the follow-up read to primary or use a supported session/commit-position mechanism. Replicas are not backups: mistaken deletions, corruption and operator errors can propagate. Define RPO (maximum acceptable data loss) and RTO (recovery target), back up regularly and test restoration. The failover procedure must also prevent two primaries from accepting conflicting writes.

Zero-downtime schema rollout

Expand schema -> deploy dual-compatible app -> backfill in batches
       -> switch readers -> verify -> contract obsolete schema

Before dropping a column, ensure older application versions cannot still run or roll back into it. On large tables, index creation and backfill can cause locking, high IO or replication lag depending on DB engine and DDL mode. Apply rate limits and checkpoints.

Interview: answered

Can an index make writes slower? Yes. Every index adds storage, maintenance and possibly contention; evaluate net workload benefit.

Why can a query regress without changing SQL? Statistics, data skew, parameter values, table growth, plan cache behavior or DB settings can change the optimizer decision.

Is REPEATABLE READ always safe for business invariants? No. Exact anomaly prevention differs by implementation; write skew and constraint design must be assessed against the target engine.

Should all reads use replicas? No. Freshness-sensitive reads and transactional read-modify-write flows may require primary or a defined session guarantee.

How do you prove a migration is reversible? Deploy old/new compatible readers, test backfill on production-like data, and explicitly distinguish application rollback from irreversible data transformations.

SQL and transactional correctness: Senior Interview and Design Review

Answer before reading. Every question pairs a technical explanation with a verification exercise or architectural follow-up.

1. How do you choose a composite index order?

Explain the trade-off and test.

Start from equality predicates, range predicates and required ordering for actual queries, then examine selectivity, storage, covering potential and write overhead. Equality columns commonly precede range/order columns in an index designed for a single access pattern, but optimizer and engine specifics matter.

Follow-up / exercise: Use EXPLAIN ANALYZE on realistic skewed tenant data before claiming it is optimal.

2. Why is OFFSET pagination expensive on deep pages?

Explain the trade-off and test.

A database may scan or traverse and discard preceding rows before returning a late page, making work grow with offset. Keyset pagination uses the last observed ordered values and a deterministic tie-breaker to seek forward. Neither guarantees stable snapshots across multiple HTTP requests.

Follow-up / exercise: Design a two-column (created_at,id) cursor for descending order.

3. What is a lost update and how is it prevented?

Explain the trade-off and test.

Two transactions may read the same state and independently write a new value, with one overwrite obscuring the other. Prevent it using atomic UPDATE expressions, a version predicate or appropriate row locking/isolation. The details depend on database and statement pattern.

Follow-up / exercise: Explain why SELECT then UPDATE is not equivalent to UPDATE qty = qty - 1.

4. What is write skew?

Explain the trade-off and test.

Two transactions read a common invariant under an isolation level that permits overlapping snapshots, then update different rows, producing a result that violates the invariant even though they do not write the same row. Protect the invariant with a constraint, guard row or serializable isolation and retry logic.

Follow-up / exercise: Use the classic two-doctors-on-call example and demonstrate a shared guard row.

5. Why do database isolation names mislead?

Explain the trade-off and test.

SQL standard labels describe phenomena, but engine-specific implementations vary: PostgreSQL snapshot behavior, MySQL InnoDB locking reads, and SQL Server configuration differ. State the engine and exact isolation mode. Validate with concurrent tests rather than assuming a name means universal semantics.

Follow-up / exercise: Contrast repeatable read with locking SELECT FOR UPDATE in the chosen engine.

6. How do you reason about deadlocks?

Explain the trade-off and test.

A deadlock is a cycle of lock acquisition where each transaction waits for another. Database engines typically detect and abort one participant. Keep transactions short, acquire locks in consistent order, use appropriate indexes and retry designated deadlock errors with bounded backoff.

Follow-up / exercise: Explain why increasing lock wait timeout is not a root-cause fix.

7. Why does EXPLAIN differ from EXPLAIN ANALYZE?

Explain the trade-off and test.

EXPLAIN shows the optimizer's estimated plan; ANALYZE executes the query in engines that support it and reports actual runtime and row counts. Running a write under ANALYZE may execute the write, so handle production use carefully. Compare estimated-versus-actual cardinality to find bad statistics or skew.

Follow-up / exercise: Investigate a nested-loop join with estimated 10 rows but actual 500,000.

8. What is the replication lag contract?

Explain the trade-off and test.

Asynchronous replicas may not reflect a write acknowledged on the primary. For read-your-writes, route sensitive reads to primary or use engine-supported session consistency/watermarks. Measure lag in time and log position; failover can introduce separate consistency and data-loss questions.

Follow-up / exercise: Explain a newly created order that disappears briefly from a user's history.

9. Why are replicas not backups?

Explain the trade-off and test.

Replicas copy writes and can propagate accidental DELETEs, corruption and bad migrations. Backups need retained point-in-time history, independent access controls and tested restore procedures. Define recovery point objective and recovery time objective against business needs.

Follow-up / exercise: Distinguish zero data loss wish from achievable RPO given replication and backup topology.

10. How do you roll out a breaking schema change safely?

Explain the trade-off and test.

Use expand-and-contract: add compatible fields, deploy code that handles both forms, backfill incrementally, switch readers/writers, then remove old fields only after old applications cannot run. Watch locks, IO and replica lag and make application rollback viable.

Follow-up / exercise: Handle a rolling deployment where half the pods use the old field name.

11. When does an index hurt performance?

Explain the trade-off and test.

Indexes require additional storage and maintenance on INSERT/UPDATE/DELETE; too many can cause write amplification, memory pressure and slower vacuum/compaction depending on engine. An index on low-selectivity data may provide little benefit compared with a scan.

Follow-up / exercise: Measure write throughput and plan changes before adding a speculative index.

12. How would you build a retry-safe stock reservation?

Explain the trade-off and test.

Use a business reservation ID with a unique constraint and an atomic conditional stock decrement in one transaction. Repeated reservation requests return the prior result instead of decrementing again; cancellations must be idempotent and linked to the original reservation.

Follow-up / exercise: Test a crash after decrement but before HTTP response.
