ANSWERED ADVANCED INTERVIEW BANK · 12 SCENARIOS

SQL and transactional correctness: Senior Interview and Design Review

Answer before reading. Every question pairs a technical explanation with a verification exercise or architectural follow-up.

1. How do you choose a composite index order?

Explain the trade-off and test.

Start from equality predicates, range predicates and required ordering for actual queries, then examine selectivity, storage, covering potential and write overhead. Equality columns commonly precede range/order columns in an index designed for a single access pattern, but optimizer and engine specifics matter.

Worked follow-up / exercise

Use EXPLAIN ANALYZE on realistic skewed tenant data before claiming it is optimal.

Worked answer: Create common and rare tenant distributions, record estimated versus actual rows and buffers, and compare candidate indexes under both read and write load. Keep the index only if the measured workload benefit exceeds maintenance cost.

2. Why is OFFSET pagination expensive on deep pages?

Explain the trade-off and test.

A database may scan or traverse and discard preceding rows before returning a late page, making work grow with offset. Keyset pagination uses the last observed ordered values and a deterministic tie-breaker to seek forward. Neither guarantees stable snapshots across multiple HTTP requests.

Worked follow-up / exercise

Design a two-column (created_at,id) cursor for descending order.

Worked answer: Encode both last values and query with (created_at,id) < (:time,:id), ORDER BY created_at DESC,id DESC. The unique ID makes the order total when timestamps tie.

3. What is a lost update and how is it prevented?

Explain the trade-off and test.

Two transactions may read the same state and independently write a new value, with one overwrite obscuring the other. Prevent it using atomic UPDATE expressions, a version predicate or appropriate row locking/isolation. The details depend on database and statement pattern.

Worked follow-up / exercise

Explain why SELECT then UPDATE is not equivalent to UPDATE qty = qty - 1.

Worked answer: A read-then-write can calculate from stale state unless it locks or checks a version. One conditional UPDATE evaluates and changes the row under database concurrency control and reports whether it succeeded.

4. What is write skew?

Explain the trade-off and test.

Two transactions read a common invariant under an isolation level that permits overlapping snapshots, then update different rows, producing a result that violates the invariant even though they do not write the same row. Protect the invariant with a constraint, guard row or serializable isolation and retry logic.

Worked follow-up / exercise

Use the classic two-doctors-on-call example and demonstrate a shared guard row.

Worked answer: Both doctors can update different rows after reading the same snapshot. Locking one shared schedule guard serializes the decision; Serializable with whole-transaction retry is another PostgreSQL-specific option.

5. Why do database isolation names mislead?

Explain the trade-off and test.

SQL standard labels describe phenomena, but engine-specific implementations vary: PostgreSQL snapshot behavior, MySQL InnoDB locking reads, and SQL Server configuration differ. State the engine and exact isolation mode. Validate with concurrent tests rather than assuming a name means universal semantics.

Worked follow-up / exercise

Contrast repeatable read with locking SELECT FOR UPDATE in the chosen engine.

Worked answer: In PostgreSQL Repeatable Read fixes a transaction snapshot and can reject conflicting updates; FOR UPDATE explicitly locks selected rows and makes contenders wait. Neither alone protects an invariant spanning rows that were not locked.

6. How do you reason about deadlocks?

Explain the trade-off and test.

A deadlock is a cycle of lock acquisition where each transaction waits for another. Database engines typically detect and abort one participant. Keep transactions short, acquire locks in consistent order, use appropriate indexes and retry designated deadlock errors with bounded backoff.

Worked follow-up / exercise

Explain why increasing lock wait timeout is not a root-cause fix.

Worked answer: A longer timeout merely leaves requests queued longer. Remove the cycle with consistent acquisition order, shorter transactions and indexed access, then retry only the database-selected victim safely.

7. Why does EXPLAIN differ from EXPLAIN ANALYZE?

Explain the trade-off and test.

EXPLAIN shows the optimizer's estimated plan; ANALYZE executes the query in engines that support it and reports actual runtime and row counts. Running a write under ANALYZE may execute the write, so handle production use carefully. Compare estimated-versus-actual cardinality to find bad statistics or skew.

Worked follow-up / exercise

Investigate a nested-loop join with estimated 10 rows but actual 500,000.

Worked answer: Inspect statistics, skew and parameter class, then compare BUFFERS and loop counts. Refresh or extend statistics and retest alternative joins/indexes with representative values instead of forcing a plan blindly.

8. What is the replication lag contract?

Explain the trade-off and test.

Asynchronous replicas may not reflect a write acknowledged on the primary. For read-your-writes, route sensitive reads to primary or use engine-supported session consistency/watermarks. Measure lag in time and log position; failover can introduce separate consistency and data-loss questions.

Worked follow-up / exercise

Explain a newly created order that disappears briefly from a user's history.

Worked answer: The write was acknowledged on the primary but the history read reached an asynchronous replica before replay. Route that session's freshness-sensitive read to primary or use a supported commit-position guarantee.

9. Why are replicas not backups?

Explain the trade-off and test.

Replicas copy writes and can propagate accidental DELETEs, corruption and bad migrations. Backups need retained point-in-time history, independent access controls and tested restore procedures. Define recovery point objective and recovery time objective against business needs.

Worked follow-up / exercise

Distinguish zero data loss wish from achievable RPO given replication and backup topology.

Worked answer: An asynchronous replica can lose acknowledged tail writes during failover; a daily backup can lose nearly a day. State the measured maximum gap for each failure and choose synchronous durability or tighter backup/log retention if the business RPO demands it.

10. How do you roll out a breaking schema change safely?

Explain the trade-off and test.

Use expand-and-contract: add compatible fields, deploy code that handles both forms, backfill incrementally, switch readers/writers, then remove old fields only after old applications cannot run. Watch locks, IO and replica lag and make application rollback viable.

Worked follow-up / exercise

Handle a rolling deployment where half the pods use the old field name.

Worked answer: Add the new field first, deploy readers that accept both and writers that maintain compatibility, backfill in bounded batches, switch reads, drain old binaries, and only later drop the old field.

11. When does an index hurt performance?

Explain the trade-off and test.

Indexes require additional storage and maintenance on INSERT/UPDATE/DELETE; too many can cause write amplification, memory pressure and slower vacuum/compaction depending on engine. An index on low-selectivity data may provide little benefit compared with a scan.

Worked follow-up / exercise

Measure write throughput and plan changes before adding a speculative index.

Worked answer: Replay representative reads and writes, compare latency distributions, WAL/storage growth and maintenance work, and inspect actual plans. Remove the index if its read benefit does not pay for its write cost.

12. How would you build a retry-safe stock reservation?

Explain the trade-off and test.

Use a business reservation ID with a unique constraint and an atomic conditional stock decrement in one transaction. Repeated reservation requests return the prior result instead of decrementing again; cancellations must be idempotent and linked to the original reservation.

Worked follow-up / exercise

Test a crash after decrement but before HTTP response.

Worked answer: Persist a unique reservation request ID and decrement in one transaction. After an ambiguous response, replay the same ID; it must return the stored reservation without another decrement.

What still needs practice?

Revision sheet

Invariant first: name the condition that must survive concurrent histories, then choose constraints, atomic SQL, locks or serializable retry.

Plans: compare estimated and actual rows, loops, buffers and spills on representative distributions.

Operations: bound transaction age, trace lock waits, rehearse restore and treat replica freshness as a contract.
