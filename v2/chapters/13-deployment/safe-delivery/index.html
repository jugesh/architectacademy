1. Build artifacts as a reproducibility contract

A pipeline must produce an immutable versioned artifact once, scan it, then promote that exact digest across environments. Rebuilding separately for staging and production breaks the relationship between what was tested and what was deployed. Pin critical build dependencies, record source commit, JDK/toolchain, SBOM and provenance, and use controlled secrets rather than embedding them in images. Lockfiles reduce accidental dependency drift but do not substitute for review or vulnerability analysis.

Why deploy a digest rather than a mutable image tag?

Source SHA → pinned build → tests → image digest → registry → signed attestation → deployments.

2. Test stages and quality gates

Put fast deterministic unit tests early. Follow with contract tests against externally visible API/event schemas; integration tests using representative databases; security checks; and production-like performance testing for critical changes. A green unit suite does not prove database isolation or Kubernetes shutdown correctness. Run destructive migration and failure tests in isolated environments. Use risk-based gates: every change should meet baseline security, while high-risk data changes require explicit concurrency and recovery evidence.

3. Rolling, blue/green, and canary deployments

A rolling rollout replaces replicas gradually, requiring old and new code to coexist safely. Blue/green creates two environments and switches traffic; it simplifies traffic reversal but duplicates capacity and does not roll back shared database writes. A canary routes a small percentage of traffic to a candidate and advances based on error rate, latency, business invariants and sufficient sample size. Shadow traffic can reveal performance issues but must suppress real side effects and protected data exposure.

Why can a blue/green rollback still fail?

Canary: 1% → 5% → 25% → 100%, each step guarded by user-relevant metrics.

4. Expand-and-contract database migrations

Schema deployment is a separate compatibility protocol from application deployment. First add fields/tables/indexes that older code tolerates. Deploy dual-readable/dual-writable code when needed, backfill in bounded batches, switch reads, then remove old representations only when older binaries can no longer run. Destructive DROP/RENAME in the same rollout can make application rollback impossible. Record DDL lock behavior, replication lag, transaction duration and recovery choices for the exact engine.

What is the safe path for renaming a heavily used column?

Expand → compatible deploy → backfill → read switch → verify → contract.

5. Feature flags and configuration rollout

A release should separate artifact deployment from activation when the risk justifies it. Flags allow a canary within one binary, a kill switch and targeted rollout; they also create branching complexity and stale code paths. Record owners, expiry dates and fallback behavior. Configuration changes can be more dangerous than code—database pool sizes and retry counts alter downstream load. Validate flag evaluation and configuration precedence across all instances.

What can go wrong when a kill switch is not tested?

6. Deployment lifecycle and graceful shutdown

For HTTP services, readiness should stop new traffic before process termination and the server should drain in-flight requests within its grace period. Long-running tasks need ownership and checkpoint semantics. Deployment tools should verify desired replicas, actually ready replicas, dependency health, and application SLIs. A rolling update that creates healthy-looking pods but breaks downstream state is not successful. Rollbacks should reverse code and config only when shared state remains compatible.

Why is kubectl rollout status insufficient as a quality gate?

7. Security and change governance

Protect production deployment credentials with short-lived workload identity where possible. Separate commit rights from approval of especially sensitive production changes, avoid exporting environment secrets into build logs, and audit who deployed which digest. Dependency updates can introduce compromised artifacts: require provenance, signature verification where deployed, least-privilege runners, and pinned third-party actions. Emergency patches need an auditable fast lane, not unmanaged shell sessions.

8. Release failure game day

Inject a bad SQL migration, failing readiness probe, unhealthy canary, dependency slowdown and artifact pull failure in a controlled preproduction setup. Confirm rollout pauses, rollback triggers, customer-facing monitoring, and data repair steps. Design dashboards for release correlation rather than only global CPU charts. A rollback that simply sets old image while leaving incompatible data is an incomplete recovery operation.

What should stop an automatic canary promotion?

Record detection latency, mitigation time, deployment SHA and irreversible-state assessment.

Senior interview and design review

12 answered scenarios.

For every question, explain the failure model and demonstrate evidence before reading the model answer.

1. What is an immutable artifact?

Answer before opening.
Reveal answer and exercise

One build output identified by digest and promoted unchanged across environments.

Follow-up: Explain why rebuilding in production invalidates staging evidence.

2. Why do you need SBOM and provenance?

Answer before opening.
Reveal answer and exercise

They document dependency composition and origin, supporting impact assessment and supply-chain verification.

Follow-up: How do you verify the deployed digest matches approved source?

3. Can rollback undo a DB migration?

Answer before opening.
Reveal answer and exercise

Not necessarily; shared persisted changes can outlive the binary.

Follow-up: Design a rollback-safe expand-and-contract sequence.

4. When use a canary?

Answer before opening.
Reveal answer and exercise

When limited exposure and objective telemetry can detect regressions before full rollout.

Follow-up: How do you handle low-volume endpoints?

5. How is blue/green different from canary?

Answer before opening.
Reveal answer and exercise

Blue/green maintains two environments for traffic switch; canary gradually exposes a candidate to a fraction of traffic.

Follow-up: What are their data-state limitations?

6. How do you release a breaking event schema?

Answer before opening.
Reveal answer and exercise

Deploy compatible consumers before producers emit new fields or variants, then retire old forms.

Follow-up: Plan replay of older Kafka events.

7. What is a deployment kill switch?

Answer before opening.
Reveal answer and exercise

A controlled way to disable risky behavior without rebuilding code, subject to the design's reversibility.

Follow-up: What if side effects already happened?

8. Why are CI secrets risky?

Answer before opening.
Reveal answer and exercise

Malicious build steps or dependencies can exfiltrate secrets or manipulate published artifacts.

Follow-up: Design short-lived cloud credentials for the runner.

9. What is an integration-test blind spot?

Answer before opening.
Reveal answer and exercise

A test can pass with unrealistic data, concurrency or infrastructure assumptions.

Follow-up: Design simultaneous checkout tests with a real DB.

10. How do you measure deployment success?

Answer before opening.
Reveal answer and exercise

Use service SLIs and domain invariants along with replica health and logs.

Follow-up: Define a 15-minute post-release verification window.

11. What is drift detection?

Answer before opening.
Reveal answer and exercise

Finding differences between desired infrastructure/configuration and live state.

Follow-up: How do you reconcile a console hotfix?

12. What is progressive delivery?

Answer before opening.
Reveal answer and exercise

Advancing an artifact to broader traffic or features in controlled, observed steps.

Follow-up: Specify automated abort conditions.
