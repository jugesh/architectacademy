1. The difference between monitoring and observability

Monitoring tests known conditions against signals; observability emphasizes inferring internal state from external outputs. Logs describe discrete events, metrics aggregate numeric observations, and traces connect operations across service boundaries. None is independently sufficient. Start with user-centric outcomes and a domain invariant, then connect telemetry to a request or business operation. Blindly collecting more logs increases cost without improving investigation.

2. Golden signals and SLI design

Latency, traffic, errors and saturation provide a practical service view. RED (rate, errors, duration) helps request-serving services and USE (utilization, saturation, errors) helps resources. A latency objective must define eligible traffic, success semantics and histogram units. Track attempts separately from logical operations so retries do not distort the user outcome. Business health may require an order-confirmation invariant, not merely HTTP 2xx.

3. Distributed tracing context propagation

A trace records spans linked by trace ID and parent/child relationships. W3C traceparent supports propagation across HTTP where configured, while messaging uses headers or envelopes that preserve causal links. Sampling helps cost but can miss rare incidents; combine head sampling with suitable policies and consider tail-based sampling constraints. Ensure tracing does not leak credentials through headers, span attributes or baggage. Cross-service clocks need alignment for accurate timelines.

4. Metrics design and cardinality

Counters represent cumulative events, gauges current values, and histograms distributions such as request latency. A label including every user ID, request ID or order ID creates high-cardinality series and can overwhelm storage and query performance. Choose labels such as endpoint template, status category, service and region. Preserve identifiers in logs/traces rather than metric dimensions. Histograms support fleet-level percentile approximations; never simply average p99 values from pods.

5. Structured logs and event correlation

Prefer structured JSON logging with timestamp, severity, service, environment, traceId, spanId, logical operation ID and error code. Avoid full stack traces on every expected validation error; use appropriate severity and volume limits. Keep redaction rules and access controls for PII and secrets. Correlation IDs must come from a trusted boundary or be sanitized, and tracing identity should not be used as authorization.

6. Tail latency and coordinated omission

An average hides bad customer experiences. p95 and p99 should be computed over representative requests with enough observations; the test harness must account for time when the system stalls. Coordinated omission occurs when a load generator waits for a slow response before issuing more work and thereby underrepresents delay experienced by a fixed-rate arrival stream. Measure queue wait, connection-acquisition wait, GC pauses, lock contention and downstream network time separately.

7. Alerting and incident response

Page on user harm and urgent, actionable conditions. Multi-window error-budget burn-rate alerts distinguish sudden severe regressions from slower deterioration. Dependency symptoms and resource metrics help triage but should not each create independent pages with no user impact. Build runbooks showing dashboards, owner, mitigation, known failure modes and safe verification steps. Avoid alerting solely on a threshold that changes with traffic seasonality.

8. Diagnostic playbooks and instrumentation tests

For rising p99, inspect percentile shift by endpoint, traffic mix, saturation and correlated traces. For increasing Kafka lag, compare partition skew, processing time, offset commit and downstream SQL latency. For database migrations, compare old/new write counts, CDC lag and business-level reconciliation; green infrastructure metrics do not prove data correctness. Validate instrumentation with synthetic trace fixtures and failures so missing spans or wrong labels are detected before a real incident.

Answer before opening.

Follow-up: Diagnose a slow checkout.

2. What is a RED dashboard?

Answer before opening.
Reveal answer and exercise

Rate, errors and duration for request-serving components.

Follow-up: Choose proper request denominator.

3. What is USE?

Answer before opening.
Reveal answer and exercise

Utilization, saturation and errors for resources.

Follow-up: Inspect DB pool pressure.

4. Why use histograms for latency?

Answer before opening.
Reveal answer and exercise

They retain bucketed distributions that can support aggregations and percentile approximations.

Follow-up: Avoid averaging per-pod p99.

5. What is high cardinality?

Answer before opening.
Reveal answer and exercise

Too many unique label combinations creating expensive time series.

Follow-up: Why not label by orderId?

6. What is a traceparent?

Answer before opening.
Reveal answer and exercise

W3C propagation context carrying trace identity and parent information.

Follow-up: Pass context through async processing.

7. What is head sampling?

Answer before opening.
Reveal answer and exercise

Sampling decisions near trace creation, which can discard later-important spans.

Follow-up: Design rare-error visibility.

8. What is coordinated omission?

Answer before opening.
Reveal answer and exercise

A benchmark misses latency during stalls because traffic generation is blocked or reduced.

Follow-up: Test with a constant offered arrival rate.

9. What is SLO burn rate?

Answer before opening.
Reveal answer and exercise

Rate of error-budget consumption relative to the allowed failure rate.

Follow-up: Create short- and long-window alerts.

10. How do you redact telemetry safely?

Answer before opening.
Reveal answer and exercise

Filter tokens, credentials and PII before emission, limit access, and test data retention.

Follow-up: Review baggage and HTTP headers.

11. What is an actionable alert?

Answer before opening.
Reveal answer and exercise

A timely signal of meaningful impact with a clear owner and mitigation path.

Follow-up: Reduce a noisy CPU-only page.

12. How do you verify observability?

Answer before opening.
Reveal answer and exercise

Inject known synthetic failures and assert the expected metrics, correlated spans, alerts and logs.

Follow-up: Simulate a DB timeout.
