CHAPTER 01 · PRACTICE COMPANION

Architecture Foundations: Advanced Interview Bank

30 answered technical/design questions, followed by 6 multi-part worked exercises. Expand model responses only after attempting the question.

1. How is architecture different from detailed design?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Architecture deals with system-significant structural decisions, constraints and qualities whose reversal is costly: state ownership, failure isolation, deployment and major dependencies. Detailed design elaborates components, algorithms and interfaces within those boundaries. The distinction is about consequence, not drawing level.

Challenge: Name two choices that are architecture decisions for one product but local implementation details for another.

Follow-up answer: A database choice is architectural when transaction semantics and data migration determine product correctness; a disposable local test store can be an implementation detail. A serialization format is architectural when external consumers persist it, but usually local when confined to one private in-process boundary.

2. What is an architectural driver?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

A requirement, constraint, risk or stakeholder priority that materially affects system structure. A contractual data-residency constraint can dictate regions; a strict latency SLO can force smaller critical paths. Drivers should be prioritized, quantified where possible and revisited when circumstances change.

Challenge: Convert 'must scale' into a capacity and failure scenario.

Follow-up answer: Example: sustain 600 offered checkout requests/second with p99 below 800 ms and fewer than 0.1% eligible failures for 30 minutes, including one API pod loss. State the data mix, measurement window and whether overload rejections count as failures.

3. What does a quality-attribute scenario contain?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Source of stimulus, stimulus, environment, affected artifact, intended response and measurable response criterion. It turns vague terms like scalable or secure into verifiable behavior.

Challenge: Write a scenario for zone failure during peak checkout traffic.

Follow-up answer: During peak 500 RPS, loss of one application AZ must preserve accepted orders and restore at least 99% successful eligible checkouts within ten minutes. Validate the resulting database and payment state as well as HTTP responses.

4. Why do architecture diagrams need protocols?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Protocols determine coupling, timeouts, authorization, transactional boundaries and failure behavior. Two boxes connected by an unlabeled arrow conceal whether the interaction is synchronous HTTP, durable queue or local function call.

Challenge: Annotate an order-to-payment arrow with timeout, idempotency and trust assumptions.

Follow-up answer: Example: HTTPS using workload identity; at most 350 ms from the remaining caller budget; same payment-intent key on every permitted attempt; UNKNOWN on ambiguous timeout; provider lookup for reconciliation. The numbers are a scenario budget, not defaults.

5. When is a modular monolith preferable to microservices?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

When bounded modules need cohesive transactions and coordinated release, the team is small, operational tooling is immature, or independent scaling offers little. Preserve strict module APIs and data ownership so future extraction remains possible.

Challenge: Describe a migration trigger supported by evidence.

Follow-up answer: Extract Payments when a separately accountable team needs independent security/release control and a measured workload requires distinct scaling. First prove compatible contracts and a migration path for existing intents.

6. What is data ownership in a service boundary?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

One service or module is responsible for authoritative updates to a business entity and its invariants. Other consumers access through supported contracts or projections rather than changing its storage tables directly.

Challenge: Explain why two microservices writing the same order table cannot deploy independently safely.

Follow-up answer: A shared table couples both binaries to column semantics, constraints and migration order. Coordinated expand/contract changes can make some independent releases safe, but independent deployment is not guaranteed just because the processes differ.

7. What is the difference between cohesion and coupling?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Cohesion captures how related responsibilities within a module are; coupling captures the dependencies between modules. Strong cohesion with low unnecessary coupling supports isolated change, but absolute decoupling is not an objective if it destroys required consistency.

Challenge: Identify two symptoms of an incorrect bounded context.

Follow-up answer: A routine feature repeatedly edits both domains; or a business invariant needs chatty synchronous coordination on every update. Check whether the boundary follows business meaning or merely a technical noun.

8. When does CQRS make sense?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

When write invariants and read workloads require genuinely different data models or scaling patterns. It introduces projection lag, replay and consistency work. Avoid introducing separate read stores for basic CRUD without measured benefit.

Challenge: How would a user see a just-created order before an asynchronous projection catches up?

Follow-up answer: Return the created order representation or read authoritative state for that session until the projection reaches the relevant version. Make the freshness promise explicit instead of sleeping for an assumed replication delay.

9. How do domain events differ from commands?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Commands express intent requesting action and may be rejected; events describe a fact that has occurred. An event contract should not require the original producer to synchronously supervise a consumer's immediate response.

Challenge: Rewrite 'SendEmailEvent' as an appropriate command or domain event.

Follow-up answer: Use SendConfirmationEmail as a command to a designated handler, or OrderConfirmed as a domain event that permits independent notification and analytics reactions. Neither name establishes delivery guarantees.

10. What does ACID fail to guarantee by itself?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

An ACID transaction does not automatically enforce invariants the schema or code never checks, and its isolation semantics vary. It does not make remote HTTP and independently owned service operations atomic.

Challenge: Design an atomic conditional inventory decrement.

Follow-up answer: UPDATE inventory SET available = available - :qty WHERE sku = :sku AND available >= :qty; validate qty > 0 and require exactly one affected row. Bind tenant scope where relevant, and make reservation identity idempotent in the same transaction.

11. How is write skew different from a lost update?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Lost update concerns conflicting updates to a value where one overwrites another. Write skew can update different rows based on a shared snapshot and jointly violate an invariant, even though neither row is overwritten by the other.

Challenge: Show the on-call doctors example and the guard-row alternative.

Follow-up answer: Two doctors each see the other on call and update different rows to go off call. A shared guard row locked before reading the roster serializes that invariant check. Alternatively use an appropriate serializable transaction with whole-transaction retries.

12. Why can a transactional outbox still publish twice?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

After publishing a message but before marking the outbox row delivered, a worker can crash. Recovery resends it. Outbox guarantees durability of intent with the local domain transaction; consuming systems still need idempotent effects.

Challenge: Locate the crash point and design a unique processed-event marker.

Follow-up answer: Crash after broker acceptance but before marking delivered. A SQL consumer inserts a unique (consumer_id,event_id) and applies the domain update in the same transaction; a conflict means that consumer already committed the effect. Retain markers for the replay horizon.

13. Why is a timeout an ambiguous outcome?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

The caller observed no response by a deadline, but the remote server may have committed successfully before the response was lost. Treat an external side effect as unknown and reconcile with a stable business operation ID.

Challenge: How should a payment intent recover after provider timeout?

Follow-up answer: Persist the intent before calling; retain the key after timeout; query the provider or replay under its idempotency contract. Until an authoritative result is known, expose pending status and monitor reconciliation age.

14. What does Little's Law mean for a web server?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

For stable traffic, mean in-flight requests equal arrival rate multiplied by mean response time. It describes average occupancy rather than an absolute capacity guarantee or a p99 calculation.

Challenge: Calculate in-flight requests at 350 RPS and 250 ms mean.

Follow-up answer: 350 × 0.250 = 87.5 average in-flight requests. This is a mean, not a hard integer limit or the required number of threads.

15. Why does adding API replicas sometimes harm latency?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

More replicas can multiply DB connections and retry load against a fixed bottleneck, increasing contention and queues. Scale constraints from measured service demand and global concurrency budgets.

Challenge: Compute total configured connections for 12 pods with a 30-connection pool.

Follow-up answer: 12 × 30 = 360 possible application connections, plus workers and other clients. Pool maxima are configured limits, not evidence that all connections are active.

16. What does p99 hide and reveal?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

It highlights the duration below which 99% of observations fall, exposing slow-tail behavior relative to means. But it omits the magnitude of the slowest 1%, can be noisy at low sample sizes and cannot be averaged across pods.

Challenge: Why could two endpoints' p99 values mislead when request volumes differ?

Follow-up answer: A rarely used slow endpoint and a heavily used fast endpoint cannot be combined by averaging their p99 values. Merge compatible distributions or histogram bucket counts for a defined population, and retain per-endpoint views.

17. What is a failure domain?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

A collection of resources that can fail together under one fault, such as one host, zone, region, credential or third-party dependency. Replica count alone is not resilience if replicas share an unmodeled failure domain.

Challenge: List shared dependencies in a three-AZ deployment.

Follow-up answer: Database writer, identity provider, DNS, KMS, shared configuration, release pipeline, account-level quotas and payment provider may still fail all AZs together.

18. How do circuit breakers, bulkheads and load shedding differ?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Breakers avoid repeatedly calling a suspected failing dependency; bulkheads isolate resource capacity between workloads; load shedding rejects excess work before queue growth causes cascading failures. All need deadlines and useful metrics.

Challenge: What protects payment requests when recommendation calls are slow but successful?

Follow-up answer: An independent bounded recommendation pool, short timeout and fallback contain slow successful calls. A breaker may additionally react to slow-call rate if configured; an error-only breaker is insufficient.

19. When is cache staleness acceptable?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

When the product contract permits bounded deviation from authoritative state, such as recommendation suggestions. It may be unacceptable for financial balances or inventory confirmation. Explicitly state freshness bounds and read-your-writes needs.

Challenge: Explain a stale-fill race following invalidate-on-write.

Follow-up answer: A reader loads version 4; a writer commits version 5 and invalidates; the reader then caches version 4. A TTL bounds some stale exposure but does not make reads linearizable; use a coordinated/version-aware policy when required.

20. What does a retry budget prevent?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Excess attempt amplification when several callers or layers retry while a dependency is unhealthy. Bound attempts by remaining deadline, retryable error classification and an overall rate budget.

Challenge: If three layers each allow an initial attempt plus three retries, how many leaf attempts are possible?

Follow-up answer: Four attempts per layer give 4 × 4 × 4 = 64 leaf attempts in the worst case. Three total attempts per layer give 27. Always distinguish retries from attempts.

21. Why does authentication not imply authorization?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

A valid identity says who the caller is, not which resources and actions they may access. Check tenant membership, object ownership, permissions and business constraints at trustworthy enforcement points.

Challenge: Design a negative IDOR test for orders.

Follow-up answer: Authenticate as tenant A, request tenant B’s order ID through read and mutation endpoints, and assert no data or effects escape. Include pagination, exports and alternate lookup keys.

22. How is a trace different from a metric?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

A trace connects spans for one causal operation and helps localize time spent; a metric aggregates numeric observations across operations and is better for trends, saturation and alerting. Correlate them with structured logs.

Challenge: How do you propagate context through a durable queue?

Follow-up answer: Inject trace context into approved message metadata and extract it at the consumer; create a consumer span or span link according to the async/replay semantics. Treat incoming context as untrusted and keep business identity separate from trace identity.

23. Why shouldn't metrics include order IDs as labels?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

A unique label per order creates high-cardinality time series, increasing memory, storage and query cost. Keep per-operation IDs in logs/traces and use bounded labels like route template and status class.

Challenge: Design a histogram for checkout duration.

Follow-up answer: Observe seconds in a histogram labelled by bounded route template, method and outcome category. Choose buckets around the latency objective; avoid raw URLs, customer IDs and exception text as labels.

24. What does an SLO error budget represent?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

The allowable bad fraction under a defined eligibility and observation window. For 99.9% over one million eligible operations, 1,000 may violate the objective. Budget burn allows release decisions based on user impact.

Challenge: Calculate allowed failures for 99.95% over 400,000 operations.

Follow-up answer: 400,000 × (1 − 0.9995) = 200 allowed bad eligible operations over the stated window. Define whether both errors and deadline violations count, without double-counting the same event.

25. How do RPO and RTO differ?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

RPO is maximum acceptable data loss; RTO is the time target to restore useful service. Backups and tested recovery procedures must demonstrate both, accounting for volume and dependencies.

Challenge: Explain why a hot replica is not a backup.

Follow-up answer: A replica can copy deletion or corruption immediately and may share credentials or a failure domain. Recovery requires protected historical copies, retention and a demonstrated restore procedure.

26. Why can't failback be a DNS reversal after writes switch?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Once the new side accepts writes, the old side may be stale. Switching clients back without fencing and reconciling differences can hide or lose acknowledged operations.

Challenge: Describe source-of-truth ownership across forward cutover and failback.

Follow-up answer: Fence the old writer before forward cutover, make the new store authoritative, capture subsequent changes, and reconcile them before any failback. Fence the new writer before restoring old write authority; do not allow split-brain writes.

27. What belongs in an ADR?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Context, drivers, credible alternatives, the decision, consequences, evidence, responsible owner and triggers for reconsideration. Superseded decisions should retain history to explain why the design evolved.

Challenge: Draft a four-paragraph ADR choosing Postgres over an event-sourced store for checkout.

Follow-up answer: Context: small team, relational order invariants and limited operations capacity. Decision: PostgreSQL with constraints and outbox. Consequences: straightforward local transactions but schema evolution and database scaling obligations. Validation/revisit: concurrency and restore tests; reconsider event sourcing only when audit/replay requirements justify its model and operations cost.

28. What makes an architecture review evidence-based?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Measurable scenarios traced to implementation mechanisms and tested outcomes: load curves, concurrency invariants, fault injections, authentication negatives, disaster recovery exercises and deployment compatibility.

Challenge: Propose two falsifiable tests for a claimed 99.9% checkout SLO.

Follow-up answer: Run representative steady offered load and measure eligible successful-within-deadline operations; inject a specified AZ fault and measure the same SLI during recovery. A short test can falsify a design assumption but cannot prove a month-long availability guarantee.

29. How would you choose build versus buy?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

Compare lifecycle cost, operational ownership, compliance, feature fit, integration complexity, lock-in, incident risk and migration triggers. A higher service unit price may be cheaper when avoided engineering burden is considered.

Challenge: Compare self-managed Kafka with a managed queue for modest background notifications.

Follow-up answer: For modest notification work, a managed queue usually reduces broker operations. Kafka may be justified by retained ordered logs, multiple independent replaying consumers or existing expertise. Compare delivery semantics, quotas, retention, observability and total operating effort.

30. What is an architecture fitness function?

State assumptions, mechanism, trade-off and test.
Model answer and follow-up

A repeatable check that protects intended architectural characteristics over time, such as dependency boundaries, schema compatibility, request latency, security policy or safe replay behavior.

Challenge: Choose three fitness checks for a growing Spring Boot modular monolith.

Follow-up answer: Enforce allowed module dependencies; verify idempotent effects under duplicate delivery; check schema/event compatibility across old/new versions. Each check needs a named failure condition rather than a green dashboard with no assertion.

Worked Architecture Exercises

Exercise A — Derive workload capacity from demand

Solve independently before revealing the model solution.

Scenario: A checkout API serves 720 successful RPS at peak. Mean request time is 240 ms, CPU demand is 15 ms/request, one database call holds a connection for 30 ms, and operations target 65% CPU usage. Ignore GC and failover overhead for the first calculation.

  1. Compute average in-flight requests using Little's Law.
  2. Compute total required CPU-seconds per second and CPU core budget at 65% target.
  3. Estimate average concurrently occupied DB connections.
  4. Name three reasons this calculation alone cannot select a final replica count.
Worked solution

L = 720 × 0.240 = 172.8, roughly 173 in-flight requests. CPU demand is 720 × 0.015 = 10.8 core-seconds per second; at 65% target, 10.8 / 0.65 = 16.62 cores before spare/fault capacity. Average DB occupancy is 720 × 0.030 = 21.6 simultaneous connections under the one-query and stable-load assumptions. Additional constraints: burst arrival variance, per-instance limits, GC and CPU throttling, connection pools, hot endpoints, zone-loss headroom and downstream CPU/IO saturation.

Stretch answer: If connection hold time rises to 60 ms at 720 RPS, mean occupancy is 43.2. Waiting before acquiring a connection increases request latency but does not itself increase occupied-connection time; distinguish these two measurements.

Stretch question: Now double DB wait to 60 ms and show that occupancy increases even if completed RPS has not increased.

Exercise B — Choose a service boundary

Solve independently before revealing the model solution.

Scenario: A six-engineer team has Orders, Payments and Recommendations. Orders and Payments need coordinated business outcomes. Recommendations can be stale or unavailable. Business traffic is expected to double over a year.

  1. Choose modular monolith or three microservices for the initial release.
  2. Specify authoritative state owners.
  3. Explain how payment ambiguity is resolved without pretending to use one distributed transaction.
  4. Define the conditions that would warrant extracting services.
Worked solution

Start with strong Orders and PaymentIntent modules in a modular monolith if the team does not need independent deployability today. Isolate Recommendations so its failure does not block checkout. Put authoritative order/payment-intent state in PostgreSQL with durable stable IDs; provider payment outcome requires reconciliation using a provider idempotency identity. Define module APIs and data access ownership now. Revisit split if independent scaling, change cadence, ownership and isolation produce measurable advantages over network/distributed consistency costs.

Stretch answer: Distinct audit ownership can justify a service and separate privileges even without a scaling need. Budget for durable workflow coordination, independently versioned contracts and an explicit responsibility for unknown payments.

Stretch question: Assume Payments must be audited and deployed under distinct organizational ownership: how does that change the boundary decision?

Exercise C — Diagnose a broken checkout path

Solve independently before revealing the model solution.

Scenario: p99 rises from 300 to 1,800 ms after API replicas are increased from 8 to 16. CPU utilization is 35%. Database maximum connections is 200. Each pod's pool maximum is 20. Error rate and connection-acquisition wait increase together.

  1. List likely bottlenecks ranked by evidence.
  2. Calculate configured maximum client connections before and after scaling.
  3. Choose the first three metrics to inspect.
  4. Design an overload mitigation that does not duplicate orders.
Worked solution

Configured connection capacity rises from 8×20=160 to 16×20=320, exceeding the 200-connection DB limit even before other clients. Low CPU and growing pool wait suggest DB admission/connection pressure rather than insufficient API CPU. Inspect DB active connections, Hikari pending/acquire wait and DB query/lock times. Reduce globally offered concurrency; tune per-pod pools with aggregate budget, consider load shedding and query optimization, and only retry operations with business idempotency. Do not add more API replicas.

Stretch answer: Inspect pool distribution per pod, request executor queues, lock/query waits, DNS/TLS/connect time, provider waits and CPU throttling. A fleet total of 40 can hide one saturated small pool or a non-database bottleneck.

Stretch question: If the DB uses 40 connections but latency remains high, what other queue or network measurements are needed?

Exercise D — Crash-safe payment state machine

Solve independently before revealing the model solution.

Scenario: An API creates a payment, the provider charges the card, the API crashes before saving provider confirmation, and the client resends the POST.

  1. Define the stable logical operation identity.
  2. Describe authoritative states before and after provider invocation.
  3. Specify safe duplicate request behavior.
  4. Prove that a brand-new provider charge must not be issued blindly.
Worked solution

Use a tenant-scoped stable PaymentIntent ID and a provider idempotency identity. Persist the local intent before provider contact. On timeout or crash, state is UNKNOWN or RECONCILIATION_REQUIRED until lookup by provider identity confirms outcome; do not infer failure. A duplicate POST loads the same intent, validates request fingerprint and returns the known result or pending status. Test crashes before local intent, after local intent, after remote charge and after local confirmation. Reconciliation or idempotent provider replay—not a new charge identity—is the correct recovery path.

Stretch answer: Keep the outcome unresolved, stop automatic new charge attempts and route to operator/provider reconciliation. State the limitation in the API/product contract; no client-side algorithm can infer a remote outcome from a missing response.

Stretch question: What would you do if the provider did not offer lookup or idempotency guarantees?

Exercise E — Evaluate a reliability claim

Solve independently before revealing the model solution.

Scenario: A team claims that three application instances in three AWS availability zones prove 99.99% checkout availability. All instances use one database cluster and a single external identity provider.

  1. Identify unproven dependencies and correlated failure modes.
  2. Rewrite the claim as a measurable SLI/SLO and fault scenario.
  3. Design three controlled game-day tests.
  4. Define how accepted order writes are validated after failover.
Worked solution

Three app AZs do not establish database, IAM, IdP, DNS, payment provider or release resilience. Define checkout success as a valid logical order operation completing within deadline over a known window, and specify an AZ-failure scenario. Test one app AZ loss, database election and IdP slowdown independently. Confirm p99, error fraction, correct order persistence and no duplicate charged intents. Failover validation requires authoritative state reconciliation and safe retry behavior, not only HTTP green health probes.

Stretch answer: Choose RPO from acceptable loss of acknowledged business data and RTO from acceptable recovery duration. Measure backup age plus log replay coverage and restoration through application readiness. No universal numeric target follows merely from using backups.

Stretch question: Explain the RPO/RTO required if the database must be restored from backups instead of failing over.

Exercise F — Produce an architecture decision record

Solve independently before revealing the model solution.

Scenario: Choose between a modular monolith and independently deployed microservices for an order management platform. Team size is seven, peak workload 300 RPS, quarterly compliance audit, weekly delivery, and a requirement to recover from a single pod failure.

  1. Write one precise architecture decision statement.
  2. State assumptions and alternatives.
  3. Identify benefits, downsides and operational consequences.
  4. Choose two fitness functions and revisit conditions.
Worked solution

Decision: implement modular Spring Boot boundaries over an authoritative relational data store, deploy multiple stateless replicas and publish selected integration events via outbox. Benefits: straightforward transactions, single deployment pipeline and lower operational overhead. Downsides: shared release and scale unit. Alternatives: split services with independent stores and saga coordination, rejected pending ownership/scaling evidence. Fitness functions: module dependency architecture tests; fault-injected idempotent checkout integration test. Revisit after independent domain teams emerge or measurable scaling/release bottlenecks dominate.

Stretch answer: Risk: slow recommendations consume checkout request threads or connections. Control: a separately bounded pool and short deadline with a non-personalized fallback; verify checkout success during a recommendation stall.

Stretch question: Add one risk for the recommendation dependency and one control to prevent it from blocking checkout.

Chapter 1 — Architecture revision sheet

Definition: architecture is the set of consequential structural and policy decisions whose reversal would be expensive. Every such decision must be justified against business and quality drivers.

Core decision sequence

  1. Define business outcomes, constraints and nonnegotiable invariants.
  2. Express quality attributes as measurable scenarios with a stimulus, environment, response and measure.
  3. Draw context, container, dynamic/failure and deployment views.
  4. Assign one authoritative owner to each state transition and consistency rule.
  5. Compare credible alternatives, including their operational and migration costs.
  6. Design timeouts, retries, admission limits and unknown-outcome recovery.
  7. Test p99, saturation, business correctness, one-zone failure and safe rollback.
  8. Record ADRs with triggers for review and automated fitness functions.

Architectural red flags

Shared tables across nominally independent services; global admin roles; p99 described without request population; claims of exactly-once effects without an identity and persistence boundary; multi-AZ claimed as proof of disaster recovery; per-hop timeouts exceeding caller deadlines; unbounded queues; data migrations without compatibility or failback reconciliation.

Self-test

  1. Distinguish an architectural driver from a technology preference.
  2. Compute average concurrency at 400 RPS and 250 ms mean.
  3. Explain why a timeout does not prove business failure.
  4. Describe one stale cache-fill race.
  5. Explain a payment-provider crash window.
  6. List the evidence needed to claim safe one-zone failure.
  7. Compare outbox with synchronous publish-after-commit.
  8. Draft an ADR choosing a modular monolith over microservices.
