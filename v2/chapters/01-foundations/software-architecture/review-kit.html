CHAPTER 01 · ARCHITECTURE WORKSHEETS

Architecture Review Kit

Reusable templates and a filled decision record. Use this pack when preparing a system design or critically reviewing another architect's proposal.

1. Architecture brief: one-page decision contract

What evidence would invalidate this claim?

Before choosing infrastructure, make the decision context explicit. A complete review should reveal what is known, what is assumed, what matters most and how quality will be verified.

  • System/business outcome: the user-visible action and what success means.
  • In scope/out of scope: which journeys, regions, integrations and migration steps are covered.
  • Actors and trust boundaries: customers, internal services, administrators, providers.
  • Scale profile: peak and normal arrival rates, read/write mix, burst duration and expected growth.
  • Top three quality scenarios: stimulus, environment, response and numerical measure.
  • Correctness invariants: uniqueness, inventory, balances, authorization and ordering.
  • Hard constraints: compliance, budget, skills, platform, vendor contracts and rollout window.
  • Evidence: observed metrics versus untested assumptions.
  • Decision owner, review date, and explicit trigger for re-evaluation.

2. Quality-attribute scenarios

What evidence would invalidate this claim?

Replace adjectives with cases that can fail a test. Every row is a contract about one workload and one operating environment.

  • Availability: during loss of one API pod at 500 RPS, checkout successful logical operations remain above the agreed SLO while replicas drain.
  • Latency: p99 of eligible checkout requests remains below 900 ms under representative peak mix with less than the defined error ratio.
  • Correctness: repeating the same payment intent, including after a process crash, never creates a second independent provider charge.
  • Security: an authenticated customer cannot read a different tenant's order by altering any identifier or pagination filter.
  • Recoverability: an operator restores the order database from a tested backup within the defined RTO and preserves the agreed RPO.
  • Deployability: old and new application versions coexist during rolling deployment without corrupting shared schema or events.
  • Observability: a timeout incident exposes the logical order identity, span chain, DB wait, provider attempt and reconciliation state without sensitive data leakage.

4. Trade-off and decision matrix

What evidence would invalidate this claim?

Score only against the actual drivers, not popularity. A weighted matrix forces assumptions into the open but should not hide disqualifying constraints.

  • Candidates: modular monolith, microservices, event-driven integration, managed workflows.
  • Dimensions: domain isolation, transaction simplicity, independent scale, team ownership, deployment complexity, operational recovery, cloud cost.
  • Nonnegotiables: compliance and no duplicate charges cannot be offset by arbitrary weighted scores.
  • Quantify where possible: p99, engineer-hours, RPO/RTO, expected incident cost, write volume.
  • Write negative consequences explicitly for the selected option.
  • Give a threshold at which the selected option must be revisited.

5. Sample ADR — modular monolith for checkout

What evidence would invalidate this claim?

This is a filled architecture decision record, not merely a blank template.

  • Status: accepted for initial rollout; owner: checkout tech lead.
  • Context: six engineers, 500 peak RPS, weekly release, strict payment-intent uniqueness, limited on-call coverage.
  • Alternatives: (A) single unstructured codebase; (B) modular Spring Boot monolith; (C) independently deployed Order/Payment/Inventory microservices.
  • Decision: choose B, enforcing dependency boundaries and order/payment data ownership internally, with outbox for asynchronous integrations.
  • Benefits: one authoritative transactional boundary for order state; simpler local debugging and deployment.
  • Costs: coupled release artifact and coarse scale unit; modules can erode without fitness checks.
  • Validation: module dependency tests, provider timeout reconciliation test, SQL concurrency tests, load-test knee and one-pod-loss drill.
  • Revisit if: independent teams own domains; payment traffic needs separate scaling/security isolation; release conflicts cause measurable delays.
  • Supersession: create a new ADR rather than rewriting this accepted historical decision.

6. Failure-mode and effects analysis (FMEA)

What evidence would invalidate this claim?

For each credible fault, identify detection, safe user behavior and recovery; severity should reflect business impact rather than infrastructure aesthetics.

  • Loss of checkout pod during SQL commit: retry using stable request ID; verify no duplicate record or charge.
  • Payment provider charged but response timed out: mark UNKNOWN, query provider with the same intent key, reconcile and replay.
  • Kafka event published twice: processed-event unique constraint prevents duplicated business effects.
  • DB connection pool exhausted: bounded admission, fail-fast overload response and controlled retries; verify no unbounded queue.
  • Recommendation timeout: suppress personalization only; do not make payment availability dependent on it.
  • Zone failure: verified spare capacity and target-group draining while authoritative database remains consistent.
  • Corrupted or deleted orders: isolated backup restore plus replay from approved point-in-time logs; prove RPO and RTO.
  • Leaked credential: revoke/rotate, audit downstream access and test blast-radius limits.

7. Performance and capacity calculation worksheet

What evidence would invalidate this claim?

Use measured service demands; these sample figures illustrate arithmetic rather than promise actual capacity.

  • Peak offered rate λ = 500 requests/second; steady mean W = 0.18 second → mean L ≈ 90 in-flight operations.
  • CPU demand Dcpu = 0.012 CPU-seconds/request; at 500 completed RPS → 6 CPU-cores of demand.
  • At planned 60% CPU utilization → 10 cores before operational headroom, GC variation and zone-loss capacity.
  • DB connection occupancy Wdb = 0.03 second per request → approximately 15 concurrent active DB connections under assumptions.
  • If 10 pods each have 25 maximum connections → configured application maximum of 250, plus background worker pools.
  • If DB max connections is 180, do not treat configured 250 as harmless; bound aggregate admission and independently measure active usage.
  • Run at 50%, 75%, 100%, 125%, 150% peak and repeat one-pod loss, slow DB, cold cache and error burst.
  • Record offered load, successful throughput, p99, CPU throttling, GC, DB pool waits, SQL duration, queue age and reject rates.

8. Release and schema compatibility protocol

What evidence would invalidate this claim?

A deployable architecture handles multiple binary versions and partially applied state safely.

  • Expand: create new nullable columns/events while old readers still work.
  • Deploy compatible writer: maintain old and new representations during the transition if necessary.
  • Backfill: use bounded batches and checkpoints; watch locks, replication lag and operational load.
  • Read switch: move readers after backfill and consistency validation.
  • Observe and hold rollback window: verify old binary remains compatible with resulting data.
  • Contract: remove obsolete fields only after all old executables are retired and rollback is no longer required.
  • For events, deploy compatible consumers before producers emit incompatible payload variants.
  • Rollback means application/config rollback only where data state remains compatible; destructive migration needs explicit recovery plan.

9. Test pyramid for architectural claims

What evidence would invalidate this claim?

Map each guarantee to the narrowest test that can genuinely prove it, adding larger end-to-end exercises where boundaries interact.

  • Unit tests: domain calculations, validation and pure state transitions.
  • Architecture tests: allowed dependency directions, forbidden package imports and module ownership.
  • Contract tests: HTTP schemas, event compatibility, authentication/authorization behavior.
  • Integration tests: actual database isolation and concurrent unique constraints; outbox atomicity and consumer deduplication.
  • Fault injection: kill process after commit, provider timeout after charge, broker duplicate delivery, disk/network slowdown.
  • Load tests: offered versus completed throughput, queueing knee, realistic data cardinalities and one-zone capacity.
  • Security negatives: token audience mismatch, cross-tenant object IDs, SSRF attempts, leaked request headers.
  • Recovery exercise: backup restoration, point-in-time correctness, RPO/RTO measurement and operator runbook.

10. Production readiness sign-off

What evidence would invalidate this claim?

A chapter or service can only be called reviewed when there is enough evidence to support significant claims, not when checklist boxes were guessed.

  • Architecture context and at least one runtime failure sequence are linked from documentation.
  • Top user-facing SLOs have owner, denominator, monitoring and a tested alert.
  • Transactional invariants have database constraints and crash/concurrency tests.
  • External side effects have idempotent identities and unknown-outcome recovery.
  • AuthN/AuthZ boundaries include tenant-object negative tests.
  • Queries, caches and queues have bounded capacity, TTL/age limits and overload behavior.
  • Changes are reversible where claimed, and schema evolution has compatibility tests.
  • Backups are restored on a schedule with measured RPO/RTO.
  • Incident runbooks identify containment actions and evidence sources.
  • Each unresolved risk is named, prioritized, owned and dated.
