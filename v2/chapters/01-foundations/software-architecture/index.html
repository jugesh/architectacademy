1. What software architecture actually is

Which decisions are expensive to reverse, and why?

Software architecture is the set of consequential decisions that determine a system’s structure, constraints, interaction patterns, and ability to evolve. Components and boxes are useful representations, but they are not the architecture itself. The architecture exists in dependency directions, ownership of state, failure boundaries, consistency contracts, deployment topology, operational policies, and the constraints under which engineers make changes.

A decision is architecturally significant when changing it later has a high economic or operational cost. The choice between PostgreSQL and a document store may be significant when it determines transactional invariants and query access patterns. The choice of a Java class name usually is not. An architecture should explain why a system is structured a particular way, not merely describe what is deployed.

Architecture is both a design and a decision process. The design is evaluated against measurable requirements; the process records assumptions, alternatives, evidence, trade-offs, and what would invalidate a choice. An architecture document that lists Kafka, Redis, Kubernetes and microservices without naming the problem each solves is a technology inventory, not an engineering argument.

Four practical views

  1. Logical: domains, responsibilities, business rules, module boundaries, and dependency directions.
  2. Runtime: request flows, communication protocols, state transitions, retries and concurrency.
  3. Deployment: regions, zones, networks, processes, persistence, trust boundaries and failover paths.
  4. Development: repositories, teams, code ownership, build dependencies, release and migration paths.

Good architecture keeps these views consistent: a “stateless service” on a diagram cannot secretly depend on local pod memory to preserve a shopping cart across deployments.

Feedback into the next decision
If every microservice uses the same database schema, is it really independent?

Not in its data ownership or release evolution. Separate processes do not create autonomous service boundaries when one schema change can break several services. Independence must be tested through deployments, contracts and data ownership.

2. Architectural drivers: constraints, risks, and assumptions

What makes a requirement architectural?

Begin by separating functional outcomes, quality attributes, hard constraints and assumptions. Functional requirements describe what the system does, such as “accept an order and reserve inventory.” Quality attributes describe how well it must do so, under specified conditions: “99.9% of eligible checkouts complete successfully within 800 ms during peak traffic.” Constraints include regulatory jurisdiction, the existing Java platform, identity provider, data retention law, budget, release calendar and team size. Assumptions are beliefs that need validation, such as an expected 2% peak write ratio.

Rank requirements by risk and sensitivity, not by how interesting the technology is. A weak assumption about request traffic can invalidate instance sizing. An undocumented cross-region data-residency rule can invalidate the entire deployment topology. Gather evidence from product, operations, security, finance and delivery teams. When requirements conflict, force an explicit trade-off.

Quality attribute scenario template

Specify source, stimulus, environment, artifact, response, and response measure. Example: “During a single availability-zone failure (environment/stimulus), existing authenticated customers (source) can place orders (artifact/response) with fewer than 1% failed eligible operations for the 10-minute recovery period (measure).” This is testable; “highly available” is not.

A requirements workshop should produce an ordered list of business-critical scenarios, acceptable degradation modes, a list of assumptions to test and a definition of what the system may sacrifice under stress. If inventory correctness is nonnegotiable but recommendation freshness is not, the architecture should make that asymmetry visible in deployment and failure design.

CorrectnessNo duplicate charge for one payment intentDurable intent IDs and reconciliation

Which is more useful: 'five nines uptime' or 'users can check out during an AZ failure'?

The second frames user-visible behavior and a failure scenario. Add explicit percentages, scope and observation windows to make it testable. Five nines alone is ambiguous about the denominator and affected functionality.

3. Stakeholders, system boundaries and the C4 model

Where does the system end and its environment begin?

Start with a system context diagram: who uses the system and which external systems supply identity, money movement, messaging or reporting. Then draw a container-level view of separately deployable applications and data stores. Component-level diagrams are useful where a container has genuinely meaningful internal boundaries; code-level diagrams should be created only when they answer a concrete maintenance question. The C4 approach provides a common vocabulary for these views without prescribing a particular programming style.

A diagram should name protocols and responsibilities on relationships. The arrow “Order Service → Payment Provider” is incomplete without indicating whether it is synchronous HTTPS, what timeout applies, how ambiguous results are reconciled, and which system owns the payment state. Diagram legend and timestamps matter because deployments and failure handling change.

Draw external trust boundaries and data ownership boundaries explicitly. A message bus often carries asynchronous communication but does not imply that consumers own the source’s data. A shared read replica also does not automatically create shared write authority. Resist putting every implementation detail in one enormous diagram; use separate static, dynamic and failure views with cross-references.

Diagram review checklist

Can a new engineer identify the entry point, the writer of record, external dependencies, data classification, protocols, authorization decisions, failure boundaries, and each state transition requiring idempotency? If not, the diagram is decoration rather than an operational artifact.

Can one C4 diagram prove the architecture is reliable?

No. Static component relationships omit timing, concurrency and failure semantics. Add sequence diagrams, deployment topology, state machines, resource budgets and explicit failure scenarios.

4. Functional decomposition and domain boundaries

What should be grouped, and what should be separated?

Decompose by business capability and invariant rather than by framework layer alone. “Orders” may own order lifecycle and a stable order ID; “Payments” may own provider interactions and a payment-intent state machine. An order workflow can span both without pretending that a single database transaction crosses external systems. Identify aggregates where invariants must hold together, then decide whether an aggregate can be updated atomically within its storage boundary.

High cohesion means closely related responsibilities and changes stay together. Low coupling means one component can evolve without forcing synchronized changes in other components. These are not purely code-level ideas. At runtime, synchronous dependency chains create availability coupling. At the data layer, shared tables create schema and ownership coupling. Organizationally, separate services owned by one overburdened team can add coordination without gaining independent delivery.

Use a modular monolith when cohesive module boundaries provide enough separation without the deployment, network and observability overhead of microservices. Split only when there is evidence of independent scaling, change cadence, ownership, isolation or technology requirements. A microservice boundary should be hard to cross accidentally and should not require distributed transactions for routine operations.

Boundary test

Ask: does the proposed module own its data updates? Can it be tested in isolation? Would a new requirement force cross-boundary edits? Can the failure of a noncritical module be contained? Is the team capable of deploying and operating it independently? These questions are more informative than the number of API endpoints.

BoundaryStrong reasonWarning sign
OrdersOwns lifecycle and order invariantsOther services update its tables
PaymentsDistinct external risk and reconciliationOrders directly stores provider credentials
RecommendationsIndependent latency and failure budgetCheckout hard-fails when it is unavailable
When does splitting a monolith increase risk?

When it introduces synchronous chains, cross-service invariants and operational overhead without independent ownership or scaling benefit. Prefer strong modular boundaries inside one deployment until evidence justifies a distributed split.

5. Architecture styles: layered, hexagonal, event-driven and services

Which style addresses which change pressure?

A layered architecture separates presentation, application, domain and infrastructure concerns. It is familiar, but accidental downward dependencies and generic service classes can turn layers into pass-through ceremony. Hexagonal architecture (ports and adapters) makes domain behavior depend on interfaces expressing required capabilities, while HTTP controllers and SQL repositories implement adapters. It improves testability and replacement cost but should not produce one abstraction per trivial line of code.

Event-driven designs decouple producers from consumer timing and enable fan-out and replay, at the cost of event schema governance, duplication, delayed consistency, ordering constraints and difficult incident correlation. Service-based architectures allow independent deployment but increase networking, security, testing and operational costs. A system may combine these styles: a modular monolith internally, with an outbox publishing selected domain events to independent analytical consumers.

Separate commands (requests to change state), queries (read state), and events (statements of what has occurred). An event is not a disguised remote procedure call just because it travels via Kafka. Consumers must expect redelivery. CQRS can separate read/write models for performance or complexity reasons, but most CRUD systems do not need distinct infrastructures merely to satisfy a pattern name.

Decision rule

Choose the least complicated style that satisfies independent change, correctness, availability, performance and ownership requirements. Prove the need for complexity by tracing one representative business workflow through faults and deployments.

Does event-driven mean eventual consistency everywhere?

No. Local transactions may remain strongly consistent within their database or aggregate. Events commonly make communication across service boundaries asynchronous and eventually reflected in downstream projections.

6. Data ownership, ACID, consistency and distributed transactions

Which invariants cannot be temporarily violated?

Define the writer of record for each business entity and distinguish transactional correctness from data freshness. ACID describes atomicity, consistency, isolation and durability in a database transaction context; it does not assert that every application invariant is automatically enforced. Isolation levels permit different concurrent outcomes, and constraints or locking may still be required. For an inventory quantity, a conditional atomic decrement is often safer than read-then-write performed from application memory.

When an invariant crosses independently owned services, a single local transaction is insufficient. A saga coordinates local transactions and compensation while exposing intermediate states; compensation can fail and is not equivalent to rollback. A transactional outbox atomically stores the local business mutation and intention to publish an event; the publisher and consumer still need retry and deduplication. Avoid claiming exactly-once effects without defining the persistence boundary and stable business IDs.

Consistency is a product contract. Payment confirmation should not be based on a stale cache. A recommendation list can tolerate seconds of staleness. Replication lag and read preference can violate read-your-writes if not addressed. Define what users see during PENDING, UNKNOWN, COMPENSATING and FAILED states before writing infrastructure code.

Checkout:
1. Begin SQL transaction
2. Enforce unique orderRequestId
3. Insert order and outbox event
4. Commit
5. Outbox worker publishes (may publish twice)
6. Consumer applies using unique processedEventId

Never include remote HTTP charge inside an imaginary
all-resource atomic SQL transaction.
Why does a Kafka transaction not make a SQL update exactly once?

Kafka transactions cover supported Kafka operations, not arbitrary external SQL state. The SQL domain update and deduplication marker must be atomic in SQL, while offset/acknowledgment ordering tolerates replay.

7. Availability and failure domains

What fails together even when replicas exist?

List the boundaries at which a failure can be correlated: thread, process, container, node, availability zone, region, cloud account, DNS, identity provider, KMS and a third-party API. Running three pods on the same node is process redundancy, not node redundancy. Running across zones mitigates many zonal events but not regional control-plane or configuration failures. Shared credentials or a single database primary can become common points of failure even across zones.

Architecture decisions must state the acceptable degraded service. For example, order creation may proceed without personalized recommendations but must refuse a charge when authoritative inventory state is unavailable and overselling is forbidden. Design graceful degradation at explicit boundaries instead of swallowing dependency exceptions and claiming success. Define availability from user-visible eligible operations rather than host uptime.

A circuit breaker limits some calls to a failing dependency; a bulkhead reserves resources for independent work; admission control rejects overload rather than letting queues grow without bound. These mechanisms cannot make an unavailable authoritative data store consistent or recover lost acknowledged writes. Use the proper mechanism for the failure mode.

Failure review

Simulate process death before database commit, process death after commit before response, dependency slowdown, zone loss and expired credentials. For each, name the authoritative state, caller-visible result, retry owner, recovery mechanism and telemetry evidence.

Recommendation service downCheckout succeeds without suggestionsBulkhead and fallback
Payment outcome unknownOrder shows pendingIntent and provider reconciliation
DB unavailableFail safely without duplicate writesBounded timeout, retry policy, restore/failover
Does deploying in three availability zones guarantee 99.99%?

No. Database dependencies, IAM/DNS, capacity distribution, rollout bugs and regional failures may remain correlated. Availability must be validated under explicit fault assumptions with suitable data correctness.

8. Performance engineering: latency, throughput, concurrency

How do demand, service time and queues interact?

Performance is a resource and queueing problem, not merely an instance-count problem. Arrival rate is offered operations per second; completed throughput is successful operations per second. Mean concurrency follows Little’s Law for a stable system: L = λW. If 500 requests arrive per second and the average end-to-end time is 0.2 seconds, about 100 requests are in flight. If time rises to 1 second without change in arrival rate, about 500 may be in flight. This does not imply the service can process more work; the extra concurrency may be queueing and waiting.

Differentiate CPU demand (CPU-seconds per request), wall-clock latency, time holding a database connection and waiting for connection acquisition. A service requiring 20 ms CPU per completed request at 600 RPS demands about 12 CPU cores at full theoretical utilization; at a 60% operating target, approximately 20 cores are needed before fault headroom. If its DB access holds a connection for 40 ms per request, mean DB connection occupancy at 600 RPS is about 24, assuming one such operation per request and stable load.

Latency percentiles describe distributions. p99 of 800 ms means 99% of sampled requests finish in 800 ms or less; 1% take longer. Never average independently calculated p99s and treat the result as fleet p99. Use raw observations or aggregatable histograms. Queues and tail latency often grow disproportionately as utilization approaches saturation, and one hot partition may limit throughput despite low average CPU.

Capacity test protocol

Run staged traffic with representative data, warm and cold caches, separate read/write mixes and error-rate tracking. Graph offered versus completed RPS, p95/p99, CPU throttling, active and pending database connections and queue age. Identify the throughput knee, then inject pod loss and downstream slowdown to evaluate required capacity margin.

λ = 500 requests/second
W = 0.2 second (mean latency)
L = λ × W = 100 in-flight requests

CPU demand = 0.020 CPU-s/request × 600 RPS
           = 12 CPU cores worth of demand
At 60% target use: 12 / 0.60 = 20 cores
(plus explicit failure headroom)
Can Little’s Law tell you how many Kubernetes replicas to deploy?

Not alone. It relates stable mean concurrency, arrival rate and mean time; replica count requires CPU demand, downstream concurrency limits, target utilization, distribution of work and resilience headroom.

9. Caching and asynchronous processing

Where does eventual work enter, and what happens on a miss?

A cache reduces repeated expensive reads when data is reused and some staleness is acceptable. It introduces invalidation, hot-key and miss-storm failure modes. A successful writer invalidating a key does not by itself prevent a concurrent stale reader from filling an older value after the invalidation. Versioned entries, coordinated fills or a documented TTL may be appropriate depending on the consistency contract. A 99% cache hit ratio can still yield poor p99 if the slowest 1% are cache misses.

Asynchronous queues decouple request latency from background work but introduce delivery semantics. A worker that writes SQL then crashes before acknowledging the queue message may process it again. Therefore, use a stable event ID and a unique processed-event marker in the same database transaction as the business update when repeated effects matter. Queue lag is not only a count; age of the oldest unfinished business operation is often more user relevant.

Asynchrony is not a free capacity increase. It relocates waiting and creates a backlog that must be drained. If arrivals average 120 jobs/second and each worker can complete 20 jobs/second, six workers merely keep up in an ideal model. Clearing an existing backlog requires additional capacity, provided the database and provider allow it.

API → durable business write + outbox → event bus

                        ▼                              ▼
                    Search index                 Email worker
                 eventual projection            deduped send

Each consumer: state + event-id marker, then ack
When does moving work onto a queue reduce user-visible latency but not system load?

When work is performed after acknowledgment rather than inline. CPU, IO and downstream demand still exist; only their scheduling and user-perceived blocking path change. A queue requires a sustainable drain rate.

10. Security, trust boundaries and least privilege

Who is allowed to cross each boundary?

Authentication establishes an identity; authorization determines permitted operations on a particular resource. A valid signed token for another API must not be trusted solely because the signature verifies; validate issuer, audience, temporal claims and appropriate permissions. Apply tenant and object ownership checks within domain workflows, not only at a gateway. A caller should not retrieve an order by changing its identifier in the URL.

Service-to-service access uses distinct workload identities and narrowly scoped permissions. Do not share broad administrative credentials across services. Treat ingress request headers that claim user identity as untrusted unless a trusted, authenticated proxy is known to set them. Secrets, traces and logs should not expose access tokens, card details or private user data. Encrypt transport and stored data as needed, but remember that encryption does not prevent an overprivileged application from reading plaintext.

Use threat modeling to identify assets, attacker entry points, trust boundaries and plausible abuse. STRIDE prompts spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege. For every important threat, state a preventive or detective control plus a negative test. This produces a better outcome than adding “zero trust” to a diagram without specifying identity and policy enforcement.

Untrusted Internet
  └── API ingress: TLS + token validation + rate limiting
        └── Order API: tenant/order authorization
              └── Database: least-privilege workload identity
                    └── Audit: immutable protected log destination

Each arrow crosses an explicit trust/permission boundary.
Is mutual TLS enough to authorize a payment refund?

No. mTLS can establish service identity and protect transport, but the domain still needs policy on refund amount, account, actor permissions and the specific payment intent.

11. Observability and operational diagnosis

Can an incident be reconstructed from evidence?

Metrics tell you the trend and scale; logs record discrete facts; traces show causal journeys across components. Use RED—rate, errors, duration—for request paths and USE—utilization, saturation, errors—for constrained resources. Business metrics can identify incorrect behavior even while servers return 200. A trace should connect the incoming checkout request, order transaction, outbox publication and async consumer where the tracing design supports propagation.

Instrument saturation rather than only utilization: a CPU may be mostly idle while all database connections are in use and requests wait. A request-duration histogram supports aggregate percentile estimation; per-request IDs should appear in logs or traces, not high-cardinality metric labels. Keep an SLI that counts eligible logical operations, not each internal retry attempt.

Define SLOs before configuring pages. At a 99.9% success target over one million eligible requests, 1,000 bad requests exhaust the budget. Burn rate measures how rapidly that allowance is consumed. A severe but brief incident can deserve immediate response even while the monthly percentage remains superficially healthy. Alert on user impact and actionable failure conditions, then use dependency metrics and traces to locate cause.

Dashboard:
- checkout_success_total / checkout_eligible_total
- latency histogram by route template and status category
- DB pool active / pending / acquire-wait
- Kafka oldest event age
- order-to-payment reconciliation lag
- failed business invariants

TraceId belongs in logs and traces, not one metric series per ID.
Why can all pods show green while customers cannot complete checkout?

Shallow readiness checks can pass while dependency saturation, bad authorization rules or inconsistent business data break the workflow. User-visible SLIs and representative synthetic transactions close this gap.

12. Resilience: timeouts, retries and circuit breakers

Who retries, within whose remaining deadline?

A timeout is a bound on a local wait; a deadline is the latest acceptable completion for the entire operation. If a 900 ms checkout has already spent 300 ms on authentication and 200 ms on inventory, a downstream payment timeout of 1,000 ms is invalid because the budget is nearly exhausted. Propagate remaining time and reserve capacity for response serialization and cleanup.

Retries amplify work. When three layers each permit three attempts, one request can generate up to 27 leaf attempts in the worst case. Keep retry ownership explicit, apply bounded backoff with jitter and consider an attempt budget. Retrying an ambiguous POST is safe only when the domain operation is idempotent or has a reconciliation mechanism. A circuit breaker limits calls into a failing dependency, while a bulkhead bounds resource consumption by a subsystem; neither fixes an unsafe payment state machine.

Resilience mechanisms themselves require tests. A circuit breaker that only opens on 5xx may remain closed when a dependency slowly returns 200 responses and exhausts caller pools. Load shedding should protect critical workflows first and communicate a meaningful retry contract to callers.

900-ms caller deadline
  auth 120 ms | inventory 160 ms | serialization reserve 70 ms
Remaining maximum for payment and other work: 550 ms

Retry topology:
client (3) × gateway (3) × service (3) = 27 leaf attempts
Choose one retry owner and enforce end-to-end deadline.
Why is an end-to-end deadline preferable to independent per-hop timeouts?

It prevents downstream work continuing long after the caller can use it, bounds compounded waits and enables rational allocation of a finite latency budget.

13. Architecture economics: build, buy and operational cost

What is the total cost of a design decision?

Total cost includes cloud resources, engineer time, incident response, on-call load, release coordination, compliance effort, vendor lock-in and the cost of delaying features. An event bus may reduce coupling for independently deployed consumers but add schema governance and debugging. EKS may provide ecosystem standardization for a large Kubernetes-capable organization while adding needless operational weight for three simple services. The correct decision depends on context.

Consider cost sensitivity. A 100 ms database call that occupies an expensive connection can limit throughput even when the compute service is cheap. Cross-region data transfer can dominate the cost of a chatty microservice protocol. Failing to budget logs and metrics may produce a large observability bill, especially with per-user high-cardinality labels. Resilience also costs capacity: planning for one-zone loss requires additional headroom.

Record the expected break-even point for a technology choice: traffic, team count, availability target, operating cost or growth assumption. Revisit decisions when the trigger changes. Avoid architecture for speculative global scale when present constraints are an understaffed operations team and rapidly changing product requirements.

Why can managed cloud services cost less even at a higher unit price?

They may reduce engineering and operational time, upgrade burden, recovery risk and time to market. Compare total lifecycle cost against measured requirements, not raw instance hourly prices.

14. Architecture decision records (ADRs)

How do teams preserve reasoning and revisit decisions?

An ADR is a concise, versioned record of a decision's context, options, consequences and status. It makes assumptions reviewable and prevents teams from endlessly relitigating choices. Record what was known at decision time, why alternatives were rejected and the evidence or trigger that would warrant reconsideration. A decision might be “Use PostgreSQL as the authoritative order store and publish domain events via a transactional outbox” with trade-offs around write schema flexibility and eventual projections.

ADRs should be discoverable near code and architecture documents. They are not immovable law: supersede them when evidence changes, rather than silently editing history to pretend a design had always been obvious. Include security, operations and deployment consequences, not only programming advantages. If a proposal has no explicit downside, it has not been evaluated seriously.

Compact ADR template

Title: decision statement. Status: proposed/accepted/superseded. Context: drivers and constraints. Options: credible alternatives. Decision: selected approach. Consequences: positive and negative. Validation: tests, measurements and owners. Revisit when: thresholds or assumptions change.

ADR-001: Keep checkout as modular monolith (Accepted)
Drivers: 5 engineers; 300 RPS; one DB transaction boundary;
         weekly releases; scarce on-call coverage.
Alternatives: 3 independently deployed microservices.
Consequence: simpler reliability now; coupled deployment unit.
Revisit: independent ownership and materially different
         scaling demands emerge.
Evidence: load-test result, change-frequency history.
What is an ADR's most valuable content?

The causal link between constraints, alternatives, decision, consequences and measurable revisit criteria. A one-line technology choice without rationale provides little long-term value.

15. Evolutionary architecture and fitness functions

How do we prevent erosion as the system changes?

Architecture decays when short-term changes break intended boundaries: controllers start accessing another domain's tables, synchronous calls creep into formerly isolated flows, or teams add shared utilities with hidden global state. An evolutionary approach uses automated checks—architecture fitness functions—to verify characteristics that matter as code and infrastructure change.

Examples include ArchUnit tests preventing domain code from depending on Spring MVC controllers; contract tests validating event schema compatibility; integration tests verifying duplicate webhook delivery does not duplicate charges; policy tests ensuring workloads do not receive administrator cloud roles; and performance baselines that detect connection pool wait regressions. Fitness functions do not replace design reviews but make violations visible early.

Design for incremental migration with a strangler approach where appropriate: introduce new behavior behind a stable interface, move specific flows, reconcile data and retire old paths only after proven correctness. Migration must preserve the business invariant throughout old/new coexistence. The most elegant future target architecture is irrelevant if there is no safe transition from today's state.

Architecture fitness functions
 ├── dependency direction tests
 ├── API/event contract compatibility
 ├── tenant authorization negative tests
 ├── crash-window idempotency tests
 ├── SLO load-test threshold
 └── backup restoration drill
What is an architecture fitness function?

An automated or repeatable verification that an intended architectural property continues to hold, such as allowed dependency directions, acceptable p99 or idempotent retries.

16. End-to-end worked case: design a checkout service

Apply every principle to one concrete problem.

Given: 500 RPS peak, 2% payment operations may experience unknown outcomes, orders must not be duplicated by retries, checkout p99 target is 900 ms under expected load, recommendation service may fail without blocking checkout, and the team has six engineers. Assume a single approved AWS region and one availability-zone failure tolerance for the API layer. These are fictional exercise requirements, not measured production facts.

Boundary: Begin with a modular Spring Boot application: Order, Inventory and PaymentIntent modules; PostgreSQL stores authoritative state and enforces uniqueness; transactional outbox records events; separate background workers publish confirmation messages and update search. Use an external payment provider with stable provider idempotency identity and reconciliation. Keep recommendations behind a short timeout and fail-open fallback that does not affect correctness. Deploy stateless API instances in multiple zones behind an ALB.

Critical workflow: (1) client sends logical request ID; (2) API authenticates and checks tenant scope; (3) database atomically claims request ID and records order intent; (4) inventory reservation uses a conditional update; (5) payment intent is persisted; (6) provider is called with stable key outside long SQL transaction; (7) result is reconciled and order state advances; (8) a committed outbox row drives downstream events; (9) client can query order status after ambiguous response.

Failure cases: an API process crash before commit leaves no committed intent; after commit before response the same request ID returns stored state; after external charge before local confirmation provider reconciliation resolves UNKNOWN; duplicate event delivery is suppressed at consumers; recommendation outage degrades only personalization. The design prioritizes consistency of charges over immediate success response.

Capacity: 500 RPS with 180 ms mean implies about 90 in-flight requests under stable operation. Size CPU from measured CPU-seconds/request and DB pool capacity from observed connection occupancy, not from 90 alone. Run tests at nominal, burst, dependency-slowdown and one-zone-loss conditions. Validate payment reconciliation age, duplicate-charge count, checkout p99, SQL pool waits and outbox lag.

Alternative: three microservices with separate databases improve isolation only if independently owned and released, but introduce saga coordination and operational overhead. For a six-person team with current requirements, favor a modular monolith until independent scaling and ownership justify the split. Document this in an ADR with revisit triggers.

What would make you reverse the modular-monolith decision?

Evidence that independently changing, owned domains need different scaling/release/security failure boundaries and that the organization can absorb operational and distributed consistency costs. Record measurable triggers and a staged migration plan.

17. Systematic architecture review and production readiness

What would you sign off before going live?

Review architecture as an argument supported by evidence. Every claimed property should map to a scenario, mechanism and test. For correctness, enumerate invariants and show where they are enforced. For availability, prove failure boundaries and recovery. For security, perform negative authorization tests across all entry points. For performance, show load-test curves and explicit downstream capacity assumptions. For evolution, show compatibility and rollback paths.

Evaluate five forms of completeness: functional (happy path and edge cases), state (writes, invariants, idempotency), failure (timeouts, crashes, partitions, overload), operational (deploys, alerts, restore), and organizational (owners, decision authority, runbooks). An architecture that cannot be safely deployed or operated is not production ready regardless of diagram quality.

Separate verified facts from untested assumptions. “Multi-AZ” is a topology claim; “survives AZ failure within 60 seconds without losing accepted orders” is a measurable claim requiring an exercise. “Exactly once” without naming the business identity, storage boundary and retry semantics is an incomplete claim. Treat unknowns as explicit risk register entries with verification owners.

What are the strongest signals that an architecture review is superficial?

Technology labels with no quantified requirements, diagrams with no state ownership, promises of zero data loss without recovery evidence, and no clear handling of ambiguous outcomes, operational failure or backward compatibility.

Chapter 1 — Architecture revision sheet

Definition: architecture is the set of consequential structural and policy decisions whose reversal would be expensive. Every such decision must be justified against business and quality drivers.

Core decision sequence

  1. Define business outcomes, constraints and nonnegotiable invariants.
  2. Express quality attributes as measurable scenarios with a stimulus, environment, response and measure.
  3. Draw context, container, dynamic/failure and deployment views.
  4. Assign one authoritative owner to each state transition and consistency rule.
  5. Compare credible alternatives, including their operational and migration costs.
  6. Design timeouts, retries, admission limits and unknown-outcome recovery.
  7. Test p99, saturation, business correctness, one-zone failure and safe rollback.
  8. Record ADRs with triggers for review and automated fitness functions.

Architectural red flags

Shared tables across nominally independent services; global admin roles; p99 described without request population; claims of exactly-once effects without an identity and persistence boundary; multi-AZ claimed as proof of disaster recovery; per-hop timeouts exceeding caller deadlines; unbounded queues; data migrations without compatibility or failback reconciliation.

Self-test

  1. Distinguish an architectural driver from a technology preference.
  2. Compute average concurrency at 400 RPS and 250 ms mean.
  3. Explain why a timeout does not prove business failure.
  4. Describe one stale cache-fill race.
  5. Explain a payment-provider crash window.
  6. List the evidence needed to claim safe one-zone failure.
  7. Compare outbox with synchronous publish-after-commit.
  8. Draft an ADR choosing a modular monolith over microservices.
