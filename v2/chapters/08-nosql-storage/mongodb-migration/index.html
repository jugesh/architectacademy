1. Data model: aggregates and access patterns

Why not copy a relational schema into MongoDB?

A document model begins with query and update boundaries, not tables. Embed a bounded set of line items inside an order when the parent and children are usually read and updated together. Reference independently growing entities such as a customer's historical orders or millions of telemetry events. An unbounded array is a design smell because document growth, update contention, and BSON document limits make it fragile. MongoDB has a 16 MiB BSON document size limit; it is not a target size.

Think of an order document as an aggregate: a single-document write is atomic. If a workflow must modify a customer's wallet, order, and inventory documents as one indivisible operation, that crosses aggregate boundaries and needs different machinery. Multi-document transactions exist, but require planning for contention and retries. Choose consistency requirements first, then document boundaries.

{
  "_id": "order-934", "tenantId": "t-42",
  "status": "CONFIRMED", "version": 4,
  "items": [
    {"sku": "P1", "quantity": 2, "unitPrice": 199}
  ], "createdAt": "2026-10-24T10:00:00Z"
}

A per-order version number can guard against lost updates. Avoid embedding customer profile objects into every order if profile changes need to propagate instantly.

2. Indexes and query plans

What does a compound index actually accelerate?

A query filtered by tenantId and status and sorted by createdAt descending can benefit from a compound index with equality fields first and the sort field after them. Its usefulness depends on cardinality, sort requirements, projection, data skew and writes. A low-selectivity index can make writes slower without improving a selective query. Indexes use memory and must be updated on document mutations.

Inspect explain("executionStats") and compare totalKeysExamined, totalDocsExamined, nReturned and execution time on representative data. A covered query avoids fetching documents if all required fields are available in the index, subject to query and index limitations. Explain output and optimizer choices vary by server version.

db.orders.createIndex(
  { tenantId: 1, status: 1, createdAt: -1, _id: -1 }
);
db.orders.find(
  {tenantId:"t-42",status:"CONFIRMED"},
  {_id:1,createdAt:1}
).sort({createdAt:-1,_id:-1}).limit(50)
 .explain("executionStats");

3. Atomic updates, concurrency and transactions

How do two checkouts avoid overwriting stock?

Read-modify-write in application memory can lose updates. Use a conditional atomic update where all predicates and mutations affect one document; check matchedCount and modifiedCount. When a request can be retried, include a unique business operation identifier so a repeated request cannot reserve stock twice. A conditional decrement protects a numeric bound, but not automatic idempotency.

Multi-document transactions can coordinate related writes, but increase cost and lock/contention exposure. Plan retry logic for transient transaction errors and unknown commit outcomes according to driver labels and documented transaction retry patterns. A timeout after commit must be reconciled; do not assume it rolled back.

db.inventory.updateOne(
 {sku:"P1", available:{$gte:2}},
 {$inc:{available:-2}}
);
// Check modifiedCount == 1 before reporting success.
// This alone is NOT idempotent across retries.

4. Replica sets, elections, and write concern

What does acknowledged mean?

A replica set has an elected primary accepting writes and secondaries replicating the oplog. Driver operations can be routed and retried based on topology and operation type. During election, writes may temporarily fail or be delayed. Write concern describes the acknowledgment requirement; w:"majority" requests acknowledgment by a majority of voting data-bearing members, within MongoDB's defined majority rules. A w:1 acknowledgment is weaker against failover than a majority acknowledgment. Durability nuances depend on journaling settings, server version, and deployment configuration.

Read preference controls where reads are served; it is different from read concern, which controls consistency semantics. Reads from secondaries can lag the primary. Majority writes plus an arbitrary secondary read do not guarantee that the subsequent read immediately reflects the write. Session causal consistency can give stronger session properties when correctly configured.

Client -> primary P -> oplog replicated -> secondary S1
             |                           -> secondary S2
         majority acknowledgment after configured conditions
         ^ primary election changes reachable write endpoint

5. Change streams and incremental migration

How can writes be caught up while moving clusters?

For an account-to-account migration, take a consistent baseline snapshot or documented logical copy, and establish a CDC boundary that allows subsequent writes to be replayed in order. MongoDB change streams are based on change events and use resume tokens. They generally require a replica set or sharded deployment and adequate oplog/change-stream history retention. A resume token is not an eternal replay guarantee; if history is lost, resnapshot or another recovery mechanism may be required.

Change streams identify changed documents and operations. Full-document lookup is not the same as a transactionally frozen after-image for arbitrary workflows; choose updateLookup or pre/post images only after understanding semantics and configuration. Preserve stable document IDs, handle deletes, duplicate events and idempotent replays, and reconcile counts plus checksums at the business-entity level. For interdependent microservices, coordinate which system is the writer of record.

Phase A: baseline copy old -> new
Phase B: replay CDC old -> new; monitor replication lag
Phase C: stop writes briefly, drain writes, apply last delta
Phase D: switch application writers to new cluster
Phase E: validate and observe; only then retire old writer

6. Cutover and rollback correctness

Why isn't switching the endpoint back a rollback?

After switching clients to the new database, new writes exist only there unless explicit reverse replication or dual-write coordination is active. Pointing clients back to the old cluster discards or hides those new writes. A credible rollback plan names one writer at every instant, establishes a durable write fence for cutover, and decides whether reverse synchronization is supported and how conflicts are resolved.

A safer short rollback window can include reversible CDC from new to old, but bi-directional replication introduces update loops, ordering conflicts, deletion semantics, and divergent business state. A practical alternative is forward recovery and failback only after controlled reconciliation. Treat migration rollback as a data-consistency protocol, not a DNS operation.

Old cluster --initial copy + forward CDC--> New cluster
         (writer)                          (standby)
                [drain/fence old writes]
Old cluster (standby) <-- optional reverse CDC -- New (writer)
                     [no concurrent writers]

7. Sharding, partition keys and hot spots

What happens when the shard key is monotonic?

Sharding spreads data and operations according to a shard key. Poor key choice creates hot shards, scatter-gather queries or excessive migration work. A monotonically increasing value can concentrate inserts into a narrow key range in range-based sharding. Hashed shard keys can distribute values but may reduce locality for range access. Choose with tenant boundaries, targeted query predicates, cardinality, write skew and operational growth in mind.

Do not shard only because the dataset is large. Scale-out raises operational complexity: routing, distribution, balancer activity, index constraints and cross-shard transactions. Benchmark a realistic distribution and include one unusually large tenant, not merely uniformly random data.

Query -> mongos -> shard A / shard B / shard C
          |
       shard key determines targeted vs scatter-gather route

8. Operations, security and backup recovery

What evidence proves the design works?

Capture driver pool wait, command latency, server connections, queues, cache pressure, disk IOPS, replication lag, election events, slow queries and p99 by operation. Configure TLS, least-privilege database users and secret rotation. Plan encryption at rest, auditability and access controls for backups. A replica set is not a backup because deletions and application bugs propagate.

Define RPO (maximum acceptable loss) and RTO (maximum restoration duration) and prove them in a restore exercise. Include point-in-time recovery capabilities for the exact deployment and backup tooling, not merely periodic snapshot creation. Test a member loss, an election during transaction commit, an expired change-stream resume token and a post-cutover rollback request.

Incident drill:
1. Kill primary during traffic
2. Capture errors and recovery latency
3. Verify no missing accepted business operations
4. Restore backup into isolated cluster
5. Reconcile counts, IDs and representative checksums

Senior interview bank: 18 answered scenarios

Attempt the question before viewing the answer.

These questions are intentionally focused on invariants, real failure modes and validation evidence—not memorized configuration defaults.

1. When is embedding preferable to referencing?

Explain before revealing answer.
Reveal answer

Embed when bounded child data shares a consistency and access boundary with its parent. Reference when cardinality grows unbounded, lifecycle differs, or independent querying dominates.

Follow-up: What happens if 200,000 events are embedded in one user document?

2. Can a single-document update be atomic?

Explain before revealing answer.
Reveal answer

Yes. A write operation modifying one document is atomic; use conditional predicates to enforce invariants. Atomicity does not imply that retries are idempotent.

Follow-up: Show a conditional decrement and explain how repeated calls still double-decrement.

3. What is the BSON size limit?

Explain before revealing answer.
Reveal answer

MongoDB BSON documents have a maximum size of 16 MiB. Keep bounded aggregates well below that limit and avoid endlessly growing arrays.

Follow-up: Design a separate collection for append-only audit records.

4. What is a covered query?

Explain before revealing answer.
Reveal answer

A query answered from an index without fetching full documents, where the predicate and projection permit it. Verify with explain output rather than assuming projection alone guarantees it.

Follow-up: Why can a query stop being covered after adding a new projected field?

5. How do you select a compound index?

Explain before revealing answer.
Reveal answer

Use actual filters, sort order, cardinality and index write cost. Equality, then relevant sort/range fields is a useful starting heuristic, not a universal optimization rule.

Follow-up: Compare explain metrics across differently sized tenants.

6. What is write concern majority?

Explain before revealing answer.
Reveal answer

An acknowledgment policy involving a majority of voting data-bearing replica-set members according to MongoDB's rules. It affects failover durability relative to weaker acknowledgment, though exact semantics depend on server configuration.

Follow-up: How does this differ from read preference secondary?

7. Why can a secondary read be stale?

Explain before revealing answer.
Reveal answer

Replication is asynchronous relative to primary writes; a secondary may not yet have applied recent updates. Choose read routing and concern based on the user-facing freshness contract.

Follow-up: Provide a read-your-writes strategy for an order confirmation screen.

8. What happens during a primary election?

Explain before revealing answer.
Reveal answer

Client write operations can fail, wait or be retried depending on driver behavior and operation safety until a new primary is elected. Budget timeouts and idempotent operations.

Follow-up: How would you measure effective recovery time during an election?

9. What do retryable writes not guarantee?

Explain before revealing answer.
Reveal answer

They address supported retry scenarios within MongoDB's retryable write mechanisms; they do not automatically deduplicate all external side effects or repeated business workflows with newly generated IDs.

Follow-up: Explain charging an external payment provider from a retried application request.

10. When do you need a multi-document transaction?

Explain before revealing answer.
Reveal answer

When an invariant spans documents and must be atomic within the supported MongoDB transaction scope. Prefer good aggregate boundaries when they meet the business requirement, because transactions add cost and contention.

Follow-up: Explain a cross-document transfer invariant.

11. What is an unknown transaction commit result?

Explain before revealing answer.
Reveal answer

The client cannot determine whether commit succeeded due to network or failover ambiguity. Handle driver error labels and transaction commit retry guidance, and reconcile application state when needed.

Follow-up: Why is blind business re-execution dangerous?

12. What is a change-stream resume token?

Explain before revealing answer.
Reveal answer

A token identifying a position from which a stream can resume while sufficient change history remains. It should be checkpointed durably with applied migration progress.

Follow-up: What if the oplog history needed by the token is gone?

13. Why isn't baseline plus CDC automatically safe?

Explain before revealing answer.
Reveal answer

A consistent capture boundary, correct event ordering, retention, deletes, duplicate handling and convergence proof are needed. Without those, gaps and reordering can silently corrupt migrated state.

Follow-up: How do you guarantee there is no gap between snapshot and stream?

14. Can you roll back just by switching the MongoDB URI?

Explain before revealing answer.
Reveal answer

Not once new writes were accepted only by the destination. The source may be stale; reverse delta replay or forward recovery with fencing and reconciliation is required.

Follow-up: Draw old/new writer ownership during failback.

15. Why are dual writes risky?

Explain before revealing answer.
Reveal answer

Partial successes, ambiguous failures, ordering differences and conflicts can create divergence. A single writer plus CDC often simplifies consistency; any dual-write protocol needs reconciliation and conflict semantics.

Follow-up: Describe a failure between writing the old and new clusters.

16. What does a shard key determine?

Explain before revealing answer.
Reveal answer

Data distribution and whether queries can target a specific shard. A poor key can cause hotspots, scatter-gather or uneven storage and write demand.

Follow-up: Compare range and hashed approaches for a timestamp-like key.

17. When is a replica set not enough for disaster recovery?

Explain before revealing answer.
Reveal answer

Replicas propagate logical mistakes and may share failure domains. Backups and tested restoration with defined RPO/RTO are necessary.

Follow-up: Show how accidental deletion reaches all secondaries.

18. What is the most important validation after migration?

Explain before revealing answer.
Reveal answer

Business-level reconciliation of IDs, counts, high-value invariants, sample payloads and write continuity, not just aggregate document counts or green dashboards.

Follow-up: Design a deterministic checksum for tenant-scoped collections.

Architecture decision record: MongoDB migration

Document the invariants before switching writers.

Context. Several independently deployed services currently read and write collections in an older MongoDB cluster. The destination cluster runs in a different cloud account. Outages must be minimized and no acknowledged business write may be silently lost during migration.

Decision. Inventory all writers and consumers, establish a baseline-and-CDC pipeline with a checkpointed change-stream position, reconcile before cutover, drain in-flight writes, fence the old writers, cut over controlled service groups and verify a single primary writer-of-record. Do not permit unconstrained dual writes. Reverse replication is a separate, explicitly designed protocol—not an automatic rollback feature.

Acceptance criteria. No writer remains pointed at the old cluster after fencing; destination catches up to the final source checkpoint; entity counts and business invariants reconcile; any unresolved transactions are investigated; read/write timeouts and election behavior stay within SLO; rollback plan is demonstrated with newly accepted destination writes.

Risk. A missing writer, expired resume history or unnoticed asynchronous consumer can create silent gaps. Maintain ownership and per-service cutover evidence.
