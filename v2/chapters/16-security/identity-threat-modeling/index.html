1. Security as a set of explicit invariants

Confidentiality prevents unauthorized disclosure, integrity prevents unauthorized changes and availability preserves useful access. Begin with protected assets, trust boundaries, attacker capabilities and business consequences. Data flows across browser, API gateway, service, database and event broker each cross boundaries with different authentication and authorization requirements. A perimeter firewall does not guarantee that one authenticated user cannot access another user's resource. Defenses must be layered and measured.

2. OAuth 2.0 and OpenID Connect

OAuth 2.0 defines authorization mechanisms; OpenID Connect builds an identity layer on top. An access token is used to authorize API access and an ID token communicates authentication claims to its intended client. Do not use an ID token as a generic API authorization token. Validate issuer, audience, signature and temporal claims. Browser apps should follow appropriate authorization-code and PKCE flows; never embed long-lived client secrets in public clients. Security depends on actual authorization server and resource server configuration.

3. JWT validation and key rotation

JWT is an encoded token format, not inherently encrypted. A base64-decoded payload is readable and must not contain secrets merely because it is signed. The verifier must constrain algorithms, validate signature against trusted issuer keys, reject expired tokens subject to controlled clock skew, and verify issuer/audience and authorization claims. JWKS key selection and refresh must fail safely during rotation without accepting arbitrary attacker-controlled key URLs or untrusted header parameters.

What is a classic JWT vulnerability?

Negative tests: wrong audience, expired token, different issuer, changed alg, malicious key ID.

4. Authorization: RBAC, ABAC and object boundaries

Role-based access maps roles to privileges; attribute-based checks combine user, resource and environmental attributes. Roles such as ADMIN do not automatically authorize access to every tenant: resource ownership and tenant membership must be checked for every object operation. Centralize policy where practical, but enforce at the domain boundary; gateways may not know record ownership. Prefer deny-by-default and explicit policy decisions with auditable inputs.

How does an IDOR vulnerability arise?

GET /tenants/T/orders/O must verify membership in T and permission for O.

5. Service-to-service trust and workload identity

Use short-lived credentials, cloud workload identities or mTLS where appropriate. A bearer credential copied from logs can be replayed until revoked or expired. Propagate caller identity as an authenticated context only through trusted components, not arbitrary X-User headers. For microservices, distinguish a service's own permissions from permissions delegated on behalf of a user; avoid a universal admin service account. Mutual TLS authenticates peers but does not itself enforce per-operation business authorization.

Why doesn't mTLS replace authorization?

Caller identity + service identity -> policy decision -> resource access.

6. Secrets, key management and encryption

Store credentials outside source and images, control retrieval with least privilege, rotate on a tested schedule and audit access. A KMS key policy may be required in addition to IAM grants. Envelope encryption separates data-encryption keys from centrally managed wrapping keys, but applications still need safe plaintext handling. Hash passwords with purpose-built adaptive password hashing algorithms and unique salts; do not use reversible encryption or fast unsalted hashes for password storage.

How do you rotate a database credential without outage?

Secrets Manager / Vault -> short-lived authorized retrieval -> application memory.

7. API, browser and data protection

Validate inputs structurally and semantically, use parameterized SQL to prevent injection, defend against SSRF by constraining outbound destinations, and protect browser sessions with appropriate cookies, CSRF rules and output encoding. Rate limits and bot defenses reduce abuse but are not identity verification. Log enough for investigation while redacting credentials, access tokens, PII and payment data. Apply field-level access rules to search endpoints and cached responses; an overly broad cache key can bypass otherwise correct authorization.

8. Threat modeling and security release gates

A threat model inventories entry points, identities, trust transitions, abuse cases and mitigations, then tests whether each control actually holds. STRIDE helps prompt consideration of spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege. Use dependency scanning, secret detection, infrastructure-policy tests, runtime monitoring and incident rehearsals. Prioritize exploitable paths to crown-jewel data rather than counting scanner findings alone.

Senior interview and design review

12 answered scenarios.

Attempt each question before opening the response and explain the proof or failure mode.

1. Authentication versus authorization?

Answer before opening.
Reveal answer and exercise

Authentication establishes identity; authorization decides permitted actions for that identity on a resource.

Follow-up: Design negative tenant-access tests.

2. What does OIDC add to OAuth?

Answer before opening.
Reveal answer and exercise

It defines an interoperable identity layer and ID tokens alongside OAuth authorization.

Follow-up: Why not send an ID token to arbitrary APIs?

3. What JWT claims must be checked?

Answer before opening.
Reveal answer and exercise

Signature, allowed algorithm, issuer, audience, expiry and applicable authorization claims, with controlled clock skew.

Follow-up: Test wrong-audience tokens.

4. Why doesn't JWT encode mean encrypt?

Answer before opening.
Reveal answer and exercise

Base64url-encoded token fields are readable; signing protects integrity rather than confidentiality.

Follow-up: What should never be included in claims?

5. What is PKCE?

Answer before opening.
Reveal answer and exercise

Proof Key for Code Exchange binds authorization-code redemption to the initiating client with a verifier.

Follow-up: Why is it important for public clients?

6. What is IDOR?

Answer before opening.
Reveal answer and exercise

Insecure direct object reference: missing object-level access checks for user-selected identifiers.

Follow-up: Try one tenant's order ID under another login.

7. What is ABAC?

Answer before opening.
Reveal answer and exercise

Authorization based on attributes of principal, action, resource and environment.

Follow-up: Design approval rules for financial thresholds.

8. What does mTLS prove?

Answer before opening.
Reveal answer and exercise

Cryptographic peer authentication and protected transport when correctly configured.

Follow-up: Why is it not domain authorization?

9. How do you prevent SSRF?

Answer before opening.
Reveal answer and exercise

Constrain egress destinations, resolve/validate addresses safely and reject dangerous networks and redirects.

Follow-up: Test metadata endpoint access.

10. What is envelope encryption?

Answer before opening.
Reveal answer and exercise

Encrypt data with data keys protected by a key-encryption key managed separately.

Follow-up: Plan key rotation.

11. How do you prevent secret leakage in logs?

Answer before opening.
Reveal answer and exercise

Avoid logging raw request headers and tokens, apply redaction, set least-privilege log access and retention.

Follow-up: Inspect trace baggage for credentials.

12. What is a useful threat model output?

Answer before opening.
Reveal answer and exercise

An attack-path list tied to mitigations, tests, owners and residual risk.

Follow-up: Threat-model a webhook receiver.
