Caching, Consistency and Invalidation

Why caches accelerate reads, why stale data appears, and how to design safe invalidation.

The reason to cache Cache-aside and write strategies The invalidation race Stampede and hot keys Operational boundaries

1. The reason to cache

What outcome improves?

A cache exchanges freshness, memory and complexity for lower latency and reduced backend load. First identify the expensive operation and its read frequency. Cache only if repeated access, acceptable staleness and invalidation economics justify it. A cache hit ratio alone is not success: compare backend QPS, tail latency, memory cost and incorrect/stale reads.

2. Cache-aside and write strategies

What can be lost with write-behind?

Cache-aside reads cache then database on miss, and typically invalidates on write. Read-through delegates loading to a cache layer. Write-through updates backing store and cache in a coordinated path but cannot make two independent systems atomic. Write-behind acknowledges writes before durable storage and risks data loss on failure. Choose based on the consistency contract, not familiarity.

3. The invalidation race

Draw the read/write interleaving.

A reader misses cache and fetches old value V1. Meanwhile a writer commits V2 and invalidates the key. The reader then fills V1, resurrecting stale data after the write. TTL eventually heals but may violate correctness. Mitigations include versioned keys, compare-and-set cache fills, version checks, and narrowly scoped locks. Delete-after-write alone does not remove every race.

4. Stampede and hot keys

Why can 99% hit rate still fail?

When a popular key expires, thousands of requests can hit the database simultaneously. Add TTL jitter, request coalescing/single-flight, stale-while-revalidate for tolerant data, and backend rate limits. A hot key can overload one Redis shard even with a high overall hit ratio. Consider replication, local near-cache, or request distribution; measure key-level skew.

5. Operational boundaries

What must never be cached blindly?

Use namespaced keys with tenant isolation, schema versions and predictable cardinality. Set bounded TTL and memory eviction policy; distinguish not-found caching from sensitive negative results. Never treat Redis as the sole authority for balances, inventory reservations or permission decisions without a deliberate consistency model. Cache outages should degrade predictably rather than cascade to the origin.

Interview and design review

Try answering before expanding.
Why is cache invalidation difficult?

A database write and a cache mutation are separate operations. Concurrent readers can refill stale values, failures can drop invalidations, and multiple nodes may observe events in different orders.

When is stale-while-revalidate appropriate?

For data with an explicit freshness budget such as catalog descriptions or public content. It is usually inappropriate for authorization decisions or financial balances.

How do you handle a cache stampede?

Coalesce concurrent misses, stagger expirations, optionally serve bounded stale data, and cap backend concurrency. Test synchronized expiry and cache-restart scenarios.

Should you cache every frequently read query?

No. Consider data sensitivity, update rate, key cardinality, correctness cost, invalidation burden and whether a database index solves the bottleneck more simply.

A stale-fill race in detail

Why does delete-on-write fail in this timeline?

At T1 reader A misses key K. At T2 A queries the database and sees version 11. At T3 writer B commits version 12 and invalidates K. At T4 A writes version 11 to cache, undoing the invalidation. Simply invalidating after commit does not close this race. One mitigation is a cache entry carrying a monotonically increasing version, with conditional compare-and-set that never replaces a newer version. Another is versioned cache keys derived from an authoritative generation counter, at the cost of coordinating generation changes. TTL bounds eventual staleness but cannot guarantee immediate freshness. Design around the actual business freshness contract.

Why does delete-on-write fail in this timeline?

The older read finishes after the invalidation and repopulates the cache with stale data.

Cache stampede and invalidation playbook

Trace the invariant, failure boundary and recovery.

A popular product key expires and 2,000 concurrent requests miss the cache. Without coordination, all 2,000 may hit the origin, which can cascade into DB pool exhaustion. Use request coalescing or a per-key single-flight mechanism, add randomized expiry jitter, and consider stale-while-revalidate only when freshness permits. Distributed locks introduce lease-expiry and ownership concerns: a slow loader can overwrite newer data after its lease expires. Use versions or fencing tokens where correctness demands monotonic updates. In a stale-fill race, a reader can fetch version 11 before a writer commits version 12, then populate cache after invalidation; invalidation alone does not guarantee read-after-write consistency. Set explicit freshness and failure contracts by data type.

Design review and interview follow-ups

Why is a cache lock not sufficient for strict consistency?

Lease expiry, process pauses and concurrent writers can still allow stale writes; validate versions or fencing tokens against an authoritative state.

When should you bypass cache entirely?

When the correctness contract requires authoritative reads and a cache cannot satisfy freshness, or when cardinality/churn makes caching uneconomic.

Cache architecture decision matrix

When is a local cache preferable?

Local in-process caches offer microsecond access and avoid network hops but have per-instance duplication and inconsistent invalidation. Distributed caches centralize shared state and can support atomic operations, but add network latency, cluster failure modes and hot-key concentration. CDNs are appropriate for cacheable HTTP content at the edge, with Vary, Cache-Control, ETag and invalidation rules. Select based on data size, update frequency, consistency contract, miss penalty, fan-out and failure behavior. Do not cache sensitive user-specific content under an unscoped key.

When is a local cache preferable?

When data is small, relatively stable, safely duplicated and each instance can tolerate independent expiry or refresh.

Eviction and memory economics

Why can a 99% hit ratio still produce poor p99?

TTL determines maximum age but is not an eviction policy. LRU approximates recency; LFU rewards frequently accessed items; size-based eviction protects memory. A high hit ratio can hide expensive misses: if 1% of requests miss but each miss costs 500 ms, the miss tail may dominate p99. Model object overhead and cardinality, not just payload bytes. Watch for negative caching of absent keys, which can reduce repeated origin lookups but risks hiding newly created data until expiry.

Why can a 99% hit ratio still produce poor p99?

The slowest 1% may be precisely the misses; percentile latency reflects those expensive origin calls.

Consistency, versioning and incident response

How do you prevent cache failure from taking down the database?

Specify whether the cache is authoritative, advisory or a performance layer. For correctness-critical state, use the database as source of truth and validate versioned writes. In a cache outage, a sudden fail-open policy can stampede the database; enforce concurrency limits and graceful degradation. For stale data incidents, inspect invalidation event delivery, TTL configuration, key namespaces and stale-fill races. Use cache namespace versioning during schema changes to avoid deserialization errors.

How do you prevent cache failure from taking down the database?

Bound origin concurrency, use request coalescing, shed excess load and preserve safe fallback behavior.
