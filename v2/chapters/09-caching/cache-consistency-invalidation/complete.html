09-CACHING · TECHNICAL CHAPTER

Caching, Consistency and Invalidation

Why caches accelerate reads, why stale data appears, and how to design safe invalidation.

The reason to cache Cache-aside and write strategies The invalidation race Stampede and hot keys Operational boundaries

1. The reason to cache

What outcome improves?

A cache exchanges freshness, memory and complexity for lower latency and reduced backend load. First identify the expensive operation and its read frequency. Cache only if repeated access, acceptable staleness and invalidation economics justify it. A cache hit ratio alone is not success: compare backend QPS, tail latency, memory cost and incorrect/stale reads.

2. Cache-aside and write strategies

What can be lost with write-behind?

Cache-aside reads cache then database on miss, and typically invalidates on write. Read-through delegates loading to a cache layer. Write-through updates backing store and cache in a coordinated path but cannot make two independent systems atomic. Write-behind acknowledges writes before durable storage and risks data loss on failure. Choose based on the consistency contract, not familiarity.

3. The invalidation race

Draw the read/write interleaving.

A reader misses cache and fetches old value V1. Meanwhile a writer commits V2 and invalidates the key. The reader then fills V1, resurrecting stale data after the write. TTL eventually heals but may violate correctness. Mitigations include versioned keys, compare-and-set cache fills, version checks, and narrowly scoped locks. Delete-after-write alone does not remove every race.

4. Stampede and hot keys

Why can 99% hit rate still fail?

When a popular key expires, thousands of requests can hit the database simultaneously. Add TTL jitter, request coalescing/single-flight, stale-while-revalidate for tolerant data, and backend rate limits. A hot key can overload one Redis shard even with a high overall hit ratio. Consider replication, local near-cache, or request distribution; measure key-level skew.

5. Operational boundaries

What must never be cached blindly?

Use namespaced keys with tenant isolation, schema versions and predictable cardinality. Set bounded TTL and memory eviction policy; distinguish not-found caching from sensitive negative results. Never treat Redis as the sole authority for balances, inventory reservations or permission decisions without a deliberate consistency model. Cache outages should degrade predictably rather than cascade to the origin.

Implementation sketch

What assumptions does this example make?

  Product cached = redis.get(key);

Interview and design review

Try answering before expanding.
Why is cache invalidation difficult?

A database write and a cache mutation are separate operations. Concurrent readers can refill stale values, failures can drop invalidations, and multiple nodes may observe events in different orders.

When is stale-while-revalidate appropriate?

For data with an explicit freshness budget such as catalog descriptions or public content. It is usually inappropriate for authorization decisions or financial balances.

How do you handle a cache stampede?

Coalesce concurrent misses, stagger expirations, optionally serve bounded stale data, and cap backend concurrency. Test synchronized expiry and cache-restart scenarios.

Should you cache every frequently read query?

No. Consider data sensitivity, update rate, key cardinality, correctness cost, invalidation burden and whether a database index solves the bottleneck more simply.

A stale-fill race in detail

Why does delete-on-write fail in this timeline?

At T1 reader A misses key K. At T2 A queries the database and sees version 11. At T3 writer B commits version 12 and invalidates K. At T4 A writes version 11 to cache, undoing the invalidation. Simply invalidating after commit does not close this race. One mitigation is a cache entry carrying a monotonically increasing version, with conditional compare-and-set that never replaces a newer version. Another is versioned cache keys derived from an authoritative generation counter, at the cost of coordinating generation changes. TTL bounds eventual staleness but cannot guarantee immediate freshness. Design around the actual business freshness contract.

Why does delete-on-write fail in this timeline?

The older read finishes after the invalidation and repopulates the cache with stale data.

Cache stampede and invalidation playbook

Trace the invariant, failure boundary and recovery.

A popular product key expires and 2,000 concurrent requests miss the cache. Without coordination, all 2,000 may hit the origin, which can cascade into DB pool exhaustion. Use request coalescing or a per-key single-flight mechanism, add randomized expiry jitter, and consider stale-while-revalidate only when freshness permits. Distributed locks introduce lease-expiry and ownership concerns: a slow loader can overwrite newer data after its lease expires. Use versions or fencing tokens where correctness demands monotonic updates. In a stale-fill race, a reader can fetch version 11 before a writer commits version 12, then populate cache after invalidation; invalidation alone does not guarantee read-after-write consistency. Set explicit freshness and failure contracts by data type.

Design review and interview follow-ups

Why is a cache lock not sufficient for strict consistency?

Lease expiry, process pauses and concurrent writers can still allow stale writes; validate versions or fencing tokens against an authoritative state.

When should you bypass cache entirely?

When the correctness contract requires authoritative reads and a cache cannot satisfy freshness, or when cardinality/churn makes caching uneconomic.

Cache architecture decision matrix

When is a local cache preferable?

Local in-process caches offer microsecond access and avoid network hops but have per-instance duplication and inconsistent invalidation. Distributed caches centralize shared state and can support atomic operations, but add network latency, cluster failure modes and hot-key concentration. CDNs are appropriate for cacheable HTTP content at the edge, with Vary, Cache-Control, ETag and invalidation rules. Select based on data size, update frequency, consistency contract, miss penalty, fan-out and failure behavior. Do not cache sensitive user-specific content under an unscoped key.

When is a local cache preferable?

When data is small, relatively stable, safely duplicated and each instance can tolerate independent expiry or refresh.

Eviction and memory economics

Why can a 99% hit ratio still produce poor p99?

TTL determines maximum age but is not an eviction policy. LRU approximates recency; LFU rewards frequently accessed items; size-based eviction protects memory. A high hit ratio can hide expensive misses: if 1% of requests miss but each miss costs 500 ms, the miss tail may dominate p99. Model object overhead and cardinality, not just payload bytes. Watch for negative caching of absent keys, which can reduce repeated origin lookups but risks hiding newly created data until expiry.

Why can a 99% hit ratio still produce poor p99?

The slowest 1% may be precisely the misses; percentile latency reflects those expensive origin calls.

Consistency, versioning and incident response

How do you prevent cache failure from taking down the database?

Specify whether the cache is authoritative, advisory or a performance layer. For correctness-critical state, use the database as source of truth and validate versioned writes. In a cache outage, a sudden fail-open policy can stampede the database; enforce concurrency limits and graceful degradation. For stale data incidents, inspect invalidation event delivery, TTL configuration, key namespaces and stale-fill races. Use cache namespace versioning during schema changes to avoid deserialization errors.

How do you prevent cache failure from taking down the database?

Bound origin concurrency, use request coalescing, shed excess load and preserve safe fallback behavior.

Cache consistency, hot keys and failure lab

Choose a consistency contract before a cache

A cache may be an optimization for recomputable data, a nearline read model or a component of an authoritative workflow. Those roles are not interchangeable. If a balance must be correct when money moves, do not accept arbitrary cache staleness. For product descriptions, 30 seconds of staleness may be acceptable. Express the contract in terms of maximum staleness, availability during origin failure and whether read-your-writes matters.

The stale-fill race

T1 reader: cache MISS
T2 reader: SELECT version=8 from DB
T3 writer: UPDATE DB -> version=9; invalidate cache
T4 reader: puts version=8 into cache AFTER invalidation
T5 next reader: reads stale version=8

Cache invalidation alone does not serialize in-flight fills. Possible mitigations include per-key coordination, checking authoritative versions, compare-and-set based on versions, or embedding the version in cache keys. Their correctness depends on where the authoritative version lives and whether old writers can overwrite new values.

Cache stampede numbers

A hot key receives 2,000 RPS and expires. If the origin lookup takes 80 ms, a naive simultaneous miss wave can create roughly 160 overlapping lookups even under steady Poisson-like arrival; synchronized expiry across many keys can be worse. Single-flight coalescing makes concurrent requests share one refresh. Add jitter to TTLs so many entries do not expire together. Stale-while-revalidate may preserve availability but must be disabled for data with strict freshness.

Operational fallback

Client -> API -> cache
                 | HIT -> response
                 | MISS -> single-flight -> bounded origin -> cache fill
                 | DOWN -> bounded origin + load shedding

If cache fails and every request falls through, the database may be overwhelmed. Predefine an origin concurrency budget, a degraded response policy and alarms for miss-rate spikes. Negative caching reduces repeated lookup for absent IDs but must consider creation shortly after a miss.

Cache key design

Include tenant and authorization-relevant dimensions when response visibility differs. Canonicalize request parameters consistently and version cache namespaces when response formats change. Avoid accidental cache poisoning via untrusted headers, unbounded key cardinality and caching PII in global shared keys. A CDN needs appropriate Cache-Control, Vary, ETag and explicit private/public rules.

Interview: answered

Why can hit rate be 99% while p99 is terrible? The 1% misses may dominate the 99th percentile when they involve slow origin calls.

Does a distributed lock solve stampede permanently? Lease expiry and paused owners can allow stale fills; compare versions or use fencing where necessary.

Is TTL a replacement for invalidation? Only if the maximum stale window is acceptable. TTL bounds age but does not guarantee immediate freshness.

Should cache errors fail open? Only with a bounded origin fallback; unbounded fail-open behavior can cause cascading failure.

What signals prove cache usefulness? End-to-end latency, avoided origin load, miss penalty, memory cost and effect of cache outage, not hit ratio alone.

ANSWERED ADVANCED INTERVIEW BANK · 12 SCENARIOS

Caching and consistency: Senior Interview and Design Review

Answer before reading. Every question pairs a technical explanation with a verification exercise or architectural follow-up.

1. Why can invalidate-on-write still return stale data?

Explain the trade-off and test.

A reader may miss and fetch old DB state while a writer commits and invalidates. If the reader then fills the cache after invalidation, stale data survives. Use version checks, fenced fills, coordinated loading or tolerable TTL depending on the consistency contract.

Follow-up / exercise: Write a five-step timeline proving stale fill after correct invalidation.

2. How does single-flight reduce cache stampedes?

Explain the trade-off and test.

Concurrent misses for one key share one in-flight origin load instead of all hitting the database. This reduces redundant work but introduces coordination and failure semantics: followers need bounded waits and an owner failure recovery path. For distributed deployments, local coalescing is only per instance unless coordinated.

Follow-up / exercise: Measure origin calls during a synchronized hot-key expiry.

3. What is the difference between TTL and eviction?

Explain the trade-off and test.

TTL makes entries stale or invalid after age; eviction decides which entries leave when capacity is constrained, such as LRU or LFU. An entry can be evicted before TTL, and a hot but expired entry must be refreshed. Memory sizing must include object overhead, not just serialized payload size.

Follow-up / exercise: Explain why a 24-hour TTL does not guarantee the item remains cached 24 hours.

4. When should you cache negative results?

Explain the trade-off and test.

Negative caching can suppress expensive repeated lookups for missing IDs, but it risks hiding newly created data until expiration. Use short TTLs or invalidation on creation, scope keys to authorization context and avoid caching transient upstream failures as permanent absence.

Follow-up / exercise: Distinguish legitimate 404 from a 503 caused by a broken origin.

5. How do local caches differ from distributed caches?

Explain the trade-off and test.

Local caches save network latency and infrastructure but duplicate memory and diverge across replicas. Distributed caches share working set and support cross-node operations while adding network hops, hot-key bottlenecks and cluster incidents. Choose based on data volume, update frequency and acceptable staleness.

Follow-up / exercise: What happens when one application pod misses an invalidation event?

6. Why is a cache not automatically safer than a database?

Explain the trade-off and test.

It can return stale data, lose entries during failover, overload the origin on outage and introduce consistency races. Treat it as an optimization unless explicitly engineered as the authoritative durable store. Make fallback behavior bounded by admission controls.

Follow-up / exercise: Run a chaos test with cache unavailable and document database protection.

7. How do you prevent cross-tenant cache leaks?

Explain the trade-off and test.

Include tenant, principal or authorization-related dimensions in keys for personalized data, and avoid public CDN caching of private responses. Use appropriate HTTP Cache-Control and Vary semantics and test role-change invalidation. Shared keys derived solely from an untrusted query string can disclose another user's data.

Follow-up / exercise: Create a test where two tenants request the same resource ID.

8. What does 99% hit rate mean for p99?

Explain the trade-off and test.

A 1% miss population can align with the slowest percentile, making p99 close to origin latency even when most hits are fast. Distribution shape and endpoint mix matter; calculate latency from histograms rather than weighted average of percentile values.

Follow-up / exercise: Explain why average hit ratio is not a latency SLO.

9. What is cache key versioning?

Explain the trade-off and test.

A key namespace can include a schema or data version so old serialized entries are not misread after deploy, and a monotonic entity version can reject stale fills. Versions require lifecycle and memory accounting: retaining multiple namespaces temporarily increases usage.

Follow-up / exercise: Plan a rolling deployment with old and new object serialization formats.

10. How would you choose write-through versus write-behind?

Explain the trade-off and test.

Write-through synchronously updates authoritative state and cache according to a protocol, increasing write latency and handling partial failures. Write-behind defers origin writes, improving apparent latency but creating loss and ordering risks. Choose based on durability and consistency requirements, not only speed.

Follow-up / exercise: Explain why write-behind is inappropriate for unprotected account-balance mutations.

11. How do you size a cache?

Explain the trade-off and test.

Estimate unique hot keys, average serialized size plus metadata/allocator overhead, desired hit curve, object churn, replication and headroom. Measure eviction rate, cache miss penalty, memory fragmentation and cost per avoided origin query. Bigger is not always better if updates churn the working set.

Follow-up / exercise: What does a sustained eviction rate near insert rate indicate?

12. How do you safely fail open when cache is down?

Explain the trade-off and test.

Allow only bounded origin concurrency, coalesce duplicate loads, shed low-priority traffic and optionally serve stale data where acceptable. Unbounded bypass converts a cache incident into a database outage. Define metrics and a runbook for degraded mode.

Follow-up / exercise: Describe recovery when cache returns and thousands of keys refill at once.
