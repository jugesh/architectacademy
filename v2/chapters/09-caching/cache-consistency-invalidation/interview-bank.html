Caching and consistency: Senior Interview and Design Review

Answer before reading. Every question pairs a technical explanation with a verification exercise or architectural follow-up.

1. Why can invalidate-on-write still return stale data?

Explain the trade-off and test.

A reader may miss and fetch old DB state while a writer commits and invalidates. If the reader then fills the cache after invalidation, stale data survives. Use version checks, fenced fills, coordinated loading or tolerable TTL depending on the consistency contract.

Follow-up / exercise: Write a five-step timeline proving stale fill after correct invalidation.

2. How does single-flight reduce cache stampedes?

Explain the trade-off and test.

Concurrent misses for one key share one in-flight origin load instead of all hitting the database. This reduces redundant work but introduces coordination and failure semantics: followers need bounded waits and an owner failure recovery path. For distributed deployments, local coalescing is only per instance unless coordinated.

Follow-up / exercise: Measure origin calls during a synchronized hot-key expiry.

3. What is the difference between TTL and eviction?

Explain the trade-off and test.

TTL makes entries stale or invalid after age; eviction decides which entries leave when capacity is constrained, such as LRU or LFU. An entry can be evicted before TTL, and a hot but expired entry must be refreshed. Memory sizing must include object overhead, not just serialized payload size.

Follow-up / exercise: Explain why a 24-hour TTL does not guarantee the item remains cached 24 hours.

4. When should you cache negative results?

Explain the trade-off and test.

Negative caching can suppress expensive repeated lookups for missing IDs, but it risks hiding newly created data until expiration. Use short TTLs or invalidation on creation, scope keys to authorization context and avoid caching transient upstream failures as permanent absence.

Follow-up / exercise: Distinguish legitimate 404 from a 503 caused by a broken origin.

5. How do local caches differ from distributed caches?

Explain the trade-off and test.

Local caches save network latency and infrastructure but duplicate memory and diverge across replicas. Distributed caches share working set and support cross-node operations while adding network hops, hot-key bottlenecks and cluster incidents. Choose based on data volume, update frequency and acceptable staleness.

Follow-up / exercise: What happens when one application pod misses an invalidation event?

6. Why is a cache not automatically safer than a database?

Explain the trade-off and test.

It can return stale data, lose entries during failover, overload the origin on outage and introduce consistency races. Treat it as an optimization unless explicitly engineered as the authoritative durable store. Make fallback behavior bounded by admission controls.

Follow-up / exercise: Run a chaos test with cache unavailable and document database protection.

7. How do you prevent cross-tenant cache leaks?

Explain the trade-off and test.

Include tenant, principal or authorization-related dimensions in keys for personalized data, and avoid public CDN caching of private responses. Use appropriate HTTP Cache-Control and Vary semantics and test role-change invalidation. Shared keys derived solely from an untrusted query string can disclose another user's data.

Follow-up / exercise: Create a test where two tenants request the same resource ID.

8. What does 99% hit rate mean for p99?

Explain the trade-off and test.

A 1% miss population can align with the slowest percentile, making p99 close to origin latency even when most hits are fast. Distribution shape and endpoint mix matter; calculate latency from histograms rather than weighted average of percentile values.

Follow-up / exercise: Explain why average hit ratio is not a latency SLO.

9. What is cache key versioning?

Explain the trade-off and test.

A key namespace can include a schema or data version so old serialized entries are not misread after deploy, and a monotonic entity version can reject stale fills. Versions require lifecycle and memory accounting: retaining multiple namespaces temporarily increases usage.

Follow-up / exercise: Plan a rolling deployment with old and new object serialization formats.

10. How would you choose write-through versus write-behind?

Explain the trade-off and test.

Write-through synchronously updates authoritative state and cache according to a protocol, increasing write latency and handling partial failures. Write-behind defers origin writes, improving apparent latency but creating loss and ordering risks. Choose based on durability and consistency requirements, not only speed.

Follow-up / exercise: Explain why write-behind is inappropriate for unprotected account-balance mutations.

11. How do you size a cache?

Explain the trade-off and test.

Estimate unique hot keys, average serialized size plus metadata/allocator overhead, desired hit curve, object churn, replication and headroom. Measure eviction rate, cache miss penalty, memory fragmentation and cost per avoided origin query. Bigger is not always better if updates churn the working set.

Follow-up / exercise: What does a sustained eviction rate near insert rate indicate?

12. How do you safely fail open when cache is down?

Explain the trade-off and test.

Allow only bounded origin concurrency, coalesce duplicate loads, shed low-priority traffic and optionally serve stale data where acceptable. Unbounded bypass converts a cache incident into a database outage. Define metrics and a runbook for degraded mode.

Follow-up / exercise: Describe recovery when cache returns and thousands of keys refill at once.
