1. Packets, sockets and connection establishment

Why can a healthy backend still have high request latency?

Follow the request from DNS resolution through address selection, TCP connection, TLS negotiation and application framing. DNS lookup may be cached and can return multiple IPs; TCP establishes a reliable ordered byte stream with flow and congestion control. A packet retransmission can affect tail latency even when application CPU is idle. TLS authentication depends on trust chains and hostname validation, not just encryption. Measure each stage separately using network timing and distributed tracing.

DNS does not route an existing socket

Separate name resolution from connection lifetime. DNS provides candidate addresses; the client chooses an address and creates a connection. A later DNS update does not move bytes already flowing over that socket. A failover design therefore needs both resolver behavior and connection retirement. Lowering a DNS TTL shortly before a migration does not shorten older cached records retroactively. Test the application runtime, local resolver and any proxy that resolves on its behalf.

A TCP connection is an ordered byte stream, not a sequence of application messages. One write can arrive through several reads; multiple writes can be combined. HTTP framing tells the receiver where a request or response ends. Flow control protects the receiver's buffers, while congestion control adapts sending to network conditions. Neither knows your checkout SLO. Retransmission, receiver backpressure and handshake costs can dominate latency with nearly idle application CPUs.

TLS establishes a different boundary

Encryption without peer verification does not establish that the endpoint is the intended one. Check certificate validity, the configured trust chain and hostname verification. SNI helps select the server configuration for a hostname; ALPN negotiates an application protocol. These are different functions. Mutual TLS additionally authenticates a client certificate where configured, but business authorization still decides which tenant and operation that identity may access.

TLS 1.3 resumption can reduce handshake work, but early data introduces replay considerations. Do not enable 0-RTT for a state-changing operation merely to improve a latency chart. Document what may be replayed and where duplicate effects are prevented. See TLS 1.3 specification.

Cold and warm paths need separate measurements

A cold request can include DNS, TCP establishment, TLS negotiation and application work. A reused connection skips some of those stages but can still wait for a stream slot or a pooled connection. Compare both populations. A performance test that reuses one connection indefinitely cannot establish user experience after deploys, idle periods or connection churn. On the server side, distinguish accepting a connection from starting a handler: accept queues and application executors are separate waiting rooms.

Why can a healthy backend still have high request latency?

DNS lookup, packet loss, connection handshakes, proxy queuing, TLS handshakes and certificate validation, and client pool exhaustion can dominate response time.

2. HTTP semantics and resource representations

Does 504 prove a downstream write failed?

HTTP methods communicate intent: GET is safe and idempotent, PUT is idempotent in defined semantics, POST is not automatically idempotent. 200, 201, 202, 204, 409, 429, 502, 503 and 504 indicate different outcomes; consistent error payloads are more useful than generic 500 responses. Content negotiation and caching headers influence intermediaries. For a JSON API, prefer explicit versioning and stable response contracts. A retry policy must consider the operation's business effect and ambiguous completion, not just method name.

Intent, effect and response are different contracts

Method semantics guide intermediaries, but the business implementation must honor them. Idempotency concerns the intended effect of repeating a request, not identical response bytes: a repeated DELETE can return a different status while leaving the resource absent. A POST can be made idempotent through a durable operation identity, but proxies cannot infer that guarantee from its name. A successful transport exchange is also distinct from a successful business operation.

ResponseContract to clarify
201 CreatedWhich resource exists and where its representation can be retrieved
202 AcceptedHow to observe pending, success and failure; acceptance is not completion
409 Conflict / 412 Precondition FailedWhether the caller should reconcile state or refresh a stale version
429 / 503Admission policy, retry guidance and remaining caller budget
502 / 504Which intermediary generated the failure and whether an upstream effect may already exist

Reference: HTTP semantics. Treat status, headers and a stable error schema as one API contract. Do not expose internal stack traces or sensitive provider payloads.

Conditional updates prevent silent overwrite

Suppose two clients read order version 7. Both edit different form fields and submit a complete replacement. Without a precondition, the later replacement can erase the earlier edit. An ETag can represent the version; a write using If-Match asks the server to apply the change only if the relevant representation still matches. The version check and update must be atomic in the authoritative store. Comparing a tag in application memory and then issuing an unconditional update reintroduces the race.

For asynchronous commands, return a stable status resource scoped to the authenticated caller. Specify retention, retry identity and terminal outcomes. An operation that was accepted but later failed needs a discoverable result; merely logging the failure leaves the client unable to distinguish slow progress from lost work. Test duplicate submissions, stale preconditions, caller disconnects and a status lookup from a different tenant.

Does 504 prove a downstream write failed?

No. It usually indicates a gateway timeout; the downstream operation may have committed before the response was lost.

3. HTTP/1.1, HTTP/2 and HTTP/3

Why can an HTTP/2 connection bottleneck multiple requests?

HTTP/1.1 keep-alive reuses TCP connections but pipelining is not generally relied on; clients commonly use pools. HTTP/2 multiplexes streams over a TCP connection and reduces application-level connection overhead, but loss at TCP level still holds up affected bytes. HTTP/3 uses QUIC over UDP and provides independent streams with TLS 1.3 integration, with different operational trade-offs. Protocol choice must be tested with proxies, browsers, middleboxes and latency profiles.

Multiplexing changes where contention occurs

HTTP/1.1 generally uses a connection pool for parallel exchanges. Sequential reuse avoids repeated handshakes; increasing connections can reduce client-side waiting while increasing server concurrency and socket overhead. HTTP/2 introduces frames and streams, so multiple exchanges share one connection. Stream limits and flow-control windows become capacity constraints in addition to connection count. A large response or slow consumer can affect shared connection resources.

Because HTTP/2 uses TCP, missing transport bytes can delay delivery of later bytes even when those bytes belong to another HTTP stream. Multiplexing therefore does not remove all head-of-line blocking. Measure negotiated protocol and active streams on each hop: browser-to-gateway HTTP/2 does not imply gateway-to-application HTTP/2. See HTTP/2 framing and stream control.

HTTP/3 maps requests onto QUIC streams. Loss affecting one stream need not prevent delivery of available data on another, although congestion control, connection limits and application dependencies still create shared constraints. UDP reachability, protocol discovery and fallback behavior must work through the actual network path. A faster transport does not repair a serial database lock or a slow payment provider. See HTTP/3 over QUIC.

Choose with a falsifiable experiment

Keep payloads, request mix, concurrency and server capacity constant while comparing protocols. Run low-loss and controlled-loss cases, small and large responses, and slow readers. Record completed throughput, request latency, handshake count, open connections, stream-limit waits, CPU and memory. A gain measured only for small static assets should not be generalized to large uploads or long-lived streaming APIs.

During a rolling deployment, observe how connections are drained and how clients discover that no new streams should be sent. A retry after a connection shutdown still needs operation safety. Protocol-level knowledge that a stream was not processed may permit a retry; a timeout after a request reached the application usually cannot provide that certainty. Prefer client libraries that expose meaningful failure categories, then verify their behavior in your pinned runtime version.

Why can an HTTP/2 connection bottleneck multiple requests?

Streams share transport capacity and connection-level resources; TCP packet loss and flow-control contention can affect many streams.

4. Reverse proxies and load balancing algorithms

What happens when readiness is always 200 but the DB pool is dead?

Layer 4 forwarding routes by network connection, while Layer 7 gateways can route by host, path and HTTP metadata. Round robin balances count but not service time; least-outstanding-requests can adapt better to variable work, while consistent hashing trades distribution for affinity. Termination and draining influence deployments; retrying at the proxy without operation awareness may duplicate business effects. Health checks must indicate ability to serve traffic and should avoid false positives caused by shallow process checks.

Distribute work, not merely request counts

Round robin treats requests as equal. If one endpoint takes 5 ms and another takes 2 seconds, equal counts need not produce equal outstanding work. Least-outstanding policies can respond to that difference but still need accurate backend health and bounded work. Hash-based affinity can improve cache locality while concentrating a hot tenant on a small subset of capacity. A balancing policy is a trade-off between locality, fairness, predictability and adaptation.

Layer 4 decisions operate on connections; a long-lived multiplexed connection may concentrate many requests on one backend. Layer 7 routing sees HTTP metadata and can terminate or translate protocols, but adds parsing, configuration and trust boundaries. Document where TLS terminates and whether the next hop is encrypted and authenticated. A private subnet is not a substitute for identity and authorization.

Health checks can amplify an incident

A process-alive check can route traffic to a useless instance. The opposite extreme is also dangerous: making every backend fail readiness when a shared database briefly slows can remove the entire fleet, amplify churn and destroy recovery capacity. Distinguish local inability to serve from shared dependency failure. Combine bounded readiness checks with admission limits, graceful degradation and business-level monitoring. Liveness should not restart every process because an external provider is unavailable.

Draining is a sequence: stop admitting new work, allow routing updates to propagate, finish or durably hand off accepted work, then stop the process within the platform's termination budget. Existing connections, in-flight requests and background jobs have different lifetimes. Test this under real traffic and measure which requests are rejected, completed or recovered.

AWS example: idle is not total duration

An ALB idle timeout concerns inactivity on a connection, not an end-to-end business deadline. AWS documents that HTTP/2 PING frames do not reset this timer, and recommends coordinating backend idle settings to avoid premature backend closure races. Streaming data and keepalive policies must be checked against the actual listener and target configuration. Consult the ALB guide; do not copy a timeout number from a different topology without identifying the layer it bounds.

What happens when readiness is always 200 but the DB pool is dead?

The load balancer continues routing traffic to an instance that cannot complete meaningful requests, increasing retries and errors.

5. Timeouts, connection pools and retry budgets

Why does adding more client connections sometimes hurt?

Use separate timeouts for connection establishment, TLS handshake where supported, acquiring a pooled connection, reading/writing, and end-to-end deadline. A downstream timeout longer than the caller deadline wastes resources. Pool starvation can look like a network outage. Retry only bounded transient failures with backoff, jitter and idempotency contracts. Record whether the timeout fires at the client, gateway, service or upstream connection layer.

Build a budget that includes waiting

For a fictional 900-ms caller budget, reserve 100 ms for response work and 150 ms for already completed authentication. Only 650 ms remains for pool acquisition, any new connection, request transmission and upstream response. Giving each stage 650 ms independently can exceed the total. Track elapsed time with a monotonic clock locally; propagate a bounded deadline contract while allowing for clock skew when comparing timestamps between hosts.

A connection-acquisition timeout bounds waiting for permission to use a connection. A connect timeout bounds creating a new transport connection and may not apply at all when one is reused. An idle-read timeout limits a period without progress; a server that sends a small amount of data repeatedly can keep it alive far longer than the intended total duration. Verify the exact client implementation rather than assuming all settings named timeout cover the same interval.

Reusable clients and bounded bodies

HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(2))
    .followRedirects(HttpClient.Redirect.NEVER)
    .build(); // Reuse this client across calls.
HttpRequest request = HttpRequest.newBuilder(uri)
    .timeout(Duration.ofMillis(600))
    .GET().build();
HttpResponse<String> response = client.send(
    request, HttpResponse.BodyHandlers.ofString());

This small example buffers a response and is suitable only when its size is controlled. Streaming consumers must release resources correctly and enforce their own size/progress policies. Reuse the client so connections can be reused; an asynchronous API changes how callers wait but does not create unlimited sockets, streams or upstream capacity. Reference: JDK HttpClient.

Bound total outgoing concurrency separately from the choice of synchronous or asynchronous programming. If 20 pods each permit 100 concurrent provider calls, the fleet can offer 2,000 calls even though each pod appears conservatively configured. Scale limits with quotas and measured downstream capacity. Record pool waiting, active calls, rejections, cancellation and response duration separately.

Executable timeout experiment

Run java --add-modules jdk.httpserver v2/examples/ch02/TimeoutLab.java. The complete loopback lab starts a local server, warms a connection, sends a POST with a 200-ms client timeout and delays the simulated server effect for 800 ms. It asserts that the caller times out while the server still completes one effect. This demonstrates ambiguity; it is not a production payment implementation or a claim about every server's cancellation behavior.

Why does adding more client connections sometimes hurt?

It can overwhelm a bounded server or database and increase resource contention; pool tuning must respect downstream capacity.

6. Caching, CDN, headers and security boundaries

How can a CDN expose private data?

HTTP caching decisions depend on Cache-Control, Vary, ETag, Authorization and content sensitivity. CDN can offload public assets and cacheable API content, but a shared cache must not leak tenant-specific or authenticated responses. TLS termination at a gateway creates a trust boundary: forwarded identity headers should be accepted only from trusted proxies. HSTS, secure cookies and origin checks matter where browsers are involved.

Choose freshness and privacy deliberately

A private cache serves one user agent; a shared cache may serve many users. Cache-Control: no-store prohibits storage under HTTP caching rules, whereas no-cache permits storage but requires validation before reuse. An ETag lets a client validate a stored representation. Vary identifies request-header dimensions relevant to representation selection; it is not an authorization mechanism. Reference: HTTP caching.

Design a cache test around identities, not just hit ratio. Fetch an order as tenant A, then request the same path as tenant B through the actual CDN. Check both content and headers. Repeat after logout, role change, error responses and deployment. A cache that keys on path while the origin chooses data by identity can leak data even when the origin's authorization code is correct, because the second request may never reach it.

Forwarded metadata is a claim

Headers describing the original client address, protocol or host are safe inputs only when the request arrived through an authenticated and controlled proxy path. Strip or overwrite untrusted incoming values at the boundary; configure the application with the trusted hops rather than accepting the leftmost address blindly. Do not use a forwarded IP address as a substitute for an authenticated principal. Host and redirect handling also need explicit allowlists where untrusted values influence generated links.

Parsing differences between intermediaries can be security boundaries. Requests with ambiguous framing, conflicting lengths or inconsistent normalization must be rejected consistently; do not invent a permissive home-grown HTTP parser. Keep gateways and server runtimes patched and include malformed-request tests in a controlled environment. Capture only the metadata required for diagnosis, with secrets and private bodies redacted.

Browser policy is not service authorization

CORS controls what browser scripts can read across origins; it does not prevent a non-browser client from calling an API. Cookie-based sessions need their own cross-site request protection. Server-to-server APIs still need authentication, authorization and replay handling. Distinguish these threats before adding headers: a response that is unreadable to one script may still have caused a state change.

How can a CDN expose private data?

If user-specific responses are cached under an insufficiently scoped key or marked public, subsequent requests may receive another user's content.

7. Incident: intermittent 502/504 under traffic

What distinguishes an upstream pool timeout from a slow SQL query?

Start with timing decomposition: gateway upstream connect time, response wait, service trace, pool acquisition, dependency span and packet retransmissions. A 502 often means an invalid or failed upstream exchange; a 504 typically means gateway timeout. Validate gateway status conventions rather than treating them as universal server diagnoses. Test draining during deployments and compare failure timestamps with pod termination events.

Investigate one failing logical operation

Start with the user-visible failure, timestamp, route template and operation identity. Identify the component that generated the HTTP status; a gateway response is not a database diagnosis. Correlate edge access logs, target selection, application traces and deployment events. Missing spans may mean the request never reached the service, but can also mean sampling or broken propagation. Absence of telemetry is a hypothesis constraint, not proof.

ObservationHypothesisDiscriminating evidence
High client latency, no handler spanClient pool, DNS/connect/TLS or proxy queueClient stage timers, gateway connect timing, accepted-connection counters
Fast handler once started, high pool waitAdmission bottleneckPending/active pool usage and queue age
502 bursts during rolloutConnection drain or premature backend closeReset/termination timestamps and target lifecycle
504 with completed orderResponse lost or late after effectAuthoritative order/payment identity and commit time

Suppose a rollout produces resets only during the 20 seconds after old pods become unready. CPU and SQL times stay normal. A useful experiment changes one drain/grace setting in staging while holding offered load constant. If the reset window disappears without changing SQL behavior, that supports a lifecycle hypothesis. Increasing every timeout would obscure the evidence and could merely delay failures.

Contain before tuning

Reduce retries and offered concurrency if the system is overloaded. Pause a rollout if it correlates with errors. Protect ambiguous writes with existing operation identities and status lookup. Preserve enough logs and counters to distinguish the next hypothesis. Then fix the causal mechanism and repeat the same experiment. A successful retry is not proof that the original failure was harmless; check for duplicate side effects.

What distinguishes an upstream pool timeout from a slow SQL query?

Instrument acquisition wait and query execution separately; the SQL engine may be fast while callers wait for scarce connections.

8. Production runbook and experiments

Which failures are safe to retry?

Exercise DNS failure, expired certificate, TCP reset, lost packet, slow upstream response, half-closed connections and pod termination. Capture request IDs end to end, gateway error categories, TLS alerts, retransmissions and p99. Verify load balancer health transitions and client retries against safe endpoints. Define target behavior for partial network partitions and graceful degradation.

A passing loopback test proves a particular mechanism, not the behavior of your production gateway, certificate chain or network.

Worked budget exercise

A service calls a provider at 300 completed calls/second and holds a client connection for a mean of 120 ms. For one exchange per call under stable load, average occupancy is 36 connections. If half of a 48-connection fleet budget becomes unavailable, there is insufficient capacity to maintain the same average work at that hold time. Options include reducing offered rate, reducing hold time or provisioning measured spare capacity. Selecting 36 as the pool maximum leaves no room for variance; selecting 1,000 may overwhelm the provider.

Answer to the architectural question: size against a latency distribution, downstream quotas and the desired fault scenario, then load-test at fixed offered rates. For HTTP/2, streams and connections have distinct limits, so do not equate 36 concurrent exchanges with 36 TCP connections. Observe both.

Release checklist

Document the hop-by-hop protocol, trust boundaries, timeout ownership, maximum concurrency, retry ownership, shutdown behavior, cache privacy policy and status lookup for ambiguous effects. Include one successful cold request, one reused-connection request, one controlled timeout and one rolling-deployment test. Link the results to a runbook explaining safe containment and the data needed to investigate.

Which failures are safe to retry?

Only those that are transient and proven safe under the operation's idempotency or reconciliation contract; a timeout alone cannot establish safety.

9. Routing, CIDR and egress capacity

Which boundary drops a packet before HTTP exists?

An IP address identifies an interface destination; a route chooses the next hop. CIDR writes an address range as a prefix: 10.24.8.0/24 fixes the first 24 bits, leaving 256 IPv4 addresses in that block. Address availability is smaller when a platform reserves addresses. A /16 contains 256 /24 blocks, not 16. Allocate non-overlapping ranges across VPCs, on-premises networks and future peers: overlapping private ranges make later connectivity difficult even though each network works independently.

Routing uses the most specific matching prefix. Given a local route for 10.24.0.0/16, a 10.80.0.0/16 route to a transit attachment and a default 0.0.0.0/0 route to NAT, a packet for 10.80.4.9 follows the transit route. It does not use the default merely because the destination is outside the local VPC. The return path needs a compatible route too. Reachability is bidirectional even when the business request is described as one outbound call.

BoundaryDecisionFailure evidence
Route tableNext hop for destination prefixMissing, overlapping or blackholed route
Security groupStateful permission at attached resourceSource group/CIDR, protocol and port mismatch
Network ACLStateless subnet packet filteringReturn ephemeral ports denied
NAT mappingTranslate private source for egressMapping allocation failures or expired idle state
ApplicationAuthenticate, authorize and execute HTTPOnly relevant after lower layers succeed

In a conventional IPv4 AWS topology, public-subnet internet routing uses an internet gateway; a private-subnet default route can lead to a public NAT gateway in a public subnet. The NAT provides outbound translation, not an inbound application listener. A route alone does not grant access, and a security-group rule cannot compensate for a missing route. IPv6 requires its own address, route and egress design; do not assume the IPv4 NAT path applies.

NAT is a finite shared resource

Source translation must distinguish concurrent flows. Thousands of pods connecting to the same provider may share translation capacity even when their own CPU and memory are low. Recreating clients per request increases connection churn; increasing replicas can worsen the incident by creating more sockets. Separate local ephemeral-port exhaustion from gateway mapping exhaustion: they occur at different boundaries and have different evidence.

AWS documents up to 55,000 simultaneous connections per NAT IPv4 address for each unique destination IP, port and protocol tuple. Treat that as a service constraint to verify, not a safe target. Observe ErrorPortAllocation, traffic concentration and connection lifetimes. Connection reuse, bounded concurrency, appropriate secondary addresses or distribution across NAT paths address different causes. See NAT address capacity and NAT troubleshooting.

Worked incident: scale-out makes provider timeouts worse

A fleet grows from 100 to 160 pods, each permitting 400 simultaneous connections to one provider destination. The configured maxima rise from 40,000 to 64,000. With one NAT IPv4 address the latter exceeds the documented per-destination ceiling, though actual usage still depends on reuse and demand. Confirm allocation errors before blaming the provider. First bound fleet concurrency and reduce churn; then size egress and provider capacity together. Doubling read timeouts retains mappings longer and can worsen exhaustion.

MTU and asymmetric failures

A connection that succeeds for tiny responses but stalls for large bodies suggests a different hypothesis from DNS failure. Encapsulation reduces usable packet size; blocked path-MTU feedback or incompatible fragmentation can create payload-sensitive failures. Compare the same route with small and large transfers, inspect retransmissions and permitted ICMP feedback, and identify tunnels. Blindly shrinking every application's payload hides the boundary that needs repair. Record the path and packet evidence before changing MTU.

10. DNS caches and failover

Why does a correct DNS change leave some callers broken?

The application may consult a runtime cache, an operating-system stub, a local forwarding resolver and a recursive resolver before reaching authoritative DNS. A recursive resolver caches answers; the authoritative server publishes the zone's current records. Querying only the authoritative server proves publication, not what a particular application currently sees. A CNAME introduces another lookup and record lifetime. Split-horizon DNS can deliberately return different answers inside and outside a network.

Separate NXDOMAIN (name does not exist), NODATA (name exists without the requested record type), SERVFAIL and timeout. A negative answer can also be cached. Publishing a missing name therefore need not immediately fix clients that recently observed its absence. RFC 2308 describes name/data negative caching; RFC 9520 updates requirements for caching resolution failures. Do not treat every resolution error as an instruction to query aggressively.

A cutover has several clocks

Suppose authoritative publication is correct at 12:00. One resolver still has a positive answer, a second holds a previous negative answer, a JVM uses an independent runtime policy, and an HTTP client continues using an established connection. These clients can disagree without an authoritative inconsistency. Verify the deployed JDK's security properties and client behavior; do not rely on remembered runtime defaults. Record DNS answers, address selection and actual remote socket addresses separately.

Model recovery as detection time, authoritative selection change, resolver/application refresh and reconnection/admission time. These stages can overlap, but TTL alone is not an end-to-end recovery bound. For a planned migration, lower TTL early enough for previously cached records to age out, validate both endpoints, move a small population, observe old endpoint traffic, and drain connections deliberately. Keep rollback routes and certificates usable until the old population is gone. See Route 53 DNS practices.

Worked exercise: 30-second TTL, five-minute outage

A 30-second record does not rule out a five-minute outage. Test three hypotheses independently: the process cached the address longer; the pool retained connections to the old endpoint; the new endpoint lacked capacity or network access. Restarting one pod changes all three variables and is weak evidence. Compare a fresh process, a new connection in an existing process, and the current pooled connection. The result tells you whether to fix resolver policy, connection retirement or the destination.

11. Certificate lifecycle and rotation

How do you rotate trust without disabling verification?

A certificate has a subject identity, public key, issuer signature and validity interval. A usable deployment also needs the corresponding private key, a suitable chain, hostname coverage and clients that trust the issuer. A successful renewal job proves issuance; it does not prove every listener serves the renewed certificate or every client accepts it. TLS termination at an edge and at an internal service creates separate certificate inventories.

Assign ownership for issuance, validation records, secret access, deployment and expiry monitoring. Maintain an inventory of names, listeners, environments, renewal mechanism, trust stores and independent end-to-end probes. Alert on the certificate actually presented, not only the file intended for deployment. Protect key material from source control and diagnostic output. A compromised key calls for incident handling and replacement, not merely extending validity.

For eligible ACM public certificates using DNS validation, retain the validation CNAME and ensure the certificate remains in use; those conditions matter for managed renewal. Imported certificates have a different lifecycle. Follow ACM renewal guidance and verify the precise certificate type and integration before assuming automatic rollout.

Worked trust-root rotation drill

  1. Inventory clients, including batch jobs, old mobile clients and pinned trust stores. Establish a baseline with hostname verification enabled.
  2. Add the new root to clients while retaining the old root. Roll out this overlapping trust set and prove adoption before changing server chains.
  3. Issue a leaf for the correct hostname under the new chain. Canary it on a controlled endpoint, then test cold handshakes from representative clients.
  4. Deploy the new chain gradually. Observe handshake failures by client cohort and verify the certificate presented at each termination point.
  5. Keep a bounded rollback window. Remove old trust only after the last legitimate old-chain dependency is retired and rollback no longer needs it.

This sequence assumes a planned issuer migration and clients that support overlapping trust. A compromise can make retaining old trust unacceptable; then isolate affected traffic and explicitly accept the availability trade-off. Leaf renewal under the same trusted issuer usually does not require distributing a new root, but chain changes and certificate pinning can still break clients.

# Inspect a controlled endpoint using the expected SNI and hostname.
openssl s_client -connect api.example.test:443 \
  -servername api.example.test -verify_hostname api.example.test \
  -verify_return_error </dev/null

Use the relevant CA file when testing a private issuer. A raw IP connection without SNI may inspect the wrong virtual host. This command tests a new handshake, whereas an existing session can continue without revealing a newly deployed chain. Validate both new handshakes and the application's trust store; successful OpenSSL verification does not establish Java trust-store parity.

Failure exercise: the edge renews but internal calls fail

Browser traffic succeeds because the edge certificate renewed. The edge-to-service leg still serves an expired internal certificate. Test both TLS legs and identify which client reports the alert. Correct the internal deployment and renewal ownership; changing the public certificate or disabling backend verification cannot repair that lifecycle. Acceptance requires representative internal clients to complete fresh verified handshakes.

12. AWS checkout request path

Which timer, trust boundary and recovery owner applies at each hop?

Consider an illustrative checkout service: Route 53 names an ALB, the ALB routes to an EKS service, application pods write an authoritative database and call an external payment provider through private-subnet egress. This is a design exercise, not a deployed reference stack. DNS participates in endpoint discovery; it is not a data-plane hop for each HTTP request. Worked failure and recovery

A checkout records a pending payment intent, calls the provider and receives no response before its deadline. Meanwhile, a rollout starts draining its pod. The user gets a gateway timeout. Neither the timeout nor pod termination proves the payment failed. The durable intent must survive the pod; a recovery worker queries by the same provider operation identity and applies a guarded state transition. A retry from the user references the same logical operation. A new provider key would risk a second charge.

Investigate three independent outcomes: whether the provider accepted the payment, whether the database recorded it, and whether the caller received the result. Correlate using durable identities instead of treating one trace ID as business truth. Bound outgoing concurrency while reconciling; a retry storm can consume NAT capacity and delay recovery. If a shared dependency is unavailable, avoid making every pod restart itself.

Acceptance exercise

At a fixed offered rate, test cold connections, reused connections, one draining target, provider response loss after acceptance, DNS endpoint change, a deliberately invalid certificate and egress pressure in an isolated environment. For each logical checkout, account for exactly one intended payment or an explicit unresolved state requiring reconciliation. Record latency, rejection, recovery lag and duplicate-effect counts. Abort on unexpected real side effects. A successful HTTP load test without durable outcome accounting is insufficient.

Design review: does a second Availability Zone solve every failure?

No. It can reduce exposure to a zonal failure if routing, compute, data and egress are designed for it, with enough surviving capacity. A shared bad certificate, shared DNS mistake, exhausted common provider quota or duplicate-payment bug can affect both zones. Name the failure domain and demonstrate that the remaining path preserves the contract before claiming resilience.

1. What does DNS TTL guarantee?

Show answer and follow-up

A resolver can cache data up to configured policy, but clients, local resolvers and intermediaries may apply their own caching. DNS changes do not atomically migrate existing TCP connections.

Follow-up: How do you drain long-lived connections when changing endpoints?

Follow-up answer: Limit connection age where supported, stop admitting new work to old endpoints, allow accepted work to drain, and monitor old connections until the cutover criterion is met. DNS alone cannot retire long-lived sessions.

2. Why is TCP latency sometimes high with low server CPU?

Attempt answer, then reveal.

Packet loss, congestion, receive windows and connection establishment delays can dominate when CPUs are idle.

3. What does TLS authenticate?

Attempt answer, then reveal.
Show answer and follow-up

Properly verified TLS authenticates the peer endpoint using certificate chains and hostname checks, and protects session confidentiality and integrity.

Follow-up: What happens if hostname verification is disabled?

Follow-up answer: An attacker with a certificate trusted for a different name could be accepted as this endpoint. Keep hostname verification enabled and fix the certificate name, trust configuration or intended destination instead.

4. Why use HTTP/2?

Attempt answer, then reveal.
Show answer and follow-up

It supports multiplexed streams and header compression over a shared connection, reducing overhead for some workloads.

Follow-up: Why might one TCP loss still affect streams?

Follow-up answer: TCP delivers bytes in order. Missing bytes can delay later bytes containing frames for other streams even though HTTP/2 can identify those streams independently.

5. Why is 202 different from 201?

Attempt answer, then reveal.
Show answer and follow-up

202 indicates accepted for processing without implying completion; 201 indicates a resource was created.

Follow-up: How do clients poll or receive completion safely?

Follow-up answer: Return an authorized operation-status URI with stable identity and documented terminal states. Poll with bounded backoff or deliver deduplicated callbacks; do not equate accepted with completed.

6. What is a reverse proxy trust boundary?

Attempt answer, then reveal.
Show answer and follow-up

Only trusted infrastructure may assert forwarded client identity or TLS metadata; untrusted request headers must not override authentication.

Follow-up: How do you prevent forged X-Forwarded-For?

Follow-up answer: Restrict direct access to the backend, configure the trusted proxy chain and overwrite or validate forwarded headers at ingress. Avoid assuming an arbitrary caller-supplied address is trustworthy.

Retries, sticky sessions, draining errors and unrepresentative health checks can concentrate or amplify traffic.

8. How do you distinguish 502 and 504?

9. What is connection pool starvation?

Attempt answer, then reveal.
Show answer and follow-up

All pooled connections are occupied, forcing new requests to wait even if the downstream responds quickly to active work.

Follow-up: Measure pool pending count versus query duration.

Follow-up answer: Graph pending acquisition requests, active connections and per-operation hold time separately. A few leaked/slow responses can exhaust the pool despite fast server execution for requests that actually start.

An original request may have committed its side effect despite a lost response; retry can duplicate it.

Follow-up answer: The key must identify one logical business operation, be scoped to the caller/tenant, and reject conflicting payload reuse. A new random key on each retry defeats the guarantee.

When cache keys or response directives fail to separate private user representations.

Summarize the chapter from memory

Networking revision sheet

  1. Decompose latency into resolution, connection, TLS, admission, application and response transfer.
  2. DNS changes affect future resolution; they do not move an existing socket.
  3. TCP supplies an ordered stream. HTTP supplies message framing and semantics.
  4. TLS verification establishes peer identity; authorization remains an application responsibility.
  5. HTTP/2 multiplexes streams over TCP; HTTP/3 uses QUIC. Shared resource limits remain.
  6. Pool acquisition, connect, idle-read and total request timeouts are different limits.
  7. A timeout or 504 cannot prove that a remote effect did not happen.
  8. Bound retries by operation safety, remaining deadline and fleet-wide capacity.
  9. no-cache means validate before reuse; no-store forbids storage under HTTP caching rules.
  10. Trust forwarded metadata only from controlled proxies; CORS is not API authorization.
  11. Drain accepted work explicitly during shutdown. Check target transitions against errors.
  12. Use stage timings and controlled faults to falsify a specific incident hypothesis.
  13. Route by longest matching prefix; check the return path and stateless ACL ports.
  14. NAT capacity is shared; scale-out can increase egress pressure.
  15. DNS recovery includes caches and reconnection. A negative answer can persist.
  16. Rotate trust with overlap, canaries and fresh verified handshakes.
