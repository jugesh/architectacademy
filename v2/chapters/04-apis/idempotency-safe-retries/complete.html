Idempotency and Safe Retries

Why retrying a timed-out POST can charge a customer twice, and how to make retries safe.

The ambiguous outcome What idempotency guarantees Request identity and conflict detection Transactional state machine Retries, TTL and operations

1. The ambiguous outcome

What did the client actually observe?

A client sends POST /payments and times out after 2 seconds. The server may have committed the payment but lost the response. Retrying is necessary for availability, yet a naive retry can duplicate the side effect. A timeout proves only that the client did not receive a response, not that the operation failed.

2. What idempotency guarantees

Differentiate delivery and business effect.

An idempotent operation has the same intended effect when repeated with the same identity. HTTP PUT and DELETE are specified as idempotent in their intended semantics, but real implementations may still emit duplicate side effects. POST is not automatically idempotent. The design goal is at-most-once business effect per logical operation, not exactly-once network delivery.

3. Request identity and conflict detection

Why is a request-body hash insufficient?

Prefer a client-generated unique Idempotency-Key scoped to authenticated tenant and operation. Persist a canonical request fingerprint; the same key with a different payload must be rejected, commonly with 409 Conflict. If clients cannot supply keys, a stable business identifier such as orderId can serve as the uniqueness boundary, but hashing the request body alone can accidentally collapse two legitimate identical purchases.

4. Transactional state machine

What if the process dies after charging?

Model records as PROCESSING, SUCCEEDED or FAILED with a unique constraint on (tenant, operation, key). Claim the key atomically, execute the database effect in the same transaction where feasible, and store the outcome for replay. Concurrent duplicates must not both proceed. A PROCESSING record needs a lease or recovery policy for crashed workers. An external payment provider requires its own idempotency contract or a reconciliation workflow; a local DB transaction cannot atomically commit a remote charge.

5. Retries, TTL and operations

When is a retry safe?

Retry transient failures with bounded exponential backoff and jitter. Never retry indefinitely or retry validation failures. Choose retention based on the longest credible retry window and business risk; expiry reintroduces duplication risk. Track duplicate-key rate, conflict rate, stuck PROCESSING records and recovery outcomes. Document whether repeated requests return the original status and response body.

Interview and design review

Try answering before expanding.
Does an idempotency key guarantee exactly-once execution?

No. It can enforce at-most-once recorded business effects within the chosen persistence boundary. Network retries and crash recovery still occur. External side effects need a provider key or reconciliation.

How can you avoid relying on a client key?

Use a stable business identity, such as an order or payment-intent ID, with a database uniqueness constraint. Distinguish truly separate purchases that happen to have identical payloads.

What response should a duplicate request receive?

For a completed identical operation, replay the documented original result. For an in-progress operation, return a documented pending/conflict response or wait briefly; never start an uncoordinated duplicate.

What breaks if the key expires?

A late retry can be treated as new work. TTL must align with retry policy and business semantics; durable business uniqueness may need to outlive the cache.

Crash-window analysis

What is the hardest crash window?

Enumerate crash points explicitly: before claiming the key, after claiming but before business write, after the write but before response persistence, and after response persistence but before the HTTP response reaches the client. If claim and write use separate transactions, a PROCESSING row may be orphaned and must be recovered. If the business write and completion record share one database transaction, a crash before commit rolls both back; a crash after commit permits replay of the stored result. External side effects such as card charges create a different boundary: persist a payment intent, pass a stable provider idempotency key, query provider status after ambiguity and reconcile before retrying.

What is the hardest crash window?

The remote provider may have charged the customer while the local process has no confirmed result. Reconciliation with the provider is required.

Idempotency implementation contract

Trace the invariant, failure boundary and recovery.

Specify the uniqueness scope as (tenant, operation, logical_key), persist a canonical request fingerprint, and reject the same key with a different fingerprint. For an all-database operation, claim the key and write business state and final response within one transaction, protected by a unique constraint. Handle concurrent claims using a documented pending/conflict or wait policy. For an external charge, persist a payment intent before calling the provider, send a stable provider idempotency key, and reconcile ambiguous timeouts against provider status before any new charge attempt. A local key cannot make a remote side effect atomic. Define TTL based on realistic retry horizons and retain durable business uniqueness if the consequence of late duplicates is severe.

Design review and interview follow-ups

What happens after a timeout if the provider charged but the local response was lost?

Query the provider using the stable payment intent/provider key, reconcile the local state and replay the result; do not blindly issue a new charge.

Can a request hash alone identify a purchase?

No. Two legitimate purchases can have identical payloads. Identity must represent the logical business operation.

Canonical request identity

Why not hash the whole JSON body as the key?

The idempotency key identifies a logical operation, not merely a byte-identical HTTP request. Scope keys by authenticated principal or tenant, endpoint/business operation and retention period. A canonical fingerprint should normalize semantically equivalent inputs consistently, while excluding volatile headers and request IDs. Reject a reused key with different business parameters. Distinguish validation failure before execution from a committed business failure: your API contract must state which outcomes are stored and replayed. Document the status returned while the first attempt is still processing.

Why not hash the whole JSON body as the key?

Equivalent JSON may differ in ordering, and two legitimate purchases can have identical bodies. Business identity is distinct from content equality.

Concurrency and state transitions

How do you avoid two workers recovering the same expired key?

A robust claim is an atomic INSERT protected by a unique constraint. If a second request arrives concurrently, it must observe the existing record and must not execute the business operation. A state machine may use NEW, PROCESSING, SUCCEEDED and terminal FAILED states, with ownership leases and fencing to recover abandoned work. Never allow a worker whose lease expired to overwrite a newer worker's result. For database-only effects, place the domain mutation and terminal result in one transaction; for remote effects, split into durable intent, provider call and reconciliation steps.

How do you avoid two workers recovering the same expired key?

Acquire ownership with a conditional atomic update and monotonically increasing lease generation, then reject stale completion attempts.

HTTP semantics and observability

Does exactly-once HTTP delivery exist?

A completed replay should return a stable, documented status and body or a link to the resource. A mismatch should be a client error such as 409. An in-progress duplicate may return 409, 202 or a brief wait depending on the contract. Instrument new operations, successful replays, payload conflicts, stale PROCESSING claims, provider reconciliation and duplicate business effects. Alert on stuck claims and provider/local status divergence. Include chaos tests that kill the process at every persistence and network boundary.

Does exactly-once HTTP delivery exist?

No general network protocol can prevent a client from losing a response after the server commits. The useful guarantee is deduplicated business effect and recoverable outcome.

Crash-safe POST and payment intent lab

Contract before code

A payment API must support retries when the client never receives the first response. The unit of deduplication is a payment intent or other stable business operation, not the exact HTTP bytes. For each authenticated tenant and operation ID, one logical intent must not cause two independent charges.

Define four cases: new key with new request; same key with equivalent request while processing; same key after completion; same key with different canonical request payload. Document status codes and responses. A server cannot promise exactly-once network delivery. It can promise durable deduplication for the domain effect under explicit assumptions.

Suggested durable tables

CREATE TABLE payment_intent (
  tenant_id      varchar(80) NOT NULL,
  intent_id      varchar(100) NOT NULL,
  request_hash   char(64) NOT NULL,
  state          varchar(20) NOT NULL,
  provider_ref   varchar(150),
  result_json    text,
  version        bigint NOT NULL DEFAULT 0,
  updated_at     timestamp NOT NULL,
  PRIMARY KEY (tenant_id, intent_id)
);
CREATE UNIQUE INDEX payment_provider_ref_unique
  ON payment_intent(provider_ref);

Whether a nullable unique index permits multiple NULL values is database-specific. Payment states should include a requires-reconciliation path, not merely a catch-all FAILED state. A provider timeout is an unknown outcome, not proof of decline.

Atomic state ownership

UPDATE payment_intent
SET state = 'PROCESSING', version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE tenant_id = :tenant AND intent_id = :intent
  AND state IN ('NEW','RETRYABLE')
  AND version = :expectedVersion;

Check updated-row count. An update count of zero means ownership was not obtained; reread and follow the current state instead of charging. A generation/version prevents a stale worker from committing after another owner has recovered the intent. Leases require time assumptions and fencing because a paused owner can wake up after expiry.

What must be in one transaction?

For a wholly local business effect, put the claim, domain mutation and terminal response in one database transaction if doing so does not require blocking remote calls. For a remote effect, persist intent before invocation, then reconcile asynchronously or after a retry. Do not keep a SQL transaction open across a slow card-provider call merely to pretend there is distributed atomicity.

Tests to kill the process at every boundary

  1. Before intent insert: next request can start fresh.
  2. After insert but before remote call: recover intent and safely invoke.
  3. After provider commit before local confirmation: reconcile; do not double charge.
  4. After local confirmation before HTTP response: return stored outcome on retry.
  5. Two simultaneous requests with same key: unique ownership; only one provider interaction.
  6. Same key with different amount: reject without charge.
  7. Retry after expiration: explicit business uniqueness still prevents a second charge when required.

Architecture interview: answered

What is wrong with hashing the body as the key? Two separate legitimate purchases can have identical bodies, and semantically equivalent JSON can have different bytes. The key must identify a business intent.

Is 409 mandatory for in-progress duplicates? No. 409, 202 or a bounded wait can work; publish one consistent contract.

Will an idempotency cache guarantee correctness? No. Cache eviction and TTL expiry can cause re-execution. Durable business constraints must protect irreversible side effects.

Should transient provider failures always be retried? Only when the request's outcome is known safe to retry under the provider's contract. Timeout ambiguity requires lookup/reconciliation.

What belongs in metrics? In-flight intents, age of unresolved intents, deduplicated replays, fingerprint conflicts, successful reconciliations, provider mismatches and actual double charges.

Final design principle

Exactly-once effect is a product and persistence contract. Exactly-once execution across an unreliable network is the wrong mental model.

ANSWERED ADVANCED INTERVIEW BANK · 12 SCENARIOS

API correctness: Senior Interview and Design Review

Answer before reading. Every question pairs a technical explanation with a verification exercise or architectural follow-up.

1. What is idempotency in a POST endpoint?

Explain the trade-off and test.

An operation is idempotent with respect to its intended effect if repeating the same logical operation does not create additional effects. POST is not inherently idempotent, but a server can impose deduplication using a stable operation ID and durable state. Replaying the original response is a separate API contract decision.

Follow-up / exercise: Distinguish one logical payment repeated from two intentional equal-amount purchases.

2. Why is a request hash not sufficient as an idempotency key?

Explain the trade-off and test.

Two legitimate operations can have identical payloads; hashing conflates intent with content. JSON field ordering and volatile attributes create false differences unless normalized. Prefer a client-supplied key or stable business intent ID and persist a fingerprint only to reject conflicting reuse.

Follow-up / exercise: Show a concrete example involving two equal-value top-ups.

3. What does a timeout tell the client?

Explain the trade-off and test.

A timeout proves that the response was not received within the deadline; it does not prove the server did not commit. A database transaction may complete after the client disconnects, and a remote provider may charge despite a network failure. Retry safely by looking up the logical operation.

Follow-up / exercise: Map the exact crash window between commit and response write.

4. Where must the uniqueness constraint live?

Explain the trade-off and test.

For a domain effect stored in SQL, enforce uniqueness on tenant, operation and idempotency key or business intent in the same authoritative database that guards the effect. An in-memory map is process-local; a cache entry can expire or evict. Durable uniqueness protects against restarts and concurrency.

Follow-up / exercise: Discuss whether a key should be reusable across different endpoints.

5. How should concurrent duplicate requests behave?

Explain the trade-off and test.

The database must arbitrate one owner through an atomic insert or conditional state transition. The second caller can receive the stored result, a documented pending response, a conflict, or bounded waiting; it cannot perform the effect independently. State updates require generation checks so stale recovery workers cannot overwrite new outcomes.

Follow-up / exercise: Design an integration test with a barrier releasing two threads simultaneously.

6. What if the payment provider succeeds before local persistence?

Explain the trade-off and test.

A local SQL transaction cannot atomically commit the external charge. Persist an intent first, send a stable provider idempotency identity, then reconcile uncertain results via provider lookup. If the provider returns a success but local storage fails, the same intent must be recoverable without issuing a new charge.

Follow-up / exercise: Describe how operations staff investigate a persistent UNKNOWN state.

7. Does a transactional outbox make remote calls exactly once?

Explain the trade-off and test.

An outbox makes the local business state and intention to publish atomic in one database. Publishers can still send a record twice after a crash between publish and delivered marking. Consumers must make side effects idempotent; external providers need stable keys and reconciliation.

Follow-up / exercise: Give the publish-then-crash sequence and replay consequence.

8. What should a fingerprint mismatch return?

Explain the trade-off and test.

A reused idempotency key with different business parameters must not silently replay the old result or start a new effect. A documented 409 Conflict or equivalent client error conveys the mismatch. Fingerprinting should cover semantically relevant fields only and exclude volatile transport metadata.

Follow-up / exercise: Explain tenant scoping to prevent cross-customer leakage of stored responses.

9. How long should the server retain keys?

Explain the trade-off and test.

Retention depends on maximum credible retry horizon and business risk. Cache TTL alone is not safe for financially irreversible effects; a durable order or payment intent ID should prevent duplicate execution after cache cleanup. Document behavior after expiry and after archival.

Follow-up / exercise: Challenge a proposed 24-hour TTL for a mobile offline client retrying after a week.

10. When is FAILED terminal versus retryable?

Explain the trade-off and test.

An invalid request may be permanently rejected without executing an effect, whereas a transient provider error may require retry or reconciliation. A timeout should be treated as UNKNOWN until checked. State machines must represent these distinctions; marking every exception FAILED can cause unsafe new attempts.

Follow-up / exercise: List transitions allowed from PROCESSING and UNKNOWN after crash recovery.

11. How do you prevent stale lease owners from writing results?

Explain the trade-off and test.

Use an ownership generation or fencing token acquired with a compare-and-set update. Every completion checks that token against current state, so a process resuming after lease expiry cannot overwrite a newer worker. Time-based expiry without fencing alone does not establish exclusive execution.

Follow-up / exercise: Simulate a paused worker resuming after lease transfer.

12. What belongs in the idempotency test suite?

Explain the trade-off and test.

Test concurrent identical calls, identical payload under different intent IDs, key reuse with altered amount, all crash boundaries, provider timeout after charge, TTL expiry, client disconnect and duplicate response replay. Assert business effects, not just HTTP status.

Follow-up / exercise: Inject a process kill immediately after provider success but before local terminal persistence.
