API Contracts, Idempotency and Safe Retries

Why retrying a timed-out POST can charge a customer twice, and how to make retries safe.

1. The ambiguous outcome

What did the client actually observe?

A client sends POST /payments and times out after 2 seconds. The server may have committed the payment but lost the response. Retrying is necessary for availability, yet a naive retry can duplicate the side effect. A timeout proves only that the client did not receive a response, not that the operation failed.

2. What idempotency guarantees

Differentiate delivery and business effect.

An idempotent operation has the same intended effect when repeated with the same identity. HTTP PUT and DELETE are specified as idempotent in their intended semantics, but real implementations may still emit duplicate side effects. POST is not automatically idempotent. The design goal is at-most-once business effect per logical operation, not exactly-once network delivery.

3. Request identity and conflict detection

Why is a request-body hash insufficient?

Prefer a client-generated unique Idempotency-Key scoped to authenticated tenant and operation. Persist a canonical request fingerprint; the same key with a different payload must be rejected, commonly with 409 Conflict. If clients cannot supply keys, a stable business identifier such as orderId can serve as the uniqueness boundary, but hashing the request body alone can accidentally collapse two legitimate identical purchases.

4. Transactional state machine

What if the process dies after charging?

Represent confirmed terminal outcomes separately from UNKNOWN/requires-reconciliation; use PROCESSING, SUCCEEDED or confirmed FAILED with a unique constraint on (tenant, operation, key). Claim the key atomically, execute the database effect in the same transaction where feasible, and store the outcome for replay. Concurrent duplicates must not both proceed. A PROCESSING record needs a lease or recovery policy for crashed workers. An external payment provider requires its own idempotency contract or a reconciliation workflow; a local DB transaction cannot atomically commit a remote charge.

5. Retries, TTL and operations

When is a retry safe?

Retry transient failures with bounded exponential backoff and jitter. Never retry indefinitely or retry validation failures. Choose retention based on the longest credible retry window and business risk; expiry reintroduces duplication risk. Track duplicate-key rate, conflict rate, stuck PROCESSING records and recovery outcomes. Document whether repeated requests return the original status and response body.

Interview and design review

Try answering before expanding.
Does an idempotency key guarantee exactly-once execution?

No. It can enforce at-most-once recorded business effects within the chosen persistence boundary. Network retries and crash recovery still occur. External side effects need a provider key or reconciliation.

How can you avoid relying on a client key?

Use a stable business identity, such as an order or payment-intent ID, with a database uniqueness constraint. Distinguish truly separate purchases that happen to have identical payloads.

What response should a duplicate request receive?

For a completed identical operation, replay the documented original result. For an in-progress operation, return a documented pending/conflict response or wait briefly; never start an uncoordinated duplicate.

What breaks if the key expires?

A late retry can be treated as new work. TTL must align with retry policy and business semantics; durable business uniqueness may need to outlive the cache.

Crash-window analysis

What is the hardest crash window?

Enumerate crash points explicitly: before claiming the key, after claiming but before business write, after the write but before response persistence, and after response persistence but before the HTTP response reaches the client. If claim and write use separate transactions, a PROCESSING row may be orphaned and must be recovered. If the business write and completion record share one database transaction, a crash before commit rolls both back; a crash after commit permits replay of the stored result. External side effects such as card charges create a different boundary: persist a payment intent, pass a stable provider idempotency key, query provider status after ambiguity and reconcile before retrying.

What is the hardest crash window?

The remote provider may have charged the customer while the local process has no confirmed result. Reconciliation with the provider is required.

6. Resource and operation contracts

What can callers safely assume across failures and versions?

An API is a behavioral contract across a trust and deployment boundary. A JSON schema describes shape but cannot by itself say whether a charge committed, whether a list is a snapshot, or whether retrying a command is safe. Document identity, authorization, validation, preconditions, side effects, consistency, completion, retention and failure behavior. An endpoint that returns the correct fields but violates those assumptions is incompatible.

Model resources around domain identities rather than exposing persistence tables directly. An order can be a resource with a stable URI while a payment attempt has a separate lifecycle. PUT represents replacement under its defined semantics; PATCH needs a documented patch format and concurrency policy. Commands that do not map cleanly to replacement can be represented as operation resources. Do not use GET for a business mutation merely because a browser can invoke it easily.

Choose a protocol by interaction

HTTP/JSON often suits interoperable request/response APIs with resource semantics and existing intermediaries. gRPC offers typed service contracts and streaming but needs compatible clients, proxy support and explicit retry/deadline behavior. SOAP integrations bring WSDL/XSD contracts, binding/version details and fault semantics. Asynchronous events decouple time but require ownership, ordering and replay contracts. None removes partial failure. Hide a third-party protocol behind a domain adapter so provider faults and schemas do not become your entire public API.

A contract-first workflow defines the schema and behavioral examples before implementing handlers. Generate or validate clients against a pinned specification, review wire changes, and test actual serialized requests. Generated code saves mechanical work; it does not establish correct authorization, timeouts or business invariants. Keep representative consumer contracts in CI and include real error responses, not only a happy-path 200.

Worked design: order creation and payment confirmation

POST /orders creates a durable order identity. A separate payment-intent command references it and can return an operation URI. The caller observes pending, succeeded or declined state without equating acceptance with completion. A business constraint prevents two successful captures for the same intended payment even if two request keys arrive. If split payments are allowed, model each allocation explicitly rather than weakening uniqueness accidentally.

7. Validation, authorization and errors

Which failures can clients correct, retry or reconcile?

Validate transport limits before materializing an unbounded body: byte size, nesting, collection length and allowed content type. Then validate syntax and field shape, authenticate the caller, authorize the target operation, and enforce domain invariants within the authoritative transaction. Exact ordering can vary to prevent resource enumeration and bound expensive work. A syntactically valid amount can still be forbidden or inconsistent with current business state.

Use explicit request DTOs rather than binding directly to persistence entities. Allowlist mutable properties so clients cannot set tenant, role, state or price by adding unexpected fields. Derive ownership from trusted authentication context and check object-level access on creation, read, replay and status polling. An unpredictable UUID is an identifier, not an authorization control. Error messages must not disclose another tenant's operation or secrets from a provider response.

Machine-readable errors

RFC 9457 defines problem details, including a problem-type identity and occurrence details. Keep the HTTP status meaningful and provide stable extension fields when clients need structured decisions. Clients should not parse localized prose to determine retry behavior. Redact stack traces and distinguish public diagnostics from internal correlation metadata.

HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://api.example.test/problems/key-conflict",
  "title": "Operation key conflicts with the stored request",
  "status": 409,
  "instance": "/operations/support-reference",
  "code": "IDEMPOTENCY_PAYLOAD_CONFLICT"
}

This fictional response rejects changed parameters under a reused identity. It does not reveal the stored payload. In Spring MVC, an exception-handler layer can map domain failures to responses; ProblemDetail and ResponseEntityExceptionHandler support this style. Pin your framework version and test serialization and content negotiation. A global catch-all that converts every failure to 200 destroys transport semantics and monitoring.

Separate pre-execution validation errors from durable business outcomes. A malformed request can be corrected before an operation is claimed. A confirmed decline may be a terminal result for that intent. A provider timeout is unknown. Do not store every exception as a replayable terminal failure: doing so can permanently hide a charge that actually succeeded.

Failure exercise: tenant B replays tenant A's key

If lookup uses only the raw key, B may receive A's response or suppress its operation. Scope the key to the authenticated tenant and logical operation. Authorize the referenced resource independently before replaying data. Test equal keys across tenants, altered resource IDs and polling after permission revocation. Define whether retained outcomes are redacted when authorization changes.

8. Atomic claims and local effects

Which committed record proves the effect and its outcome?

For a wholly local database effect, aim for one transaction that claims identity, mutates business state and records the terminal result. A transaction that rolls back must not leave an externally visible claim presented as success. A preliminary SELECT followed by an INSERT is racy: two callers can both see absence. Let a unique constraint arbitrate, and handle the losing transaction deliberately.

BEGIN;
INSERT INTO idempotency_record
 (tenant_id, operation, request_key, request_hash, state, expires_at)
VALUES (:tenant, 'reserve', :key, :hash, 'PROCESSING', :expiry)
ON CONFLICT (tenant_id, operation, request_key) DO NOTHING
RETURNING request_key;
-- Continue with the effect only when this transaction inserted the claim.
-- Otherwise follow the documented duplicate path; never execute blindly.
UPDATE inventory SET available = available - :quantity
WHERE tenant_id = :tenant AND sku = :sku AND available >= :quantity;
-- Check row count; store a durable success or a documented business rejection.
UPDATE idempotency_record
SET state = 'SUCCEEDED', response_json = :result
WHERE tenant_id = :tenant AND operation = 'reserve' AND request_key = :key;
COMMIT;

This is parameterized PostgreSQL design pseudocode, not a complete runnable transaction: the application must branch on both row counts and construct an outcome. If inventory is insufficient, do not execute the shown success update. Choose whether to commit a business rejection or roll back and leave the operation unclaimed. A lock timeout or serialization failure needs bounded transaction retry with the same logical identity.

INSERT conflict handling is database-specific. Under PostgreSQL Read Committed, a conflict may involve a concurrent transaction not visible to the statement's starting snapshot. If no row was inserted, do not assume one statement's fallback read must see the winner. After appropriate transaction handling, read in a fresh statement/snapshot and follow the current record; stronger isolation needs its own retry policy. Never catch a unique violation and continue issuing SQL in an aborted transaction.

The authoritative effect needs domain protection too. A unique request key prevents duplicate execution under that key; two different keys for the same business intent can bypass it. If only one reservation per order line is allowed, enforce that identity on the reservation table. Durable business constraints should outlive short-lived replay bodies when the product requires late-duplicate protection.

Worked concurrency timeline

T1 and T2 submit the same scoped key. T1 inserts and changes inventory within its transaction. T2's conflicting insert waits or follows the database's conflict policy. If T1 commits, T2 must replay or observe its outcome; if T1 aborts, T2 can become the owner according to the insertion result. Test both branches with two actual database sessions, lock timeouts and a process kill. An in-memory concurrency test cannot verify SQL isolation.

9. Remote effects and fencing limits

Can an old worker still charge after losing its lease?

A local generation check can stop a stale worker from overwriting a newer database row. It cannot stop that worker from calling an external provider unless the provider also enforces a suitable identity or fencing contract. This is the central difference between fencing local state and preventing remote effects. A paused process can resume after lease expiry and still possess valid network credentials.

Persist the intent and stable provider identity before invocation. Treat response loss as an unresolved outcome and use provider lookup or documented replay semantics. If the provider has neither durable deduplication nor a reliable lookup by your identity, you cannot promise automatic at-most-once remote effects plus unlimited retry availability. Choose an explicit pending/manual resolution path, accept a weaker guarantee, or select a provider with a suitable contract.

Outbox and callback boundaries

An outbox makes local business state and publication intent atomic. A relay can publish twice after sending but before marking delivery. Consumers need durable deduplication or idempotent effects. A callback can be delayed, duplicated or reordered; verify authenticity, authorize the referenced operation and apply a guarded transition. Do not let an older failure overwrite a later confirmed success merely because its callback arrived last.

Recovery needs an operational owner. Index unresolved intents by age and next-attempt time, apply bounded backoff, and expose a support view with redacted provider references. Alert on aged ambiguity, provider/local disagreement and duplicate effects. An operator must not create a replacement payment simply because the dashboard says pending. Require evidence from the authoritative provider and preserve an audit trail of manual resolution.

Failure exercise: provider key expires before a late retry

A provider forgets deduplication keys after a window, while a client retries much later. Reusing the same string may now cause a new charge. Retain local business identity and confirmed provider reference, replay the local result when allowed, and query existing remote state when unresolved. If the provider cannot establish the old outcome, escalate rather than assuming expiry means failure. Document this retention mismatch before promising safe late retries.

10. Pagination and compatibility

What changes when data or clients evolve during a request sequence?

Offset pagination is simple for small, stable lists but deep offsets can be expensive and concurrent inserts/deletes can shift page boundaries. Keyset pagination uses a stable ordered tuple such as (created_at, id) with a matching index and explicit direction. Include a unique tie-breaker. An opaque cursor should bind the relevant filter, sort and tenant scope; base64 encoding alone does not protect it from tampering. Bound page size and avoid accepting arbitrary expensive sort expressions.

SELECT id, created_at, state
FROM orders
WHERE tenant_id = :tenant
  AND (created_at, id) > (:last_created_at, :last_id)
ORDER BY created_at, id
LIMIT :bounded_page_size;

This PostgreSQL pattern needs an index aligned with tenant and sort, plus non-null ordered values or an explicit null policy. It does not create a snapshot across pages. Rows can change while the caller traverses them; exports requiring a fixed point-in-time view need a separate snapshot/export contract. A list endpoint must not quietly imply complete audit extraction under concurrent writes.

Compatibility is more than adding fields

Adding an optional response field can still break strict clients; adding an enum value can break exhaustive switches; changing a default can alter business behavior without changing schema. Keep stable field meaning, units, timestamp interpretation, nullability and error semantics. Test old clients against new servers and, during rolling deployments, new clients against old servers where that combination can occur. Removing a field needs measured consumer migration and a deprecation plan.

A version identifier does not excuse breaking all consumers at once. Separate transport-version changes from domain state migrations, publish compatibility rules and observe usage before retirement. Pin OpenAPI/schema generation inputs and review the generated wire contract in CI. Consumer-driven tests complement provider tests but cannot prove correctness for unknown consumers.

Worked exercise: adding PARTIALLY_REFUNDED

An old client recognizes only PAID and REFUNDED. Returning a new enum can cause a parsing failure or an incorrect default branch. Plan an unknown-state strategy, negotiate or version where necessary, and roll out reader compatibility before emitting the new state. Test historical records and rollback readers too; disabling the writer does not remove the new values already persisted.

11. Async APIs, testing and release evidence

How can the client learn the outcome after losing the response?

A 202 response should lead to an authorized operation resource with stable identity, pending and terminal states, polling guidance and retention. Cancellation is a request with a race: work can complete before cancellation is observed. Distinguish cancel-requested, cancelled-before-effect and completed. A promise to stop an external charge needs the provider's capabilities, not just an interrupted Java thread.

Webhooks need authentication, replay handling, bounded retries and a status lookup fallback. A successful callback delivery does not prove the receiving business effect committed unless the receiving contract says so. Replays should use the original event identity and payload meaning. Keep notification delivery separate from the authoritative operation state so a mail failure does not turn a successful payment into a failed payment.

Release acceptance worksheet

Record uniqueness scope, canonical fingerprint version, atomic local boundaries, provider key retention, ambiguous-state recovery, authorization on replay/poll, concurrency bounds, error schema, compatibility matrix and evidence IDs. The pass criterion is recoverable correct business state under the stated faults. Mark unsupported cases explicitly, such as automatic retry after an unresolvable provider outcome.

Summarize from memory

API revision sheet

  1. Specify identity, authorization, effects, consistency, completion and failure semantics.
  2. A timeout means the response was not observed; the effect may exist.
  3. Scope operation keys to authenticated tenant and operation. Compare canonical fingerprints.
  4. Two equal purchases need different intent identities. A hash is not intent.
  5. For local effects, claim, mutation and terminal outcome share one authoritative transaction.
  6. For remote effects, persist intent, use stable provider identity and reconcile ambiguity.
  7. A local generation check cannot fence a provider that ignores it.
  8. Key expiry does not erase business uniqueness or prove remote failure.
  9. Use explicit DTOs, object authorization and stable machine-readable error types.
  10. Keyset pagination needs stable order and a tie-breaker; it is not automatically a snapshot.
  11. Reader compatibility precedes new enum values and schema emission.
  12. 202 is acceptance. Status lookup, callback replay and cancellation races need contracts.

Worked recall

Provider charged, local confirmation missing: keep the same intent and provider identity, query/reconcile, then record the result. Do not mark unknown as declined or mint a new charge key.

Acceptance

Test concurrent duplicates, changed payload, separate equal intents, tenant isolation, expiry and every crash window. Count durable effects, not only successful HTTP responses.
