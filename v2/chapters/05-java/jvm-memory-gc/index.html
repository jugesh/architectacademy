JVM Memory, Garbage Collection and Performance

A practical model of Java heap, allocation, garbage collection, memory leaks and latency tuning.

Memory regions and ownership Allocation and object lifetime GC behavior and trade-offs Memory leak diagnosis Tuning workflow

1. Memory regions and ownership

Why can a pod be OOM-killed with free heap?

Each JVM process has a heap for ordinary objects, per-thread stacks for call frames and local variables, metaspace for class metadata, code cache for compiled methods, and native/off-heap allocations. The Java heap is not the process's total memory footprint. In a container, a process can be killed for exceeding its memory limit even when heap occupancy appears healthy. Inspect RSS, direct buffers, thread counts, native memory and heap metrics together.

2. Allocation and object lifetime

Which allocations actually matter?

Most objects are cheap to allocate with thread-local allocation buffers, but high allocation rate creates GC pressure. Generational collectors exploit the observation that many objects die young. Allocation profiling often reveals excessive temporary objects, boxing, serialization and large intermediate collections. Optimize proven hotspots; do not assume object pooling improves performance for ordinary small Java objects.

3. GC behavior and trade-offs

Does a low-pause collector mean zero pauses?

Garbage collectors reclaim unreachable objects by tracing references from roots. Stop-the-world pauses can occur even with concurrent collectors. G1 balances throughput and pause goals across regions; ZGC targets very low pause times, with different overhead and compatibility considerations. Collector selection should follow observed latency SLOs, heap size, allocation rate and JDK version, not fashion.

4. Memory leak diagnosis

Why doesn't a larger heap fix a leak?

A Java leak means objects remain reachable longer than intended, often through static maps, unbounded caches, thread locals, listener registrations or retained request contexts. Rising old-generation occupancy after major collections is a warning, not definitive proof. Compare heap histograms and dominator trees across time; inspect retained size and reference paths before changing heap size.

5. Tuning workflow

Which metrics prove a tuning improvement?

Capture baseline throughput, p50/p95/p99, allocation rate, GC pause distribution, CPU, heap after collection and RSS under realistic load. Enable unified GC logging, inspect JFR recordings and thread dumps, then change one variable at a time. Size heap with container headroom for metaspace, direct buffers, code cache, thread stacks and native libraries. Validate warm-up and steady-state behavior separately.

Architecture review questions

Answer before expanding.
Why can CPU be high when request throughput is low?

High allocation and GC work, lock contention, busy spinning or excessive serialization may consume CPU without useful throughput. Correlate profiles, GC logs and dependency latency.

What is the difference between heap usage and RSS?

Heap usage measures managed Java objects in the heap. RSS approximates resident process memory including native areas, direct buffers, stacks and mapped pages.

How do you investigate a suspected leak?

Reproduce under stable load, compare post-GC occupancy, inspect heap dumps and dominators, identify retention paths, fix lifecycle or bounds, then verify the trend.

When would you choose ZGC over G1?

When tail-latency goals justify low-pause collection and testing confirms acceptable CPU, memory and throughput overhead on the target JDK.

Capacity mathematics and GC pause budgets

Why can good average GC time coexist with poor p99?

Suppose a service allocates 180 MB/s and the young generation has 900 MB of effective allocation headroom. A rough first approximation is one young collection every five seconds, although survivor promotion, TLAB waste, concurrent work and changing allocation rates alter the interval. If each pause is 40 ms, this alone contributes approximately 0.8% stopped time, but request p99 can still be strongly affected when many requests overlap a pause. Distinguish GC throughput (fraction of time doing application work) from latency (pause duration and frequency) and footprint (heap plus native memory). A target such as 99.9% of requests under 250 ms must be validated at peak load, not inferred from average pause time.

Why can good average GC time coexist with poor p99?

A pause may affect many concurrent requests simultaneously; its overlap with request execution and the existing latency distribution determines tail effects.

GC tuning decision record

Trace the invariant, failure boundary and recovery.

A production API has a 300 ms p99 SLO, 2 GiB pod memory limit and 700 MiB/s allocation at peak. Start with container memory accounting: heap + metaspace + code cache + thread stacks + direct buffers + native libraries must fit below the limit with safety margin. A 1.4 GiB maximum heap leaves only 648 MiB for everything else; measure RSS and native allocations before accepting that budget. Compare G1 and ZGC on the same workload, JDK build and CPU quota. Record pause distributions, CPU, throughput, allocation rate, promotion rate, post-GC live set, and p99 during burst and steady load. Do not tune MaxGCPauseMillis as if it were a hard deadline: it is a collector goal. Use JFR allocation profiling to identify hot allocation sites and distinguish GC pressure from lock contention.

Design review and interview follow-ups

GC logs reveal frequent short young pauses but rising old-gen occupancy. What next?

Check whether the post-collection live set rises over repeated steady-load cycles, inspect allocation and retention profiles, then look for long-lived caches or reference chains. A larger heap is a mitigation, not a diagnosis.

If the pod is OOM-killed with 40% heap free, what do you inspect?

RSS, direct-buffer limits, thread stacks, metaspace, code cache, native allocations and container limits. Enable Native Memory Tracking at startup if its overhead is acceptable.

Java Memory Model and safe publication

Why does volatile not make count++ atomic?

The Java Memory Model defines visibility and ordering relationships between threads. A happens-before edge can arise from monitor unlock/lock, volatile write/read, thread start/join and higher-level concurrent utilities. A volatile field provides visibility and ordering for reads and writes to that field but does not make a multi-step check-then-act sequence atomic. Immutable objects with final fields benefit from special initialization guarantees when safely constructed. Prefer explicit ownership, immutability and java.util.concurrent abstractions over ad hoc double-checked synchronization.

Why does volatile not make count++ atomic?

The increment performs a read, arithmetic and write. Other threads can interleave; use AtomicInteger, a lock or another atomic coordination mechanism.

Threading, pools and virtual threads

Why can virtual threads increase outages?

Platform threads have native scheduling and stack costs; virtual threads reduce the cost of blocking-style concurrency but do not increase database or CPU capacity. A service using virtual threads can still overwhelm a 50-connection pool with 10,000 simultaneous requests. Bound access to scarce downstream resources with semaphores, pools or admission limits. Watch for pinning patterns and carrier-thread utilization on the exact JDK in use. Compare throughput and tail latency under realistic blocking ratios before migrating.

Why can virtual threads increase outages?

Cheap concurrency can flood a limited database or remote API unless downstream concurrency is bounded.

Diagnostic decision tree

Which metric best distinguishes memory leak from high allocation churn?

For high p99 with high CPU, inspect JFR method profiles, allocation events, GC pauses and lock contention. For high p99 with low CPU, inspect thread states, dependency spans, pool acquisition time and queue depth. For rising RSS with stable heap, investigate direct buffers, native libraries, metaspace and thread stacks. Capture evidence during the incident: thread dumps are point-in-time snapshots, while JFR and metrics show evolution. Validate hypotheses by changing one variable and repeating the workload.

Which metric best distinguishes memory leak from high allocation churn?

Post-GC retained live-set trend under stable workload, supported by heap histograms and dominator analysis; allocation rate alone does not prove retention.
