JVM Memory, Garbage Collection and Performance

A practical model of Java heap, allocation, garbage collection, memory leaks and latency tuning.

ConceptsWorked LabInterviews

Concepts

1. Memory regions and ownership

Why can a pod be OOM-killed with free heap?

Each JVM process has a heap for ordinary objects, per-thread stacks for call frames and local variables, metaspace for class metadata, code cache for compiled methods, and native/off-heap allocations. The Java heap is not the process's total memory footprint. In a container, a process can be killed for exceeding its memory limit even when heap occupancy appears healthy. Inspect RSS, direct buffers, thread counts, native memory and heap metrics together.

2. Allocation and object lifetime

Which allocations actually matter?

Most objects are cheap to allocate with thread-local allocation buffers, but high allocation rate creates GC pressure. Generational collectors exploit the observation that many objects die young. Allocation profiling often reveals excessive temporary objects, boxing, serialization and large intermediate collections. Optimize proven hotspots; do not assume object pooling improves performance for ordinary small Java objects.

3. GC behavior and trade-offs

Does a low-pause collector mean zero pauses?

Garbage collectors reclaim unreachable objects by tracing references from roots. Stop-the-world pauses can occur even with concurrent collectors. G1 balances throughput and pause goals across regions; ZGC targets very low pause times, with different overhead and compatibility considerations. Collector selection should follow observed latency SLOs, heap size, allocation rate and JDK version, not fashion.

4. Memory leak diagnosis

Why doesn't a larger heap fix a leak?

A Java leak means objects remain reachable longer than intended, often through static maps, unbounded caches, thread locals, listener registrations or retained request contexts. Rising old-generation occupancy after major collections is a warning, not definitive proof. Compare heap histograms and dominator trees across time; inspect retained size and reference paths before changing heap size.

5. Tuning workflow

Which metrics prove a tuning improvement?

Capture baseline throughput, p50/p95/p99, allocation rate, GC pause distribution, CPU, heap after collection and RSS under realistic load. Enable unified GC logging, inspect JFR recordings and thread dumps, then change one variable at a time. Size heap with container headroom for metaspace, direct buffers, code cache, thread stacks and native libraries. Validate warm-up and steady-state behavior separately.

Architecture review questions

Answer before expanding.
Why can CPU be high when request throughput is low?

High allocation and GC work, lock contention, busy spinning or excessive serialization may consume CPU without useful throughput. Correlate profiles, GC logs and dependency latency.

What is the difference between heap usage and RSS?

Heap usage measures managed Java objects in the heap. RSS approximates resident process memory including native areas, direct buffers, stacks and mapped pages.

How do you investigate a suspected leak?

Reproduce under stable load, compare post-GC occupancy, inspect heap dumps and dominators, identify retention paths, fix lifecycle or bounds, then verify the trend.

When would you choose ZGC over G1?

When tail-latency goals justify low-pause collection and testing confirms acceptable CPU, memory and throughput overhead on the target JDK.

6. Runtime, JIT and object lifetime

What is specified by Java and what depends on HotSpot?

The Java language and virtual-machine specifications define observable behavior, while HotSpot chooses implementation strategies. Avoid teaching a specific object header size, allocation region or compilation threshold as a universal language guarantee. Architecture decisions should name the JDK vendor/build, collector, CPU architecture and container constraints. A performance conclusion from one combination does not automatically survive an upgrade.

Class loading locates bytecode, linking verifies and prepares it, and initialization executes class initialization logic under the runtime's rules. A classloader is part of class identity; two classes with the same binary name loaded by different defining loaders are not necessarily interchangeable. Plugin/redeployment systems can retain old loaders through threads, static registries or callbacks, keeping class metadata and associated graphs alive. A metaspace problem therefore needs ownership analysis, not just a larger limit.

HotSpot can interpret bytecode and compile hot code using execution profiles. Inlining, speculative optimization and escape analysis can remove work that a hand-written microbenchmark intended to measure. A method can deoptimize when an assumption fails. Warm-up includes class loading, compilation, cache population and connection establishment; each has a different operational consequence. A rolling deployment can expose users to cold latency even if a steady-state benchmark looks excellent.

Allocation is not retention

Objects commonly allocate through thread-local fast paths, but optimization can eliminate some allocations and large allocations may take different paths. Allocation rate measures churn, not the amount retained. An application allocating 500 MiB/s with a stable 300-MiB live set presents a different problem from one allocating 30 MiB/s while retaining another 20 MiB each minute. Optimize the relevant mechanism: excessive temporary work, an oversized live graph, or unintended ownership.

A reference from a GC root keeps an object reachable according to the collector's reachability rules. A small map entry can retain a large graph, which is why shallow object size and retained size differ. Weak/soft references have specialized semantics and are not a general substitute for a cache capacity and freshness policy. Resource cleanup such as closing a socket must have an explicit lifecycle; garbage collection is not a prompt business-resource management contract.

Worked exercise: a tiny listener retains a large tenant graph

A global event registry retains a listener; the listener captures a tenant service; that service references a large catalog. The listener's shallow size is small, but removing it can release the entire otherwise-unreachable graph. Inspect paths to roots and lifecycle registration/unregistration, then verify old tenant graphs disappear across repeated create/delete cycles. A heap histogram alone may identify the large catalogs without identifying the retaining listener.

7. Container memory and native headroom

Which memory number is being limited?

Xmx limits the Java heap, not total memory. Reserved virtual address space, committed memory, resident pages and cgroup-charged memory are different quantities. Linux container accounting can include file cache and other charged memory beyond process RSS. Read the actual cgroup version and limits rather than assuming a host-wide memory number represents the container. An OOMKilled termination and a Java OutOfMemoryError are different observations with different evidence.

Worked budget

For an illustrative 2,048-MiB container, reserve 1,024 MiB for maximum heap, 160 for metadata, 96 for code, 128 for thread stacks, 256 for direct/native buffers and 128 for other charged memory. This leaves 256 MiB of margin. These are planning allocations, not measured guarantees: stack reservation differs from resident use, categories can overlap in reporting, and a native library may exceed its estimate. Measure peak and soak behavior before accepting the budget.

Setting MaxRAMPercentage does not reserve the remaining percentage for native consumers, nor does it cap arbitrary native allocation. Direct-buffer limits do not necessarily cover every native library. Hundreds of platform threads can consume meaningful native resources; thousands of virtual threads also retain stacks and task-local state, though their implementation differs. Bound retained requests and results as well as running threads.

Native Memory Tracking

Enable HotSpot NMT at startup with -XX:NativeMemoryTracking=summary or detail when appropriate. Establish a baseline and compare later measurements with jcmd. NMT tracks JVM-managed categories and has overhead; it does not account for every allocation by third-party native code. Treat a stable NMT report with rising charged memory as a clue to inspect uncovered allocations and OS accounting, not proof the memory is imaginary. See NMT operation and tracking limitations.

java -XX:NativeMemoryTracking=summary -jar service.jar
jcmd <pid> VM.native_memory baseline
# Later, at comparable workload:
jcmd <pid> VM.native_memory summary.diff scale=MB
Failure exercise: increase Xmx after a native-memory incident?

If the container was killed while heap remained stable and direct/native growth dominated, raising Xmx reduces available headroom. First verify termination reason and charged memory, then identify and bound the growing owner. A temporary lower concurrency or smaller buffers may contain the incident. Raising the container limit can be a measured mitigation, but does not establish the cause or prevent unbounded growth.

8. GC mechanisms and measurement

Why does a pause target fail to guarantee API latency?

Tracing collectors identify reachable objects and reclaim other storage. Generational strategies exploit typical lifetime patterns; barriers and remembered structures track references that cross collection boundaries. Concurrent work runs alongside application threads but still consumes CPU and memory bandwidth. Stop-the-world work, allocation stalls and concurrent-cycle progress all matter. A collector that lowers pause duration can reduce application throughput under a tight CPU quota.

G1 organizes the heap into regions and combines young collections with concurrent marking and reclamation of selected old regions. Live-set size, evacuation reserve, allocation pressure and humongous objects influence behavior. Its pause target guides heuristics rather than setting a hard upper bound. Start with the G1 tuning model instead of copying a long flag list that overrides ergonomics without evidence.

ZGC moves much work concurrently and pursues low pauses using different barriers and metadata strategies. Its implementation and available modes vary across JDK releases. Parallel GC can be a rational throughput choice for a workload whose pause requirements permit it; a smaller process can have different trade-offs again. Compare latency, throughput, footprint and operating complexity for the actual service. Collector names are not quality rankings.

Pause overlap and allocation pressure

At 180 MiB/s allocation with 900 MiB of effective headroom, a five-second interval is only a crude churn illustration. Survivor promotion, region policy, fragmentation and concurrent reclamation change it. A 40-ms stop every five seconds is 0.8% stopped time, but does not imply 0.8% of requests are affected: requests overlap pauses and may queue afterward. Correlate request and GC timelines, and report offered load and timeouts.

If concurrent collection cannot keep pace with allocation and retention, more frequent work or allocation stalls can appear. A smaller heap can increase pressure; a larger heap can change footprint and live-set behavior. Neither is universally faster. Measure the post-collection occupancy over equivalent cycles, collector phase timing and CPU quota before attributing every latency spike to heap size.

Worked comparison experiment

Pin the JDK build, dataset, request mix, CPU/memory limits and offered-rate schedule. Establish a warm baseline and soak for both candidate collectors, then repeat burst and replica-loss cases. Compare useful completed operations, latency histograms, timeouts, allocation, charged memory, GC phase timing and total CPU. Reject an apparent improvement that results from dropping load, omitting failed requests or allowing more memory than the production limit.

9. Java Memory Model and invariants

Does seeing a reference mean seeing a coherent object graph?

The Java Memory Model describes legal interactions between threads. A happens-before relationship provides visibility/order guarantees; elapsed wall-clock time is not a synchronization mechanism. Monitor unlock/lock, volatile publication, thread lifecycle and concurrent utilities establish relevant edges. Correctly constructed final fields have special initialization guarantees, but mutable fields reachable from an object still need their own ownership or synchronization policy. Do not leak this during construction.

A volatile counter increment is a read, arithmetic and write. Two threads can read the same old value and lose an update. AtomicInteger can provide atomic counter operations; LongAdder suits high-contention statistics where a sum during concurrent updates need not be an atomic snapshot. Neither automatically protects a multi-field business invariant. Protect balance and overdraft limit together, or publish an immutable combined state through a suitable atomic reference.

record Limits(int maxConcurrent, int queueCapacity) {
    Limits {
        if (maxConcurrent <= 0 || queueCapacity < 0)
            throw new IllegalArgumentException("invalid limits");
    }
}
final AtomicReference<Limits> limits =
    new AtomicReference<>(new Limits(20, 100));
void reload(Limits validated) { limits.set(validated); }
void handle() {
    Limits snapshot = limits.get(); // Read once for a coherent pair.
    use(snapshot.maxConcurrent(), snapshot.queueCapacity());
}

Reading the reference separately for each field can combine two different valid versions into an invalid pair for the operation. Atomic publication does not make a mutable graph immutable; the record's components here are primitives, but a record containing a mutable list would need defensive ownership. Reference: JLS memory-model rules.

Keep locks short, define a consistent ordering and avoid callbacks or slow remote I/O while holding a monitor. Deadlock is a wait cycle; starvation and livelock differ and may not appear in a simple deadlock detector. Several thread dumps across time help distinguish a transient wait from a persistent cycle. Performance testing does not prove race freedom, and a stress test that never observes a forbidden result is not a substitute for a memory-model argument.

Worked exercise: a snapshot is atomic, the policy is not

A reload atomically changes (maxConcurrent=20, queueCapacity=100) to (5, 10). Existing admitted work does not disappear when the new reference is published. Define whether current permits drain, whether admission uses the new maximum immediately, and how queued work is treated. The reference solves coherent configuration visibility; the resource controller still needs a transition policy.

10. Threads, cancellation and context

What capacity remains scarce with cheap blocking?

Platform-thread pools bound running threads but can hide unbounded task queues. Queueing a million tasks retains request context even if only 100 threads run. Rejection policy, deadline checks and queue bounds are part of correctness under overload. CompletableFuture moves composition and execution choices; it does not make blocking work nonblocking or remove executor capacity. Avoid blocking a shared pool needed by tasks that must complete the blocked operation.

Virtual threads, finalized in Java 21, make many blocking-style tasks cheaper to represent. They do not accelerate CPU work, enlarge a DB pool or create provider quota. A semaphore around scarce work remains useful. Do not pool virtual threads merely to recreate a small platform pool; limit the protected resource explicitly. Also bound response buffering and retained task context, which can dominate memory at large concurrency.

Version matters for pinning. Java 21 has important monitor-related pinning cases described in JEP 444. JEP 491, delivered in JDK 24, removes monitor-related pinning for ordinary synchronized use; native/foreign-code cases and other constraints still require checking. Do not blanket-rewrite synchronized to another lock based on Java 21 advice when operating a later runtime. Diagnose the exact JDK and library path.

Cancellation is cooperative

Interruption requests cooperation; it is not forced rollback. Propagate interruption where appropriate, release owned resources in finally, and distinguish caller abandonment from the lifetime of remote work. A future cancelled locally can coexist with a provider still processing. A lock or permit should represent the intended protected lifetime, not merely the waiting client's patience.

ThreadLocal context belongs to a thread, not automatically to a logical request across executors. Long-lived pool threads can retain sensitive or large values after request completion. Use explicit context transfer or a supported scoped mechanism for your runtime and always define cleanup. Millions of virtual threads carrying large per-thread caches can also consume substantial memory. Avoid assuming a ThreadLocal optimization designed for a small fixed pool stays economical.

Failure exercise: executor dependency deadlock

A fixed pool of four threads runs four request tasks. Each submits a child task to the same pool and blocks waiting for it. All workers are occupied, so no child can start. More timeout retries can refill the same trap. Compose without blocking where suitable, use a separate execution boundary or restructure ownership. Validate the intended dependency graph instead of only increasing the pool size.

11. Evidence-led JVM incident case

Which observation would disprove the leading hypothesis?

A hypothetical Java service develops high p99 and periodic restarts after a release. First verify whether restarts are Java exceptions, container kills, probes or deployment events. Align incoming/admitted/completed rates with CPU throttling, allocation, post-GC occupancy, charged memory, thread states and dependency waits. Avoid changing collector, heap and concurrency together: that makes the result hard to explain.

Worked diagnosis

The live heap stabilizes after each comparable collection, while platform-thread count rises with requests and native stack categories grow. That weakens a heap-retention hypothesis and supports unbounded thread creation. Inspect thread creation sites, executor configuration and missing shutdown. Contain by bounding work and restore the intended lifecycle; then repeat a soak and verify thread/native growth stops. If native categories stay flat while charged memory grows, investigate different evidence rather than insisting on the initial theory.

Architecture review answer: when is tuning complete?

When the causal hypothesis is supported, the change preserves correctness, and repeatable workload/fault/soak evidence meets the declared latency, throughput and footprint objectives. Keep a rollback path and compare warm-up as well as steady state. A lower GC pause average alone does not establish a better service.

Lab

Distinguish memory pools

A Java process consumes heap, metaspace, JIT code cache, GC structures, native libraries, direct buffers and thread stacks. The operating system can kill a container even when heap occupancy is low. Build a memory budget against the container limit, not only -Xmx. Example: a 2 GiB container with -Xmx=1536m has about 512 MiB left for all nonheap/native consumption and headroom; validate against RSS under burst and after warmup.

Allocation versus retention

High allocation rate is not automatically a memory leak. A leak is retained reachable data increasing over time under a stable workload. Diagnose using post-collection live set, heap histograms and dominator trees. Common culprits include unbounded maps, static collections, thread locals, queues with slow consumers, listeners never detached, and cached graphs holding large subgraphs.

Separate GC-correlated stalls, CPU execution, blocked work and native memory growth using an aligned evidence timeline. See the diagnostic boundary diagram.

Concurrency correctness

Visibility is different from atomicity. The Java Memory Model provides happens-before rules; synchronized monitor operations and volatile publications establish important ordering relationships. A volatile integer is visible but count++ is still read-modify-write, not an indivisible operation.

import java.util.concurrent.atomic.AtomicLong;

public final class RequestMetrics {
    private final AtomicLong accepted = new AtomicLong();

    public long recordAccepted() {
        return accepted.incrementAndGet();
    }

    public long acceptedSoFar() {
        return accepted.get();
    }
}

For high-contention statistics where exact immediate reads are unnecessary, consider LongAdder. For invariants spanning several fields, use a lock, an immutable snapshot via AtomicReference, or a transactional boundary. Do not silently assume an atomic counter protects related mutable collections.

Garbage collector comparison

G1 divides the heap into regions and pursues pause targets through mixed and young collections. ZGC minimizes stop-the-world work and is attractive for latency-sensitive workloads, with CPU and memory trade-offs depending on workload and JDK version. Compare with identical traffic, allocation profiles, pod CPU quotas and heap headroom. A configured pause target is a *goal*, not a latency guarantee. Collect throughput, p99, allocation rate, pause distributions, concurrent GC CPU, and post-GC live-set trend.

Virtual threads are not a throughput multiplier

Virtual threads make blocking-style concurrency cheaper; they do not create DB connections, CPU cores or downstream API quota. An application with 5,000 waiting virtual threads and a 30-connection pool still has a 30-connection bottleneck. Bound access to scarce resources; measure request cancellation and timeouts, and inspect blocking/pinning behavior on your actual JDK.

Senior interview: answered

Why can GC pause p99 be low while API p99 is high? Application latency includes locks, pool waits, queues, network and business work. A GC pause histogram is only one contributor.

Why use AtomicReference for configuration? It can publish an immutable configuration snapshot atomically, preventing readers from seeing inconsistent combinations of fields.

How can a large heap worsen latency? Memory pressure, larger live set, GC overhead and container headroom may make pauses or OOM behavior worse; outcome is collector- and workload-specific.

Why can ThreadLocal leak memory? Long-lived threads can retain values beyond request lifetime when cleanup is missing.

How do you choose G1 versus ZGC? Based on measured tail latency, throughput, CPU/memory overhead and collector availability on the production JDK, not the collector name.

Incident evidence

Capture a workload timeline with deployment markers, RSS, heap used after GC, GC pause durations, allocation rate, active threads, pool waits and p99. Record hypothesis and disconfirming evidence before changing heap/collector flags.

Interviews

1. Why can the container OOM-kill a Java process with free heap?

Explain the trade-off and test.

The process RSS includes heap pages plus direct buffers, metaspace, code cache, thread stacks and native allocations. Container limits apply to total charged memory, not merely used Java heap. Capture heap and RSS time series and investigate native allocation before raising Xmx, which can reduce remaining headroom.

Follow-up / exercise: Compare -Xmx, committed heap, process RSS and cgroup memory.current.

Worked answer: Xmx is a managed-heap ceiling; committed heap is memory made available to that heap; RSS counts resident process pages; cgroup charged memory has its own accounting and may include file cache. Compare time series and termination evidence rather than subtracting unrelated snapshots.

2. How can you distinguish allocation churn from a leak?

Explain the trade-off and test.

Allocation churn creates many short-lived objects and frequent collections; a leak produces a rising post-GC live set under a comparable steady workload. Capture JFR allocation profiles, post-GC occupancy and heap dominators. A single large heap dump does not establish a growth trend.

Follow-up / exercise: Explain why high young-GC frequency alone is not proof of a leak.

Worked answer: Frequent young collections can result from high short-lived allocation with a stable live set. Compare retained occupancy across equivalent collection cycles, workload cardinality and dominators. A growing bounded cache during warm-up is also different from unbounded retention.

3. How does the Java Memory Model define visibility?

Explain the trade-off and test.

The happens-before relation establishes when writes in one thread are guaranteed visible to another, including monitor unlock/lock, volatile write/read, and thread lifecycle rules. Data races outside these relationships can expose stale or inconsistent state. Immutable safely published snapshots reduce coordination complexity.

Follow-up / exercise: Describe publication of a shared configuration object without readers seeing partially updated fields.

Worked answer: Build an immutable Limits object, validate it, publish via AtomicReference and have each reader get one snapshot for both fields. Do not mutate a referenced list after publication. Existing active work still needs a policy when limits are reduced.

4. Why is volatile not enough for a counter?

Explain the trade-off and test.

Volatile reads and writes have visibility and ordering semantics, but x++ combines a read and write with an intervening computation. Concurrent threads can lose updates. Use AtomicInteger, LongAdder for approximate high-concurrency statistics, or locks for multi-field invariants.

Follow-up / exercise: Ask whether exact linearizable reads are needed before choosing LongAdder.

Worked answer: AtomicLong provides atomic operations and an exact read at its linearization point. LongAdder combines striped counters; sum during concurrent updates is not an atomic snapshot. Use it for suitable statistics, not a balance or reservation invariant.

5. How do G1 and ZGC differ in tuning goals?

Explain the trade-off and test.

G1 is region-oriented with configurable pause-time goals and concurrent phases; ZGC aims for very short pauses with most work concurrent. Both trade CPU, memory and throughput according to workload and JDK version. Benchmark under realistic allocation, heap occupancy and CPU quotas; pause targets are not hard guarantees.

Follow-up / exercise: Specify your JDK version and compare tail latency and total CPU under the same load.

Worked answer: Pin JDK vendor/build, heap/container CPU limits, dataset and workload. Compare steady, burst and soak runs using latency histograms, failed outcomes, total CPU and charged memory. Report collector-specific modes for that JDK rather than assuming identical availability.

6. What is the meaning of GC pause percentage?

Explain the trade-off and test.

Total stop-the-world pause duration divided by observation interval indicates pause overhead, but it is not directly equal to request p99 impact. A 50-ms pause can stall latency-sensitive threads even with modest average overhead. Correlate timestamps and application spans rather than extrapolating from one aggregate percentage.

Follow-up / exercise: Explain coordinated omission in latency testing during JVM stalls.

Worked answer: A closed workload stops producing arrivals while the JVM stalls, so it records fewer observations in the worst period. Use an appropriately scheduled arrival model, record generator misses and timeouts, and correlate pauses with user-visible latency.

7. When do virtual threads help?

Explain the trade-off and test.

Virtual threads reduce the cost of blocking-style concurrency for IO-heavy tasks and can simplify control flow. They do not accelerate CPU-bound code or expand scarce DB connections. Use explicit downstream concurrency limits and test carrier-thread pinning and library compatibility on the actual JDK.

Follow-up / exercise: Compare 2,000 blocked calls on platform threads versus 2,000 virtual threads with a 30-connection pool.

Worked answer: Both designs still compete for 30 connections. Virtual threads usually reduce the representation cost of waiting, but retained request data and dependency saturation remain. Bound admission, measure memory and actual connection occupancy, and identify JDK-specific pinning paths.

8. How do you investigate a CPU-bound Java API?

Explain the trade-off and test.

Capture JFR method sampling under load, check CPU throttling and warmup, inspect allocation/GC cost, lock contention and native crypto/compression overhead. Verify the hot path with flame graphs or profile trees and repeat after changing one variable. Avoid optimizing code before proving its contribution.

Follow-up / exercise: Explain why tracing slow requests alone can miss aggregate CPU hotspots.

Worked answer: A frequent fast method can consume more aggregate CPU than a rare slow trace. Profile representative execution and native work, then relate CPU samples to useful completions. Tracing is valuable for request decomposition but is not a substitute for CPU profiling.

9. What is safe publication of immutable state?

Explain the trade-off and test.

Construct the object fully and publish through a happens-before mechanism such as a volatile reference, synchronization or a concurrent collection. Immutable fields avoid readers observing partial updates; final-field semantics help correctly constructed objects but do not excuse leaking this during construction.

Follow-up / exercise: Demonstrate a configuration snapshot swapped through AtomicReference.

Worked answer: Use AtomicReference with a fully constructed immutable value; reload replaces the reference. A reader captures one reference and uses its fields consistently. The provided PublicationLab exercises this pattern, though the JMM argument establishes the visibility guarantee.

10. What causes ThreadLocal retention?

Explain the trade-off and test.

A long-lived pool thread can retain ThreadLocal values across requests if not removed, including large request-scoped graphs and classloader references. Wrap use in try/finally remove, or favor explicit context propagation. Measure retained objects rather than assuming ThreadLocal is always the culprit.

Follow-up / exercise: Discuss risks of context propagation across executors and virtual threads.

Worked answer: ThreadLocal values do not automatically follow logical work across executor hops. Capture only necessary context, install and restore it around work, and remove retained values. Per-thread caches become expensive with many virtual threads; verify the runtime-supported context mechanism.

11. How does JIT warmup distort benchmarks?

Explain the trade-off and test.

The JVM profiles execution and progressively compiles hot methods; class loading, caches and dynamic optimization can change latency after startup. Always record warmup duration, steady-state windows and deoptimization events. Compare identical JVM versions and flags; microbenchmarks benefit from a harness such as JMH.

Follow-up / exercise: Why is timing one invocation with System.nanoTime unreliable?

Worked answer: A single invocation includes uncontrolled warm-up, compilation and timer noise, and the optimizer can remove unused work. Use JMH for isolated microbenchmarks with forks, warm-up and proper result consumption; use full workload tests for service-level conclusions.

12. What should a production JVM evidence bundle contain?

Explain the trade-off and test.

Capture build and JDK identity, GC configuration/logs, RSS and cgroup memory, post-GC heap occupancy, thread states, JFR profiles, CPU throttling, request p99 and dependency waits aligned on one timeline. Heap dumps can contain secrets and require secure handling.

Follow-up / exercise: Explain how you would choose an intervention only after a falsifiable hypothesis.

Worked answer: If post-GC live heap is stable but charged memory and platform-thread count rise, a heap-leak hypothesis is weak. Inspect executor/thread lifecycle and native categories, bound the suspected source, then repeat the same soak. Change course if that intervention does not change the predicted trend.
