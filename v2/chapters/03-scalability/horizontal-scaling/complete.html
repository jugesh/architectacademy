Vertical vs Horizontal Scaling

How to grow application capacity without simply moving the bottleneck.

Prerequisites: latency, throughput, concurrency · Related: load balancing, autoscaling, database connections

ConceptsWorked LabInterviews

Concepts

1. Identify the constraint before scaling

What is saturated?

Why might more servers not help?

A Spring Boot API handles 400 RPS comfortably. At 1,000 RPS its p99 latency increases dramatically. Adding replicas sounds reasonable, but the bottleneck might be CPU, a lock, a database connection pool, a slow query, or an external API. Scaling an unconstrained tier increases cost without improving useful throughput.

Start with measurements: request arrival rate, mean and tail response times, completed throughput, error rate, CPU, memory, queue depth, thread states, connection wait time and dependency latency. Locate the resource whose utilization or contention increases as performance deteriorates.

Scaling means increasing useful capacity while meeting service objectives; it does not simply mean increasing instance count. A fleet of twenty replicas can still depend on one saturated database writer.

2. Scale up or scale out?

When is a larger host better?

What coordination does scale-out require?

Vertical scaling increases resources allocated to an instance: vCPUs, RAM, disk throughput or IOPS. It minimizes distributed coordination and can suit tightly coupled workloads. However, performance gains are workload-dependent, machines have limits, and one large node may be an important failure domain.

Horizontal scaling adds instances and distributes requests or partitions data. It can increase throughput and isolate individual host failures, but introduces routing, lifecycle management and shared-state concerns. For HTTP services, a stateless request-processing tier is usually easier to scale than one storing authoritative sessions in memory.

Horizontal scaling is not automatically better. If each of four replicas has a 50-connection database pool, the theoretical maximum is 200 connections. Increasing to twenty replicas raises that maximum to 1,000. The database may spend more time contending and waiting, increasing latency despite lower application CPU.

3. Capacity mathematics and tail latency

What does Little’s Law calculate?

Why is p99 different from average?

Little’s Law relates stable-system averages: L = λ × W, where L is average in-flight requests, λ is average arrival rate and W is average time spent in the system.

At 1,000 RPS with 200 ms average response time, the system has approximately 200 in-flight requests. If response time increases to 800 ms while arrivals remain stable, concurrency increases to approximately 800. More concurrent requests can exhaust bounded resources such as database connections, worker threads and memory.

These are averages, not capacity predictions. p99 measures the latency below which 99% of requests complete; it exposes tail behavior that averages conceal. Validate scaling decisions with stepped load tests, realistic traffic mix and dependency metrics.

Operating rule: Scale the constrained resource, not the most visible component.

4. Production implementation on AWS

What should drive autoscaling?

What happens during task warm-up?

A common architecture routes HTTP traffic through an ALB to an ECS service distributed across Availability Zones. ECS Service Auto Scaling adjusts desired task count. CPU target tracking is reasonable for CPU-bound services, while requests per target or a queue-derived metric may better describe other workloads.

Autoscaling is reactive: new tasks need time to start, initialize and pass readiness checks. Preserve headroom for bursts, set sensible minimum capacity, and ensure termination drains in-flight work. A readiness endpoint should represent whether the instance can safely accept requests; it is not identical to process liveness.

management.endpoint.health.probes.enabled=true
management.endpoints.web.exposure.include=health,info

These Spring Boot properties expose probes, but do not themselves configure graceful shutdown or load-balancer draining. For an SQS consumer, backlog per worker and age of the oldest message are often better scaling signals than CPU.

Database-backed services need fleet-wide connection budgeting, query tuning, and sometimes connection proxies. Scaling ECS tasks beyond downstream capacity can amplify outages.

5. Interview and architecture review

Answer first, then expand the explanation.
When is vertical scaling preferable?

When a workload is hard to partition, a larger instance can satisfy demand economically, and simpler operation is valuable. Evaluate cost, single-node failure impact and whether the bottleneck can use the extra CPU or memory. Scale-up does not fix a slow remote dependency.

Why can adding replicas worsen p99 latency?

Replicas can multiply pressure on a shared database, cache or rate-limited service. Inspect connection acquisition time, active sessions, query waits, downstream p99 and aggregate completed throughput. Reducing per-replica concurrency or fixing expensive queries may outperform adding hosts.

What is average concurrency at 1,500 RPS and 300 ms average latency?

Under stable conditions, Little’s Law gives 1,500 × 0.3 = 450 average in-flight requests. This is not peak concurrency, a guaranteed thread count or an estimate of p99.

How would you scale an SQS worker fleet?

Use backlog per worker and oldest-message age, calibrated to processing time and acceptable queue delay. Account for worker warm-up, downstream limits, retry storms and poison messages. Load-test bursts before production rollout.

6. Demand, utilization and queueing

Which demand belongs to which resource?

Begin with units. End-to-end response time includes queueing, execution and dependency waits. CPU demand is CPU-seconds consumed per request; connection demand is connection-seconds occupied per request. These are different service centers. If a request spends 80 ms waiting for a remote API but only 4 ms executing locally, adding CPU cannot eliminate that remote wait. Conversely, a slow CPU-bound serialization path can consume capacity even when the database is idle.

For resource i with mean demand Dᵢ per completed operation and mᵢ equivalent parallel servers, utilization is approximately Uᵢ = X Dᵢ / mᵢ under the model's stable workload assumptions. A utilization target u gives a planning bound X ≤ mᵢu/Dᵢ. Take the minimum across constrained resources. This is a first-order bound, not a latency guarantee: contention, skew, cache behavior and service-time variance can lower observed capacity. Use measured demands from the relevant workload, not a benchmark for another endpoint.

Worked multi-resource model

A hypothetical API needs 12 ms CPU per request. Twelve usable cores at a 60% target imply 12 × 0.60 / 0.012 = 600 RPS. Each request holds a database connection for a mean 40 ms; 30 allocated connections at a 70% occupancy target imply 30 × 0.70 / 0.040 = 525 RPS. A provider quota of 500 calls/s is needed by 20% of requests, giving a separate quota bound of 2,500 API requests/s if that fraction holds and retries are excluded. The database occupancy bound is smallest, so adding API cores alone does not remove it. The real database may saturate below 30 simultaneous queries; measure execution and lock behavior as concurrency increases.

Changing the request mix changes all three calculations. If a bulk endpoint uses 100 times the CPU of a normal read, an RPS-only model can drastically understate work. Track a small set of meaningful operation classes, their proportions and resource demands. Tenant skew and payload-size distributions belong in the model as well. A capacity report must specify the dataset and mix for which its claims hold.

Why the tail grows before saturation

As utilization rises, an arrival is increasingly likely to find a busy server and wait. In the deliberately simplified M/M/1 model, mean response time is S/(1−ρ), with exponential independent arrivals and service times, one server and ρ < 1. At mean service time 10 ms, ρ = 0.5 gives 20 ms mean response; ρ = 0.9 gives 100 ms. These are model illustrations, not Spring Boot p99 predictions. Real lock queues, batching, bursty arrivals and heavy-tailed jobs violate those assumptions.

Little's Law needs a matching boundary and stable averages. For a queue, use queue waiting time and queue occupancy; for an entire service, use end-to-end time and all in-flight requests inside that service. During overload, backlog grows, so multiplying offered arrivals by a recent response-time mean does not establish equilibrium concurrency. Include rejected, failed and outstanding work in accounting rather than quietly dropping them from charts.

Exercise: distinguish work reduction from scale-out

CPU demand falls from 12 ms to 8 ms after an optimization, while connection hold time stays 40 ms. The CPU target bound rises from 600 to 900 RPS, but the modeled database bound remains 525. The change can lower CPU cost and add fault headroom without increasing system throughput. To raise the limiting bound, investigate query work, transaction duration and database capability. Validate that the optimization did not merely move work outside the measured window.

7. Parallelism, partitions and hot keys

What limits the useful work of the next replica?

Amdahl's Law illustrates a fixed-workload limit: if fraction s is serial and the rest parallelizes ideally across n workers, speedup is 1/(s+(1−s)/n). With 20% serial work, four workers give 2.5× speedup and unlimited workers approach 5×. The model assumes no extra coordination cost. Real systems can regress because locking, communication, cache misses or replication overhead grows with concurrency. A measured scaling curve is more useful than declaring a service horizontally scalable.

Partitioning distributes ownership rather than simply copying workers. Hash partitioning can spread independent keys, but a single hot key still has one ownership or serialization boundary under many designs. Range partitioning supports locality and ordered scans but monotonic inserts can concentrate writes. A secondary index, global uniqueness requirement or cross-partition transaction can recreate shared coordination. Choose a key using measured access patterns and invariants.

Worked hot-tenant incident

Ten partitions each handle 1,000 operations/s in isolation. One tenant contributes 6,000 operations/s to one partition while the other nine partitions each receive 200. Total demand is 7,800, below the nominal sum of 10,000; the tenant still overloads its partition. Doubling stateless API pods changes neither ownership nor that partition's serial work. Splitting the tenant by a stable sub-key may help only if its operations can be separated without violating ordering or atomicity. Alternatives include a dedicated tenant partition, admission quotas, batching or changing the aggregate boundary.

Replication and partitioning solve different problems. A read replica can offload suitable reads while introducing replication lag and consistency decisions; it does not multiply a single writer's update capacity. A stateless fleet still depends on authoritative state elsewhere. Session affinity may improve local cache hits but creates uneven load and complicates failover. State exactly which tier and operation scales.

Exercise: preserve uniqueness while sharding

A unique constraint on each shard does not enforce a globally unique email if the same email can land on different shards. Route every uniqueness claim for that value to one owner, use a separate authoritative reservation mechanism, or change the requirement to tenant-scoped uniqueness. Each choice introduces a routing, availability or product trade-off. Test concurrent claims from different shards and retry after an ambiguous reservation outcome.

8. Admission, fairness and bounded work

How do you retain useful throughput during overload?

Concurrency limits cap simultaneous work; rate limits cap work over time. They are not interchangeable. A 100-RPS limit can still permit many in-flight operations when each takes seconds. A concurrency cap of 20 can allow thousands of very short requests per second. Combine limits according to the protected resource. Bound request bodies, waiting queues, execution concurrency and outgoing calls; otherwise rejected work can consume resources before reaching the intended guard.

A token bucket allows a configured burst while replenishing at a sustained rate. A semaphore controls active work. A bounded executor controls workers plus queue capacity. Each is scoped to an instance unless coordinated or conservatively partitioned across the fleet. A fleet of 20 instances with 40 permits each can offer 800 concurrent calls, plus workers and rollout surge. A per-pod limiter is useful isolation, not a global quota guarantee.

Choose where to reject. Waiting briefly can absorb harmless variation, but a queue consumes latency budget and memory. If service capacity is 400 requests/s and 300 ms of queue delay is acceptable, 120 queued requests is a rough deterministic planning bound, not a p99 promise. Large jobs, priority inversion and bursts change it. Expired work should leave the queue before expensive execution when the business contract permits cancellation. Rejection must be observable and distinguishable from completed work.

Bulkheads protect independent workloads

Separate expensive exports from interactive checkout concurrency, and partition capacity for tenants where needed. A single global FIFO queue can let one slow job class block everyone. Strict priorities can starve low-priority work; weighted fair sharing needs explicit minimum progress and maximum tenant use. Keep admission metadata bounded: a limiter that creates an unlimited entry for every attacker-controlled key can become its own memory incident.

final Semaphore downstream = new Semaphore(8);
boolean admitted = downstream.tryAcquire();
if (!admitted) {
    // Map to a documented overload response before starting the effect.
    throw new OverloadedException();
}
try {
    return callWithRemainingDeadline();
} finally {
    downstream.release();
}

This sketch limits active calls within one process and fails immediately. A fair semaphore does not make all tryAcquire variants fair, and fairness itself is not a latency guarantee. A timed acquisition also creates waiters; place a bound on their number. Releasing a permit when a caller times out is safe only if the protected work has actually ended or is independently accounted for. Otherwise abandoned downstream operations can exceed the limit while the application believes capacity is free.

Measure goodput as useful operations that meet the intended contract and time objective, alongside throughput, rejection and ambiguous outcomes. Counting fast overload responses as successful throughput produces impressive but misleading graphs. Retries should share an attempt budget and use backoff with jitter; they consume the same constrained resources as first attempts.

Failure exercise: cancelled callers leave work running

Eight calls are admitted. All callers stop waiting after 100 ms, but the provider takes 2 seconds. If all eight permits are released at 100 ms while the actual calls continue, the next wave can exceed eight active provider calls. Keep the permit until the protected operation terminates, or use an execution model that can prove cancellation. Report both waiting callers and actual downstream occupancy.

9. Autoscaling as a delayed control loop

What happens between detecting demand and usable capacity?

Autoscaling observes a metric, computes a desired count and asks a platform to provision capacity. Scheduling, image retrieval, JVM startup, warm-up, connection creation and readiness all add delay. Desired replicas are not ready replicas; ready replicas may not yet have representative cache or JIT state. A capacity strategy needs a warm floor, admission controls and a cold-start measurement, even when scale-out is automated.

For a hypothetical queue with 20,000 jobs, continuing arrivals of 100/s, worker service rate 50/s and a 50-second drain deadline, require n×50−100 ≥ 20,000/50. The simplified model gives n ≥ 10. Eight workers drain only 300 net jobs/s and need about 66.7 seconds. Startup delay consumes the deadline: if useful extra capacity arrives after 10 seconds, backlog has changed during that interval and only 40 seconds remain. Recalculate from that state.

Kubernetes HPA starts from a current-to-target metric ratio, then considers readiness, missing metrics and stabilization. CPU utilization relative to requests requires correctly specified CPU requests. Do not interpret a recommendation as instantly available capacity. Consult the HPA algorithm for your cluster version; custom and external metrics need a working adapter and permissions. Missing data is not the same as zero demand.

For queue workers, normalize backlog by usable processing capacity and relate it to processing duration. AWS describes backlog per instance and backlog per ECS task. Keep oldest-message age and completion rate visible too: a poison message and a uniformly overloaded queue require different treatment.

Fleet-wide budgets include transient replicas

If a database budget permits 180 application connections and a rollout can temporarily have 15 instances, a uniform cap cannot exceed 12 per instance before other consumers and reserve are considered. Sizing for 12 steady instances at 15 connections consumes 180 already; three surge instances could raise the configured maximum to 225. Include terminating instances whose connections are still open, background consumers, migrations and administration.

Scale-in can also amplify failure. Removing warm instances shifts demand, drops cache locality and retires sockets. Stabilization and drain policies should prevent oscillation while retaining recovery capacity. A reduced CPU metric after a dependency fails may indicate blocked work, not spare capacity. Test dependency slowdown with autoscaling enabled, and ensure the fleet does not shrink into an incident.

Worked exercise: one-zone headroom

A 1,200-RPS peak needs 20 effective cores at the chosen utilization target. With three equally provisioned zones, losing one leaves two-thirds of installed capacity, so at least 30 effective cores are needed before the loss if no immediate replacement is assumed. This arithmetic does not prove resilience: data, routing, connection quotas and surviving-node placement must also work. Unequal traffic distribution invalidates the equal-zone assumption.

10. Checkout capacity and overload case

Make a capacity claim that another engineer can reproduce.

Define a hypothetical workload: 70% catalog reads, 20% cart updates and 10% checkouts, authenticated across a realistic tenant distribution. The peak target is 900 logical operations/s, with 99% of successful interactive responses within 300 ms, a stated maximum rejection fraction and correct handling of ambiguous payments. These are acceptance targets, not measurements. Separate provider-dependent checkout latency from local response time if the API returns an asynchronous acceptance.

Run open and closed workload models deliberately

A closed model keeps a fixed number of clients issuing the next operation after the previous one completes. When responses slow, offered rate falls automatically. This can hide overload and coordinated omission: slow periods generate fewer latency observations. An open model schedules arrivals independently of completion; it must still bound generator resources and report missed scheduling deadlines. Report which model you used and whether the generator sustained the intended arrivals.

Run a warm baseline, stepped load, a burst, a sustained soak and a fault condition. In each stable step record offered, admitted and successful operation rates; rejected, failed and timed-out counts; backlog change; and latency histograms by operation class. Track generator saturation, CPU throttling, heap/native memory, active/queued tasks, database acquisition and lock waits, provider attempts and retry fractions. Do not average p99 values from multiple pods; merge compatible histograms or raw observations.

Failure analysis and recovery

Inject a database slowdown while holding offered rate constant. First establish whether the application queue, DB acquisition queue or DB execution time grows. A correctly bounded design rejects excess demand before every accepted request becomes late. Then remove the fault and observe recovery: large queues and retries can keep an otherwise healthy database overloaded. Recovery succeeds when backlog age returns to target and logical operations are reconciled, not simply when CPU falls.

Repeat with one replica removed and, if the availability claim includes it, one zone absent. During rollout, inspect both old and new instances' connection counts. Capture a versioned evidence bundle: build SHA, infrastructure and runtime configuration, test script, seed/data cardinality, metric definitions, timestamps, plots, error samples and pass/fail criteria. A future query change or traffic mix can invalidate the baseline; make revalidation a release responsibility.

Design decision: grow the fleet or reduce work?

If DB connection hold dominates, first examine transaction scope, query plans and unnecessary network calls inside transactions. Caching can reduce reads but adds a freshness contract; asynchronous processing changes completion semantics; batching can improve throughput while increasing latency. Compare cost per useful completed operation, failure behavior and implementation risk. Select a measured change and rerun the same baseline rather than combining five untraceable optimizations.

11. Executable admission lab

Does rejection occur before the protected effect?

The dependency-free AdmissionLab.java runs on Java 17 or later. It holds two admitted calls at a barrier, verifies that a third is rejected before its effect starts, releases the work, and verifies that permits recover after both success and an exception. It exercises a concurrency invariant with synchronization instead of timing guesses.

The lab is a local admission policy, not an HTTP server or distributed quota service. It does not model a provider that continues processing after a disconnected caller. Extend the design by assigning a separate lifecycle owner to actual remote work and by budgeting all replicas. A meaningful integration test must count real active work at the protected dependency, not only threads still waiting for results.

Worked extension: a 30-permit global budget with four pods

Static equal allocation of seven permits per pod allows at most 28 calls, reserving two but risking underuse with skew. Eight per pod allows 32 and violates the budget if all are active. A shared coordinator can allocate more flexibly but introduces availability and fencing concerns. Account for surge and failed owners before choosing. A safe static limit can be preferable when the small loss of utilization is acceptable.

Lab

Problem statement

You operate a stateless checkout API on Kubernetes. The baseline is 450 requests per second, the burst target is 1,200 RPS, and the API has a 300 ms p99 objective. Calls require a PostgreSQL lookup and sometimes write an order. A downstream database has a connection limit. Your architecture must tolerate loss of one application replica without an uncontrolled queue.

First-principles model

Little's Law is about averages, not a percentile: L = λW for a stable system. At 450 RPS with mean response time 0.18 seconds, approximately 81 requests are in progress. If the same traffic starts taking 0.8 seconds, in-flight requests rise to about 360. This does not imply throughput improved; it means more work accumulated. Distinguish end-to-end latency, service CPU demand, database occupancy and queue wait.

If each request uses 15 milliseconds of CPU at a sustained 1,200 RPS, application CPU demand is 18 core-seconds per second, before GC, TLS, logging and headroom. If each request holds a DB connection for 25 milliseconds, expected average active connections under this simplified workload is 30. A pool cap of 25 will cause waits at that arrival rate unless batching, caching or query reduction changes service demand. It is dangerous to multiply the pool size by replica count without checking database limits.

Architecture

The capacity gate diagram separates admission, ready API instances and independent dependency budgets.

The load balancer is not the bottleneck by default. Every arrow needs a measured concurrency bound. API pod readiness must mean it can safely receive work, not merely that the process responds to an HTTP GET. Startup probes, graceful termination and connection draining matter during scale events.

Execute the experiment

  1. Collect traffic mix, payload sizes, cache-hit rate, and one-week p50/p95/p99 distributions. Separate read and write operations.
  2. Run steady steps at 200, 450, 700, 900 and 1,200 RPS, each long enough to reach equilibrium. Run a separate short burst test.
  3. Capture incoming RPS, successful RPS, CPU throttling, pool-acquisition wait, database query time, queue depth and error rates.
  4. Plot offered traffic versus completed traffic. The capacity knee is where completed throughput stops keeping pace while queues and tail latency rise.
  5. Terminate one pod and then simulate database slowdown. Verify overload is bounded and recovers without retry storms.

Implementation: bounded downstream concurrency

final Semaphore permits = new Semaphore(40, true);

Response handle(Request request) throws InterruptedException {
    if (!permits.tryAcquire(75, TimeUnit.MILLISECONDS)) {
        throw new ServiceOverloadedException("Retry with backoff");
    }

        return service.process(request);

This sketch is intentionally framework-agnostic: in real services, map overload to a documented HTTP response, instrument rejection rates, preserve interruption and avoid nesting unbounded blocking calls. The semaphore is per process, not a global DB limiter; choose its size with replica count in mind.

Design interview: answered scenarios

A. Why does p99 rise before CPU reaches 100%? Pool contention, lock waits, per-core hotspots and queueing can dominate latency. Aggregate CPU averages hide unequal utilization and long-tail service times.

B. Can Little's Law predict replica count? Not alone. It describes stable average concurrency, whereas replicas depend on CPU demand, IO waits, pool limits, target utilization and failure headroom.

C. Should you scale on Kafka lag or CPU? For backlog-driven workers, use lag age and the ratio of arrival and processing rates, subject to downstream limits. Raw lag count is not a universal scaling signal.

D. What is the effect of a retry policy on capacity? At 5% failures, retrying once adds roughly 5% attempt load if failures are independent; cascading failures can make attempts multiply at several layers. Apply a retry budget.

E. How would you validate one-zone resilience? Run load at the stated peak while one zone is absent; confirm remaining zones hold target throughput, p99 and DB connection budget without assuming instantaneous autoscaling.

Review checklist

  • Define arrival rate, completed throughput, latency objective and maximum backlog.
  • Measure CPU-seconds/request and DB connection-seconds/request separately.
  • Prove overload rejection and retry behavior using fault injection.
  • Reserve capacity for a replica or zone failure as required.
  • Document the test conditions under which the capacity claim is valid.

Interviews

1. What is the difference between throughput, arrival rate and concurrency?

Explain the trade-off and test.

Arrival rate counts offered work per second; throughput counts completed work per second. Concurrency is in-flight work. In stable equilibrium, Little’s Law relates mean concurrency to mean time in system: L = λW. At overload, arrivals exceed completions, queues grow and using offered RPS as completed throughput leads to false capacity claims.

Follow-up / exercise: Compare offered-versus-successful throughput under a load ramp; plot queue depth and latency together.

Worked answer: At each stable step, admitted arrivals should balance departures and occupancy should stop trending upward. If offered load rises while successes plateau and backlog grows, report overload rather than claiming capacity at the offered rate. Include rejections and generator scheduling misses.

2. How do you estimate CPU cores for an API?

Explain the trade-off and test.

Measure CPU-seconds per completed request on representative traffic. Multiply by peak successful RPS, then divide by target utilization and include GC, telemetry, throttling and fault headroom. For 12 ms CPU per request at 800 RPS, baseline CPU demand is 9.6 cores; at a 60% target, that implies roughly 16 cores before redundancy.

Follow-up / exercise: Check request mixes: an expensive endpoint invalidates averages derived from a cheaper traffic mix.

Worked answer: If a cheap operation costs 4 ms and an expensive operation 40 ms, an 80/20 mix costs 11.2 ms on average. A 50/50 mix costs 22 ms, nearly doubling CPU demand at the same RPS. Use a representative distribution and validate both classes separately.

3. Why can latency rise sharply at constant traffic?

Explain the trade-off and test.

Service time can rise due to lock contention, database query slowdown, noisy neighbors or resource exhaustion. Little’s Law then implies more in-flight work at the same admitted rate, while finite pools cause waiting. Tail latency is sensitive to queueing and variance even before a machine appears fully utilized.

Follow-up / exercise: Separate queue wait, execution CPU time and downstream span duration.

Worked answer: A growing queue with unchanged execution time suggests admission exceeds service rate. Increasing execution time with stable queue wait points to the service center. A dependency span can itself include connection acquisition, so instrument those phases independently.

4. What makes a load test credible?

Explain the trade-off and test.

Use realistic data cardinalities, authenticated traffic, representative read/write mix, warm cache state and production-like dependency limits. Step demand to identify the throughput knee; repeat cold starts and failure runs. Report error rate, completed throughput and percentiles for each stage, not the maximum synthetic generator RPS.

Follow-up / exercise: Include duration, build SHA, hardware configuration and test dataset in every result.

Worked answer: The evidence bundle needs the exact build, runtime, infrastructure, dataset, seed, traffic model, duration and fault conditions. Repeat the baseline before attributing a difference to an optimization. Check generator saturation and successful-operation accounting.

5. When would vertical scaling beat horizontal scaling?

Explain the trade-off and test.

Vertical scaling may lower coordination overhead or be necessary for nonpartitionable state, large local working sets or database primary workloads. Horizontal scaling improves replica redundancy and parallelism when instances are stateless and downstream capacity scales. Compare marginal cost, failure domain, migration risk and scaling limits rather than assuming horizontal is always superior.

Follow-up / exercise: Explain how sessions, filesystem writes and local caches affect horizontal scaling.

Worked answer: Authoritative sessions and filesystem writes need shared or partitioned durable ownership before replicas can replace each other. Local caches can remain disposable but cold misses and affinity change capacity. Kill one replica and verify session continuity and data durability.

6. Why does adding replicas overload the database?

Explain the trade-off and test.

Each replica can open its own connection pool and initiate parallel queries. Doubling pods may double offered concurrent DB work without increasing DB CPU, locks or IOPS. Enforce aggregate budgets via pool size, admission limits, queueing and workload reduction; scale the bottleneck only if measurements support it.

Follow-up / exercise: Calculate maximum DB connections as replica count × per-instance pool size plus workers and administration.

Worked answer: For 12 steady replicas, 3 rollout surge replicas and a pool cap of 10, allow for 150 application connections, then add workers, administrative access and reserve. A configured maximum is a bound, not measured database query capacity.

7. Which autoscaling metric should drive worker replicas?

Explain the trade-off and test.

For asynchronous workers, queue age and arrival-versus-service rates are often stronger than CPU alone. Queue length must be interpreted with processing time and backlog deadline. Enforce downstream concurrency caps and scale-up warmup; aggressive scaling can overwhelm an API or database.

Follow-up / exercise: Give a target drain time and show capacity calculation under continuing arrivals.

Worked answer: For 20,000 jobs, 100 ongoing arrivals/s and 50 jobs/s per worker, a 50-second drain needs at least 10 workers in an ideal model. Eight give 400 gross minus 100 arrivals = 300 net jobs/s and need about 66.7 seconds. Include startup delay and failure headroom.

8. How do you handle sudden overload safely?

Explain the trade-off and test.

Bound queues and concurrent dependency calls. Reject excess work promptly with documented 429/503 semantics where appropriate, backpressure and Retry-After when meaningful. Prefer preserving critical flows over waiting until all requests time out. Ensure retry behavior does not amplify overload.

Follow-up / exercise: Failure-inject DB latency and watch whether pool wait and inbound queues remain bounded.

Worked answer: Admitted concurrency and queued count should reach configured bounds while excess work is rejected before its effect. After removing slowdown, backlog age must recover without a sustained retry wave. Count timed-out operations that may still execute.

9. What is the difference between p99 and average latency?

Explain the trade-off and test.

Average latency summarizes total time divided by request count; p99 is the duration at or below which 99% of observed requests complete. A stable mean can hide a severe 1% tail. Percentiles cannot be averaged across arbitrary unequal populations; aggregate from raw observations or proper histogram distributions.

Follow-up / exercise: Check sample size and whether a p99 is meaningful for a low-volume endpoint.

Worked answer: At 100 observations the p99 is determined by roughly the slowest observation and is unstable. Increase the window or use suitable histogram thresholds and report counts. Do not average per-instance p99 values or omit timeouts from the outcome report.

10. How do you size for one-zone failure?

Explain the trade-off and test.

State the failure assumption: a zone may hold one-third of current capacity and autoscaling takes time. Remaining zones must have spare CPU, network, connection and DB capacity to handle the peak during failover. Load test with a zone removed, including termination and connection-drain behavior.

Follow-up / exercise: Do not equate multi-zone deployment with proven zone-loss resilience.

Worked answer: With three equal zones and no immediate replacement, install 1.5 times the needed effective capacity to retain the target after losing one zone. Then validate traffic redistribution, DB/egress budgets, placement and quotas; arithmetic alone does not prove availability.

11. What is backpressure across a synchronous API?

Explain the trade-off and test.

Backpressure is signaling or enforcing that producers cannot push unlimited work into slower consumers. APIs commonly use admission limits and fail-fast responses; internal stages use bounded work queues and concurrency controls. It prevents hidden latency growth but requires callers to treat rejected work correctly.

Follow-up / exercise: Distinguish temporary overload from permanent validation errors before recommending retries.

Worked answer: Validation failures need correction and should not be retried unchanged. Temporary admission rejection may be retried within a shared budget if operation safety and remaining deadline allow. A timeout after an effect begins requires identity-based reconciliation.

12. What is a good capacity acceptance criterion?

Explain the trade-off and test.

A claim should specify workload, dataset, traffic distribution, observed successful RPS, p99, maximum error fraction, and downstream constraints over a fixed duration, including a stated fault scenario. Without those boundaries, a capacity number is not portable.

Follow-up / exercise: Explain how deployment changes, query plans and cache ratios can invalidate past baselines.

Worked answer: A new query plan, slower provider, changed tenant mix or cache misses can change per-request demand and the bottleneck. Define revalidation triggers and keep a comparable baseline. Capacity is conditional evidence, not an enduring property of the service name.

Revision sheet

Vertical: Add resources to one host. Simpler, but bounded by machine limits and failure-domain concentration.

Horizontal: Add instances. Requires routing, state strategy, lifecycle management and downstream capacity.

Formula: L = λ × W (stable-system averages).

Failure mode: More API replicas can exhaust database connections and worsen p99 latency.

AWS pattern: ALB → ECS tasks across AZs → database. Select workload-relevant scaling metrics and account for warm-up.

Worked recall

20,000 jobs, 100 arrivals/s, 50 jobs/s/worker and 50-second drain: at least 10 workers in an ideal model without startup delay. A 180-connection budget across 15 concurrent instances permits at most 12 each before reserve and other consumers.
