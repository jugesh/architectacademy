1. Control plane and reconciliation model

The API server stores desired state in etcd; controllers reconcile observed state toward that desired state. The scheduler binds pending pods to nodes according to capacity and scheduling constraints; kubelet manages node-local execution. A Deployment creates ReplicaSets that manage pod replicas. Kubernetes is not a distributed transaction manager for your application database; controllers retry convergence rather than ensuring application business invariants.

2. Requests, limits and scheduling

CPU/memory requests influence placement and resource accounting; limits constrain runtime consumption. CPU limit can throttle a container even when the node has nominal spare compute. Memory-limit breach can cause OOM kills rather than throttling. Overcommit may be valid for mixed workloads but must be controlled by observed working sets and eviction risk. JVM Xmx needs headroom for native memory. Use resource quotas and LimitRanges for multi-tenant namespaces.

3. Probes and graceful shutdown

Startup probe grants slow initialization time; readiness decides whether pod endpoints should receive traffic; liveness restarts a process judged unhealthy. An overaggressive liveness check during DB latency can cause cascading restart storms. On termination, application handlers should stop accepting new work, drain in-flight operations and close resources within terminationGracePeriodSeconds. Endpoint removal and load balancer draining are not instantaneous.

4. Service discovery, ingress and network policy

Services provide a stable virtual access point to changing endpoint pods, but targetPort and service port are different concepts. A ClusterIP service on port 80 can forward to a container listening on 8080. Ingress/controller or Gateway API handles HTTP entry depending on installed implementation. NetworkPolicy restricts traffic only when supported by the network plugin; default allow behavior changes when policies select pods.

5. Deployments, strategies and disruption budgets

Rolling updates gradually replace pods subject to maxSurge and maxUnavailable. A PodDisruptionBudget protects against selected voluntary evictions, but it does not guarantee availability during node crashes or all upgrade paths. Readiness gates and preStop/drain behavior determine whether requests complete during rollout. StatefulSets add stable pod identity and ordered semantics where needed; they are not a substitute for database backup.

6. Horizontal and event-driven autoscaling

HPA adjusts replicas based on configured metrics and target behavior; CPU percentage is relative to CPU request for resource utilization metrics. Scaling is not instantaneous and cannot expand database throughput by itself. Queue-driven scaling requires backlog age and consumption rates with downstream caps. VPA changes resource recommendations/allocations depending on mode and environment, with restart implications in some configurations.

7. Security and operational boundaries

Use restricted service accounts, namespace RBAC, image provenance, immutable tags/digests, secrets management, network policies and admission controls. Kubernetes Secrets are not automatically a complete secret-management strategy; at-rest encryption and RBAC configuration matter. Avoid mounting cloud permissions everywhere or treating namespace isolation as complete trust separation.

8. Troubleshooting drill and commands

Begin with workload desired-versus-ready count, events, pod phase, readiness transitions, restarts and resource usage. Inspect logs for current and previous container when crashes occur. Check Service endpoints, DNS resolution and NetworkPolicies before blaming application code. For periodic OOMs, inspect exit code/reason, cgroup metrics, JVM native/headroom and requests/limits. Use controlled rollout rollback where compatible with database schema.
